# AGENTS.md

Guidance for AI coding agents (Claude, Codex and others) working on Portifact. Keep this file short: it states the rules and points to the detailed documents. Read the linked documents that apply to your task before changing code.

## Project

Portifact publishes static artifacts (HTML sites, Markdown and plain text) with their own URL, access control, archive/restore and optional annotations. It ships with three interfaces that share one domain layer: CLI, remote MCP server and web dashboard. It runs on Cloudflare Workers, D1 and R2.

The project is in its initial build. Some commands and paths below are planned and appear as the monorepo is scaffolded; keep this file in sync as they become real.

## Commands

Use Bun from the repository root as package manager and script runner. Turborepo runs and caches tasks across packages. Node 24 LTS must also be installed, because Vitest, wrangler and Stryker run on it.

```bash
bun install
bun run check          # Biome, typecheck, skills validation and the design-system check
bun run format         # apply Biome formatting and safe fixes
bun run test           # Vitest with coverage thresholds, through Turborepo (Workers tests run in workerd)
bun run build          # build apps (the landing in apps/web/dist)
bun run dev            # local dev servers (Vite for apps/web, wrangler for apps/app)
bun run build:cli      # compile the CLI for this platform into dist/release (--all for every platform)
bun run notices        # regenerate third-party-notices.md and the CLI's copy after dependency changes (check fails when stale)
bun run --cwd packages/db generate -- --name <change>   # create a D1 migration from schema.ts
bun run --cwd packages/db generate:access -- --name <change>   # create an access log migration from access-schema.ts
bun run --cwd packages/ui sync-tokens   # regenerate tokens-css.ts after editing tokens.css
bun run --cwd packages/render build     # build the diagram script (Mermaid and its runner) into packages/render/dist; turbo runs it before the content Worker's tasks and the e2e typecheck
bun run --cwd packages/emails preview   # render every email to /tmp/portifact-email-previews (.html and .txt) for review
bun run test:e2e       # Playwright end to end in Chromium, Firefox and WebKit with third-party cookies blocked (see docs/testing.md); CI runs it as one parallel job per project
bun run test:mutation  # Stryker on domain, anchors, contracts, render and services, one package at a time (slow; see docs/testing.md)
bun run landing:shots  # regenerate the landing page's product screenshots and CLI transcripts from the real app on the e2e stack (docs/design.md, "Landing page")
bun run test:load      # load and concurrency scenarios against the local e2e Worker, or staging with --app-url (never production)
bun run spike:review-cookies   # Playwright review-cookie spike; not part of bun run test (see spikes/review-cookies)
bun run spike:workspace-model  # Better Auth organization, SSO and SCIM plugins on D1 in workerd (decision 0004); also part of bun run test
bun run --cwd apps/jobs operator <command>   # operator tool: reports, suspensions, storage-report, export-tombstones, apply-tombstones, budget state and override, email-suppressions and lift-email-suppression, find-share-link (reads a reported link from standard input), plan, set-plan, remove-plan, export-plans and apply-plans (deploy credentials; --local for wrangler dev state, --config <file> for a scratch database in a backup drill); docs/operations.md
```

A task is not done until `bun run check` and `bun run test` pass. Use `bun run test`, not `bun test`: the latter starts Bun's own test runner instead of Vitest. Run `bun run test:e2e` when the change affects a user flow, a browser behavior or content delivery.

Dependencies newer than 3 days are not installed (`minimumReleaseAge` in `bunfig.toml`). If `bun install` says a version is blocked, use a range that allows an older release instead of disabling the rule.

## Architecture rules

- Business rules live only in `packages/domain` (pure functions) and the use cases that apply them with storage live in `packages/services`. API routes, MCP tools, CLI commands and the dashboard are thin adapters over these services; never reimplement a rule in an adapter.
- In a D1 batch, condition every write after a guarded update on that update having happened (for example `exists(...)` on the new state), and close the session or token last, so a retried or concurrent request cannot apply effects twice. If two concurrent requests would write the same new state (a counter or generation plus one), `exists(...)` on it is true for both: condition the dependent writes on the old state the request read and run the guarded update last instead (see `packages/services/src/access.ts`), or claim the change first with a row that carries a per-request unique token and condition the rest on that token (see `write_id` in `packages/services/src/annotations.ts`). Drizzle's `db.run`/`db.all` with raw SQL cannot go in a D1 batch; use `db.insert(table).select(sql)` with a raw `sql` template, which lists every column in schema order.
- Web, CLI and MCP must behave identically for the same operation: same permission checks, quotas, states and errors. Add a parity test when you add an operation. The artifact list's items carry `activity` (built once in `artifactListItem`, `apps/app/src/mcp/present.ts`, for both `/api/v1` and `list_artifacts`); traffic is per account, never per artifact.
- MCP has no privileged path. It goes through the same authorization as the API. `apps/app/src/mcp` serves `/mcp` with the official SDK (`@modelcontextprotocol/server`, pinned exactly; the 2026-07-28 revision plus the stateless 2025 fallback). Every request passes `authorizeResourceRequest` with the scope of the tool it calls, from `TOOL_SCOPES` in `apps/app/src/mcp/tools.ts`, before the SDK runs; a new tool must be added there with the same scope as its API route, and to `test/mcp-parity.test.ts`. Tool results return the API's body as structured content and errors as `{ error: { code, message } }`. Uploads through MCP (`prepare_upload`, `get_upload_status`, `commit_upload`) build their presigned targets with the API in `apps/app/src/api/uploads.ts`; the agent sends the bytes itself, so MCP never carries them, and `read_artifact` reads through `readVersionFile` with the download's authorization. Access widening tools (`set_access`, `add_reader`) tell the agent to ask the user first.
- `/api/v1` accepts a bearer token or the dashboard's session cookie; both resolve in `apps/app/src/api/access.ts` to one user and the same scope check. Session requests must carry `Sec-Fetch-Site: same-origin` and, on mutations, the exact app `Origin`. New routes go through `guarded` and get both for free. The account endpoints (`apps/app/src/api/account.ts`) accept only the session and refuse bearer tokens; end sessions through Better Auth's API, never by deleting `sessions` rows, or its hooks do not revoke the tokens bound to them (see [docs/security.md](docs/security.md)). The one bearer path to credentials is `/api/v1/tokens` (`apps/app/src/api/tokens.ts`, `portifact tokens`): bearer only, scope `credentials:manage`, which only the CLI client's record lists ([decision 0003](docs/decisions/0003-credentials-scope.md)); never add it to `REGISTRATION_SCOPES`, `SESSION_SCOPES` or an MCP tool, and keep it on the same services and presentation as the dashboard's Apps page.
- The acting user, owner or author always comes from the authenticated session or token, never from request input.
- Owners and roles (premium plan F3, decisions [0004](docs/decisions/0004-workspace-model.md) and [0005](docs/decisions/0005-regions.md); "Owners, workspaces and roles" in [docs/security.md](docs/security.md)): an owner is a user's personal space (owner ID = user ID) or a workspace (`ws_` prefix, `WorkspaceId`), and a user acts on it with a role (`admin`, `editor`, `member`). `resolveActor`/`actorOn` in `packages/services/src/actors.ts` are the only places a role is decided (from `workspace_members`, or admin of one's own personal space with no read); `can`/`authorize`/`actsForOwner` in `packages/domain/src/actor.ts` decide what it allows over `ROLE_ACTIONS`. Owner-scoped services take the `Actor` the adapter got from `resolveActor` (today always the personal space: nothing can choose a workspace yet); services that name an artifact or upload take `userId` and resolve the actor on its owner (`authorizeOn`); never build an `Actor` in an adapter. A user with no role gets exactly what a missing artifact gives, a role without the action `forbidden`. Every rule that said "the owner" means an admin or editor of the owner (`actsForOwner`, `ownerSide` for the threads that count as the owner's, `ownerRecipients` for notices). `workspaces`, `workspace_members` and `artifact_directory` are Portifact's own tables, changed only by the services; Better Auth never sees them and its organization plugin is not installed. Adapters take database handles from `regionsFromEnv(env)` (`packages/db/src/regions.ts`; `apps/app/src/regions.ts` has the app's helpers), never `createDb(env.DB)` for product data: `GlobalDb` for identity, workspaces and the directory, `RegionalDb` (which carries `.global`) for an owner's data; with one region both wrap `DB`. `preparePublish` claims a new artifact's ID in `artifact_directory` (`claimNewArtifactId`) before its regional batch; directory rows and a workspace's `region` never change (triggers in 0029).
- Input and output shapes live in `packages/contracts` and are validated at every boundary.
- Multi-step state changes in D1 use transactional batches with checked results. A read followed by a separate write is not a transaction.
- The D1 schema lives in `packages/db/src/schema.ts`; never edit a committed migration, generate a new one (`--custom` for triggers and other SQL Drizzle does not model). Active-slot accounting for lifecycle transitions is done by triggers in `0001_lifecycle_triggers.sql`; do not also adjust `active_artifacts` in code for those transitions. Annotation usage per owner (`annotation_usage`) is kept by triggers in `0007_annotation_usage_triggers.sql`; never adjust it in code. At most two open uploads per account are enforced by a trigger in `0016_open_uploads_limit.sql`, which `preparePublish` maps to `quota_exceeded` like the CHECK constraints. Account limits are also CHECK constraints against per-row limit columns (`account_usage.active_limit` and `bytes_limit`, `annotation_usage.messages_limit` and `bytes_limit`, migration 0027; their defaults are the free plan and must equal `LIMITS` and `ANNOTATION_LIMITS`, which `packages/db/test/limit-columns.test.ts` checks), so a race the application misses still fails in the database; a SQL clamp that must stay under a limit reads the column, never the constant. Rebuilding a table drops its triggers, and SQLite refuses to rename one while a trigger refers to a missing table: drop and recreate every trigger on or writing it in the same migration, as 0027 does.
- Mutations that may be retried take an idempotency key.
- Follow-up work goes through the transactional outbox (`packages/services/src/outbox.ts`): write the `outbox` row in the same batch as the state change, before a guarded update and on the same old-state condition, never in a separate write. The jobs Worker relays rows to the `portifact-jobs` queue, which delivers at least once, so every job is idempotent: a missing row means done, a `purge_artifact` acts only on the `purging` state and lifecycle generation it carries, a `delete_objects` job keeps keys that have a row again, and the consumer deletes the row only when the job is done. Keep the scheduled scans as the safety net. A new topic goes in `OUTBOX_TOPICS` (`packages/db`), `OutboxTopic` (`packages/contracts`) and `runJob`. The queue must exist before deploying a binding to it ([docs/releasing.md](docs/releasing.md)).
- Objects over 64 MiB (`MULTIPART` in `packages/contracts/src/limits.ts`, the plan in `packages/domain/src/multipart.ts`) use presigned multipart for clients that send `multipart: true`; others keep one PUT per object, so older CLIs still work. `packages/services/src/multipart.ts` opens the R2 upload with the binding at prepare, the API signs one UploadPart URL per missing part, the client reports each part's ETag (`POST /api/v1/publishes/:id/parts`) and the commit assembles at the session's staging key (`uploads/...`), rehashes with `crypto.DigestStream` and only then copies to `objects/...`. Never assemble parts straight into `objects/...`. A closed session writes `abort_multipart` in the same batch; follow "Uploads" in [docs/security.md](docs/security.md). Tests inject a small `MultipartConfig` (R2 parts are at least 5 MiB, also in workerd).
- `releaseOrphans` writes the `delete_objects` job, releases the bytes and deletes the object rows in one batch; never delete `objects` rows or R2 objects outside it. The storage reconciliation (`packages/services/src/backups.ts`) only reports into `storage_findings`, it never deletes or repairs.
- A D1 Time Travel restore rewinds the tombstones: tombstones, pending account deletions and `purging` artifacts are exported before it and re-applied after it with the operator tool ([docs/operations.md](docs/operations.md)), which also rebuilds the `artifact_directory` rows the restore rewound (`rebuildArtifactDirectory`). A new kind of permanent deletion must be covered by `exportTombstones` and `applyTombstones`.
- Drizzle's `insert(table).select(query)` inserts into every column of the table in schema order, so the select must list all of them in that order. In select fields Drizzle leaves columns unqualified, so a correlated subquery there must name each column's table (as `activityColumns` in `packages/services/src/artifacts.ts` does), or the outer column silently binds to the subquery's table. `rollbackArtifact` in `packages/services/src/versions.ts` copies `versions`, `version_files` and `source_origins` rows this way: a column added to any of them must be added there too, or rollbacks lose it.
- A rollback is a new publish of retained objects. When annotation threads land, moving the base version's open threads to history must happen in both `commitPublish` and `rollbackArtifact`, conditioned on the switch, like their other writes (`rollbackArtifact` marks the spot).
- Protected artifacts are opened through a one-use handoff from `app.portifact.com/read/<id>` to `/__portifact/callback` on the artifact origin, which sets the host-only `__Host-pf_read` cookie; the content Worker needs the `READ_SESSION_SECRET` secret. Handoffs and read sessions reference Better Auth's `sessions.id` and end with it, so keep Better Auth sessions in D1 (no secondary storage) and keep sign-out deleting the row. Follow "Entry to protected artifacts" in [docs/security.md](docs/security.md) before touching any of it.
- Every cookie the content Worker reads is a `__Host-` name listed in `isPortifactCookie` (`apps/content/src/injected.ts`), matched exactly. Any other cookie on an artifact origin may have been injected by a sibling through `Domain=portifact.dev`: it grants nothing, and `handle` expires it once the foreign cookies pass `FOREIGN_COOKIE_LIMIT`. Add a new artifact-origin cookie there, or it counts as foreign. See "Injected cookies" in [docs/security.md](docs/security.md).
- No account or session exists without the current terms accepted: the Better Auth hooks in `apps/app/src/auth/terms.ts` enforce it for every sign-in method, and sessions of accounts that have not accepted `TERMS_VERSION` count as none. Consent is a sign-in-wrap: no checkbox, a notice above every sign-in button, and choosing a method records the acceptance; keep its conditions ("Acceptance at sign-in" in [docs/legal.md](docs/legal.md)) when changing the login page. Bump `TERMS_VERSION` only for material changes to the legal pages; see [docs/legal.md](docs/legal.md).
- `markdown` and `text` artifacts are rendered once, when `commitPublish` commits the version (`packages/services/src/documents.ts`), never per request. The page and the Markdown block map are stored as `rendered` and `block_map` entries of the version at the entrypoint's path, backed by objects counted in the account's storage. Clients only ever send the source. A renderer change that fixes a security flaw raises `SECURE_RENDERER_VERSION` in `packages/render/src/version.ts`, and the maintenance job re-renders older documents; nothing else re-renders. Fenced code is highlighted at commit (only `pf-tok-*` spans the renderer writes, within `HIGHLIGHT_LIMITS`), and Mermaid blocks are drawn in the browser by the self-hosted diagram script, loaded only by the constant `DIAGRAM_LOADER` that the page's policy allows by hash; never load Mermaid from a CDN, never insert its SVG into the page (it becomes a `blob:` image) and never change the loader's text without keeping the old hash in `documentPolicy`. Follow "Diagrams and highlighted code" in [docs/security.md](docs/security.md).
- Traffic metering: the content Worker charges every authorized request it answers for an artifact to the owner's `traffic_counters` row of the UTC month, through the per-isolate `TrafficMeter` in `apps/content/src/traffic.ts` (one batched upsert per 5-second window via `waitUntil`, `recordTraffic` in `packages/services/src/traffic.ts`). Never add a D1 write per delivery request, and keep the quota check in `serve` after authorization so refusals before it charge nothing. The limits come from the owner's plan (see "Plans" below), whose row `findDeliveryArtifact` joins into the artifact lookup so the quota adds no read, the rules `packages/domain/src/traffic.ts`; the maintenance job prunes cycles older than the previous one and account deletion removes the account's rows. Portifact's own scripts under `/__portifact/` (the bridge, the diagram script) are answered before any artifact lookup and are not charged.
- Access logs (plan sections 11 and 13): the content Worker records page loads of `restricted` artifacts by signed-in visitors who are not the owner (read and review sessions; `recordOpenings` also drops a workspace's admins and editors; `isLoggedOpening` in `packages/domain/src/access-log.ts`) through the per-isolate `OpeningLog` in `apps/content/src/access-log.ts`, one batched write per 5-second window via `waitUntil`, like traffic; never add a D1 write per delivery request, and never identify anonymous visitors. Page loads through a share link of an `authenticated` or `restricted` artifact are recorded for the link (`isLoggedLinkOpening`, `user_id` and `link_id` hold the link ID, `email` empty), never a person. Rows live in the separate `portifact-access` database (`ACCESS_DB`), one per artifact, visitor and 30-minute window, kept 30 days (pruned by the jobs Worker). Only the owner reads them (an admin or editor of it; `getAccessLog`; 404 for anyone else). No batch spans both databases: a purge (`deleteArtifactData`) and an account deletion write `erase_access_events` outbox jobs, which `runJob` runs with the access database; a new way to delete artifacts or accounts must go through those paths. See "Access logs" in [docs/security.md](docs/security.md).
- Suspensions happen only through the operator tool ([docs/operations.md](docs/operations.md)), never a web route. A suspended artifact is simply not servable, so delivery, read sessions, handoffs, downloads and annotations refuse it through their existing state checks; keep any new content path behind the same servable check. Suspended artifacts hold no active slot: triggers in `0010_moderation_triggers.sql` free it on suspend and retake it on reinstate, so never adjust `active_artifacts` for those transitions either. The same migration refuses inserting an artifact whose ID has a tombstone.
- Budget protection (plan section 12) is decided only in `packages/domain/src/budget.ts`, persisted in the single `platform_budget` row by the jobs Worker and the operator override, and read through `platformProtection` in `packages/services/src/budget.ts`. High coverage is required, but coverage alone is not the goal: tests must prove behavior and fail when the behavior breaks. Coverage thresholds and mutation testing enforce both. Follow [docs/testing.md](docs/testing.md).

## Git and changes
