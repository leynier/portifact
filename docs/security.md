# Security

## Reporting a vulnerability

Do not open a public issue. Report it privately through GitHub's "Report a vulnerability" button in this repository's Security tab, with steps to reproduce and the impact you observed. You will get a first response within 7 days.

## Invariants

Portifact serves arbitrary HTML and JavaScript from untrusted users next to accounts and private content. These invariants are not optional. Each one has at least one test that tries to break it (see [testing.md](testing.md)).

### Origins

- `portifact.com` hosts everything with credentials or that mutates data: dashboard, API, auth, OAuth, MCP and the viewer with the Portifact bar.
- `portifact.dev` serves only user content and the viewers that render it. Its only state-changing endpoints are one-time code exchanges under `/__portifact/`.
- An artifact's active custom domain (decision 0006, "Custom domains" below) is one more origin of that artifact's user content, served by the same Worker under the same rules, and never holds credentials of anything but that one artifact.
- `portifact.dev` is not on the Public Suffix List. All `*.portifact.dev` artifacts are the same site, so any artifact can set cookies with `Domain=portifact.dev` and is same-site with every other artifact. Never rely on `SameSite` between artifacts.
- Paths under `/__portifact/` are reserved (`callback`, `link`, `report`, `raw`, `review`, `review/check`, `review/tab`, `review/tab/check`, `review/end`, `bridge.js`, the diagram script and `brand/<sha256>` today). No uploaded file can shadow them, a viewer link can never point the frame at one, and none of them is ever redirected to the viewer.

### Cookies and sessions

- Portifact cookies use the `__Host-` prefix: `Secure`, `Path=/`, no `Domain` attribute.
- The one exception is the two display preferences, `__Secure-pf_theme` (`system`, `light` or `dark`) and `__Secure-pf_lang` (a code of `LOCALES`), shared by `portifact.com` and `app.portifact.com` with `Domain=portifact.com; Path=/; Secure; SameSite=Lax`, one year (`packages/contracts/src/preferences.ts`). They hold only that value, no identifier, and are validated on every read; anything else is ignored. The `Domain` comes only from `PREFERENCE_DOMAINS` (`portifact.com`, and the reserved `portifact.test` of the e2e stack), so any other host, `portifact.dev` included, can never get them: it is another registrable domain, and the pages that write them never run there. Nothing reads them for authorization, sessions or access; the only server that reads one is the site Worker, to send a visitor to the same page in their language ("Language preference" below). They are not HttpOnly because the pages' scripts, including the pre-paint theme script, read and write them.
- Each surface has its own session: dashboard, read session per artifact, link session per artifact and share link, and review session per artifact and version. Artifact code never receives an admin credential.
- The review cookie is `Partitioned` (CHIPS). It grants reading one version and nothing else. The fallback review tab's cookie (`__Host-pf_review_tab`) is first-party and `SameSite=Lax`, grants the same and lasts 15 minutes (see "Review mode").
- Sibling artifacts in the viewer's partition can send credentialed requests that carry another artifact's review cookie. The content Worker honors the review cookie only for `Sec-Fetch-Site: same-origin`, or `cross-site` with `Sec-Fetch-Mode: navigate`, fails closed without fetch metadata, and sends `Cross-Origin-Resource-Policy: same-origin` on review responses. See [decision 0002](decisions/0002-review-mode-cookies.md).
- Cookie names are matched exactly and case-sensitively. WebKit lets a sibling set `__host-` (lowercase) cookies with a `Domain` attribute, so case-folding a name would let it shadow a `__Host-` cookie.
- The content Worker reads only its own cookies by exact name and ignores every other one; it expires injected cookies once they grow (see "Injected cookies").
- Read sessions carry signed claims that expire in 60 seconds or less. After that, the Worker rechecks D1. Revocation must take effect within 60 seconds.

### Injected cookies

Any artifact can set cookies with `Domain=portifact.dev`, for `/` or any other path, and every other artifact origin then receives them. The content Worker handles them in `apps/content/src/injected.ts`, for every response it gives, whatever its status:

- **They grant nothing.** Authorization reads only Portifact's names on artifact origins, exactly and case-sensitively and with one value each: `__Host-pf_read`, `__Host-pf_read_tx_<tag>`, `__Host-pf_link`, `__Host-pf_review`, `__Host-pf_review_tab` and `__Host-pf_nobar` (`isPortifactCookie`). Names that imitate them (`pf_read`, `pf_review`, or ending in `pf_link`) are cleared at any size. Browsers refuse a `__Host-` cookie with a `Domain`, so a sibling can only add look-alikes (`pf_read`, `__host-pf_read` in WebKit), which are foreign. A new cookie on artifact origins must be added to `isPortifactCookie`, or it counts as foreign.
- **They are expired once they grow.** When the foreign cookies of a request pass 8 KiB of `name=value` (`FOREIGN_COOKIE_LIMIT`), the response carries `<name>=; Max-Age=0; Domain=portifact.dev; Path=<path>; Secure; SameSite=None`, and the same with `Partitioned`, for each foreign name. The Cookie header does not say which path a cookie was set for, so each name is expired at every path the request matches: `/` and each prefix of the requested path, at most 8 (`cookiePaths`). Names that imitate ours are cleared first and at any size, then the largest; whole names at a time, up to 16 KiB of `Set-Cookie` per response (`CLEANUP_BUDGET`), so the next requests, usually the page's own subresources, clear the rest. The visitor recovers on the first request that still reaches the Worker, with no extra round trip.
- **Nothing else is touched.** Portifact's cookies are never cleared and never counted. The artifact's own host-only cookies survive, because a `Domain` cookie is a different cookie from a host-only one with the same name. Under the limit only imitations are cleared: analytics scripts set their cookies on the widest domain they can, which is `portifact.dev` while it is not on the Public Suffix List, and clearing those on every response would break them.
- **No `Clear-Site-Data`.** Its `cookies` type clears every cookie of the registrable domain, so on an artifact origin it would end the visitor's read sessions on every artifact and wipe every artifact's own cookies.

Limits:

- A request whose headers pass the platform's limit (128 KB in total on Cloudflare; local workerd answered `431` at 500 KiB and accepted 200 KiB) is refused before the Worker runs, so no `portifact.dev` response can clear its cookies, and `Clear-Site-Data` could not either. Browsers keep about 180 cookies of up to 4 KiB per registrable domain, so one artifact can push a visitor past that limit on every artifact. Until `portifact.dev` is on the Public Suffix List, that visitor has to clear the site data of `portifact.dev` in the browser; reporting and suspending the artifact stops it from injecting more.
- Cookies a response cannot name (without a name, or with control or non-ASCII characters in it) count toward the limit but are not cleared.
- Browsers evict a registrable domain's least recently used cookies past their per-domain limit, so an injecting artifact can push out a visitor's read sessions of other artifacts; the visitor signs in again.

### Entry to protected artifacts

A visitor of an artifact that is not `public` signs in on `app.portifact.com` and comes back with a read session for that one artifact origin. No credential, email or session ever lives on `portifact.dev`; the code in `apps/content/src/read-session.ts`, `apps/app/src/read.ts` and `packages/services/src/read-access.ts` follows these rules.

1. A navigation without a usable read session gets a transaction cookie `__Host-pf_read_tx_<first 16 characters of the nonce>` (sealed with `READ_SESSION_SECRET`, 10 minutes) holding the artifact, a random nonce and the requested path, and a `303` to `app.portifact.com/read/<id>?state=<nonce>`. The app never sees the path; the `Referrer-Policy: no-referrer` on the redirect keeps it out of `Referer` too. Each transaction has its own cookie, so a second tab does not break the first; at most three stay open per artifact, and starting another clears the oldest plus any that are expired, unreadable or sent twice. A requested URL that would make the sealed cookie longer than 2,048 characters is replaced by `/`, so sign-in always finishes.
2. `/read/<id>` takes the account only from the dashboard session cookie. Without one it sends the visitor to `/login?next=/read/<id>?state=…`; the login page accepts `next` only for its own pages and `/read/<artifact-id>`. With one, it counts the entry against a per-account limit in the D1 rate-limit counters (60 per 10 minutes, `READ_ENTRY_LIMIT`; past it, a `303` to `/login?error=read_rate_limited` with `Retry-After` and nothing stored), then `checkReadAccess` applies the domain's `canRead` to the artifact's current policy and requires it to be servable. A missing, unavailable or forbidden artifact gets the same `303` to `/login?error=artifact_unavailable`.
3. On success the app stores a handoff (`read_handoffs`): only the SHA-256 of a 32-byte code and of the nonce, the artifact, the user, the dashboard session's ID (Better Auth's `sessions.id`) and the policy generation, valid 60 seconds. It redirects to `https://<id>.portifact.dev/__portifact/callback?code=…`, a host built from the validated ID, never from input.
4. The callback accepts only a `GET` navigation that carries a live transaction cookie of the same artifact; the code matches at most one of the browser's open transactions. One guarded update marks the code used and names the new session, only while the dashboard session that asked for the code is live, and the `read_sessions` row (with that dashboard session's ID) is inserted only if that update happened, so a replayed, expired, cross-artifact or other-browser code (fixation) creates nothing. Every failure answers the same `400` page and clears only transactions that are no longer usable, because another tab may still need the others; success clears the transaction it used.
5. The callback sets `__Host-pf_read` (`Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`, 12 hours) and returns to the stored path as an absolute URL on the same origin, so `//evil.example` stays on the artifact.

The read cookie holds the session ID and claims (artifact, user, policy generation, claims expiry of 60 seconds, session expiry), encrypted and authenticated with AES-GCM under a key derived from `READ_SESSION_SECRET` with HKDF, the cookie's purpose as associated data and a random IV (`seal` in `apps/content/src/cookies.ts`): nobody without the secret can read or change them, and two values of the same claims differ. Every cookie the content Worker seals works this way; values signed with HMAC before cookies were encrypted are still read until they expire (at most a session's lifetime) and can be dropped after that. The Worker trusts the claims without D1 only while they are unexpired and their generation equals the artifact's current `policyGeneration`, which it reads on every request anyway, so a policy change applies to the next request. Otherwise `refreshReadSession` rechecks the session row, the dashboard session it came from and the policy; it renews the claims or clears the cookie and starts the entry again.

Read sessions end with the dashboard session that opened them. Signing out of `app.portifact.com`, signing out everywhere and revoking a session delete the `sessions` row, which cascades to its handoffs and read sessions, and a dashboard session that expired fails the same check. Claims already issued are trusted for at most their remaining 60 seconds, so artifact access ends within 60 seconds of signing out, like any other revocation.

- The read cookie is used only for `Sec-Fetch-Site: same-origin` requests and for navigations. Sibling artifacts are same-site, so their `<script>`, `<img>` and CSS loads would carry it; they get a `401` instead. Protected responses also send `Cross-Origin-Resource-Policy: same-origin` and are never embeddable.
- Requests without fetch metadata fail closed with a `401` page and no redirect, so a client cannot loop.
- An anonymous visitor cannot tell a missing artifact, an active protected one and an artifact that is not servable (archived, expired, suspended or without a version, in any access mode, public included) apart: all of them go through sign-in. Only a public artifact that is servable is served directly.
- Without a `READ_SESSION_SECRET` of at least 32 characters, protected artifacts answer `503`; public ones keep working.
- Values are sealed per purpose, so a transaction cookie never validates as a read cookie, and claims are parsed with the strict `ReadClaims` and `ReadTransaction` schemas from `packages/contracts`.
- Expired handoffs and read sessions are deleted by the maintenance job in bounded batches (500 rows of each per run, like `pruneOperations`); deleting an account, an artifact or a dashboard session cascades to its read sessions.

### The viewer

A visitor who opens an artifact's page in the browser's own tab lands in the viewer at `app.portifact.com/view/<id>` (plan section 8, "Flujo", decision of 2026-11-08): a slim Portifact bar (the mark, then the artifact's name as plain text and its version, then icon buttons for "Copy link" and the owner's settings or a report link, the comments toggle with the count of open threads, the dashboard and the account or sign-in; below the `sm` breakpoint everything but the mark, the name and the toggle moves into one "More" menu), the page in a sandboxed iframe on the artifact origin, in a bordered panel set apart from the bar, and the comments sidebar. The code is in `apps/content/src/viewer.ts`, `packages/domain/src/viewer.ts`, `apps/app/src/app-host.ts` (`VIEWER_ROUTE`), the viewer route in `apps/app/src/api/review.ts`, `packages/services/src/viewer.ts` and `apps/web/src/dashboard/screens/viewer.tsx`. The frame is the review frame of "Review mode" below, with every rule there; this section covers what is new.

1. **When the content Worker redirects.** Only a `GET` with `Sec-Fetch-Mode: navigate` and `Sec-Fetch-Dest: document` (`isTopLevelVisit`), whatever its `Sec-Fetch-Site`, to a page (a site's `text/html` file or a document's rendered page) of an artifact whose owner left the bar on, after the request was authorized and passed the traffic and budget checks, outside review mode, answers `303` to `<app>/view/<id>?path=<path and query>` with `no-store`, `no-referrer`, `nosniff` and `noindex`; it charges one request and no bytes, and for a protected artifact the read session's opening is logged as for the page. Everything else is served as before: frames (the viewer's own and other sites' embeds are `iframe`), subresources, `HEAD`, other methods, images, downloads and other files that are not pages, missing files (404), the reserved paths under `/__portifact/`, clients without fetch metadata, and every request of an artifact with the bar off, and every request that carries this browser's opt-out (item 13). Every answer of the content Worker sends `Vary: Sec-Fetch-Dest, Sec-Fetch-Mode, Sec-Fetch-Site`, because the redirect, review mode and session use all depend on them.
2. **Nothing leaks before access is checked.** The redirect is decided in `serveFile`, after authorization, so an anonymous visitor of a protected, missing or unavailable artifact goes through sign-in exactly as before ("Entry to protected artifacts") and never learns whether the bar is on. After the read handoff, the reader's next top-level visit of a page is the redirect; the viewer then reads through its own review session, so the read session only carried them through sign-in.
3. **No loops.** The viewer's frame navigations are `iframe` and never redirected. A review tab is served in review mode before the redirect is considered (the tab cookie is honored for top-level documents), so it keeps showing the artifact; the tab link and `/__portifact/review/end` are reserved paths. The app never navigates the top level to an artifact origin except through the review tab link. A planted frame cookie on a top-level visit is cleared as before (`strayFrameCookie`) whatever the answer is, redirect included.
4. **The path is untrusted at both ends.** `viewerPath` (`packages/domain/src/viewer.ts`) accepts only a path on the artifact origin: it must start with `/`, holds no backslash or control character, is parsed against a stand-in origin (so `//host`, `/\host`, tabs and newlines cannot leave it), refuses any first segment that decodes to `__portifact` in any case, and is at most 2,048 characters once normalized. The content Worker applies it when it builds the redirect and serves the page itself when the path does not fit, so the visitor never lands on a different page; the viewer applies it again to `?path=`, which anyone can write, and falls back to `/`. The fragment never reaches the server: the browser keeps it across the `303` and the viewer passes at most 1,024 characters of it, without control characters (`viewerHash`), to the frame. The review exchange accepts the same path as a single `to` parameter and its check page redirects there (`returnPath` in `apps/content/src/viewer.ts`), so review starts on the linked page; a missing, repeated or refused `to` starts at `/`. A link someone crafts can only open another page of the same artifact.
5. **The viewer page.** `/view/<id>` (an ID that is not an artifact ID answers 404) serves the dashboard bundle with or without a session, with the dashboard's policy narrowed to this artifact (`viewerCsp`: `frame-ancestors 'none'`, and `frame-src` naming only `https://<id>.portifact.dev` and the Turnstile origin, so the frame can never be navigated to another artifact or site), `X-Frame-Options: DENY`, `no-store`, `no-referrer` and `X-Robots-Tag: noindex`. It holds no data of its own: what the bar shows comes from `GET /api/v1/artifacts/:id/viewer` (`ViewerInfo`: name, type, origin, version number, access mode, comment mode and the visitor's role, never threads, readers or emails), a dashboard helper with no state, so it has no CLI command or MCP tool. It refuses bearer tokens and anything that is not `Sec-Fetch-Site: same-origin` (failing closed without fetch metadata), takes the visitor from the session cookie when there is one (an account that has not accepted the current terms counts as none) and applies `checkReadAccess`; without a session it answers only for a public artifact that is servable, and 404 exactly like a missing artifact for everything else. It answers without a session, so it is limited per IP (`VIEWER_LOOKUP_LIMIT`, 300 per 10 minutes, in the D1 counters). The old `/review/<id>` answers `301` to `/view/<id>`. The viewer's links to the dashboard and the dashboard's links to the viewer ("Review and comment" on the artifact page, the list and the publish result) are full page loads, so each page keeps its own policy (client-side navigation would keep the first page's).
6. **Signed-in visitors** get a review code (`POST /api/v1/artifacts/:id/review`: dashboard session only, exact `Origin`, `checkReadAccess`) and the frame redeems it, so every reader who can open the artifact, owner or not, public or protected, gets the bridge, the highlights and the sidebar. Selecting text or picking an element in a site offers a comment through a "Comment" control the viewer draws next to the selection, which opens a composer there; both are drawn by the viewer over the frame, never inside the artifact (see "Inline comments" in "Review mode"). Any site can make a signed-in browser load the viewer (a popup reloading `/view/<id>` of the attacker's public artifact sends the session cookie every time), so codes are bounded in ways that one artifact cannot spend for the others: `REVIEW_START_LIMIT` (60 per 10 minutes) counts per account and artifact, and an account keeps at most `REVIEW_SESSION.openCodesPerUser` (10) unredeemed codes, issuing another deletes the oldest in the same batch (`issueReviewHandoff`). A flood can therefore only expire a code that was not redeemed within the moment it took to load the frame; the viewer then offers to reload. Where the frame keeps no session (the check page reports `unavailable`) or no code can be issued, a public artifact's frame shows the page itself without review tools and a protected one keeps the notice; both offer "Open without the Portifact bar" (item 13), and where the frame keeps no session, the review tab too, which also opens on the linked page.
7. **Anonymous visitors** reach the viewer only for public artifacts. The frame loads the page itself (no code, no session, no bridge), so nothing names them, the content Worker logs nothing and the page's subresources stay ordinary public requests. Threads are for signed-in readers only (plan section 8, "Permisos": anonymous visitors get public content only), so the sidebar, shown while comments are not off, holds only "Sign in to comment", which goes to `/login?next=/view/<id>?path=…`; the login page accepts `next` for `/view/<artifact-id>`. A protected artifact answers 404 to the viewer's lookup, and the viewer sends the visitor to sign in with the same `next`.
8. **Comment modes.** While comments are off, readers get no sidebar and no thread requests (the bar stays); the owner keeps the sidebar with the switch to turn them on. Locked is read-only as before. The owner sees the moderation actions; every permission still comes from the API.
9. **The owner's opt-out.** The bar is part of the access policy (`artifacts.bar`, on by default for new and existing artifacts, `PATCH /api/v1/artifacts/:id/access` with `bar`, scope `artifacts:share`, the MCP tool `set_portifact_bar` with the same scope, `portifact access bar <id> on|off` and the dashboard's access settings). Turning it on or off does not bump the policy generation: it changes neither who may read nor what other sites may load, and a bump would end every reader's read and review sessions for nothing. It is still conditioned on the generation the request read, so it conflicts with a concurrent access change, and the content Worker reads `bar` on every request, so it applies at once. With the bar off, every request is answered exactly as before the viewer existed.
10. **Embeds and crawlers.** Other sites' frames are `iframe`, so an embeddable public artifact is still served under `frame-ancestors *` and `cross-origin` CORP, and a non-embeddable one is still refused there by its `frame-ancestors`. Crawlers do not send fetch metadata, so they get the artifact itself on its own origin, where `indexable` keeps deciding `noindex`; the viewer is always `noindex` and carries no `rel="canonical"` (Google treats `noindex` with a canonical as conflicting signals, and the artifact's own URL is the only one ever indexed). A browser that does not send fetch metadata also gets the artifact itself.
11. **Links that leave the frame.** The frame's sandbox stays `allow-scripts allow-same-origin allow-forms allow-popups`, without any top navigation, so `target="_top"` and `target="_parent"` links and form posts inside a site are blocked by the browser, as in review mode; pages that rely on them, full-screen apps and pages that must be embedded elsewhere are what the owner's opt-out is for. Links that open a new window (`target="_blank"`, `window.open`) are allowed; the new window's top-level visit to a page of the artifact is redirected to the viewer like any other. Content responses that are not `GET` still answer 405, so a form post never reaches the redirect. A link inside the frame to another site or another artifact that does not open a new window is refused by the viewer's `frame-src` (Chromium shows an error page and the watchdog says the frame stopped answering from the artifact; Firefox keeps the page).
12. **Clickjacking and isolation.** The viewer, like every app page, is never framed (`frame-ancestors 'none'` and `X-Frame-Options: DENY`). The artifact never gets more than in review mode: no tokens, emails or bodies, the same message rules, and review responses keep `frame-ancestors 'self'` plus the app origin.
13. **The bar is not a security control.** Owners turn it off for everyone, and any visitor can leave it: "Open without the Portifact bar" (offered when the viewer cannot show the artifact with its tools) is `https://<id>.portifact.dev/__portifact/raw?to=<path>`, which only a top-level navigation (`isTopLevelVisit`) may use; it sets `__Host-pf_nobar=1` (`Secure; HttpOnly; SameSite=Lax; Path=/`, host-only, one hour) and continues to the page through `viewerPath`, and top-level visits that carry exactly that value get the artifact itself (through the read handoff for a protected one). The cookie grants nothing and is matched exactly like every Portifact cookie, so a sibling cannot set it (a `__Host-` name) and anything else (another value, a lowercase look-alike, two values) still opens the viewer; a site that sends a visitor to the path can only show them the artifact without the bar. Nothing that keeps users safe may depend on the bar being shown.
14. **Phishing through the viewer.** The viewer puts untrusted content under `app.portifact.com`, next to Portifact's real mark, which a hostile artifact can use: a name like "Portifact: session expired" over a page with a code form, under an address bar that reads `app.portifact.com/view/…`. The security review proposed keeping the artifact's name out of the bar, in a caption attached to the frame with the artifact's own link and a "Published by a user, not by Portifact" badge. On 2026-11-09 the maintainer decided against that caption and accepted the residual risk: the bar now shows the artifact's name, as plain text (normal weight, after a divider, never styled as a Portifact heading), and its version, "Copy link" copies the artifact's own link without showing it, and there is no user-content badge. The mitigations that remain are: the owner's per-artifact opt-out of the bar (item 9), the frame's sandbox (item 11), `frame-ancestors 'none'` on the viewer (item 12), the frame drawn below the bar's border and shadow (edge to edge since 2026-11-09, by the maintainer's decision; the bordered panel around it was dropped), and that the bar never shows a Portifact action that asks for credentials, and must stay that way: every Portifact form (sign-in, comments) lives outside the frame, the bar's controls only link, copy or toggle, and no Portifact page asks for credentials inside an artifact. What a page draws inside its frame can still imitate anything, as on its own origin; the human check, the report link in the bar and suspensions are the remaining controls.

#### Owner branding

Premium plan P9 (feature `branding`, Pro and above): an owner's brand on the viewer's bar. The code is in `packages/domain/src/branding.ts`, `packages/services/src/branding.ts`, the account routes in `apps/app/src/api/account.ts`, the logo route in `apps/content/src/index.ts`, `BrandMark`, `HostingNotice` and `brandPalette` in `packages/ui` and `apps/web/src/dashboard/screens/branding.tsx`.

1. **Four values, never markup.** A name (NFC, spaces collapsed, at most 60 code points, no control, format, separator, private-use or unassigned characters, so no bidi overrides or zero-width tricks, and nothing whose letters, with look-alike digits read as letters, contain "portifact"), one `#rrggbb` accent, an optional `https` link and an optional logo. The viewer renders the name as text, the link as an `<a target="_blank" rel="noopener noreferrer">` and the logo as an `<img alt="" referrerpolicy="no-referrer">`; nothing an owner sends reaches the app origin as HTML, CSS or script. The accent is set as a custom property through the CSSOM on the brand chip only, after `brandPalette` validated it as one color, so it cannot inject CSS.
2. **The link** is checked like an outbound link (`normalizeBrandLink`): parsed by the WHATWG URL parser, `https` only, no user name or password, no port, no IP literal in any spelling (the parser normalizes them, IPv6 keeps its brackets), no single-label, `.local`, `.localhost`, `.internal`, `.test`, `.invalid` or `.example` host, and no Portifact host: `portifact.com`, `portifact.dev` and the deployment's own app and content domains, with their subdomains. It is stored as the parser serializes it, at most 2,048 characters.
3. **The logo is judged by its bytes** (`inspectLogo`), never by its name or declared type, and the upload's `Content-Type` is ignored: a PNG, JPEG or WebP signature, a walk of the whole file (PNG chunks with their CRCs up to `IEND`, JPEG segments and entropy-coded data up to `EOI`, the RIFF size of a WebP matching the file), nothing after the end, dimensions from the header between 16 and 1,024 pixels a side, at most 100 KB, no animation (APNG `acTL`, `fcTL`, `fdAT`; WebP's animation flag, `ANIM`, `ANMF`) and no markup anywhere in the bytes (`<html`, `<script`, `<svg`, `<?xml`, `javascript:` and similar, case-insensitive), so a polyglot that is also an HTML or SVG document is refused. SVG and every other format are refused at the signature. The request body is read up to the cap and no further.
4. **Where the logo lives and how it is served.** R2 at `brands/<owner>/<sha256>`, written before the batch that names it, with a `delete_objects` job written first as the safety net, so an upload that dies leaves nothing behind; the job keeps any key a brand names. It is served only on the artifact's own origin, at `/__portifact/brand/<sha256>`, by the content Worker: only for `Sec-Fetch-Dest: image` (never a document, a frame or a client without fetch metadata), only the current logo of that artifact's owner while the artifact is servable and the brand is shown, with its exact type, `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: cross-origin` (the viewer is another site), `noindex`, `no-referrer` and `public, max-age=31536000, immutable` (its address is its hash). The viewer's `viewerCsp` adds exactly that artifact origin to `img-src`, so the viewer never loads an image from a host an owner chose, and nothing the owner uploads is ever served by `portifact.com`. The Branding page's own preview reads the logo through `GET /api/v1/account/branding/logo` (session only, same-origin, the same inert headers with `same-origin` CORP), never linkable from another site. The URL is a capability: it reveals the owner's logo to anyone who has it, which the viewer gives only to visitors allowed to see the artifact; the logo is not charged as traffic.
5. **Who sees it.** `getViewerArtifact` returns the brand only with the rest of `ViewerInfo`, so a visitor who cannot open the artifact gets the same 404 as before and learns nothing about the brand; it joins the brand and the owner's plan into its one query, so unbranded owners cost no extra read. It returns null (the default bar) without a brand, while the owner's plan lacks `branding` (the brand is kept, unused) and while the operator suspended it.
6. **Not a phishing aid.** A branded bar always keeps a `HostingNotice` under it, at every width: "Powered by Portifact" with Portifact's mark, the artifact's real host (`<id>.portifact.dev`) in monospace and, for everyone but the owner, the report link, besides the bar's own report link. The brand's chip replaces the Portifact symbol as the bar's first element, never the notice. Review mode, inline comments, the sidebar, the fallback review tab's banner, emails and artifacts themselves are never branded: the content Worker never sees a brand except to serve the logo. An operator suspension (`suspend-brand`) brings back the default bar at once and stops the logo; the owner cannot delete a suspended brand. Removing Portifact's mark entirely is not offered.
7. **Management.** Only admins of the owner (role action `brand`) read and change it, through the session-only `/api/v1/account/branding` routes (bearer tokens refused, exact `Origin`, `Sec-Fetch-Site: same-origin`); there is no MCP tool or CLI command, because a token that could rebrand the bar would turn a leaked credential into a phishing page and agents have no need for it ([decision 0003](decisions/0003-credentials-scope.md) keeps such powers out of tokens). A user without a role gets what a missing owner gives. Setting the brand or a logo answers `plan_required` without the feature (the owner's plan, never the caller's); removing either never does.

### Review mode

The viewer at `app.portifact.com/view/<id>` (see "The viewer" above) shows one pinned version of the artifact to a signed-in visitor in a sandboxed iframe on the artifact origin, with the bridge (`packages/bridge`) injected; comments are written and confirmed in the viewer (in a composer it draws over the frame next to the selection, or in the sidebar) and posted through the annotations API. The code is in `apps/app/src/api/review.ts`, `apps/content/src/review.ts`, `apps/content/src/inject.ts`, `packages/services/src/review-access.ts` and `apps/web/src/dashboard/screens/viewer.tsx`, following [decision 0002](decisions/0002-review-mode-cookies.md).

1. The viewer calls `POST /api/v1/artifacts/:id/review`, which accepts only the dashboard session (exact `Origin`, `Sec-Fetch-Site: same-origin`; bearer tokens get 403), is limited per account and artifact (`REVIEW_START_LIMIT`, 60 per 10 minutes) with at most 10 unredeemed codes per account (see "The viewer") and applies the same `checkReadAccess` as reading the artifact, so a missing and a forbidden artifact both answer 404. It stores a one-use code (`review_handoffs`: only its SHA-256, the user, the current version, the dashboard session's ID and the policy generation, valid 60 seconds) and returns the iframe URL on the artifact origin, built from the validated ID, and the session tag (`reviewSessionTag`: 16 bytes of a domain-separated SHA-256 of the code, which reveals neither the code nor the session ID).
2. `/__portifact/review?code=…` redeems it only for a cross-site iframe navigation (`Sec-Fetch-Site: cross-site`, `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: iframe`), which stops a top-level visit and a sibling artifact's direct request. It does not prove that the viewer started the navigation: an artifact framed in the viewer can open a frame to a redirector on another site that lands on the exchange with a code of its own (for an artifact it can read), and that arrives with the same metadata, so the attacker's review session replaces the visitor's in the viewer's partition. That is why the claims carry the session tag, the bridge script gets it as `data-session-tag` and echoes it in `ready`, and the viewer refuses a `ready` whose tag is not the one it got with its code: it gives that page no nonce, turns the review tools off and offers to reload the review, which redeems a new code of the visitor's. Comments are not affected either way, because they are posted with the dashboard session. One guarded update marks the code used while the dashboard session is live, and the `review_sessions` row is inserted only if it happened. It sets `__Host-pf_review` (`Secure; HttpOnly; SameSite=None; Partitioned`, no `Domain`, 4 hours) with encrypted claims (session, artifact, pinned version, user, policy generation, session tag, 60-second claims expiry, session expiry), sealed with `READ_SESSION_SECRET` under its own purpose, and redirects to `/__portifact/review/check`.
3. The check page redirects to `/` when the cookie came back. When it did not (the browser blocks partitioned cookies in frames), it answers a page whose one nonce-allowed script posts a fixed `status: unavailable` message to the viewer's exact origin, and the viewer offers general comments only.
4. The review cookie is honored only for `Sec-Fetch-Site: same-origin` or `cross-site` with `Sec-Fetch-Mode: navigate`, never for `Sec-Fetch-Dest: document` (the viewer's frame navigations are always `iframe`), matched exactly and case-sensitively, and requires exactly one value. A frame cookie on a top-level document navigation was planted, and every such response clears it (see "The review tab"). Siblings are `same-site` and get the normal public or sign-in answer. Claims are trusted without D1 only while unexpired and while the artifact's policy generation is unchanged; then `refreshReviewSession` rechecks the session, the dashboard session it came from and the access policy. The pinned version must still be current. Otherwise the response is a status page (`ended`) that clears the cookie with the same partition attributes, so revocation, archiving, signing out or a new version ends review within 60 seconds or at once.
5. Review responses serve the pinned version with `Cross-Origin-Resource-Policy: same-origin`, `frame-ancestors 'self'` plus the app origin (never `*`, even for an embeddable public artifact) and `Cache-Control: private, no-store`. HTML is rewritten on the way out with `<script src="/__portifact/bridge.js?v=<bundle version>">` appended; the stored bytes and downloads never change, and rewritten pages carry no `ETag` or ranges. For a page rendered by Portifact, the document's CSP `<meta>` is dropped and the header carries the same policy with the bridge's `'nonce-…'` added to its one `script-src` (which otherwise allows only the diagram loader and the diagram script, see "Diagrams and highlighted code"). A site's own CSP is left as it is; if it blocks the bridge, the viewer stops waiting after 5 seconds and offers general comments.

The bridge and the viewer exchange `postMessage` only with each other's exact origin and window, within size limits (16 KiB from the bridge, 2 MiB of at most 200 highlights to it) and strict schemas (`packages/bridge/src/protocol.ts`, `REVIEW_PROTOCOL` 2 since threads became highlights without numbered markers; the bridge script is versioned with the bundle, so both sides change together). The viewer gives each page load a fresh instance nonce after its `ready` message and drops every later message without it. The artifact's own scripts share the bridge's window and can overhear the nonce, so every bridge message stays untrusted data: a selection or a picked element only fills in a comment that the reader writes and confirms, and the server takes the author from the session. The frame receives the targets of the threads to highlight, their IDs and the element-mode hint, never thread numbers, bodies, author names, emails or tokens. Its sandbox is `allow-scripts allow-same-origin allow-forms allow-popups`, without top navigation. The bridge draws in a closed shadow root marked `data-portifact-ignore` and reads no form values, cookies or storage. The closed shadow root keeps the page's styles out of the overlay, not its scripts: they run in the same window and can patch the DOM APIs the bridge uses, hide or fake markers and send anything the bridge sends. The dashboard's CSP allows `frame-src https://*.portifact.dev` and keeps `frame-ancestors 'none'`.

What the frame can and cannot do to the viewer, given that the page can forge any bridge message:

- It cannot open or retarget a comment. The viewer accepts an `element` only while the reader is picking (the bridge sends `element` before `pick-ended`, which ends the wait), and ignores `selection`, `element` and `selection-rect` while a comment is open. The composer keeps the target and the position it opened with. A forged selection only offers a comment: the "Comment" control appears, and nothing is written until the reader types and saves.
- It cannot place the viewer's UI outside the frame. See "Inline comments" below.
- It sees only what the current page needs: the IDs and targets of the threads whose target is on the page the bridge reports (at most 200), which threads are selected, and which one the reader points at in the sidebar (`hover`).
- Highlights are drawn in the closed shadow root, take no pointer events and no focus, and add nothing to the page's tab order. Overlapping threads are layered translucent boxes, so text several threads cover is darker. Clicks stay the page's (links and buttons under a highlight still work); the bridge listens to them in the capture phase and reports `select` with the IDs of every highlight that covers the point, innermost first (`threadsAt` in `packages/bridge/src/overlay.ts`), or an empty list when the click missed every highlight while threads were selected. Keyboard activations (`detail` 0) and the end of a text selection are not reported.
- `resolved` and `select` count only for the threads the viewer last highlighted on that page (`useBridge` drops every other ID, and the screen keeps only threads its sidebar shows), and only change which threads are marked placed or orphaned and which are selected: the sidebar scrolls to them, shows several together and announces them politely, without moving focus out of the artifact. A forged `select` can select threads the reader already sees and nothing else; it never opens a composer, posts or changes a thread.
- `status` (`ended`, `failed`, `unavailable`) has no nonce because the content Worker's status pages send it, so any page of the artifact can forge it. It only changes the frame's notice and turns the review tools off; the viewer then refetches the threads, and whether the reader can comment, the threads and their state always come from the API. A forged status is a denial of service of the review tools, which a hostile artifact can cause anyway by not running the bridge.
- After every load of the frame the viewer must hear from the artifact's origin within 5 seconds: the new page's `ready`, or a `pong` to the `ping` it sends with the current nonce. Otherwise it warns that the frame stopped answering from the artifact, says not to trust what it shows, and turns the review tools off. A page can navigate its own frame to another artifact (a look-alike, or a file without the bridge); that navigation is `same-site`, so the review cookie is not honored there and the other artifact gets its public or sign-in answer. A bounce through a redirector on another site, which would arrive as the `cross-site` navigation the review cookie honors, is refused by the viewer's `frame-src https://*.portifact.dev` (Chromium shows an error page, Firefox keeps the page; `e2e/tests/review.spec.ts` checks both), so a page cannot make another artifact render in review mode inside this viewer. A nested frame is not covered by the viewer's `frame-src`, which is why planting a session (above) works, but a review response's `frame-ancestors` keeps it from rendering there.

#### Inline comments

Plan section 8, decision of 2026-11-08 ("comentar en línea y visibilidad"): selecting text in the frame (or picking an element in a site) shows a small "Comment" control next to the selection, and activating it opens a compact composer there (a text area, Cancel and Save). The code is in `apps/web/src/dashboard/screens/viewer.tsx`, `packages/ui/src/patterns/frame-overlay.tsx` and `packages/bridge/src/geometry.ts`.

1. **Drawn by the viewer, never by the artifact.** The control and the composer are elements of the viewer page on `app.portifact.com`, in a layer (`FrameOverlay`) that covers exactly the iframe's box and clips its content, so the artifact cannot reach, restyle or read them, and they cannot be drawn over the bar, the sidebar or anything else outside the frame. The bridge draws nothing for them inside the artifact's document.
2. **Rectangles are untrusted hints.** The bridge sends where the selection or picked element is drawn, in the frame's viewport (`rect` on `selection` and `element`, and `selection-rect` while it moves with the page's scrolling or resizing, at most every 50 ms). The page can forge any of them, so the schema accepts only finite numbers within ±1,000,000 pixels with non-negative sizes (anything else drops the whole message), and the viewer keeps only the part inside the frame's visible box (`visibleRect`), hides the control when none is left or the bridge says the selection is no longer drawn, and places the control and composer wholly inside the frame (`placeNear`). A selection reported without a rectangle gets the control in the frame's corner. A `selection-rect` changes only where the current offer's control sits: it is ignored when nothing is offered and while a comment is open, and never carries or changes a target.
3. **Every rule above still holds.** The bridge never posts; the viewer accepts a selection only with the nonce of its session's current page and an element only during a pick; while a comment is open it ignores what the frame sends, and the composer keeps its target and its position (it does not follow later rectangles). Save posts with the dashboard session, after the reader typed the comment, and the server takes the author from the session.
4. **Narrow screens and small frames.** Below 40rem, or when the composer does not fit beside the selection inside the frame, it is a bottom sheet across the screen instead, whose position does not depend on the frame at all. The sheet follows the visual viewport (`keyboardInset`), so it stays above an on-screen keyboard and never grows taller than what is left of the screen.
5. **Keyboard and screen readers.** Focus stays in the artifact when the control appears; a polite announcement says it is there, and it follows the frame in the tab order. The composer takes focus when it opens; Enter saves, Shift+Enter adds a line and Escape (from anywhere in it) cancels, after which focus returns to the frame.

Expired review codes and sessions are deleted by the maintenance job in bounded batches, like read sessions.

#### The review tab

Where the frame cannot run review mode (the check page reports `unavailable`, which Firefox with all third-party cookies blocked and WebKit on Linux do, or the bridge never answers), the viewer offers the fallback from decision 0002: the artifact in a top-level review tab. Comments are still written, confirmed and posted only in the viewer, as general comments; the tab has no bridge and no channel back to the viewer.

A hostile artifact in the viewer's frame can force this offer, by forging `status: unavailable` or by staying silent. The tab it leads to is the artifact itself, an untrusted page on the artifact origin that may imitate Portifact's UI (a fake sign-in, a fake comment box). The offer says so: the tab shows the artifact, written by its author, not Portifact, so nothing should be signed in to or entered there. No credential, session or comment form of Portifact ever lives on the artifact origin.

1. "Prepare a review tab" calls `POST /api/v1/artifacts/:id/review/tab`, with every check of the review code route (dashboard session only, exact `Origin`, `Sec-Fetch-Site: same-origin`, the same per-account limit and `checkReadAccess`). It stores a code like a review code with `kind = 'tab'` (`review_handoffs.kind`), and redemption is conditioned on the kind, so a frame code never opens a tab session and a tab code never opens a frame session.
2. The viewer shows the URL as a link (`target="_blank" rel="noopener" referrerpolicy="origin"`) and withdraws it 10 seconds before the code expires or once it is clicked. `noopener` keeps the tab from reaching or navigating the viewer (reverse tabnabbing); `referrerpolicy="origin"` overrides the dashboard's `no-referrer` for this link only, so the artifact origin receives just `https://app.portifact.com` as `Referer`. The link is a second click rather than `window.open` after the API call, which popup blockers stop and which would keep an opener or lose the referrer.
3. `/__portifact/review/tab?code=…` redeems the code only for a top-level cross-site navigation (`Sec-Fetch-Site: cross-site`, `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`) whose `Referer` origin is exactly the app origin. An artifact, in the viewer's frame, a popup or a tab of its own, starts navigations with its own origin as referrer (or none, and redirects keep the initiator's referrer), so it cannot redeem a tab code of its own in a visitor's browser, directly (`same-site`) or bounced through another site (`e2e/tests/review-tab.spec.ts`). The app's pages are the dashboard's own and never redirect to an artifact origin on input. A browser that strips cross-site referrers entirely cannot open review tabs; the viewer still offers general comments. A planted tab session would in any case only show the visitor the artifact's current version through an account that may already read it, and could post nothing. One guarded update marks the code used while the dashboard session is live, as for frame codes.
4. It sets `__Host-pf_review_tab` (`Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`, no `Partitioned`, 15 minutes, `REVIEW_SESSION.tabSessionTtlSeconds`) with the same claims as the review cookie sealed under their own purpose (`pf_review_tab`), so neither cookie's value validates as the other, and redirects through `/__portifact/review/tab/check` to `/`. `Lax` keeps it out of the viewer's cross-site frame and out of every other site's subresource requests.
5. The tab cookie is honored for `Sec-Fetch-Site: same-origin` requests and for top-level navigations (`Sec-Fetch-Mode: navigate` with `Sec-Fetch-Dest: document`, from any site), and never without fetch metadata. Unlike the frame's cookie it lands in the artifact's own partition, so later visits in that browser carry it until the session ends; honoring their document too keeps the banner on every page that is served in review mode, instead of a normal page whose subresources come back in review mode. A sibling artifact's subresource or frame request carries it as `same-site` and gets the normal answer, and its top-level navigation shows the visitor the page and lets the sibling read nothing. Claims, renewal, the version pin, `Cross-Origin-Resource-Policy: same-origin`, `frame-ancestors` and `no-store` are those of the frame session, so signing out, revocation, archiving or a new version end the tab within 60 seconds or at once, with a status page that clears the tab cookie.
6. HTML in the tab gets a banner instead of the bridge, at the start of the body (or the end of a page without a body tag): plain markup in a declarative shadow root, so the page's styles cannot restyle it and it needs no script. It says the tab is in review mode, that comments are written in the viewer and that it ends within 15 minutes, and links to `/__portifact/review/end`, in the browser's language (`Accept-Language`, `bannerLocale`) and marked with its own `lang`; the response is `private, no-store`, so the language is never cached for another reader. Rendered documents keep their policy, whose only scripts are the diagram loader and the diagram script. The page's scripts can hide or fake the banner, which is why the session is short and the viewer also says how long it lasts and how to end it.
7. `/__portifact/review/end` ends the session only for a `GET` navigation from the artifact itself (`Sec-Fetch-Site: same-origin`, `Sec-Fetch-Mode: navigate`), so another site or a sibling cannot end a visitor's review: it deletes the `review_sessions` row named in the claims (`endReviewSession`) and clears the cookie, so the next request is a normal visit and a copied cookie is refused when its claims next need renewing. Ending twice or without a session only clears the cookie. The artifact's own scripts can follow the link too, which only ends review.
8. A sibling can plant a frame session in the artifact's own partition: it frames a redirector on another site that forwards to the artifact's exchange with a frame code of its own (for any artifact its author can read). The exchange sees the same `cross-site`, `navigate`, `iframe` request as the viewer's and redeems it, and because that frame sits under the `portifact.dev` top-level site, the partitioned `__Host-pf_review` lands in the partition of the artifact's top-level visits (Firefox keeps it even with all third-party cookies blocked, since the frame is first-party). Three rules keep it from reaching a visitor's top-level pages or review tab: the frame cookie is never honored for `Sec-Fetch-Dest: document`; every response to a top-level document navigation (`navigate` and `document`, including `/__portifact/review/end`) that carries a `__Host-pf_review` clears it with `Partitioned` (`strayFrameCookie`), before the page's same-origin subresources can carry it, which never touches a genuine frame cookie because that lives in the viewer's partition; and the tab cookie is tried before the frame cookie, so a frame cookie that does reach a request never outranks the visitor's tab. `e2e/tests/review-tab.spec.ts` reproduces the plant.
9. The app sends `Referrer-Policy: no-referrer` on every response (the global middleware in `apps/app/src/app-host.ts`), so app URLs never leave as `Referer`; the review tab link alone overrides it with `referrerpolicy="origin"`.

### Identity and the authorization server

`app.portifact.com` runs Better Auth in the `portifact-app` Worker as the only identity provider and OAuth authorization server ([decision 0001](decisions/0001-oauth-server.md)). The code is in `apps/app/src/auth`.

- The session cookie is `__Host-pf.session_token` with `Secure; HttpOnly; SameSite=Lax; Path=/` and no `Domain`. Every Better Auth cookie uses the `__Host-pf.` prefix, set through `cookiePrefix` with `useSecureCookies: false` so Better Auth does not add `__Secure-` in front.
- Only the endpoints Portifact uses are reachable under `/api/auth`; the allowlist in `apps/app/src/auth/routes.ts` answers 404 for everything else, including password sign-up, admin and client management endpoints, OIDC userinfo, HTTP introspection and `/device/token` (which would issue first-party session tokens). Adding a Better Auth endpoint means adding it to the allowlist with a test.
- Browser endpoints (sign-in, sign-out, consent, device approval) require the exact `Origin` of the app on every `POST`. Client endpoints (token, revoke, registration, device code) never see cookies: the Worker strips them, so a registration or token request cannot act on a browser session.
- The legal pages (`/terms`, `/privacy`, `/acceptable-use`) are served on `portifact.com` only, with the same strict CSP, `no-cache`, `nosniff` and `X-Frame-Options: DENY`, and load no script besides the inline theme script.
- **Theme script.** Every page built by apps/web (the landing, legal and MCP pages, the auth pages, the dashboard and the viewer) carries one inline script, `THEME_SCRIPT` in `packages/contracts/src/theme.ts`, which applies the stored theme before the first paint (see "Theming" in [design.md](design.md)). The policies allow exactly its text by hash: `PAGE_CSP` and every policy built on it add `THEME_SCRIPT_HASH` to `script-src`, and so does the landing's policy in `apps/web/public/_headers`. Never allow `'unsafe-inline'` instead, and never add another inline script; tests compare the hash to the script and check each served page holds that one inline script and nothing else inline. The script only reads the `__Secure-pf_theme` cookie and `localStorage` and sets attributes, so it handles no secret. The preference is the shared cookie described in "Cookies and sessions", with this origin's `localStorage` as the fallback where cookies are blocked; it never reaches `portifact.dev`. Pages on `portifact.dev` never load the script.
- **Language preference.** The site Worker (`apps/app/src/site-language.ts`) answers a `GET` or `HEAD` of a site page (`/`, the documents and their copies under a language prefix) with a `302` to the same page in the language of a valid `__Secure-pf_lang` when it differs from the page's, with `Vary: Cookie` and `Cache-Control: private, no-store`; requests without the cookie (crawlers, first visits) are served the page they asked for, and every site page carries `Vary: Cookie`. The static switchers link to `<page>?lang=<code>`: the Worker sets the cookie from that parameter and redirects to the page without it, so a switch works on the scriptless legal pages and in a new tab and can never loop back to the previous choice. The app host never redirects by the cookie; its pages read it in the browser.
- Every `/api/auth` response sends `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. The dashboard and the auth pages (`/login`, `/device`, `/consent`) send a strict CSP (`default-src 'none'`, same-origin scripts plus the theme script's hash, styles, images and requests, `frame-ancestors 'none'`), `no-store` and `no-referrer`. They are served only on the app host; `portifact.com` answers 404 for them. The dashboard is served only at its routes and only with a valid session of an account that accepted the current terms; without one it redirects to `/login?next=...`, and `next` accepts only the device page and the dashboard routes.
- Google and GitHub accounts are keyed by the provider's stable ID. A provider sign-in joins the existing account with the same email only when the provider vouches for the email and the account's own email is verified (`requireLocalEmailVerified`); otherwise it is refused with `account_not_linked`. A provider that does not mark the email as verified cannot create an account either (`email_not_verified`), so every account's email is proven and a later email code or provider sign-in for that address always lands in the account of whoever controls it. Provider accounts are never unlinked from the web yet, and `/link-social` (linking a provider with a different email) stays off.
- Google and GitHub tokens are not stored: the account row keeps only the provider and its user ID.
- No account is created and no session is issued without the current terms accepted ([legal.md](legal.md)). The login page shows a notice above the methods and, when the user chooses one, posts the acceptance to `POST /api/auth/accept-terms` (exact `Origin`, limited per IP) before starting it; before sign-in it gets `__Host-pf_terms`, HMAC-signed with a key derived from `BETTER_AUTH_SECRET`, 30 minutes, cleared when a session is created. Better Auth hooks verify it when creating a user or a session; `terms_version` and `terms_accepted_at` are not writable from any request body. The dashboard, the `/api/v1` session lookup and `/read/<id>` treat a session of an account without the current version as no session.
- No account is created without a solved human check (Cloudflare Turnstile); see "Human check" below. Existing accounts sign in without one.
- Expiry notices go only to the owner's account address (for a workspace, each admin's), skip suppressed addresses and stop before the sign-in emails of the cycle run out (see "Expiry notices" in [operations.md](operations.md)). Their links point only at the artifact's own origin and the dashboard, built from IDs; artifact names are escaped, kept on one line and never put in the subject.
- Email codes are 6 digits, valid for 5 minutes, single use, three attempts, and stored as hashes. Sending is limited per IP, per address (one per minute, five per hour) and by a global daily budget, in D1 counters keyed by an HMAC of the address, never the address itself. The answer is the same whether or not an account exists. Only sign-in codes can be requested.
- After those limits, the auth route asks `checkSignInEmail` (`packages/services/src/email.ts`): a suppressed address answers `403 email_suppressed` with an explanation (the login page shows it), and once the cycle's sign-in emails are spent (`SIGN_IN_EMAILS_PER_CYCLE`, the 20,000-email admission limit minus a reserve of 100 for budget alerts, `packages/domain/src/email.ts`) every send answers `503 capacity_unavailable`. Every email sent (codes and budget alerts) is counted in `email_counters`, one row per UTC day without recipient data, which the budget run reads as its `emails` metric. The suppression check runs after the rate limits, so it cannot test many addresses quickly, and it reveals only that mail to the address failed, never whether an account exists.
- Suppressions (`email_suppressions`) are keyed by a SHA-256 of the normalized address with a fixed prefix, unkeyed so the operator tool can look an address up without the Worker's secrets, plus a masked hint (`a***@example.com`); the full address is never stored or logged. They come from two sources: Cloudflare Email Service events (`message.bounced` with `bounce.type` `hard`, and every `message.complained`) delivered to the `portifact-email-events` queue and recorded by the jobs Worker, and a send the `EMAIL` binding refuses with `E_RECIPIENT_SUPPRESSED` because Cloudflare's own list holds the address (`provider`). Better Auth swallows delivery errors so the answer stays the same, which means a `provider` refusal shows its explanation from the next request on. They last 30 days (hard bounce), 180 days (complaint) or 7 days (provider), the stronger reason wins on a repeat, and the maintenance job prunes them. Cloudflare keeps its own list independently, so lifting ours does not lift theirs (see [operations.md](operations.md)). Code guesses, client registrations and device codes are also limited per IP.
- The device page binds a code to the first signed-in user who opens it; nobody else can approve it. A device request cannot name the user who approves it (`user_id` is refused).
- The CLI (`packages/cli`) signs in with the device grant as `portifact-cli`, requesting every product scope, `credentials:manage` and `offline_access` for `https://app.portifact.com/api/v1`. It keeps tokens per server origin in the OS credential store (`Bun.secrets`) or, when there is none, in a `credentials.json` written `0600` in a `0700` directory with a warning. It never prints tokens or the device code, does not follow redirects with tokens, opens or shows only verification pages on the server's own origin, and accepts a `PORTIFACT_APP_ORIGIN` override only for https or loopback http. `logout` revokes before deleting and keeps the credentials if the server cannot answer. A refresh that fails with `invalid_grant` deletes them, unless another process already stored newer ones. After a successful publish the CLI may run GitHub CLI's read-only `gh auth status` and `gh api user/starred/leynier/portifact` locally (`packages/cli/src/star.ts`, argument arrays, no shell, about 3 seconds at most, never with `CI` or `PORTIFACT_NO_STAR_PROMPT` set) to decide whether to suggest a star once per device; it never stars or runs any other `gh` command, keeps only a `star-suggestion.json` flag in the config directory and sends nothing to Portifact.
- Access tokens are opaque and checked against D1 on every request. A resource accepts a token only if its audience contains that exact resource: CLI tokens work only at `/api/v1`, MCP tokens only at `/mcp`. The seeded CLI client is linked to the API only.
- **The account's own tokens** ([decision 0003](decisions/0003-credentials-scope.md)). `GET /api/v1/tokens` lists the apps holding live tokens for the caller's account (`listConnectedApps`, shown through the dashboard's `connectedAppView` plus `current`, never a token) and `DELETE /api/v1/tokens/:clientId` revokes every token that app holds for the account and its consent (`disconnectApp`, the dashboard's "Disconnect"), keyed by the user from the token, so another account's app answers 404 like a missing one. Both accept only a bearer token for the API resource holding `credentials:manage` (`apps/app/src/api/tokens.ts`); a session cookie alone gets the 401 challenge, and the dashboard keeps its session-only `/api/v1/account/apps`. `credentials:manage` is not a product scope: the provider knows it, but only clients whose own record lists it can obtain it, which is the seeded CLI (migration 0024). `clientRegistrationAllowedScopes` and the advertised `scopes_supported` leave it out, so a registered or CIMD client can neither register for it nor request it, MCP tokens never reach `/api/v1` anyway, and there is no MCP tool. A token without it (a read-only token, or a CLI login from before the scope existed) gets 403 `insufficient_scope` naming it. Revoking the CLI's own client ends the calling token too: the CLI then deletes its stored credentials like `logout`. OAuth token rows carry no Better Auth hooks, and Better Auth has no API to revoke a user's grants by client without the token values (`/oauth2/revoke` needs the token, `/oauth2/delete-consent` a browser session), so `disconnectApp` deletes the user's access tokens, refresh tokens and consent for that client in one batch, exactly as the dashboard always has; browser sessions are still ended only through Better Auth.

### Service tokens

Premium plan T4, [decision 0011](decisions/0011-service-tokens.md): a workspace's credential for automation, for workspaces whose plan includes `serviceTokens` (Team and above). The code is in `packages/domain/src/service-tokens.ts`, `packages/services/src/service-tokens.ts`, `serviceTokenDecision` in `apps/app/src/api/access.ts`, the service token routes in `apps/app/src/api/workspaces.ts`, `packages/cli/src/session.ts` and `apps/web/src/dashboard/screens/service-tokens.tsx`.

1. **The secret.** `pfst_` and 43 base64url characters (32 random bytes), returned once by the create route and never again; only its SHA-256 is stored (`service_tokens.token_hash`, unique). Creation takes no idempotency key, so no stored replay keeps it. `.gitleaks.toml` has a rule for the prefix, so CI refuses a commit that holds one; tests build samples at run time and documents write `pfst_…`. Never log it: the API never echoes it, the CLI reads it only from `PORTIFACT_TOKEN`, never writes it to disk and never prints it, and the operator tool reads a leaked one from standard input.
2. **What it is.** A row of the workspace (foreign key, cascading), with a label, the `editor` role (never `admin`, and not `member`, whose rights need a person), scopes from `SERVICE_TOKEN_SCOPES` (`artifacts:read`, `artifacts:write`, and opt-in `artifacts:share` and `artifacts:delete`; never an annotation scope or `credentials:manage`), a required expiry of at most 366 days and an optional restriction: `own` (only artifacts whose `created_by` is the token) or `key` (only artifacts whose `external_key` starts with a prefix, and every publish must carry such a key). At most 20 per workspace, enforced by the insert's condition. It is not a member, holds no seat and receives nothing.
3. **Managing.** Only admins (role action `tokens`), only through the dashboard session (`/api/v1/workspaces/:slug/service-tokens`, bearer tokens refused with 403, exact `Origin`, `Sec-Fetch-Site: same-origin`); no MCP tool or CLI command, so no token can mint, list or revoke tokens. Creating needs the plan's feature; listing and revoking never do. Create and revoke are conditioned in SQL on the caller still being an admin (`stillAdmin`). Revoking deletes the row and writes a `service_token` tombstone in one batch.
4. **Authentication.** A bearer value with the prefix is authenticated by `authenticateServiceToken` (one indexed read with the workspace's plan) and never introspected as OAuth. Unknown, malformed, revoked or of a deleted workspace: `401 unauthenticated` with `error="invalid_token"`; expired: `401` saying when; the plan lacks `serviceTokens`: `403 plan_required`; the route's scope not granted: `403 forbidden` with `error="insufficient_scope"`. The token is read on every request, so revocation, expiry, workspace deletion and a plan change apply to the next request. The session cookie path never sees it (a `pfst_` cookie is an unknown session), `/mcp` refuses it (only MCP-audience OAuth tokens), and account endpoints, `/api/v1/tokens` and webhook management refuse it like any token without `credentials:manage`.
5. **The actor.** The token's ID stands where a user ID goes. `actorOn` gives it a role only on its own workspace, from its row, and only on artifacts its restriction reaches (callers pass the artifact, `ArtifactSubject`); it has no personal space, so another owner, its creator's personal space and an artifact outside its restriction answer exactly like a missing artifact. `resolveOwnerScope` puts it in its workspace without `?workspace=`, and a slug of another workspace answers `not_found`. `can` adds `TOKEN_ACTIONS`: comments, moderation, transfers, the access log and analytics, members, plans, policies, webhooks, branding, custom domains (role action `domains`) and tokens are refused whatever the role. `checkReadAccess` never admits a token (it is not a signed-in person), and the annotation services treat it as nobody. The age rule for making an artifact public uses the token's own creation time. Inside `access`, a token reads the readers' addresses only with `artifacts:share` (`seesReaders` in `getAccess`; the list is empty otherwise) and never changes who sees comments (`checkCommentVisibilityChange` in `updateAccess`). The CLI withholds `PORTIFACT_TOKEN` from the programs it starts (`childEnvironment`).
6. **Last used.** Written at most once an hour per token (`lastUsedDue`, guarded in SQL), so requests within the hour add no D1 write.
7. **Lifecycle.** Workspace deletion deletes its tokens (foreign key); `exportTombstones`/`applyTombstones` delete restored tokens that were revoked or belong to a tombstoned workspace; account deletion clears `created_by`; an admin's account export lists the workspace's tokens without secrets.

### Publish keys

`artifacts.external_key` (decision 0011, T5): unique per owner among artifacts that are not `purging` or `deleted` (a partial unique index), so deleting an artifact frees its key at once. A publish with a key updates the owner's artifact holding it (from its current version) or creates one with it; two concurrent first publishes meet at the index and the loser becomes an update of the winner's artifact. A key never moves an artifact and never names another owner's artifact: the lookup is in the owner the request resolved.

### Human check

Account creation, an account's first comments on other people's artifacts and repeated wrong passwords of a share link need a solved Cloudflare Turnstile challenge (plan section 13, decision 0008). Turnstile tokens are verified only on the server, with siteverify and `TURNSTILE_SECRET_KEY`, in `apps/app/src/turnstile.ts`; the page only renders the widget with the public `TURNSTILE_SITE_KEY`, which the app host puts in a `<meta>` of the login page, the dashboard and the share link entry page (`withSiteKey` in `apps/app/src/app-host.ts`). Those three pages add exactly `https://challenges.cloudflare.com` to `script-src` and `frame-src`; no other page does. How the widget looks changes nothing on the server: an invisible challenge yields the same single-use token, verified the same way.

- **Fail closed.** Without the secret, or when siteverify fails, times out, answers an error or rejects the secret, every check is `unavailable` and nothing that needs one goes through: `/api/auth/verify-human` and the comment answer `503 capacity_unavailable`, and a sign-up without a valid check cookie is refused. The Worker logs that the secret is missing or rejected, never a token or the secret. There is no test-mode bypass in production code: tests and local development use Cloudflare's documented test keys, and the app tests replace the siteverify transport (`AuthDeps.siteverify`).
- **Sign-up.** The login page renders the widget with `appearance: "interaction-only"` from the moment it shows the methods (`apps/web/src/auth/human-gate.ts`): most visitors never see it and hold a token before they choose a method. Only when Cloudflare asks for an interaction does the challenge appear, below the methods, with an explanation and an announcement; a sign-in waits for it while it is visible, waits at most `HUMAN_CHECK_WAIT_MS` (8 seconds) for an invisible one still running, and goes on without a token when the challenge failed, so an existing account is never blocked by the widget. A token is used once; the next sign-in renders a fresh challenge. The page posts the token to `POST /api/auth/verify-human` (in the auth allowlist, exact `Origin`, 30 per IP per 10 minutes) after recording the acceptance and before the sign-in method. On success the Worker sets `__Host-pf_human` (`Secure; HttpOnly; SameSite=Lax; Path=/`, 30 minutes): a random 24-byte nonce and the time, HMAC-signed with a key derived from `BETTER_AUTH_SECRET` under its own purpose. Better Auth's `user.create.before` hook (`apps/app/src/auth/human.ts`), after the terms check, requires a valid cookie and claims its nonce once in the D1 counters (`human:<nonce>`), so one solved challenge creates at most one account whatever the method (Google, GitHub or email code); `session.create.after` clears the cookie. Refusals are `APIError` `FORBIDDEN` with code `human_verification_required`: the email-code sign-in answers 403 and provider callbacks redirect to `/login?error=human_verification_required`. Existing accounts never need the cookie.
- **First comments.** `createAnnotationThread` and `replyToAnnotationThread` take a `HumanCheck` (the token the request carried, if any, and a verifier bound to siteverify and the caller's `CF-Connecting-IP`) that every adapter builds the same way: the API reads the optional `turnstileToken` of the body, MCP never has one. When the caller is a participant (never the owner) with fewer than `ANNOTATION_LIMITS.humanCheckedComments` (3) `thread_created` or `message_created` events on artifacts it does not own, a comment without a token answers `403 human_verification_required` and a failed token the same with another message. The check runs after the permission, version and limit checks, so a refused request never spends a token, and a write that loses its claim and runs its checks again reuses the first verdict instead of verifying the single-use token twice. CLI and MCP callers cannot show the challenge, so those first comments must come from the viewer; the error message says so. The thread list says whether the caller's next comment needs a check (`humanCheck` in `AnnotationPage`, never for the owner), a hint only: the write decides again. In the viewer, each composer (inline, the sidebar's and replies) with that hint runs the widget invisibly (`interaction-only`, `review/human-check.tsx` over `auth/human-gate.ts`) from the moment it opens, so the token is usually ready when the reader saves; the challenge shows inside the composer, with an announcement, only when Cloudflare asks for an interaction, and the comment is posted as soon as it is solved. When the API refuses a post anyway, the composer starts the check, gets a fresh token and retries once under a new idempotency key; a second refusal says calmly that the check did not go through, and nothing on this path is shown as an error. Events go with their artifact, so deleting artifacts can make an account need the check again. The token is not part of the idempotency hash, and a refused comment's answer is stored for its key, so the viewer retries with a new key and a fresh token.

### Access control

- The API under `app.portifact.com/api/v1` accepts bearer tokens issued for the API resource and the dashboard's session cookie, checks one scope per route (`artifacts:read`, `artifacts:write`, `artifacts:share` or `artifacts:delete`) and takes the acting user from the token or session (`apps/app/src/api/access.ts`). A bearer token always wins over a cookie. A session holds every product scope (`SESSION_SCOPES`) and is honored only with `Sec-Fetch-Site: same-origin`, failing closed without fetch metadata, and, on every mutation, the exact app `Origin`; anything else answers 403. An unknown or expired session answers 401 like a request without credentials. Another account's artifact or upload answers 404 exactly like a missing one. Prepare requires an `Idempotency-Key`; a retry with the same key and body replays the stored response, and the same key with another body is refused. Access changes (`PATCH /api/v1/artifacts/:id/access`, scope `artifacts:share`) bump `policyGeneration` in the same transaction as the reader writes; those writes are conditioned on the generation the request read and the guarded update runs last, so of two concurrent changes exactly one applies. Making an artifact `public` is refused during the account's first 15 minutes; narrowing access is always allowed, also on archived artifacts. A reader list holds at most 500 addresses.
- The account endpoints under `/api/v1/account` (`apps/app/src/api/account.ts`) list the signed-in user's browser sessions and connected apps, sign out the other sessions, disconnect an app, read and change the defaults for new artifacts (`GET`/`PATCH /api/v1/account/settings`), export the account's data and delete it. They accept only the dashboard session, with the same fetch-metadata and `Origin` checks as above; a bearer token is refused with 403 even with every product scope, because no scope covers credential management yet. Every query is keyed by the session's user, so another user's grant answers 404 like a missing one. Responses never carry session or OAuth tokens, nor IP addresses. Signing out other sessions goes through Better Auth (`revokeOtherSessions`) and never deletes `sessions` rows directly: its session hooks revoke the access tokens issued through those sessions, which a direct delete would leave active (the foreign key only sets their `session_id` to null). As after signing out, those apps recover by refreshing, so only disconnecting ends an app's access: that deletes its access and refresh tokens and the consent for that user in one batch.
- The MCP endpoint `app.portifact.com/mcp` accepts only bearer tokens issued for the MCP resource. Before the SDK sees a request, it runs the same check as the API with the scope of the tool being called (`artifacts:read` for discovery and listing tools), so a missing scope answers 403 `insufficient_scope` with that scope for step-up; each tool also declares the scope to the SDK as a second check. Tools call the same services as the API and return the same errors, the acting user comes from the token, and the raw token is not passed to the tools. Inline publishing accepts at most 256 KiB of well-formed UTF-8 and the Worker writes the bytes to R2 itself, then commits through the same verification; `delete_artifact` needs `confirm` equal to the artifact ID. The annotation tools (`apps/app/src/mcp/annotation-tools.ts`) carry the annotation scope of their API route, call the same services and validate with the same contracts; `create_annotation` and `reply_annotation` require an `idempotencyKey` like the routes' `Idempotency-Key`, `delete_thread` needs `confirm` equal to the thread ID and `moderate_annotation` with `delete` needs `confirm` equal to the message ID. Their descriptions and the server instructions tell agents that bodies, quotes and author names are untrusted data. Request bodies above 1 MiB are refused with 413.
- Annotations live under `/api/v1/artifacts/:id/annotations` (`apps/app/src/api/annotations.ts`) with `annotations:read` for listing, reading and export, `annotations:write` for starting threads, replying, editing, deleting one's own messages and resolving, and `annotations:moderate` for the mode (`PUT .../annotations/mode`), hiding, unhiding and deleting other people's messages and deleting threads. The rules are in `packages/domain/src/annotations.ts`: only the owner and accounts the access policy admits take part, an account without access gets 404 like a missing artifact, visitors lose the threads when the artifact is archived or suspended and see only the current version's threads (older ones are the owner's history), `locked` lets visitors read and delete their own messages only, and the owner hides or deletes but never edits other people's words. The author always comes from the token or session; request bodies are strict, so an `authorId` field is refused. Every write in `packages/services/src/annotations.ts` claims its change with an `annotation_events` row inserted under the same checks evaluated inside the batch (artifact state and mode, current version, the visitor's policy generation, the author and artifact rate limits and the row's previous state), and the rest of the batch runs only if that row, found by a per-request `write_id`, exists; so a revocation, a new version, a lock or a concurrent edit that lands first wins, and a retry cannot apply effects twice. Starting a thread or replying needs an `Idempotency-Key`; edits carry the message `revision`. The owner's 5,000 messages and 50 MB (the defaults of `annotation_usage.messages_limit` and `bytes_limit`), and the 200 messages per thread, are CHECK constraints kept by the triggers in `0007_annotation_usage_triggers.sql` (recreated by 0027). Bodies are plain text, at most 4,000 code points and 8 KiB, with control characters refused, and requests that create content are capped at 16 KiB. Annotation bodies, quotes and author names are untrusted data: clients render them escaped, exports start with a notice saying so, the Markdown export puts bodies and quotes in fences longer than any backtick run they hold and is served as an attachment with `nosniff`, and responses show other people's names and avatars, never their email.
- Every request to `portifact.dev` follows this order: rate limit, resolve artifact, check state and dates, authenticate, authorize the version, check traffic quota, resolve the path, and only then read bytes from cache or R2.
- The traffic quota (`TRAFFIC_LIMITS`: 1 million requests and 25 GB per account per UTC calendar month) is checked after authorization, so a visitor who cannot open an artifact never learns whether its owner is over quota, and anonymous refusals charge the owner nothing. Over quota, every artifact of that account answers 429 with `Portifact-Error: traffic_exceeded` and `Retry-After` until the next month, in every access mode and in review mode; other accounts are unaffected. The counter (`traffic_counters`) is read in the same lookup as the artifact, and the content Worker adds what it served in memory per isolate and writes it once per 5-second window through `waitUntil` (`apps/content/src/traffic.ts`), so delivery does no D1 write per request. The quota can therefore be overshot by what isolates serve within one window, and a write lost with an evicted isolate is not counted; both are accepted, since per-IP rate limiting in front of the Worker is the abuse control and the quota is a cost cap.
- While budget protection tightens traffic, a per-IP limit also applies after the traffic quota check and before any bytes are read, so a refused request charges no traffic (`apps/content/src/budget.ts`); it is counted exactly per IP by the `TrafficLimiter` Durable Object, answers `429` with `Retry-After` until the visitor's window ends and fails open, logging the failure.
- Every file is authorized, including CSS, JS, images, source maps and downloads.
- Cached bytes are looked up only after authorization and are keyed by artifact, version and path. No identity or access decision is cached in a shared cache.
- The acting user always comes from the session or token, never from input, and their role on an owner always comes from `resolveActor` in the services, never from input or an adapter. An opaque ID never replaces an authorization check.
- Token scopes allow a class of action; ownership or permission on the specific artifact is always checked as well.
- R2 has no public bucket, no `r2.dev` and no custom public domain. Presigned upload URLs are bound to one object key, size, checksum and a short expiry. The `portifact-app` Worker signs them (`apps/app/src/api/presign.ts`) with an R2 token limited to that bucket: `content-length`, `host` and `x-amz-checksum-sha256` are signed headers, the key is `objects/<owner>/<sha256>`, and they expire after 15 minutes. Commit still verifies every pending object's size and SHA-256 in R2 before the version becomes current, so a client that skips the URL cannot publish other bytes. Only verified objects count as already stored; an object another open upload declared but never sent gets a new upload URL.
- Objects over 64 MiB, for a client that sends `multipart: true` at prepare, are uploaded with presigned multipart (`packages/services/src/multipart.ts`). The Worker opens the R2 multipart upload through the binding and signs one S3 UploadPart URL per part (`presignPart`), each binding the key, upload ID, part number, `content-length` and 15 minutes; parts are 16 MiB except the last. A part's SHA-256 is not signed because the server only knows the whole file's hash, so per-part integrity relies on the signed size and on the commit's rehash. The parts go to a staging key of the session (`uploads/<owner>/<session>/<sha256>`), never to the object's shared key: R2 does not check a whole-object checksum when it assembles parts, and assembling straight into `objects/<owner>/<sha256>` could overwrite bytes another publish already verified. The client reports each part's ETag (`POST /api/v1/publishes/:id/parts`, owner and open session only); the commit completes the upload with the reported ETags, streams the staged object through `crypto.DigestStream` (never buffered), refuses a wrong size or hash with `upload_incomplete` (opening a fresh upload for that object so the client can send it again), and only then copies it to the object's key with `sha256` set, so R2 checks it once more, and deletes the staging copy. A closed session (commit, abort, failure or expiry) writes an `abort_multipart` outbox job in the same batch, which aborts what was not completed and deletes the staging copies and rows; R2's default seven-day abort of incomplete uploads is the safety net for a prepare that failed before its batch. A client without the flag gets one PUT per object, as before.
- Downloads (`GET /api/v1/artifacts/:id/versions/:versionId/download`, MCP `get_download`) return presigned GET links signed by the same Worker and token (`presignGet` in `apps/app/src/api/presign.ts`): one object key each, `response-content-disposition=attachment`, valid 5 minutes, issued only after `getVersionDownload` in `packages/services/src/versions.ts` checked the caller. The owner may download published files and sources of any retained version. Anyone else gets only the published files of the current version of a `markdown` or `text` artifact that `checkReadAccess` admits right now; sources, previous versions and sites answer 404 exactly like a missing version. Version lists and manifests are owner-only. A link handed out before a revocation stays usable until it expires, so its lifetime is kept short.
- Manifests refuse any `.git` path segment, in any case and in the forms Windows resolves to it (`.git.`, `.git `, `git~1`; `isGitSegment` in `packages/domain/src/paths.ts`). `portifact pull` writes only into a folder it creates (refusing one that exists or lies inside a `.git` folder), validates every path again with the same rules before writing anything, refuses non-canonical paths and paths that leave the folder, writes with `wx`, checks each file's size and SHA-256, never sends the API token to storage, and removes the folder if the pull fails. `pull --source --git` (`packages/cli/src/history.ts`) also accepts a folder an earlier `--git` pull made, but only when it is a real directory (not a link) whose own `.git` folder is a directory (not a linked work tree), marked with the same artifact in `portifact.artifact`, on `main`, with Portifact's last commit and tag and no uncommitted changes. It writes objects only with git plumbing that runs no hooks and no filters (`hash-object --no-filters`, `update-index` on a separate index file, `commit-tree --no-gpg-sign`) and checks that git kept every path, updates the files with `read-tree -u -m`, which refuses to overwrite local changes or write through a link in the way, and moves the branch and creates the tags in one `update-ref --stdin` transaction, putting the files back if it fails.
- A rollback (`POST /api/v1/artifacts/:id/rollback`, MCP `rollback_artifact`) publishes a new version that references the retained version's objects. It changes only the current version and the expiry, never the access mode, readers or policy generation, so it cannot bring back access that was removed. It takes an `Idempotency-Key` (optional `idempotencyKey` on MCP) and the base version the client read.

- Pinning (`POST /api/v1/artifacts/:id/pin` and `/unpin`, MCP `pin_artifact` and `unpin_artifact`, scope `artifacts:write`, premium plan P2) is a lifecycle action: an admin or editor of the owner (`authorizeOn` with `lifecycle`), a member `forbidden`, anyone else the missing-artifact answer. Pinning is refused with `plan_required` unless the plan of the artifact's owner (the workspace's for a workspace, never the caller's) includes `pin`, checked after authorization; unpinning needs no plan, so an owner can always shorten what stays online. Both are guarded on the state and lifecycle generation read and are idempotent. A pinned artifact has no `expires_at`, so every check that serves or archives by expiry (`effectiveState`, the archive scan, the notices, delivery) treats it as active with no extra rule; it changes nothing about who can open it, and suspension still takes it offline.

### Owners, workspaces and roles

Premium plan F3, [decision 0004](decisions/0004-workspace-model.md) and [decision 0005](decisions/0005-regions.md). An artifact's owner is a user's personal space (the owner ID is the user ID) or a workspace (`ws_` and 32 hex characters, `WorkspaceId` in contracts, a prefix no user or artifact ID can have). A user acts on an owner with a role. Only the operator creates and deletes workspaces (no self-service while there is no billing: each workspace has its own quotas, so free self-service workspaces would multiply the free quota).

- **One place decides a role.** `resolveActor` and `actorOn` in `packages/services/src/actors.ts` read the role from `workspace_members` (one indexed read, joined with the workspace's region), or make the user the `admin` of their own personal space without a read. Adapters never decide a role and never build an `Actor`: owner-scoped services (`listArtifacts`, `getAccountUsage`) take the actor the adapter got from `resolveActor`, and services that name an artifact or an upload take the `userId` and resolve the actor on its owner themselves (`authorizeOn`). Better Auth never sees workspaces or memberships.
- **What a role allows.** `can` in `packages/domain/src/actor.ts`, over `ROLE_ACTIONS` in contracts: `admin` everything, including members, the plan, policies and deleting the workspace; `editor` publishes and manages artifacts (publish, update, access, lifecycle, versions, rollback, annotation moderation, the access log, the owner's usage); `member` reads and comments on what is shared with the workspace and manages nothing. `authorize` answers a user without a role `not_found` and a role that does not allow the action `403 forbidden` ("Your role on this workspace does not allow this.").
- **Non-members cannot tell.** A user with no role on an artifact's owner gets exactly what a missing artifact (or upload) gives: same status, code and body, in the API and in MCP (`apps/app/test/workspace-parity.test.ts`). Members know the workspace's artifacts exist and get `forbidden`; the annotation services answer everyone who cannot read an artifact, members included, like a missing one, as before.
- **"The owner" in older rules** means everyone who acts for the owner, an admin or editor (`actsForOwner`): they read every artifact of the owner whatever its access mode (`canRead` takes the actor), see every comment, count as "the owner" in the `own` comment scope (`ownerSide`, so readers see their threads, and `byOwner` marks them), are `owner` in the viewer, are not recorded in the access log and read it. External readers listed by email are not members and keep reading through the list; a member who is not on the list does not read a `restricted` artifact, only `workspace` and `domain` ones (see "Workspace and email domain access").
- **The owner's numbers.** Quotas, storage, objects, traffic, annotation usage and the plan stay keyed by `owner_id`, so they are the workspace's when it owns the artifact, and a Team plan's seats multiply its per-seat limits. The account's age for making something public and a suspension are the acting user's. Personal defaults for new artifacts apply only in the personal space; a new workspace artifact starts from the built-in defaults. Expiry notices of a workspace go to each of its admins, each with their own opt-out; a send that fails after one admin got it is dropped instead of retried, so nobody gets it twice.
- **Naming the owner.** Owner-scoped routes take `?workspace=<slug>` (`GET /api/v1/artifacts`, `GET /api/v1/usage`, `POST /api/v1/publishes` for a new artifact), and MCP's `list_artifacts`, `get_usage`, `publish_document` and `prepare_upload` take `workspace`; without it they act on the personal space. The slug only names the owner: `resolveOwnerScope` resolves the role, and a slug the user is not a member of answers 404 `not_found` "Workspace not found." exactly like one that does not exist, while a member who may not do the action gets `forbidden`. Routes that name an artifact or an upload take no workspace: the artifact's owner decides, so an update never moves an artifact. Every artifact view carries `owner` (`personal`, or the workspace's slug and name) so a user always sees where an artifact lives. The slug `personal` is reserved, because the CLI uses it for the personal space.
- **Members and invitations.** `GET /api/v1/workspaces` (and MCP `list_workspaces`, `portifact workspaces`) takes `artifacts:read` and lists only the caller's own workspaces and role, naming nobody else. The member list (`GET /api/v1/workspaces/:slug/members`, every member's name and email), changing a role, removing a member, leaving, the invitations of a workspace and accepting or declining an invitation answer only the dashboard's session (bearer tokens get 403, like the account endpoints), and the session must be of an account on the current terms: they are account-level data and actions, and a membership widens who reads and manages an owner's artifacts, so no OAuth scope, MCP tool or CLI command reaches them ([decision 0003](decisions/0003-credentials-scope.md) keeps account-level actions out of scopes). Only admins manage members and invitations, and every member or invitation write is conditioned inside its batch on the caller still being an admin of that workspace (`stillAdmin`), so an admin demoted or removed after the read changes nothing and gets `forbidden`. The last admin can never be demoted, removed or leave: the services refuse it and the triggers in the `workspace_members_invitations` migration refuse whatever a race slips past (`sole_workspace_admin`); the conditions name the role the request read, so of two concurrent demotions of two admins exactly one succeeds.
- **Invitations.** An admin invites an email address with a role; the invitation lasts 7 days, one per workspace and address, and the link carries a 32-byte random token of which only the SHA-256 is stored. The link is `app.portifact.com/invitations#token=…`: the token is in the fragment, which browsers never send, so it is in no request line, log or `Referer`, and the dashboard takes it out of the address bar before the router starts and keeps it only in that tab's `sessionStorage` (never in the login page's `next`; signed out, the page sends the person to `/login?next=/invitations`). `POST /api/v1/invitations/lookup` (session only, the token in the body) tells the signed-in account what the link names: the invitation when the account's verified email is the invited address, and otherwise only the invited address, so the person can switch accounts; the workspace, the role and the inviter stay hidden, and a missing, expired, revoked or used invitation is `not_found`. Whoever holds the link already received it at that address. A new invitation to the same address replaces the pending one in the same upsert, so a refused one keeps the earlier. The token only locates the invitation: accepting or declining needs a signed-in account whose verified email is the invited address, and anything else (another account, an unverified email, an expired, revoked or used invitation) answers `not_found` like a missing one. An invitation never creates an account, so signing up still needs the terms and the human check. The email stops with the same monthly capacity as expiry notices, is counted with `recordEmailsSent`, is rate limited per workspace (50 a day), per admin (20 an hour) and per recipient (5 a day across workspaces, keyed by a SHA-256 of the address, never the address), and is written in the inviter's account language. A suppressed address (or one the provider refuses) gets exactly the same answer as any other, so admins cannot probe suppression: the invitation is stored, nothing is sent (a log line records only that, with the reason) and it expires unanswered. Another failed send withdraws the invitation. Seats: members plus pending invitations that have not expired count against the plan's `seats`; an invitation is refused without a free seat, and accepting takes a seat only while `count(members) < seats` holds inside its batch, so of two concurrent accepts for the last seat exactly one succeeds. Both writes are also conditioned on the plan row being the one the seat limit was read from, so a plan lowered, removed or replaced meanwhile makes them a no-op and the answer is computed again. A plan that expired reads as `free` with one seat: nobody is removed, nobody is added.
- **Transfers.** `POST /api/v1/artifacts/:id/transfer` (`artifacts:write`), MCP `transfer_artifact` and `portifact transfer` move an artifact between the caller's personal space and a workspace or between two workspaces. Moving it into a space needs the `transfer` action there (admin or editor); moving it out of a workspace needs `transfer_out` (admin only), so an editor cannot take a workspace's content into their own space and keep it after being removed; in a personal space the user is its admin. The target's plan must take it the way a publish there would: a free active slot when it is active, storage for the objects it lacks and the per-artifact size of the current version. One batch, conditioned on the artifact still being where, as and at the lifecycle generation the request read it, and on no open upload to it, moves the manifests and the comments and writes the `access_history_move` job, and moves the artifact row last; triggers in the `workspace_members_invitations` migration move the active slot and the annotation usage, and the target's CHECK constraints repeat the room check against races. The move bumps both the lifecycle and the policy generation, which ends read, review and share link sessions (the readers' policy now belongs to another owner) and makes any write authorized on the old owner a no-op. Every write that authorizes on an artifact's owner and writes in a later batch also conditions that batch on the `owner_id` it read: the lifecycle guard (renew, archive, restore, delete, pin, unpin), the access update (mode, readers, the bar, comment visibility), share link creation and revocation, the annotation mode and every annotation write's artifact guard; publish and rollback already switch on the owner. Objects are deduplicated per owner: the target gets its own object row for each object it lacks, pointing at the same R2 key (no bytes are copied, the bytes count in the target's storage), and the source's rows nothing references any more are released after the batch. A key is deleted only once no row of any owner has it (`releaseOrphans` and the `delete_objects` job both check), renderings of a document the target already holds go to the key its row has (`storeRenderings`), and downloads read the row's `r2_key`. Readers, comments, versions, the URL and the ID do not change; past traffic stays with the source. An artifact with a custom domain or a pending claim does not move (`invalid_input`; the same condition holds in the batch): a domain belongs to its owner's quota and verification, so the user removes it first. Pins and share links stay as they are and follow the existing lapse rules of the target's plan (a plan without pins or links lapses them as it would for any artifact of that owner). Moving across regions is refused.
- **The access history follows the artifact.** The transfer's `access_history_move` outbox job (`moveAccessHistory`) gives the artifact's access log openings and analytics view counters, in the access database, to the owner it has now and sets their expiry from that owner's plan, like `owner_retention`; it always converges on the current owner, so a repeated or stale job changes nothing, and a purged artifact has nothing left to move (`erase_access_events` handles that). Until the job runs, within minutes, the target's admins and editors see an empty log for the artifact. The transfer's confirmation (CLI output and help, the MCP tool's description and result, the dashboard later) says that the people who manage the target will see who opened it before the move.
- **Deleting a workspace** (operator only) follows account deletion: one batch records the deletion (`workspace_deletions`) with a `workspace_deletion` outbox job, claims every artifact for purging and deletes the workspace row, which takes memberships and invitations with it; the job (and the maintenance scan) finishes once the artifacts are purged, releasing objects and deleting the counters, the plan row and the upload sessions, and leaves a `workspace` tombstone; its custom domains and claims are released first, as an account's are (`releaseOwnerDomains`). `exportTombstones` and `applyTombstones` cover it around a restore.
- **Regions and the directory.** Every Worker builds `Regions` with `regionsFromEnv` (`packages/db/src/regions.ts`); `GlobalDb` and `RegionalDb` are distinct brands over Drizzle, and a `RegionalDb` carries its deployment's `global`. With one region both wrap `DB`. A new artifact's ID is claimed in `artifact_directory` (global, never updated or deleted, refusing tombstoned IDs) before `preparePublish`'s regional batch; a lost claim draws again and gives up with `version_conflict` after five draws. A workspace's region never changes (a trigger refuses it).

### Workspace and email domain access

Premium plan T2, [decision 0010](decisions/0010-workspace-access-modes.md): two access modes for artifacts a workspace owns, `workspace` (every member, any role) and `domain` (every member, plus any signed-in account whose verified email is at one of the workspace's verified email domains). The code is in `packages/domain/src/access.ts` (`canRead`), `packages/domain/src/email-domains.ts`, `packages/services/src/workspace-domains.ts`, `packages/services/src/access.ts`, the domain routes in `apps/app/src/api/workspaces.ts` and `apps/web/src/dashboard/screens/email-domains.tsx`.

1. **Who reads.** `canRead` decides it from the policy, the session's viewer and the actor `actorOn` resolved: admins and editors as always, members in both modes, and in `domain`, while the owner's plan includes `workspaces`, a verified address whose domain (the A-label after the last `@`, normalized like a workspace domain) is one of the owner's verified domains, matched exactly (no subdomain). The reader list grants only in `restricted`. A lapsed plan leaves `domain` readable by members only, never wider, and the access view says so (`audience.featureAvailable`). On a personal owner both modes read like `restricted` without readers. The email is `users.email` with `emailVerified`, as for the reader list, never request input; the provider-vouched case is an open risk of the decision.
2. **Setting a mode.** `updateAccess` refuses, after authorization, a personal artifact (`invalid_input`), an owner without `workspaces` (`plan_required`, the owner's plan) and `domain` without a verified domain (`invalid_input`); keeping or narrowing a mode never needs the plan. Editors and admins may set either mode (role action `access`); only admins decide which domains count. A change bumps `policyGeneration`. The MCP tool and the skill tell agents to ask the user first.
3. **No delivery read.** Delivery keeps its one lookup; membership and domains are read only where `canRead` already runs (`checkReadAccess` for the read handoff, the 60-second renewal of read and review claims, the viewer lookup, review codes and downloads, and the annotation services' `roleOf`), and in `domain` mode one indexed global read asks whether the viewer's exact domain is verified by the owner. Removing a member, removing or losing a domain, a changed or unverified email and a lapsed plan therefore end reading within the 60 seconds of any revocation, without moving the generation.
4. **Domain proofs.** A claim (`workspace_domains`, global) gets a fresh 128-bit token; the TXT record `_portifact-email.<domain>` must hold `portifact-email-verify=<token>`, read through `TxtLookup` (DNS over HTTPS, injected; tests and the e2e stack use `FakeDomains`, never a real resolver). The name differs from custom domains' `_portifact.<host>`. An old record proves nothing for a new claim, so a domain released by one workspace is not claimable by another through a lingering record. One workspace holds a domain verified at a time (a partial unique index backs the batch's conditions); a claimant takes it over only when the holder's token is gone from the same DNS answer, deleting the holder's row with a tombstone in the verifying batch. Writes are conditioned on `stillAdmin`. Adding answers the same whether or not another workspace holds the name, so it reveals nothing; only someone who just proved DNS control learns another workspace still proves it.
5. **The denylist.** `checkEmailDomainAllowed` refuses Portifact's domains and the deployment's own hosts, reserved suffixes, the consumer mail domains of `CONSUMER_MAIL_DOMAINS` (exactly and as a parent), any public suffix and anything under a private-section suffix of the Public Suffix List (`tldts`, injected from the services). It is a denylist and incomplete by nature: the TXT proof is the boundary. Normalization goes through the WHATWG URL host parser (UTS 46), so case and Unicode forms are one domain; a look-alike is a different domain that only its own DNS operator can prove, and it grants only its own addresses.
6. **Re-checks and removal.** Daily, 3 missed checks in a row remove a domain (a resolver failure is not a miss); removals by admins and by the scan write a `workspace_domain` tombstone, and `applyTombstones` deletes the rows they name, so a restore cannot bring a domain back. Domains go with their workspace.
7. **Session only, admins only.** `GET`/`POST /api/v1/workspaces/:slug/domains`, `POST .../:id/verify` and `DELETE .../:id` answer only the dashboard session (bearer tokens get 403), with the members routes' checks; members get `forbidden`, anyone else `Workspace not found.` There is no MCP tool or CLI command.
8. **What follows.** Openings in these modes are never recorded in the access log (`isLoggedOpening` stays `restricted` only; a third party can send a signed-in member or company account there without a click) and analytics' distinct visitors are `null`; share link openings are recorded for the link. Members and domain readers are participants for comments: their scope follows `commentVisibility`, and reader exceptions keep applying by verified address. A transfer resets both modes to `restricted` in its batch. The account export lists a workspace's domains only to its admins, never the token.

### Comment visibility

Who sees which threads (plan section 8, decision of 2026-11-08 on comment visibility) is part of the access policy and is decided only by `commentScope` and `threadInScope` in `packages/domain/src/annotations.ts`, applied in `packages/services/src/annotations.ts`.

- **The setting.** `artifacts.comment_visibility` is `owner` (the default, also for artifacts that existed before) or `everyone`. With `owner`, a reader's scope is `own`: the threads they started and the threads the owner started, each with every reply in it, whoever wrote the reply. With `everyone`, the scope is `all`. The owner's scope is always `all`. In a workspace, "the owner" is every admin and editor: they see all, and their threads count as the owner's. It changes through `PATCH /api/v1/artifacts/:id/access` (`commentVisibility`), MCP `set_comment_visibility` and `portifact access comments` (`artifacts:share`), and does not move the policy generation: it never changes who can open the artifact, and every annotation request reads it again.
- **Exceptions.** `artifact_readers.comment_visibility` is null (inherit), `all` or `own`, set with `readerCommentVisibility` (`inherit` clears it), `portifact access reader-comments` or the menu beside each person in the dashboard's reader list, only for addresses already on the list (`invalid_input` otherwise; an addition and its exception can go in one change). It applies to the account whose verified email is that address, in every access mode: for `restricted` artifacts the list is also who may open it; for `authenticated` and `public` artifacts the list still exists (it is kept when the mode changes) and only serves the exceptions, and every other account follows the artifact's setting. An unverified address never matches. Removing a reader removes the exception; adding them again inherits.
- **Hidden means missing.** Listing, reading by ID, export and refresh never return a thread outside the caller's scope, and a thread or message ID outside it answers `not_found` with the same message as one that does not exist, for reads and for every write on it (reply, resolve, and editing or deleting someone else's message). A reader therefore cannot reply in a thread they cannot see. A write that names a thread re-checks the scope inside its claimed batch (`scopeGuard`, the same rule on the live rows), so narrowing the visibility or dropping an exception wins over a reply in flight. The rate limits and quotas stay shared on purpose (`artifactWritesPer24h` and `threadsPerArtifact` per artifact, the owner's message and byte totals), so a reader who sees no thread can still get `rate_limited` or `quota_exceeded` because of activity they cannot see: an accepted, coarse signal that hidden comments exist, which reveals none of their content, authors or number.
- **One's own words.** The author of a message can always edit and delete it, also in a thread they no longer see (they replied while the scope was wider, then the owner narrowed it): `findOwnMessage` finds it whatever the thread's scope (the version rules still apply), the batch is guarded on authorship and the current version instead of the scope, and the answer is `{ threadId, thread: null }` instead of the thread (`AnnotationEditResult` for edits, `AnnotationDeleteResult` for deletions), so nothing else of the thread is shown. Someone else's message in such a thread still answers as missing. The account export (`exportAccount`) lists those threads under `commentsElsewhere` with only the account's own messages, the target and the path: no `state` and no `createdAt`.
- **Refresh cursors.** With the `own` scope, list pages, `removed` (deleted threads, found by the `thread_created` event that outlives them, through the covering index `annotation_events_artifact_kind_actor_idx`, since this is the default path the viewer polls) and the cursor's upper bound only consider events of threads in scope, so another reader's activity never shows up as a removal or moves the cursor. `AnnotationPage.commentScope` tells the client which scope it holds; when it differs, the client starts again without a cursor, as for a change of mode or current version (`review/use-threads.ts`).
- **Widening is retroactive.** Showing more (the artifact to `everyone`, or one reader to `all`) shows the comments already written, not only new ones, so the dashboard asks the owner to confirm it; narrowing needs no confirmation. Threads the owner started are seen by every reader who reads the comments, so `AnnotationThreadView.byOwner` marks them and the viewer's reply box says that a reply there is seen by all of them.
- **What follows.** Exports give the owner every thread and anyone else what they can see. Counts and markers in the viewer come from the threads the API returned. The artifact list's `activity` (open threads) is the owner's own view. The access log is unaffected. The account export holds the account's own messages wherever they are, with nothing else from threads it cannot see but their target.

### Comment notices

Email digests of new comment activity (premium plan P5; operations in [operations.md](operations.md), "Comment notices") follow these rules:

- Only on artifacts whose owner's plan includes `commentNotices`, decided from the owner's entitlements loaded with the artifact (`load` in `packages/services/src/annotations.ts` joins `owner_plans`), so the write path reads nothing more and a free owner's writes mark nothing.
- The digest holds counts per artifact, the artifact's name and links to the viewer, the settings and the unsubscribe page. Never comment bodies, quotes, targets or authors, in the email, the outbox payload, `comment_notices` or the logs. The template can leave names out (`names: false`) for a future EU workspace ([decision 0005](decisions/0005-regions.md)).
- Visibility is decided when the notice is sent, by the same rules as every read path (`noticeView` in `annotations.ts`: the role, the artifact's state and comment mode, `commentScope` and the version a visitor sees). A reader who lost access, or whose scope no longer includes a thread, hears nothing about it. Never reimplement this check elsewhere.
- Nobody is notified of their own writes; a mute (`comment_notice_mutes`) is personal and also stops marking new activity for that person.
- The unsubscribe link carries an HMAC-SHA256 token (`signUnsubscribeToken`, key derived from `UNSUBSCRIBE_SECRET`) with the user ID and when it was issued. It only turns `account_settings.comment_notices` off. It expires after 60 days, and once the person turns the notices back on, tokens issued before that change (`comment_notices_changed_at`) are refused, so an old link cannot undo a later choice. `POST /api/v1/notices/unsubscribe` takes it from the query (RFC 8058 one-click, a cross-site form post that carries nothing else) or from the unsubscribe page's JSON; there is no `GET` handler, and the page posts only after a click, so link scanners change nothing. It is limited per IP (`UNSUBSCRIBE_LIMIT`), needs no session and answers the same for an account that no longer exists.
- The per-artifact mute and the setting are session-only account endpoints (`/api/v1/account/comment-notices/:id`, `/api/v1/account/settings`) with no MCP tool or CLI command; the mute answers like a missing artifact to anyone who cannot read the artifact's comments.

### Webhooks

Owners on a plan with `webhooks` send events about their artifacts to HTTPS URLs they choose ([decision 0009](decisions/0009-webhooks.md), premium plan P6; operations in [operations.md](operations.md), "Webhooks"). Portifact makes requests to user-chosen URLs only here, and only from the jobs Worker.

- **Switched off until verified.** Nothing is delivered and nothing can be created unless the Workers have `WEBHOOKS_ENABLED="true"` and `WEBHOOK_KEY`; the deployed configuration does not set the variable until the release checks in [releasing.md](releasing.md) ("Webhooks") pass. Without it the jobs Worker also disables every enabled webhook (`unavailable`), so writes record no events.
- **Who.** Only admins of the owner (role action `webhooks`); editors and members get `forbidden`, anyone else's webhook ID answers like a missing one. Managing (create, change, enable, disable, test, remove) takes the dashboard session or the Portifact CLI's `credentials:manage` token, never another OAuth client, because a webhook outlives the app that made it ([decision 0003](decisions/0003-credentials-scope.md), addendum); MCP only reads. Listing and the delivery log take `artifacts:read` and show hosts, never URLs or secrets. Each webhook records where it was created. Creating, enabling and testing need the feature; listing, the log, disabling and removing never do.
- **Where to.** `checkWebhookUrl` (`packages/domain/src/webhooks.ts`) runs at creation and before every attempt: `https:` only, port 443, no userinfo or fragment, a DNS name (never an IP literal in any notation, IPv6 or a trailing dot) that is not a reserved or internal suffix, not Portifact's hosts and not a Cloudflare-owned domain in `CLOUDFLARE_HOSTS` (`packages/domain/src/cloudflare-hosts.ts`, a denylist from Cloudflare's documentation, incomplete by nature); Slack and Discord formats only to those services. A public name can still resolve to a private address, and same-account reach is undocumented: that is what the release checks are for. The jobs Worker has `global_fetch_strictly_public`, which is documented only for the Worker's own zone. Deliveries use `redirect: "manual"` (a 3xx is a failure), a 5-second timeout, read at most 4 KiB of the response, and run alongside the batch's other jobs so a slow receiver delays nothing else.
- **Bounds.** A per-owner, per-UTC-day attempt counter (1,000) that removing webhooks never resets; per-owner limits on creates, tests and enables; an hour's cooldown after an automatic disable, 3 re-enables per webhook a day and a probation of 3 failures until a success. A retry is never sent before its backoff, whatever delivers the message.
- **What.** IDs, the artifact's name and links, the event type, times, counts, the version number, the access mode and the name of who acted only when that person acts for the owner and did everything counted. Never comment text, quotes, targets, thread IDs, reader or author emails or reader names, in the body, `webhook_events`, the outbox payload or the logs. A webhook never receives more than an admin could read through the API.
- **Secrets.** The URL (a Slack or Discord URL is a credential) and the signing secret are sealed with AES-256-GCM under a key derived from `WEBHOOK_KEY`, bound to the webhook and column; only the host is kept in clear and shown. The secret is returned once and the create takes no idempotency key. Generic deliveries are signed the Standard Webhooks way (`webhook-id`, `webhook-timestamp`, `webhook-signature`).
- **Writes are never blocked.** A write records its event in its own batch (`markWebhookEvent`), with no extra round trip, only when the owner's entitlements (already loaded) include the feature; budget protection, the daily cap and failures act only on the delivery job.
- **Logs.** Never a webhook's URL path or query, a secret or a payload: the jobs Worker logs only the job's ID, topic and outcome, and the delivery log keeps the outcome, status or error kind, never a body.

### Access logs

The owner of an artifact sees who opened it (plan sections 11 and 13): the verified email of each signed-in visitor and when, one entry per visitor, artifact and 30-minute window, kept for the owner plan's `accessLogRetentionDays`: 30 days on free, a year on paid plans (`ACCESS_LOG` and `PLANS` in `packages/contracts`, the rules in `packages/domain/src/access-log.ts` and `retentionExpiry` in `packages/domain/src/analytics.ts`). The code is in `apps/content/src/access-log.ts`, `packages/services/src/access-log.ts` and `apps/app/src/api/access-log.ts`.

- **What is recorded.** Only a page load (`GET` with `Sec-Fetch-Mode: navigate`, top-level or in a frame) of a `restricted` artifact (its readers are the addresses the owner listed), which the content Worker answered below 400 (the viewer redirect included) after authorizing it with a read session or a review session (the viewer's frame or a review tab), by a visitor who does not act for the owner (the user of a personal space, or a workspace's admins and editors, dropped by `recordOpenings`). Visits of public, `authenticated`, `workspace` and `domain` artifacts are never recorded (`isLoggedOpening`): any site can send a signed-in visitor top-level to such an artifact, where the viewer opens a review session or the read handoff completes without a click, so recording them would hand the owner the email of whoever was sent there. The visitor is the `uid` of the session's signed claims, never request input. A frame that a sibling artifact opens (`Sec-Fetch-Site: same-site` with a `Sec-Fetch-Dest` other than `document`) is not an opening either: artifacts share one site, so the Lax read cookie goes along and the page is served, but `frame-ancestors` keeps it from rendering, and logging it would let a hostile artifact plant openings the visitor never saw. Subresources, the owner's own visits, refusals, sign-in steps and every request served without a session (public artifacts outside review mode) are not recorded, so anonymous visitors are never identified. On a `restricted` artifact a session counts because only listed readers get one; the redirect, the viewer's frame and its first page fall in the same window.
- **No write per request.** Each isolate keeps the openings it serves in memory, skips what it already wrote for the window, and writes once per 5-second batch after the response through `waitUntil`, like the traffic meter. A failed write keeps the batch for the next one; an evicted isolate loses what it had not written. The log therefore says it is not a complete audit (API description, CLI note, dashboard hint, skill). The email is never in the cookie or on `portifact.dev`: the batch reads it, and the artifact's owner and state, from the control database when it is written, and drops openings of artifacts that are no longer `active` or by accounts that no longer exist, so a batch held across a purge or an account deletion writes nothing for them.
- **Separate database.** The rows live in the `portifact-access` D1 database (`ACCESS_DB`, schema `packages/db/src/access-schema.ts`), keyed by artifact, window and visitor, so concurrent batches from several isolates keep one row (with the earliest time). No D1 batch spans both databases, so nothing in the access log is written in the same transaction as a control-database change; erasure goes through the outbox (below).
- **Owner only** (an admin or editor of a workspace owner). `GET /api/v1/artifacts/:id/access-log` (scope `artifacts:read`, through `guarded`, so the dashboard session works with its usual checks), the MCP tool `get_access_logs` and `portifact logs` call `getAccessLog`, which answers 404 `not_found` exactly like a missing artifact to anyone but the owner, including the artifact's readers, and for artifacts being purged; archived and suspended artifacts keep their log for the owner. The query is also keyed by the owner stored with each row. Entries past the owner's current retention or their own `expires_at` are never returned, even before the prune reaches them.
- **Retention and erasure.** Each row carries `expires_at`, set when it is written from the owner's plan (capped at the plan's `valid_until` so a plan that runs out keeps nothing longer than the free plan would from then on; rows from before migration 0001 of the access database have it backfilled to 30 days). Share-link openings carry it too. A plan grant or removal writes an `owner_retention` job in its batch, which moves the expiry of every row of the owner, views included, to the new plan: a lower plan shortens them and the next prune deletes what it no longer keeps, a higher plan extends the rows still there. The jobs Worker prunes rows past their expiry on every run, in bounded statements. Purging an artifact (`deleteArtifactData`, whatever started it) writes an `erase_access_events` job for it in the batch that deletes the artifact; deleting an account writes one for the account's own openings with the request and again when the deletion finishes (so re-applied tombstones and openings recorded meanwhile are covered too). The jobs Worker runs them against `ACCESS_DB`; each deletes in bounded statements and asks to run again when there is more.
- Openings through a share link are recorded for the link, never a person, on `authenticated` and `restricted` artifacts (see "Share links", item 8).
- Emails in the access log are personal data of the visitors: they are never logged, the MCP tool and the skill tell agents to show them only to the user, and the Privacy Policy describes them ([legal.md](legal.md)).

### Audit log

An owner's admins see who changed what (premium plan T10, feature `audit`, Team and above). The catalog of kinds and their details is `AUDIT_DETAILS` in `packages/contracts/src/audit.ts`; the rules are `packages/domain/src/audit.ts`, the use cases `packages/services/src/audit.ts`.

- **Written with the change, never apart.** Each recorded change adds one statement, `auditEvent`, to its own D1 batch, on the write's own claim or old-state condition (before the guarded write, or after an insert on the row it created), so an event exists exactly when the change does and costs no round trip. A refusal never reaches its batch, a lost race matches no row, and a retried call whose change already happened records nothing more. Adapters never write events. `packages/services/test/audit-coverage.test.ts` lists every exported async use case as a read, a recorded change with its kinds, or a change with the reason it records nothing; a new one fails it until placed.
- **What is recorded.** Publish and rollback, renew, archive, restore, delete, pin, unpin and transfer in and out; access changes (mode, the bar, indexing, embedding, comment visibility, and readers as counts with the distinct domains of their addresses, never the addresses); share links created and revoked; custom domains attached (on proof) and removed (with the reason); webhooks created, changed and removed (the host only); the brand changed and removed; members invited (the role and the address's domain), invitations revoked, members joined, role changes, removals and leaving; and plans granted and removed by the operator. Each event keeps the owner, an opaque actor ID (null for the operator and scheduled jobs), the target and the artifact.
- **What is never recorded.** Comment text, artifact content, share link labels, tokens, secrets, passwords, URLs (with or without credentials), full email addresses, IP addresses or reads (reads are the access log's). The detail schemas are strict and `auditEvent` throws for a detail outside them; a test scans every event a scenario writes for addresses, tokens, URLs and comment text.
- **Where.** Events live in the owner's region next to its artifacts. Changes to global rows (members, invitations, plans and custom domains, decisions 0005 and 0006) are written in the global database by their own global batch (`GLOBAL_AUDIT_KINDS`); no batch spans two databases. They hold only what the global tables already hold (account and workspace IDs, roles, the plan, a hostname, an email domain), so nothing leaves a region. The reader asks each database only for its kinds, so with one region nothing is listed twice.
- **Who reads it.** Only the owner's admins (role action `audit`), and only when the owner's plan includes `audit` (`plan_required` otherwise, after authorization); editors and members get `forbidden`, a user with no role on the workspace exactly what a missing workspace gives. A personal space on a plan with the feature reads its own. `GET /api/v1/audit` (`?workspace=<slug>`), the MCP tool `get_audit_log` and `portifact audit` take bearer tokens with `artifacts:read`, like the access log: the role check still applies, events name members only by display name and opaque ID (never by email, so the session-only member list stays the only place with members' addresses), and decision 0003 keeps `credentials:manage` for minting credentials, which this does not.
- **Who is shown.** A current member (in a personal space, its user) by name; anyone who left, was removed or deleted their account as a removed member, by opaque ID only. An account that is deleted records `member.left` in each workspace it was in, with the system as actor (`accountLeftEvents`, in the batch that deletes the account); the workspace's earlier events keep that opaque ID until they expire, which names nobody once the account is gone.
- **Service tokens and email domains.** What a service token does (decision 0011) is stored with actor type `token` and its ID, decided in `auditEvent`, and shown under the token's current label, or as a revoked token once it is gone; the label is read at display time and never stored. Creating a token records its scopes, the kind of restriction and its lifetime in days (never the label, the secret or the key prefix); revoking one records who did it, the operator included. A workspace email domain (decision 0010) is recorded when it is proved and when it stops granting: removed by an admin, by the daily check or because another workspace proved it. A claim never proved records nothing. A token never reads the log (`audit` is not in `TOKEN_ACTIONS`).
- **Artifact names.** An event shows the artifact's current name only while the artifact is still the owner's: one that was purged, deleted or moved to another owner shows none, so the old owner never learns what the new one calls it.
- **Retention and erasure.** 90 days on every plan (`auditRetentionDays`, overridable for Enterprise), so a lapsed plan keeps what was recorded; reads never list past it and the maintenance scan deletes older events in bounded statements (`AUDIT_LIMITS.pruneBatch` rows, `pruneRounds` statements a run, 50,000 rows per database every 15 minutes, more than an owner writing several events a second accumulates). A change that changes nothing records nothing, so repeating a request does not grow the log. The global events of a deleted owner are erased before the batch that ends its deletion, so a crash in between repeats the step. Events go with their owner (account and workspace deletion, and `applyTombstones` after a restore) and are part of a personal space's account export.

### Share links

Premium plan P4, [decision 0008](decisions/0008-share-links.md): a link that lets anyone who holds it read one artifact without an account, optionally behind a password and until an expiry, created, listed and revoked by an admin or editor of the owner whose plan includes `shareLinks`. The code is in `packages/domain/src/share-links.ts`, `packages/services/src/share-links.ts`, `apps/app/src/api/share-links.ts`, `apps/app/src/mcp/share-tools.ts`, `apps/content/src/share-session.ts`, `apps/web/src/share` and `packages/cli/src/share.ts`.

1. **What a link grants.** Reading the current version of one artifact. A link visitor never reads or writes comments, never gets a review session or the viewer, is never on the reader list and is never identified. A link changes nothing about the access policy and never moves `policyGeneration`; links survive mode changes (they are listed next to the mode in the dashboard), and on a `public` artifact one adds nothing while it stays public.
2. **The token.** 32 bytes from `crypto.getRandomValues`, base64url, shown once in the create response's `url` (`https://app.portifact.com/s#<token>`) and never again: lists, the CLI's `share list`, MCP's `list_share_links`, exports and logs carry only the link's ID. Only its SHA-256 is stored (`share_links.token_hash`, unique). Creation takes no idempotency key, because a stored replay would keep the token in D1. At most 20 active links per artifact (`SHARE_LINKS.activePerArtifact`), enforced by the insert's own condition.
3. **The fragment.** The token is in the fragment, so no request line, log, analytics, link preview or scanner fetching the URL ever sees it, and `Referer` never carries it. `GET /s` serves the entry page (`apps/web/share.html`) with the page policy plus the human check (`SHARE_CSP`), `no-store`, `no-referrer` and `noindex`, and never redirects (a redirect would carry the fragment along). Its first statement takes the token and removes the fragment with `history.replaceState`; a fragment change in the same tab (the link opened again) reloads the page. The browser's global history may already hold the full URL; that is an accepted risk.
4. **Opening.** The page posts `{ token, password?, turnstileToken? }` to `POST /api/v1/share/open`, which takes no credentials (it never reads the session or a bearer token) and, like the report endpoint, accepts only the exact app `Origin` with `Sec-Fetch-Site: same-origin` and a JSON body of at most 1 KiB. `openShareLink` looks the token's hash up in each region's database (one indexed read with one region), reads the owner's plan from the global database, writes the one-use code in the region that holds the link, and opens it only while the link is live, the artifact servable and the plan includes `shareLinks`. Without a password, any link that does not open answers the same `404` (unknown, malformed, expired, revoked, paused by the plan, artifact unavailable); a live password link answers `401 unauthenticated`. With a password, a wrong password and a link that does not open answer the same `403 forbidden` body. A request with a password always runs exactly one PBKDF2 derivation (against a fixed dummy when the token is unknown or the link has no password), compared in constant time.
5. **Passwords.** 8 to 200 characters, PBKDF2-HMAC-SHA-256 through WebCrypto with a 16-byte salt per link and 100,000 iterations (workerd's ceiling), stored with the row. Every password attempt is counted before the password is checked, with one atomic upsert per counter (per token, by a prefix of its hash so unknown tokens count the same; per IP; per token and IP together; 15-minute windows), so parallel attempts see different counts; an attempt that is refused before the check, or succeeds, is given back, so a visitor with the right password never moves toward a check or a lock. `passwordGate` decides on the counts (`SHARE_OPEN_LIMITS`): past 3 per token or 5 per IP every attempt needs a solved human check (verified on the server, failing closed), which the right password plus a solved check passes; past 10 per token and IP that pair gets `429 rate_limited` with `Retry-After`; past 100 per token every attempt on it does. So nobody can lock others out below the ceiling, and reaching the ceiling takes about 97 solved human checks per 15 minutes; that residual lockout, and a guesser who can solve checks at scale getting about 100 tries per token per window, are accepted risks (decision 0008, "Open risks"). Every open request also counts against 60 per IP per 10 minutes.
6. **The handoff.** On success the app stores a one-use code in `share_handoffs` (its SHA-256, the link and the artifact, 60 seconds) and answers `https://<id>.portifact.dev/__portifact/link?code=…`, built from the stored artifact ID; the page goes there with `location.replace`. `/__portifact/link` redeems only a `GET` top-level navigation that is `cross-site` (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`), so a frame cannot, nor a sibling's direct navigation (`same-site`). That is not a boundary against a sibling: any page can send the visitor through a redirector on another site, which makes the arrival `cross-site`; the result is the session fixation described at the end of this item. One guarded update marks the code used for this host's artifact while the link is live, and the `share_sessions` row is inserted only if it happened; every failure answers the same `400` page. It sets `__Host-pf_link` (`Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`) with sealed claims (session, artifact, link, 60-second expiry, session end) under their own purpose, and redirects to `/`. The session ends after 12 hours or with the link's expiry. The code is not bound to a browser: a site holding a link can plant a session for it in a visitor's browser, which grants what sending the link would, and a read session still wins.
7. **Delivery.** The content Worker tries a link session only after review mode, public delivery and the read cookie, and before sign-in starts (`authorizeRead`'s `linkSession`), so a signed-in reader's usable read session always wins and a link never changes what an account gets. The link cookie is used only for `same-origin` requests and navigations, with exactly one value under the exact name. Every request checks that the artifact is servable and the owner's plan still includes `shareLinks` (both from the delivery lookup, no extra read); claims older than 60 seconds are renewed by `refreshShareSession` (session row, link not revoked or expired). Revocation, expiry and the deletion of the artifact end a session within 60 seconds; suspension, archiving and a plan without the feature at once. A link session that no longer works gets a page that says the link expired or was revoked, with the cookie cleared. Only that page clears it: the open page's own requests (a favicon, a poll) usually find the ended session first and are answered `401` with the cookie left in place, so the visitor's next page load is told why instead of being sent to sign in. The dead cookie grants nothing meanwhile, because every use is checked again. A link session is never redirected to the viewer, is answered with `Referrer-Policy: no-referrer`, `frame-ancestors 'self'`, `Cross-Origin-Resource-Policy: same-origin`, `noindex` and `private`, and is charged to the owner's traffic like any request.
8. **The access log.** A page load through a link session of any artifact that is not public is recorded for the link (`isLoggedLinkOpening`) through the same per-isolate batch: `user_id` and `link_id` hold the link's ID and `email` is empty. The owner sees the link's label and the 30-minute window; nobody sees an IP or a person. The CLI and the dashboard's CSV name the link.
9. **What the owner sees.** Per link: label, created, expiry, whether it has a password and the UTC day it was last opened (written once per entry, never per delivery request). Not how many people used it, who, from where, or the token.
10. **Plans and lifecycle.** Creating needs `shareLinks` in the owner's plan (`requireOwnerFeature`); listing and revoking never do. A plan without the feature pauses every link of the owner without deleting any, and they open again when it returns. Links, codes and sessions cascade from the artifact; deleting an account clears `created_by` where it names it (`advanceAccountDeletion`, `applyTombstones`), and the account export lists links without their token or hash; revoked links stay hidden until 30 days after their revocation, when the maintenance job deletes them after writing their `share_link` tombstone; `exportTombstones` exports every revoked link and `applyTombstones` revokes them again, so a restore cannot reopen one.

### Artifact analytics

Owners whose plan includes `analytics` see, per artifact, page views per UTC day, how many came with a session and, for `restricted` artifacts only, distinct signed-in visitors (premium plan P8, [decision 0007](decisions/0007-artifact-analytics.md)). The code is in `packages/domain/src/analytics.ts`, `apps/content/src/views.ts`, `packages/services/src/analytics.ts` and `apps/app/src/api/stats.ts`.

- **What a view is.** `pageView` decides it in `serve`, after authorization, the traffic quota and budget protection: a `GET` navigation answered 200, 206 or 304 with a page (an HTML file of a site or a rendered document), as the top-level document or in a frame another site opened (the viewer's frame included). The redirect to the viewer is not a view, so a visit with the bar on counts once, at the frame. Subresources, fetches, files that are not pages, `HEAD`, refusals, a sibling artifact's frame (`Sec-Fetch-Site: same-site`, which `frame-ancestors` keeps from rendering), `embed` and `object`, and clients without fetch metadata never count. A page load through a share link session (decision 0008) is an anonymous view like any other, never a signed-in one: the link names no visitor, and link visitors never get the viewer, so they count at the top-level document. The owner side's own signed-in visits never count (the personal owner in `pageView`, a workspace's admins and editors when the batch is written). Automated browsers that send fetch metadata do, and a hostile site can frame an artifact to add views (capped by the traffic quota and budget protection), so the dashboard, the CLI and the MCP tool say the numbers are an indicator, not an audit.
- **Counts only.** `artifact_views` in the access database holds the artifact, the day, the owner and two counters; no visitor, IP address or hash. Anonymous visitors appear only in `views`. Distinct visitors of `public` and `authenticated` artifacts are never computed: the access log does not record them, for the reason in "Access logs", and the read answers `null`.
- **No write per request.** The per-isolate `ViewMeter` writes once per 5-second window through `waitUntil`, next to the traffic meter; a failed write is kept for the next window and logged without identifiers. Upserts only add, so concurrent and retried batches add up. An evicted isolate loses at most one window, so counts can be slightly low, never high from that cause. Nothing is counted for an owner without the feature: the plan comes with the delivery lookup.
- **Owner side only, on the owner's plan.** `getArtifactStats` answers anyone without a role, a missing artifact and a purging one `not_found`, a workspace member `forbidden`, and an owner whose plan lacks `analytics` `plan_required`, after authorization. Ranges are UTC days, at most 366, never past today or before the owner's retention, and rows past their `expires_at` are never shown.
- **Retention and erasure** follow the access log's (above): the same `accessLogRetentionDays`, a day's row expires its retention after the day ends, the `owner_retention` job moves them, and the purge's `erase_access_events` job deletes the artifact's counters with its openings. A batch held in an isolate across a purge can recreate a counts-only row for the purged ID; it is never shown (the artifact is gone and tombstoned) and expires.

### Content search

Owners whose plan includes `contentSearch` (Team and above) search inside the text of their artifacts ([decision 0012](decisions/0012-content-search.md)). The rules are `packages/domain/src/content-search.ts` and `html-text.ts`, the use cases `packages/services/src/content-search.ts`.

- **Who.** Only actors who already read every artifact of the owner: admins and editors (role action `search`), and a service token within its reach (`own`, key prefix), applied in the query like the artifact list. A workspace `member` gets `forbidden`, a non-member what a missing workspace gives. Searching for members and outside readers, filtered by each artifact's access policy, does not exist; adding it needs a per-artifact access check in the query, not a filter after it.
- **What.** The text of the current version of each active artifact: Markdown and TXT sources, and the visible text of sites' HTML pages from a bounded, dependency-free extractor (no scripts, styles, templates, attributes or comments; linear time; capped). Archived, suspended, purging and deleted artifacts are not searchable: triggers drop their rows on any state change, and a move to another owner drops them too, before the target reindexes.
- **Queries cannot reach FTS5's syntax.** `buildMatchExpression` keeps only runs of letters, marks and digits, quotes each and joins them with AND; every MATCH starts with the owner's token in a column filter, so a query never errors, never widens and never leaves the owner. The boundaries cap the query at 200 characters, and searches are rate limited per actor after authorization.
- **Plain text out.** Snippets come from the indexed text through FTS5's `snippet()` with private-use markers, returned as text plus UTF-16 ranges; clients escape and highlight (`HighlightedText` in the dashboard, « » in the CLI). The indexed text has C0 and C1 control characters removed, so a snippet carries no terminal escape. The MCP tool tells agents snippets are untrusted content.
- **No logs.** Queries and snippets are never logged. The index is derived from content the owner already stores, in the owner's regional database; it is not part of the account export.

Premium plan P7, [decision 0006](decisions/0006-custom-domains.md): an admin or editor of an owner whose plan includes `customDomains` (Pro 1, Team 5, counted per owner) serves one artifact from a hostname of their own through Cloudflare for SaaS. The code is in `packages/domain/src/custom-domains.ts`, `packages/services/src/custom-domains.ts`, `packages/services/src/cloudflare-hostnames.ts`, `packages/services/src/domain-notices.ts`, `apps/content/src/custom-hosts.ts` (with `apps/content/src/index.ts`), `apps/app/src/read.ts`, `apps/app/src/api/review.ts`, `apps/app/src/api/domains.ts`, `apps/app/src/mcp/domain-tools.ts`, `packages/cli/src/domains.ts` and `apps/web/src/dashboard/screens/custom-domain.tsx`. A custom host is another origin of user content, never of credentials: the owner controls its DNS and can point it at their own server at any time, so everything Portifact sends there (read, review and link cookies, one-use codes, transaction cookies) must be worth nothing beyond reading the owner's own artifact, which the owner can already do. Keep it that way for anything ever set on artifact origins.

1. **Switched off by default, with one switch for serving.** Whether a Worker serves custom hosts is `customDomainsServing`: `CUSTOM_DOMAINS_ENABLED` exactly `"true"`, the same function in the app and the content Worker. While it is off, every app entry that picks a host (the read entry, review codes, share-link codes, the viewer's lookup and its page's `frame-src`, the artifact views' `url` and `customHost`) names only `<id>.portifact.dev`, whatever the tables hold, so a rollback (switching it off after domains exist) works on `.dev` at once and switching it on again restores the domains (tested in both Workers). Nothing calls Cloudflare unless the app or jobs Worker also has `CF_CONTENT_ZONE_ID` (a zone ID), `CONTENT_DOMAIN` and the secret `CF_HOSTNAMES_TOKEN` (`domainDepsFromEnv`); switched on without them it still serves the domains that exist, logs `custom_domains_misconfigured`, and adding and checking a domain answer `503 capacity_unavailable`, listing says `available: false` and removing still works. The variable must change in both Workers together: switch the content Worker on first and off last ([releasing.md](releasing.md)), since an app that sends codes to custom hosts the content Worker does not serve leaves readers on a 404. Every call to Cloudflare and DNS goes through `DomainDeps`, injected into the services; tests and the e2e stack use `FakeDomains` (`@portifact/services/testing`, never imported by a deployed Worker). The token goes only in the `authorization` header, errors carry Cloudflare's status and codes only, and IDs are checked before they reach a URL path.
2. **Proof before Cloudflare.** Adding stores a claim (`domain_claims`, global, keyed by hostname and owner) with a fresh 128-bit token; nothing reaches Cloudflare until the TXT record `_portifact.<hostname>` holds `portifact-verify=<token>`, read through DNS over HTTPS. Cloudflare would validate any hostname whose CNAME still points at Portifact in real time, so a dangling CNAME after a removal never lets another account take the name: it needs its own token in DNS. Claims of several owners for one name coexist, a squatter's claim blocks nobody, another owner's token proves nothing, and the proof spends every claim of the name in the same batch. The token is the value of a public DNS record and proves control only by being found there, so it is stored as is (the decision proposed a hash) to show the record again; it is still never logged, exported or put in an error.
3. **One write decides.** The proof's batch moves the name to the claimant (an update for a name another owner holds, an insert otherwise), each conditioned on the claim still being live with that token and on the owner's count staying under the plan's limit, and only then deletes the claims; a concurrent second proof finds no claim and answers `version_conflict`, and the count cannot be passed by two proofs at once. A name that changes hands is first cleared from the previous artifact (regional `custom_host`), keeps Portifact's Cloudflare hostname and goes back to `provisioning`.
4. **`artifacts.custom_host` is the authority, and set last.** Activation (`activate`) needs Cloudflare to report the hostname and its certificate active and the name to resolve to Portifact's target (item 17); it turns the global row active first, conditioned on it still being this owner's claim for this artifact, and only then sets the regional column, only while the artifact is still the owner's, active and without another host (the unique index refuses a second holder), detaching the domain if it cannot. Every path that sends a visitor to a custom host needs both (the delivery lookup matches the column, the `.dev` redirect also the hint from the active row, the app's entries `activeCustomHost`), so between the two writes nothing is served or sent there; the opposite order would let a reader be sent to a name whose row is still provisioning and that a new DNS holder could take. A Worker that stops in between leaves an active row without the column, which the daily check binds again. The column is cleared first on every detach, before the global row changes, and once more by the deletion job.
5. **Detaching is idempotent.** `detachDomain` writes the `delete_custom_hostname` outbox job and the `detaching` state in one global batch on the same old state, so a retried or concurrent detach writes one job; the job deletes the Cloudflare hostname (which ends its billing and certificates) and then the row, which frees the name. Removal, suspension (`suspendArtifact` clears the host in its own batch), purge (`deleteArtifactData`), account deletion (`advanceAccountDeletion`), three missed daily TXT checks, three daily checks in a row that find the name pointing elsewhere, a Cloudflare hostname that moved, was deleted, blocked or is missing, a domain still provisioning after 2 days, a lower plan (the oldest stay; an expired plan counts for 7 more days) and the reconciliation after a restore all detach through it. Reinstating a suspended artifact never brings a domain back. Hostnames need no tombstone: a released name is meant to be claimable again with a fresh proof.
6. **Same answers everywhere.** Adding, checking and removing need `artifacts:share` (a domain changes where an artifact is reachable), reading needs `artifacts:read`, all go through the same services from the API, MCP and the CLI, and the plan gate is the artifact owner's (`requireOwnerFeature`), checked after authorization. A user without a role on the owner gets the missing-artifact answer for an artifact and `Custom domain not found.` for a hostname, exactly like a name nobody holds; a role without `access` gets `forbidden`. Names are normalized and refused in the domain (`normalizeHostname`: IP literals, wildcards, fewer than three labels, Portifact's domains and the deployment's content domain, any label containing `portifact`).
7. **The bar is not changed for the owner.** With the Portifact bar on, a visit to the custom domain will still end in the viewer on the app; the dashboard, the CLI and the MCP tools say so when a domain is attached and offer to turn the bar off, and only the owner's explicit choice changes it.
8. **Delivery on a custom host.** Only while `customDomainsServing` holds on the content Worker; otherwise every host but `<id>.portifact.dev` answers 404 and nothing below applies, exactly as before custom domains (a test compares the `.dev` answer byte for byte). The isolate caches `hostname -> artifact, region` from active `custom_domains` rows as a hint only (`apps/content/src/custom-hosts.ts`): every request reads the artifact anyway through `findDeliveryArtifact`, which on a custom host also requires `artifacts.custom_host = <host>`, so a warm request costs today's one read, a cold one two, a stale hint is dropped and the table read again on the same request (a host that moved: three reads), a miss is never cached, and a removal holds at the next request in every isolate. A global row alone serves nothing. Every check after that is the same as on `.dev`, in the same order: state, sign-in, read, link and review sessions, traffic quota and budget, then bytes; traffic is charged to the owner, a page view counted once, openings logged for `restricted` artifacts only. Portifact's scripts (`/__portifact/bridge.js`, the diagram script) are answered without a lookup; every other reserved path works on the custom host after resolution. Names that `normalizeHostname` would refuse or change never reach the table.
9. **No HSTS on a customer's domain.** The domain is the customer's: a `max-age` would outlive the attachment and `includeSubDomains` would bind their other sites. The Worker upgrades plain `http` on a custom host with its own `308` (before any lookup) and never sends `Strict-Transport-Security`. `.dev` is HSTS-preloaded as a TLD.
10. **Codes work only on the host they were issued for.** `read_handoffs`, `review_handoffs` and `share_handoffs` store the exact host (`host`), and every redemption is conditioned on the request's host (`coalesce(host, <id>.portifact.dev) = <request host>`; a null host is a code issued before the column existed, which counts as the `.dev` host's). The app never takes a host from request input: the read entry's `host` parameter, which the content Worker adds only from a custom host, is compared after `checkReadAccess` with the artifact's active custom host from the tables (`activeCustomHost`, which also requires the regional `custom_host` to agree) through `handoffHost`, and anything else gets the same `artifact_unavailable` as an artifact the visitor cannot open, so the check reveals nothing. Review codes and share-link codes go to the active custom host or the `.dev` host, chosen by the services from the tables. A code sent to one host is refused on the other, and a transaction cookie lives on the host the visitor started on. A code never goes to a custom host without a click of the visitor's when any signed-in account may read the artifact (`authenticated`, `customHostWithoutClick`): the domain owner may receive codes on a server of their own and could otherwise collect a session for every signed-in visitor they send to the entry. The read entry then sends a signed-in visitor to the login page (`/login?confirm=read&next=...`), which names the host and posts the entry back (`POST /read/<id>`, JSON, exact app `Origin` and `Sec-Fetch-Site: same-origin`, so another site cannot) only when they continue; the viewer frames such an artifact on `.dev`, so its review codes never go to the custom host. Public artifacts need no code, and the readers of a restricted one are the owner's choice, so neither asks.
11. **Cookies.** Every cookie stays a host-only `__Host-` name in `isPortifactCookie` (`Secure; Path=/`, no `Domain`), so a custom host's read, link and review sessions are separate from the `.dev` origin's: a reader signs in once per origin. The injected-cookie cleanup runs only on the content domain: on a custom host the other cookies belong to the customer's own sites, and without the Public Suffix List the Worker cannot name their registrable domain. Nothing protects a customer's domain from its own sibling subdomains: `www.example.com` (or any site the customer runs under `example.com`) can set `Domain=example.com` cookies that reach `docs.example.com`, read nothing of Portifact's (they grant nothing, because authorization reads only exact `__Host-` names, and a sibling cannot set a `__Host-` cookie), but can fill the cookie jar until the browser drops the oldest (the visitor signs in again) or the headers pass the platform's limit (the request is refused before the Worker runs, and only the customer can fix it, by not setting such cookies). That is the customer's own domain hurting itself, which Portifact cannot prevent and does not try to.
12. **The viewer.** The viewer frames the artifact's active custom host only for a visitor who may read it (`viewerFrameOrigin`), and never for an `authenticated`, `workspace` or `domain` artifact (item 10): the viewer's lookup (`getViewerArtifact`, which then carries `customHost`), the review code's iframe URL and the page's `viewerCsp` all use it, and the page route runs the same lookup only while custom domains are on. For a missing, protected or unavailable artifact the header and the lookup's 404 are identical with or without a domain (tested). The frame keeps working the same way on the custom host: the review cookie is partitioned under the app's site (CHIPS) wherever the frame's origin is, so Chromium and Firefox with partitioned cookies keep review mode in the frame, and Firefox with third-party cookies blocked falls back to the review tab exactly as on `.dev` (the tab's `Referer` check is against the app origin). The owner's logo on a branded bar comes from the same framed origin. A domain attached while a viewer is open trips the frame's watchdog; a reload fixes it.
13. **Old `.dev` links.** `<id>.portifact.dev` keeps working and stays the artifact's permanent origin. A top-level page visit there answers `308` to the same path and query on the custom host only with the bar off, only after authorization (so an anonymous visitor of a protected artifact never learns its domain), never in review mode, never through a share link's session (it lives on the origin it opened on) and never for frames, subresources, files or reserved paths (`canonicalLocation`), and only while the global table agrees: the isolate's hint for that host must name this artifact (refreshed once when it does not), so the regional column alone, as in a half-finished activation or a restore, never sends readers, path and query included, to a name whose row is provisioning, detaching or another owner's (`hintAgrees`; a warm isolate reads nothing more). With the bar on the viewer wins and frames the custom host itself; a browser that chose "Open without the Portifact bar" on `.dev` stays there. The redirect is charged as one request without bytes and is neither a view nor an opening, so nothing is counted twice. It stops at the next request after a detach.
14. **Names that can never work, and names the operator blocks.** A hostname that is the apex of its DNS zone (its SOA record answers for itself, `dohZoneApex`) is refused at adding and again before Cloudflare: it cannot hold the CNAME Cloudflare for SaaS needs, which also covers registrable domains under multi-label public suffixes (`example.co.uk`) without the Public Suffix List. The operator's block list (`blocked_hostnames`, `block-domain`) refuses a name and every name under it at adding and verifying, detaches the domains it covers at once and the daily check detaches any it missed. A domain still provisioning two days after its proof is detached (Cloudflare bills pending hostnames).
15. **The downgrade notice.** When a plan that ended no longer covers some domains, the scheduled check emails the owner (each admin of a workspace) once per detach time before the grace ends, through `packages/emails` in their language; it names hostnames only, skips suppressed addresses, stops before the cycle's emails run out and is counted like every email.
16. **What a domain owner gets from codes they collect.** An owner who points their name at a server of their own can receive the codes Portifact sends there and redeem them at the edge. The cookies they get grant reading their own artifact, which they can already do, and name nobody: every claim is encrypted (see "Entry to protected artifacts" above), so neither the user ID nor the app session it hangs from is readable, and two cookies of one reader do not match. The server-side session rows keep the real user for the access log, comment authorship and the owner-side checks; nothing reads them from the cookie without the secret. With item 10, the visitors whose codes can reach such a server without a click are only the readers of a public or restricted artifact.
17. **Where the name points.** A name must resolve to Portifact's CNAME target (`domains.<content domain>`) over the same DNS over HTTPS client (`dohPointing`: the address query's CNAME chain names the target, or every address it resolves to is one of the target's, for providers that flatten or proxy the CNAME): it is not activated otherwise ("Check again" and the scheduled run say `cname_elsewhere`), "Check again" on an active domain shows the problem, and the daily check detaches it after three checks in a row that find it elsewhere (`missed_point_checks`, counted apart from the TXT misses; a DNS failure neither counts nor resets). Between two checks an owner can still repoint the name, so for up to three days the viewer could frame, inside Portifact's bar, a page Portifact never stored; the bar keeps showing the real origin (`HostingNotice`), and a report about such a domain is handled with the operator's block list ([operations.md](operations.md), "Abuse reports").

### Abuse reports, suspension and account deletion

- The report form is a trusted page on `app.portifact.com/report`; artifact origins only link to it (`/__portifact/report` answers a `303` there for any ID, so it reveals nothing, and sets no cookie). Pages rendered by Portifact (Markdown and TXT) end with a "Report this artifact" link to that path, in a `footer` outside `main` marked `data-portifact-ignore` (anchors skip it) and `data-portifact-chrome`; it is plain markup in a page without scripts, added at commit by `packages/render` (`reportLink`), never injected into a site's HTML. Review mode removes that footer (`injectBridge`), and the viewer's bar shows its own link to `/report?artifact=<id>` to everyone but the owner. Sites keep only the reserved path, which the Acceptable Use Policy documents. `POST /api/v1/reports` (`apps/app/src/api/reports.ts`) needs no credentials, so it accepts only the exact app `Origin` with `Sec-Fetch-Site: same-origin` and a JSON body (a sibling artifact cannot fake fetch metadata, and a cross-site form cannot send JSON), limits requests per IP, per artifact and globally in the D1 counters (`REPORT_LIMITS`), validates with the strict `AbuseReportInput` (reason enum, at most 2,000 code points of details without control characters, optional email, 8 KiB body) and answers `202` whether or not the artifact exists. Only reports about artifacts that exist are stored. Report text and emails are untrusted data and are never logged.
- Suspensions are applied only by the operator tool with the deploy credentials ([operations.md](operations.md)); no web route can suspend or reinstate. A suspended artifact is not servable, so every existing check refuses it: delivery answers it like a missing artifact, its share links stop opening and their sessions end at once, read-session claims stop at the next request because the Worker reads the state on every request, `/read/<id>` and `checkReadAccess` refuse it, `getVersionDownload` gives readers nothing and visitors lose annotations. Owners see only the reason category, never the operator's note. A suspended account cannot publish (`preparePublish` refuses it for every channel).
- The only admin of a workspace cannot delete their account: `requestAccountDeletion` answers `409 sole_workspace_admin`, and a trigger on `users` (`users_refuse_deleting_sole_workspace_admin`, 0029) refuses the delete too, so a concurrent change fails the whole batch. Re-applying an account tombstone after a restore is never refused. Memberships go with the user through the foreign keys; the workspace keeps its artifacts, and the account's comments on them are erased like those on other people's artifacts.
- Deleting the account (`POST /api/v1/account/delete`, dashboard session only, like every account endpoint) needs the account's email typed again and a session signed in within `FRESH_SESSION_MS` (10 minutes); an older session gets `403 reauthentication_required` and signs in again. One batch records the deletion in `account_deletions`, claims every artifact as `purging`, erases the address from abuse reports, deletes the user's device codes, writes an `erase_access_events` job for the account's openings of other people's artifacts and deletes the `users` row. The foreign keys then delete its sessions, identities, OAuth access and refresh tokens, consents, read sessions and handoffs, so no credential survives the request. This is the one place that ends sessions without Better Auth's API: the tokens those hooks would revoke are deleted by the same cascade.
- `advanceAccountDeletion` finishes it, run by the `account_deletion` queue job and by the maintenance job `processAccountDeletions`: `purgeArchived` purges the claimed artifacts (tombstone per ID), `eraseAuthorFromThread` removes the account's messages on other people's artifacts in batches (a message someone replied to after it becomes the deleted marker; a thread left without visible messages is removed; each change is claimed under the thread revision it read, so a reply that lands meanwhile wins and the next run looks again), late artifacts from an upload already in flight are claimed too, and when nothing is left the storage objects, counters, idempotency records and upload sessions are deleted and an `account` tombstone replaces the deletion row. Every step is idempotent and safe to run concurrently.
- The deletion request also writes an `account_deletion` outbox job and a `purge_artifact` job per claimed artifact in its batch, so the `portifact-jobs` queue advances the deletion right after the next scheduled relay; the scheduled scan stays as the safety net.
- Artifact IDs are never reused: `preparePublish` claims each new ID in the global `artifact_directory`, which refuses an ID ever handed out or tombstoned and whose rows triggers keep from being updated or deleted, and a trigger (`artifacts_refuse_tombstoned_id`) still refuses inserting an artifact whose ID has a tombstone.
- A D1 Time Travel restore rewinds the tombstones too, so purged artifacts and deleted accounts would come back. The operator exports the markers before restoring and applies them after it (`export-tombstones`, `apply-tombstones`, see [operations.md](operations.md)); applying claims every resurrected artifact for purging and deletes every resurrected account the way a deletion request does, deleting its `users` row directly like `requestAccountDeletion`, and puts back the directory rows of artifacts the restore of the global database rewound (`rebuildArtifactDirectory`).
- The account export (`GET /api/v1/account/export`, session only) is the account's own data as a JSON attachment with `no-store`: profile, sign-in methods, artifacts with access, versions and manifests, the threads on its artifacts and its own messages elsewhere. Other people appear by name only, never by email, and the file starts with a notice that comment text is untrusted. File bytes are fetched through the existing owner-only download links.

### Requests and responses

- No credentialed CORS for artifact origins on any `portifact.com` endpoint.
- Every mutation requires a valid session, CSRF protection and an exact `Origin` check. No mutations over GET.
- Auth callbacks never accept arbitrary redirect targets and respond with `no-store` and `Referrer-Policy: no-referrer`.
- Content responses set `X-Content-Type-Options: nosniff`, correct MIME types, `frame-ancestors` and `Cross-Origin-Resource-Policy` defaults, and `X-Robots-Tag: noindex`. User content cannot override these headers. The owner's options change them only while the artifact is public and never in review mode: `indexable` drops `noindex`, and `embeddable` allows any `frame-ancestors` and `cross-origin` CORP. A protected artifact stays `noindex` and unembeddable whatever its options say.
- Requests that register service worker scripts are blocked.
- Dashboard and viewer pages cannot be framed by user content (`frame-ancestors 'none'`, `X-Frame-Options: DENY`).

- Languages (docs/design.md, "Languages") add no cookie and no credential: the choice lives in each origin's `localStorage` (`portifact.locale`) and the account's `locale` setting (session-only `PATCH /api/v1/account/settings`, validated against `LOCALES`, no CHECK so a language can be added without a migration; unknown stored codes read as no choice). `?lang=` only selects among the listed languages and is removed from the address bar. The sign-in route reads `Accept-Language` only to pick the email's language from the same list. Translations are repository files: the auth pages insert catalog messages as markup at runtime and the build does the same for the static pages, so a catalog is code and must never hold user or external input. The static pages keep the same headers and CSP in every language (`/es/` through the assets, the documents through `legalPage`).

### Untrusted content

- Markdown is rendered by `packages/render` with markdown-it and `html: false`: raw HTML is shown as literal text, never parsed, and there is no MDX and no user plugins. Links and images keep only `http`, `https` and `mailto` URLs (plus paths on the artifact), checked with the WHATWG URL parser so `//host`, `/\host` and embedded tabs resolve as a browser resolves them. Links to other origins get `rel="nofollow noopener noreferrer"`. Remote images are off unless the document opts in; when off they become links. TXT is always escaped inside `<pre>`. Fenced code in a curated set of languages is highlighted at commit and Mermaid blocks are drawn in the browser; see "Diagrams and highlighted code" below.
- Rendered documents carry a Content-Security-Policy `<meta>` (`default-src 'none'`, no frames or forms, `base-uri 'none'`, and no scripts except, in a document with Mermaid blocks, the diagram loader by its hash and the script it adds) as defense in depth if markup ever slips through. Review mode replaces it with the same policy as a header plus a nonce for the bridge (see "Review mode").
- Rendering must stay linear in the input, because a 5 MB document is allowed. remark/micromark is quadratic on nested emphasis, links and many footnotes (seconds to minutes on a few hundred KB), which is why the renderer uses markdown-it, and why `packages/render` patches markdown-it-footnote's quadratic token concatenation. Keep the hostile-size tests in `packages/render/src/security.test.ts` passing when changing the parser or adding plugins.
- The Markdown and TXT viewers run on the artifact origin, never on `portifact.com`. The one exception is the document editor's preview: `POST /api/v1/documents/preview` (scope `artifacts:write`, 120 per user per 10 minutes in the D1 rate-limit counters, nothing stored) returns the page the commit would render, and the dashboard shows it only in an `iframe` with an empty `sandbox` and `srcdoc` (`PreviewFrame` in `packages/ui`). The frame runs in an opaque origin with no scripts, forms, popups or navigation of the page, fetches nothing to load and inherits the dashboard's policy, whose only addition for it is the hash of the renderer's constant stylesheet (`DOCUMENT_STYLESHEET`) in `style-src`; `frame-src` stays `'none'`. The dashboard never inserts rendered markup into its own document. The preview is rendered without the diagram loader (`liveDiagrams` off), so it shows highlighted code and each Mermaid block's source, never the drawing: the frame runs no scripts and has no artifact origin to load the diagram script from.
- Documents are rendered once, at commit, never per request: hostile input can expand about ten times, and a 5 MB source is allowed. The commit reads the verified source from R2, rejects binary, invalid UTF-8 and oversized sources with `invalid_input`, and stores the page (and the Markdown block map) as content-addressed objects of the version. Their bytes count toward the version's 250 MB and the account's storage: the commit batch adds them before marking them verified, so the account limit's CHECK constraint refuses a rendering that does not fit and the upload is released. Rendering a 5 MB hostile document holds the source, the page string and its UTF-8 bytes in memory at once; watch the commit's memory and CPU in production.
- A document's root serves only its rendered page, with the document policy as a `Content-Security-Policy` header too (`default-src 'none'`, no scripts but the diagram loader and the diagram script at its exact URL on that origin, plus the usual `frame-ancestors`). The original is served at its own path as a download (`Content-Disposition: attachment`), and prepare stores it with the document's MIME type (`text/markdown` or `text/plain`, UTF-8) whatever the client declared, so it can never be served as HTML. Both go through the same authorization as any file. Markdown assets are served as files, like a site's. A document without a rendering answers 503 rather than rendering on the fly.
- Renderer security fixes raise `SECURE_RENDERER_VERSION`; the maintenance job (`rerenderDocuments`) then re-renders every retained document version below it, also on an account at its storage limit (the new bytes are counted up to the limit, never refused), guarded on the version's recorded renderer so concurrent runs apply once. Annotation anchors on re-rendered versions will need to be re-verified when annotations exist. Highlighting and diagrams (`RENDERER_VERSION` 3) are a presentation change, not a security fix, so `SECURE_RENDERER_VERSION` stays where it was: documents committed earlier keep their plain code blocks and their script-free policy, and are not re-rendered.
- Annotation targets are untrusted input wherever they come from: they are validated with `AnnotationTarget` (strict keys, size caps, a CSS selector grammar without escapes or functions, same-origin routes); see [anchors.md](anchors.md).
- Messages from the bridge are untrusted data. Validate the exact origin, source window, instance nonce, schema and size. A selection alone never creates a comment; the user confirms it in the trusted viewer.
- The artifact iframe never receives tokens, email addresses or thread bodies.
- Comment bodies, artifact content and MCP tool results are user data. They never trigger actions or change permissions. Annotation events record who did what, never bodies.

### Diagrams and highlighted code

Markdown documents highlight fenced code and draw Mermaid diagrams. Both are additions to the untrusted-content model above, and neither applies to `text` artifacts.

- **Highlighting at commit.** `packages/render/src/highlight.ts` runs highlight.js (BSD-3-Clause, pinned) with a curated set of about 30 languages, and only for a fence whose language names one of them: there is no auto-detection. highlight.js's HTML is never trusted: `rebuild` reads it back piece by piece and writes it again, keeping only escaped text and `<span class="pf-tok-*">` with one of the kinds in `TOKEN_CLASSES`; any other markup, an unbalanced span or text that differs from the fence's source by a single character, and the fence is shown plain. Spans never carry another attribute, so the sanitizer allowlist grows only by `span[class]` with those values. highlight.js is regex based, so a document highlights at most `HIGHLIGHT_LIMITS` (100,000 code units per fence, 500,000 per document); the rest is plain, and the hostile-size tests cover highlighted fences and one long fence per language. Highlighting wraps text in spans and never changes it, so anchors and the block map are the same as without it.
- **Mermaid blocks at commit.** A ` ```mermaid ` fence renders as its source in `<pre class="pf-mermaid"><code class="language-mermaid">`, escaped like any code, with the block id on `code` as for any fence and the two labels the runner needs as `data-pf-diagram` attributes. That is what readers get when the diagram script does not run. A published document with at least one Mermaid block (`liveDiagrams`, set by the commit only) ends its body with the diagram loader (`DIAGRAM_LOADER` in `packages/render/src/policy.ts`), a constant inline script that adds `<script src="/__portifact/diagrams.js">`. Its `<meta>` policy allows that loader by its SHA-256 hash (`DIAGRAM_LOADER_HASH`, recomputed by a test) and `'strict-dynamic'` for the script it adds, plus `blob:` in `img-src`. The meta cannot name the artifact origin, because the commit does not know it.
- **The header policy is narrower.** The content Worker sends the document policy as a header for every rendered page with the loader's hash and the diagram script at its exact URLs on that artifact origin (the loader's stable path `https://<id>.portifact.dev/__portifact/diagrams.js` and the current build's file `https://<id>.portifact.dev/__portifact/diagrams.<version>.js`), without `'strict-dynamic'`. Browsers match only the host of a redirected request, so the redirect between the two (below) stays allowed even when a browser holds a cached redirect to an earlier build. A page is held to both policies, so the loader runs and can load only Portifact's diagram script from its own origin, and nothing the diagram script might create later is trusted by the header. Pages without Mermaid blocks carry no loader, and their meta keeps `script-src` out entirely, so they still run nothing. In review mode the meta is dropped and the header's one `script-src` also lists the bridge's nonce; the review tab keeps the same header without a nonce.
- **The diagram script.** `/__portifact/diagrams.<version>.js` is the pinned, self-hosted Mermaid build (`mermaid.min.js` of the exact version in `packages/render/package.json`, a single file that loads nothing else, uses no `eval` and is escaped to ASCII) followed by Portifact's runner (`packages/render/src/browser`), built by `bun run --cwd packages/render build` into `packages/render/dist`. `<version>` is 16 hex digits of the SHA-256 of the script (`DIAGRAM_VERSION`). No third-party CDN is involved and nothing from `portifact.com` is loaded. The content Worker answers it on every artifact origin before any artifact lookup, like the bridge, with `Cross-Origin-Resource-Policy: same-origin`, `nosniff` and `noindex`:
  - **Caching.** The build's file is `Cache-Control: public, max-age=31536000, immutable`, so a browser downloads it once per artifact origin and build and never asks again; a new build is a new URL. Documents never carry a build's hash: their loader (whose text and CSP hash never change) requests the stable `/__portifact/diagrams.js`, which answers `302` to the current file with `max-age=3600`, so a page load usually costs no request for it either. A request for a build that is gone (a cached redirect can outlive a deploy) gets a `302` to the current one with `no-store`. Old documents therefore keep working across builds without the Worker keeping old builds, and the publish-time loader and its hash did not change.
  - **Compression.** The build compresses the script once with brotli at its highest level: about 5.5 MB becomes about 1.2 MB. The Worker embeds that body as base64 (`dist/diagrams.js`, imported and decoded on first use, so an isolate that never serves the script never holds it) and sends it as is (`Content-Encoding: br`, `encodeBody: "manual"`, `Vary: Accept-Encoding`) to every client that accepts brotli, which every current browser does over HTTPS. A client without brotli gets the plain script, decompressed once per isolate with `node:zlib`, and Cloudflare's edge gzips it on the way out as it does any JavaScript a Worker answers (checked in production on `bridge.js`: `br` and `gzip` both come back compressed). Embedding only brotli keeps the content Worker's upload at about 1.6 MB compressed (a gzip body as well would have taken it to about 3.1 MB).
  - **Traffic.** These bytes do not count toward the owner's traffic. Metering charges authorized requests for an artifact's content ("Traffic metering" in [AGENTS.md](../AGENTS.md)); the diagram script, like the bridge, is Portifact's own code, identical on every origin and answered before any artifact lookup or authorization, so there is no artifact to charge without a D1 read per script request, and charging it would bill owners for the platform's implementation (and for any visit to a sibling origin's `/__portifact/diagrams.js`). The cost it leaves is a Worker request per first visit, which the budget's request metrics count like any other; with immutable caching and brotli, each reader downloads about 1.2 MB once per artifact origin and build (1,000 readers of one public artifact are about 1.2 GB of Portifact's egress, none of it on the owner's quota), instead of 5.5 MB every hour.
- **Why Mermaid is safe enough here.** Mermaid has a history of XSS through labels, `click` directives and configuration directives. The runner initializes it with `securityLevel: "strict"` (labels sanitized, no click handlers or links), `htmlLabels: false` (SVG text, no HTML in `foreignObject`) and `suppressErrorRendering`, and lists `securityLevel`, `htmlLabels` and the other sensitive keys in `secure`, so a diagram's own `%%{init}%%` or front matter cannot change them. It never inserts Mermaid's SVG into the page: each drawing becomes an `<img>` of a `blob:` URL, and an SVG image runs no scripts, loads no subresources and follows no links, so even a flaw in Mermaid's sanitizing cannot reach the document through the drawing. While it draws, Mermaid measures labels in a temporary element of the live page; the e2e test shows a hostile label (`<img onerror>`) reaching that element in Chromium and the page's policy refusing its inline handler (`script-src-attr`), which is the policy doing its job. Everything runs on the artifact's own origin, which holds no credentials and is isolated from the app and from other artifacts as described in "Origins", so the worst a Mermaid flaw could do is what any site artifact's own script may already do on its own origin. Upgrading Mermaid is a dependency change like any other: pin the exact version, rebuild, rerun the render, content and e2e tests, and regenerate the notices.
- **Annotations.** The drawing is inside a `figure` marked `data-portifact-ignore` with no text of its own, and the source block stays in the page with the same text, folded by a class (never `hidden`), so anchors and positions are the same whether the script ran, failed or was blocked (`packages/render/src/browser/diagrams.test.ts` checks it with the real `AnchorDocument`, and `e2e/tests/diagrams.spec.ts` resolves a comment again with the script blocked). A comment on a diagram goes on its source or on the page.

### Uploads

- Paths are normalized and checked on the server: absolute paths, `..`, symlinks, special entries, collisions, reserved paths, size and entry limits are all rejected.
- The server verifies the real size and checksum before commit. A client-declared value is never trusted.
- Quotas are reserved in the same transaction that admits the work.
- The CLI (`packages/cli/src/manifest.ts`) also refuses links and special files instead of following them, applies the domain's path rules before uploading, and leaves out `.git` (any case), `node_modules`, caches and files that may hold secrets (`.env*` except templates, `.dev.vars`, `.npmrc`, `.netrc`, SSH keys, `*.pem`, `*.key`, Terraform state and similar), also when such a file or folder is named directly. These are conveniences for the user; the server still enforces every rule.
- ZIP files are expanded by the CLI (`packages/cli/src/zip.ts`), never by the server, with a minimal reader that trusts nothing in the archive: it reads the central directory and refuses symbolic links (Unix mode or Windows reparse point), special files, encrypted entries, names that are not UTF-8 or fail the domain's path rules (zip slip, absolute paths, drive letters, backslashes, control characters, `__portifact`), duplicates and case collisions, a name used as file and folder, local headers that disagree with the directory, overlapping entries, multi-disk archives and more than 10,000 entries, all before writing a byte. Declared sizes must fit the limit (250 MB published, 2.5 GB sources) and an entry over 1 MB may not expand more than 200 times; inflation stops as soon as an entry passes its declared size, and the CRC-32 must match. Entries land in a private temporary folder under numbered names, so no archive name becomes a path on disk, and the folder is removed when the command ends. The server still validates the resulting manifest like any other.
- Private sources from git (`packages/cli/src/git.ts`) run `git` as a child process with argument arrays, never a shell, with `core.fsmonitor=false`, no pager, no prompts and no optional locks. A `--ref` starting with `-` is refused, so it cannot become an option. The secret filter applies to the files git chooses. The remote attached to a version loses its user name (except on ssh), password, query and fragment in the CLI, and the server refuses any declared remote that still carries them (`checkSourceOrigin` in `packages/domain/src/sources.ts`), whichever client sent it. The origin is declarative: the server checks its form, cannot verify it, and shows it only to the owner, like the sources. A rollback copies it with the sources.
- The dashboard applies the same exclusions and path rules: they live in `packages/domain/src/files.ts` and both clients import them. It builds the manifest in a Web Worker (`apps/web/src/dashboard/publish`), hashing and expanding incrementally. ZIPs are read from their central directory before anything is expanded: links and special files (Unix modes), encrypted entries, ZIP64, split archives and compression other than stored or deflate are refused, declared sizes are checked against the limits first, and each entry must expand to exactly its declared size and CRC-32, so a lying archive stops at the size it declared. Documents must be one UTF-8 file without NUL characters, within 5 MB.
- The dashboard uploads with `XMLHttpRequest` straight to R2's S3 endpoint, sending every signed header except `host` and `content-length`, which the browser sets itself to the signed values. Its page policy adds exactly that origin to `connect-src` (`dashboardCsp` in `apps/app/src/app-host.ts`), and the bucket's CORS rule allows only `https://app.portifact.com` ([releasing.md](releasing.md)). Neither the session cookie nor any token goes to storage (`credentials: "omit"` on downloads). Cancelling deletes the upload; a failed one stays open so the same page can resume it with fresh URLs from `GET /api/v1/publishes/:id`, which lists the parts of large files already reported and signs only the missing ones. Parts are `Blob` slices, so the browser reads them from disk as it sends; reading a part's `ETag` needs the bucket's CORS rule to expose it. Downloads are checked against the manifest's size and SHA-256 before the browser saves them, and several files are packaged into a ZIP in the page.
- The CLI sends each object to the presigned URL with exactly the signed headers and never with the API token. A large file's parts are streamed from disk one byte range at a time, at most four uploads in flight, so memory stays bounded whatever the file size. Upload URLs are never printed. If anything fails after prepare, it cancels the upload with `DELETE /api/v1/publishes/:id` so the reservation is released.
- Comparing versions (`GET /api/v1/artifacts/:id/versions/:from/diff/:to` and `.../file`, MCP `diff_versions` and `diff_version_file`, `portifact diff`) is for an admin or editor of the owner (`versions`), like the version list: anyone without a role gets the missing-artifact answer and a member `forbidden`, both before the plan check, so `plan_required` reveals nothing to strangers. Only retained versions of that artifact compare. The text diff reads at most `VERSION_DIFF.fileBytes` (256 KiB) of each side, only text content types that decode as strict UTF-8, and stops past 10,000 lines a side or 1,000 changed lines, so its CPU and memory are bounded; it is a read, so it is never behind budget protection and is not traffic. File contents and paths in the result are user data.
- MCP never receives the bytes of an upload: `prepare_upload` and `get_upload_status` return the same presigned targets as `POST /api/v1/publishes` (built once in `apps/app/src/api/uploads.ts`), the agent sends them with its own HTTP client, and `commit_upload` reports multipart ETags through the same service as `POST /publishes/:id/parts` before the same commit, which still rehashes everything. MCP applies no manifest exclusions of its own: an agent sends whatever it lists, so the skill tells it to leave secrets out. `read_artifact` and `GET /api/v1/artifacts/:id/versions/:versionId/content` read through `readVersionFile` (`packages/services/src/read-file.ts`), which authorizes exactly as a download (`getVersionDownload`), refuses binary content types and bytes that are not UTF-8, and returns at most 256 KiB per call.

### Secrets and logs

- No secrets in the repository. Local secrets live in `.dev.vars`, which is ignored by git. CI's `secrets` job scans every change's commits and the checked-out tree with gitleaks, and the whole history when its rules change ([releasing.md](releasing.md)); a false positive goes in the `.gitleaks.toml` allowlist with the reason it is safe, as narrow as the finding, never as a path exclusion. Public values (the Turnstile site key, the Google and GitHub client IDs, Cloudflare's documented Turnstile test keys and the e2e Worker's test-only values) are not secrets.
- Never log tokens, cookies, OTP codes, presigned URLs, the Cloudflare token (`CF_HOSTNAMES_TOKEN`), private emails (the access log stores visitors' emails in its own database and never logs them), or full comment bodies. The email sender replaces provider errors with a generic one (or `RecipientSuppressedError`), because a provider error can echo the message that holds the code and the address. The email events consumer logs only the event type, ID and outcome, never the recipient.

## Review checklist

Before finishing a change that touches the areas above, confirm:

1. Which origin serves this, and does it hold credentials it should not?
2. Who is the actor, where does that identity come from, and did the services resolve their role on the owner (`resolveActor`), answering a non-member exactly like a missing artifact?
3. Is every path authorized before bytes or data are returned?
4. Can a hostile artifact on a sibling subdomain trigger, read or forge this?
5. Is there a test that tries to break it?
6. Does a top-level visit to an artifact still reach only what it did before, and does the viewer redirect stay out of frames, reserved paths and artifacts with the bar off?
7. Can a share link's token reach a URL, a log, a response after creation, the artifact origin or a `Referer`, and does a link session still read only what a link grants?
8. Does anything reach Cloudflare for a hostname before its owner's TXT proof, and does every way an artifact or owner goes away detach its custom domains?
9. On a custom host: is the answer decided by `artifacts.custom_host` (never by the cached hint alone), does every code redeem only on the host it was issued for, does every host a code is sent to come from the tables, and is everything set there worth nothing beyond reading the owner's own artifact?
10. Does a new read path decide access through `checkReadAccess` or `canRead` with the owner's verified domains, so a removed member or domain stops reading within 60 seconds, and does it add no D1 read per delivery request?
