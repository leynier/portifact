# Security

## Reporting a vulnerability

Do not open a public issue. Report it privately through GitHub's "Report a vulnerability" button in this repository's Security tab, with steps to reproduce and the impact you observed. You will get a first response within 7 days.

## Invariants

Portifact serves arbitrary HTML and JavaScript from untrusted users next to accounts and private content. These invariants are not optional. Each one has at least one test that tries to break it (see [testing.md](testing.md)).

### Origins

- `portifact.com` hosts everything with credentials or that mutates data: dashboard, API, auth, OAuth, MCP and the viewer with the Portifact bar.
- `portifact.dev` serves only user content and the viewers that render it. Its only state-changing endpoints are one-time code exchanges under `/__portifact/`.
- `portifact.dev` is not on the Public Suffix List. All `*.portifact.dev` artifacts are the same site, so any artifact can set cookies with `Domain=portifact.dev` and is same-site with every other artifact. Never rely on `SameSite` between artifacts.
- Paths under `/__portifact/` are reserved (`callback`, `report`, `raw`, `review`, `review/check`, `review/tab`, `review/tab/check`, `review/end` and `bridge.js` today). No uploaded file can shadow them, a viewer link can never point the frame at one, and none of them is ever redirected to the viewer.

### Cookies and sessions

- Portifact cookies use the `__Host-` prefix: `Secure`, `Path=/`, no `Domain` attribute.
- Each surface has its own session: dashboard, read session per artifact and review session per artifact and version. Artifact code never receives an admin credential.
- The review cookie is `Partitioned` (CHIPS). It grants reading one version and nothing else. The fallback review tab's cookie (`__Host-pf_review_tab`) is first-party and `SameSite=Lax`, grants the same and lasts 15 minutes (see "Review mode").
- Sibling artifacts in the viewer's partition can send credentialed requests that carry another artifact's review cookie. The content Worker honors the review cookie only for `Sec-Fetch-Site: same-origin`, or `cross-site` with `Sec-Fetch-Mode: navigate`, fails closed without fetch metadata, and sends `Cross-Origin-Resource-Policy: same-origin` on review responses. See [decision 0002](decisions/0002-review-mode-cookies.md).
- Cookie names are matched exactly and case-sensitively. WebKit lets a sibling set `__host-` (lowercase) cookies with a `Domain` attribute, so case-folding a name would let it shadow a `__Host-` cookie.
- The content Worker reads only its own cookies by exact name and ignores every other one; it expires injected cookies once they grow (see "Injected cookies").
- Read sessions carry signed claims that expire in 60 seconds or less. After that, the Worker rechecks D1. Revocation must take effect within 60 seconds.

### Injected cookies

Any artifact can set cookies with `Domain=portifact.dev`, for `/` or any other path, and every other artifact origin then receives them. The content Worker handles them in `apps/content/src/injected.ts`, for every response it gives, whatever its status:

- **They grant nothing.** Authorization reads only Portifact's names on artifact origins, exactly and case-sensitively and with one value each: `__Host-pf_read`, `__Host-pf_read_tx_<tag>`, `__Host-pf_review`, `__Host-pf_review_tab` and `__Host-pf_nobar` (`isPortifactCookie`). Browsers refuse a `__Host-` cookie with a `Domain`, so a sibling can only add look-alikes (`pf_read`, `__host-pf_read` in WebKit), which are foreign. A new cookie on artifact origins must be added to `isPortifactCookie`, or it counts as foreign.
- **They are expired once they grow.** When the foreign cookies of a request pass 8 KiB of `name=value` (`FOREIGN_COOKIE_LIMIT`), the response carries `<name>=; Max-Age=0; Domain=portifact.dev; Path=<path>; Secure; SameSite=None`, and the same with `Partitioned`, for each foreign name. The Cookie header does not say which path a cookie was set for, so each name is expired at every path the request matches: `/` and each prefix of the requested path, at most 8 (`cookiePaths`). Names that imitate ours are cleared first and at any size, then the largest; whole names at a time, up to 16 KiB of `Set-Cookie` per response (`CLEANUP_BUDGET`), so the next requests, usually the page's own subresources, clear the rest. The visitor recovers on the first request that still reaches the Worker, with no extra round trip.
- **Nothing else is touched.** Portifact's cookies are never cleared and never counted. The artifact's own host-only cookies survive, because a `Domain` cookie is a different cookie from a host-only one with the same name. Under the limit only imitations are cleared: analytics scripts set their cookies on the widest domain they can, which is `portifact.dev` while it is not on the Public Suffix List, and clearing those on every response would break them.
- **No `Clear-Site-Data`.** Its `cookies` type clears every cookie of the registrable domain, so on an artifact origin it would end the visitor's read sessions on every artifact and wipe every artifact's own cookies.

Limits:

- A request whose headers pass the platform's limit (128 KB in total on Cloudflare; local workerd answered `431` at 500 KiB and accepted 200 KiB) is refused before the Worker runs, so no `portifact.dev` response can clear its cookies, and `Clear-Site-Data` could not either. Browsers keep about 180 cookies of up to 4 KiB per registrable domain, so one artifact can push a visitor past that limit on every artifact. Until `portifact.dev` is on the Public Suffix List, that visitor has to clear the site data of `portifact.dev` in the browser; reporting and suspending the artifact stops it from injecting more.
- Cookies a response cannot name (without a name, or with control or non-ASCII characters in it) count toward the limit but are not cleared.
- Browsers evict a registrable domain's least recently used cookies past their per-domain limit, so an injecting artifact can push out a visitor's read sessions of other artifacts; the visitor signs in again.

### Entry to protected artifacts

A visitor of an artifact that is not `public` signs in on `app.portifact.com` and comes back with a read session for that one artifact origin. No credential, email or session ever lives on `portifact.dev`; the code in `apps/content/src/read-session.ts`, `apps/app/src/read.ts` and `packages/services/src/read-access.ts` follows these rules.

1. A navigation without a usable read session gets a transaction cookie `__Host-pf_read_tx_<first 16 characters of the nonce>` (signed with `READ_SESSION_SECRET`, 10 minutes) holding the artifact, a random nonce and the requested path, and a `303` to `app.portifact.com/read/<id>?state=<nonce>`. The app never sees the path; the `Referrer-Policy: no-referrer` on the redirect keeps it out of `Referer` too. Each transaction has its own cookie, so a second tab does not break the first; at most three stay open per artifact, and starting another clears the oldest plus any that are expired, unreadable or sent twice. A requested URL that would make the sealed cookie longer than 2,048 characters is replaced by `/`, so sign-in always finishes.
2. `/read/<id>` takes the account only from the dashboard session cookie. Without one it sends the visitor to `/login?next=/read/<id>?state=…`; the login page accepts `next` only for its own pages and `/read/<artifact-id>`. With one, it counts the entry against a per-account limit in the D1 rate-limit counters (60 per 10 minutes, `READ_ENTRY_LIMIT`; past it, a `303` to `/login?error=read_rate_limited` with `Retry-After` and nothing stored), then `checkReadAccess` applies the domain's `canRead` to the artifact's current policy and requires it to be servable. A missing, unavailable or forbidden artifact gets the same `303` to `/login?error=artifact_unavailable`.
3. On success the app stores a handoff (`read_handoffs`): only the SHA-256 of a 32-byte code and of the nonce, the artifact, the user, the dashboard session's ID (Better Auth's `sessions.id`) and the policy generation, valid 60 seconds. It redirects to `https://<id>.portifact.dev/__portifact/callback?code=…`, a host built from the validated ID, never from input.
4. The callback accepts only a `GET` navigation that carries a live transaction cookie of the same artifact; the code matches at most one of the browser's open transactions. One guarded update marks the code used and names the new session, only while the dashboard session that asked for the code is live, and the `read_sessions` row (with that dashboard session's ID) is inserted only if that update happened, so a replayed, expired, cross-artifact or other-browser code (fixation) creates nothing. Every failure answers the same `400` page and clears only transactions that are no longer usable, because another tab may still need the others; success clears the transaction it used.
5. The callback sets `__Host-pf_read` (`Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`, 12 hours) and returns to the stored path as an absolute URL on the same origin, so `//evil.example` stays on the artifact.

The read cookie holds the session ID and HMAC-signed claims: artifact, user, policy generation, claims expiry (60 seconds) and session expiry. The Worker trusts the claims without D1 only while they are unexpired and their generation equals the artifact's current `policyGeneration`, which it reads on every request anyway, so a policy change applies to the next request. Otherwise `refreshReadSession` rechecks the session row, the dashboard session it came from and the policy; it renews the claims or clears the cookie and starts the entry again.

Read sessions end with the dashboard session that opened them. Signing out of `app.portifact.com`, signing out everywhere and revoking a session delete the `sessions` row, which cascades to its handoffs and read sessions, and a dashboard session that expired fails the same check. Claims already issued are trusted for at most their remaining 60 seconds, so artifact access ends within 60 seconds of signing out, like any other revocation.

- The read cookie is used only for `Sec-Fetch-Site: same-origin` requests and for navigations. Sibling artifacts are same-site, so their `<script>`, `<img>` and CSS loads would carry it; they get a `401` instead. Protected responses also send `Cross-Origin-Resource-Policy: same-origin` and are never embeddable.
- Requests without fetch metadata fail closed with a `401` page and no redirect, so a client cannot loop.
- An anonymous visitor cannot tell a missing artifact, an active protected one and an artifact that is not servable (archived, expired, suspended or without a version, in any access mode, public included) apart: all of them go through sign-in. Only a public artifact that is servable is served directly.
- Without a `READ_SESSION_SECRET` of at least 32 characters, protected artifacts answer `503`; public ones keep working.
- Values are sealed per purpose, so a transaction cookie never validates as a read cookie, and claims are parsed with the strict `ReadClaims` and `ReadTransaction` schemas from `packages/contracts`.
- Expired handoffs and read sessions are deleted by the maintenance job in bounded batches (500 rows of each per run, like `pruneOperations`); deleting an account, an artifact or a dashboard session cascades to its read sessions.

### The viewer

A visitor who opens an artifact's page in the browser's own tab lands in the viewer at `app.portifact.com/view/<id>` (plan section 8, "Flujo", decision of 2026-11-08): a slim Portifact bar (the mark, the owner's settings or a report link, the comments toggle, the dashboard or sign-in), the page in a sandboxed iframe on the artifact origin under a caption (the artifact's own link with "Copy link", so its origin is always in sight, its name, its version and "Published by a user, not by Portifact") and the comments sidebar. The code is in `apps/content/src/viewer.ts`, `packages/domain/src/viewer.ts`, `apps/app/src/app-host.ts` (`VIEWER_ROUTE`), the viewer route in `apps/app/src/api/review.ts`, `packages/services/src/viewer.ts` and `apps/web/src/dashboard/screens/viewer.tsx`. The frame is the review frame of "Review mode" below, with every rule there; this section covers what is new.

1. **When the content Worker redirects.** Only a `GET` with `Sec-Fetch-Mode: navigate` and `Sec-Fetch-Dest: document` (`isTopLevelVisit`), whatever its `Sec-Fetch-Site`, to a page (a site's `text/html` file or a document's rendered page) of an artifact whose owner left the bar on, after the request was authorized and passed the traffic and budget checks, outside review mode, answers `303` to `<app>/view/<id>?path=<path and query>` with `no-store`, `no-referrer`, `nosniff` and `noindex`; it charges one request and no bytes, and for a protected artifact the read session's opening is logged as for the page. Everything else is served as before: frames (the viewer's own and other sites' embeds are `iframe`), subresources, `HEAD`, other methods, images, downloads and other files that are not pages, missing files (404), the reserved paths under `/__portifact/`, clients without fetch metadata, and every request of an artifact with the bar off, and every request that carries this browser's opt-out (item 13). Every answer of the content Worker sends `Vary: Sec-Fetch-Dest, Sec-Fetch-Mode, Sec-Fetch-Site`, because the redirect, review mode and session use all depend on them.
2. **Nothing leaks before access is checked.** The redirect is decided in `serveFile`, after authorization, so an anonymous visitor of a protected, missing or unavailable artifact goes through sign-in exactly as before ("Entry to protected artifacts") and never learns whether the bar is on. After the read handoff, the reader's next top-level visit of a page is the redirect; the viewer then reads through its own review session, so the read session only carried them through sign-in.
3. **No loops.** The viewer's frame navigations are `iframe` and never redirected. A review tab is served in review mode before the redirect is considered (the tab cookie is honored for top-level documents), so it keeps showing the artifact; the tab link and `/__portifact/review/end` are reserved paths. The app never navigates the top level to an artifact origin except through the review tab link. A planted frame cookie on a top-level visit is cleared as before (`strayFrameCookie`) whatever the answer is, redirect included.
4. **The path is untrusted at both ends.** `viewerPath` (`packages/domain/src/viewer.ts`) accepts only a path on the artifact origin: it must start with `/`, holds no backslash or control character, is parsed against a stand-in origin (so `//host`, `/\host`, tabs and newlines cannot leave it), refuses any first segment that decodes to `__portifact` in any case, and is at most 2,048 characters once normalized. The content Worker applies it when it builds the redirect and serves the page itself when the path does not fit, so the visitor never lands on a different page; the viewer applies it again to `?path=`, which anyone can write, and falls back to `/`. The fragment never reaches the server: the browser keeps it across the `303` and the viewer passes at most 1,024 characters of it, without control characters (`viewerHash`), to the frame. The review exchange accepts the same path as a single `to` parameter and its check page redirects there (`returnPath` in `apps/content/src/viewer.ts`), so review starts on the linked page; a missing, repeated or refused `to` starts at `/`. A link someone crafts can only open another page of the same artifact.
5. **The viewer page.** `/view/<id>` (an ID that is not an artifact ID answers 404) serves the dashboard bundle with or without a session, with the dashboard's policy narrowed to this artifact (`viewerCsp`: `frame-ancestors 'none'`, and `frame-src` naming only `https://<id>.portifact.dev` and the Turnstile origin, so the frame can never be navigated to another artifact or site), `X-Frame-Options: DENY`, `no-store`, `no-referrer` and `X-Robots-Tag: noindex`. It holds no data of its own: what the bar shows comes from `GET /api/v1/artifacts/:id/viewer` (`ViewerInfo`: name, type, origin, version number, access mode, comment mode and the visitor's role, never threads, readers or emails), a dashboard helper with no state, so it has no CLI command or MCP tool. It refuses bearer tokens and anything that is not `Sec-Fetch-Site: same-origin` (failing closed without fetch metadata), takes the visitor from the session cookie when there is one (an account that has not accepted the current terms counts as none) and applies `checkReadAccess`; without a session it answers only for a public artifact that is servable, and 404 exactly like a missing artifact for everything else. It answers without a session, so it is limited per IP (`VIEWER_LOOKUP_LIMIT`, 300 per 10 minutes, in the D1 counters). The old `/review/<id>` answers `301` to `/view/<id>`. The viewer's links to the dashboard and the dashboard's links to the viewer ("Review and comment" on the artifact page, the list and the publish result) are full page loads, so each page keeps its own policy (client-side navigation would keep the first page's).
6. **Signed-in visitors** get a review code (`POST /api/v1/artifacts/:id/review`: dashboard session only, exact `Origin`, `checkReadAccess`) and the frame redeems it, so every reader who can open the artifact, owner or not, public or protected, gets the bridge, the highlights and the sidebar. Selecting text or picking an element in a site only opens the sidebar and offers a comment, which is written and confirmed in the sidebar as before. Any site can make a signed-in browser load the viewer (a popup reloading `/view/<id>` of the attacker's public artifact sends the session cookie every time), so codes are bounded in ways that one artifact cannot spend for the others: `REVIEW_START_LIMIT` (60 per 10 minutes) counts per account and artifact, and an account keeps at most `REVIEW_SESSION.openCodesPerUser` (10) unredeemed codes, issuing another deletes the oldest in the same batch (`issueReviewHandoff`). A flood can therefore only expire a code that was not redeemed within the moment it took to load the frame; the viewer then offers to reload. Where the frame keeps no session (the check page reports `unavailable`) or no code can be issued, a public artifact's frame shows the page itself without review tools and a protected one keeps the notice; both offer "Open without the Portifact bar" (item 13), and where the frame keeps no session, the review tab too, which also opens on the linked page.
7. **Anonymous visitors** reach the viewer only for public artifacts. The frame loads the page itself (no code, no session, no bridge), so nothing names them, the content Worker logs nothing and the page's subresources stay ordinary public requests. Threads are for signed-in readers only (plan section 8, "Permisos": anonymous visitors get public content only), so the sidebar, shown while comments are not off, holds only "Sign in to comment", which goes to `/login?next=/view/<id>?path=…`; the login page accepts `next` for `/view/<artifact-id>`. A protected artifact answers 404 to the viewer's lookup, and the viewer sends the visitor to sign in with the same `next`.
8. **Comment modes.** While comments are off, readers get no sidebar and no thread requests (the bar stays); the owner keeps the sidebar with the switch to turn them on. Locked is read-only as before. The owner sees the moderation actions; every permission still comes from the API.
9. **The owner's opt-out.** The bar is part of the access policy (`artifacts.bar`, on by default for new and existing artifacts, `PATCH /api/v1/artifacts/:id/access` with `bar`, scope `artifacts:share`, the MCP tool `set_portifact_bar` with the same scope, `portifact access bar <id> on|off` and the dashboard's access settings). Turning it on or off does not bump the policy generation: it changes neither who may read nor what other sites may load, and a bump would end every reader's read and review sessions for nothing. It is still conditioned on the generation the request read, so it conflicts with a concurrent access change, and the content Worker reads `bar` on every request, so it applies at once. With the bar off, every request is answered exactly as before the viewer existed.
10. **Embeds and crawlers.** Other sites' frames are `iframe`, so an embeddable public artifact is still served under `frame-ancestors *` and `cross-origin` CORP, and a non-embeddable one is still refused there by its `frame-ancestors`. Crawlers do not send fetch metadata, so they get the artifact itself on its own origin, where `indexable` keeps deciding `noindex`; the viewer is always `noindex` and carries no `rel="canonical"` (Google treats `noindex` with a canonical as conflicting signals, and the artifact's own URL is the only one ever indexed). A browser that does not send fetch metadata also gets the artifact itself.
11. **Links that leave the frame.** The frame's sandbox stays `allow-scripts allow-same-origin allow-forms allow-popups`, without any top navigation, so `target="_top"` and `target="_parent"` links and form posts inside a site are blocked by the browser, as in review mode; pages that rely on them, full-screen apps and pages that must be embedded elsewhere are what the owner's opt-out is for. Links that open a new window (`target="_blank"`, `window.open`) are allowed; the new window's top-level visit to a page of the artifact is redirected to the viewer like any other. Content responses that are not `GET` still answer 405, so a form post never reaches the redirect. A link inside the frame to another site or another artifact that does not open a new window is refused by the viewer's `frame-src` (Chromium shows an error page and the watchdog says the frame stopped answering from the artifact; Firefox keeps the page).
12. **Clickjacking and isolation.** The viewer, like every app page, is never framed (`frame-ancestors 'none'` and `X-Frame-Options: DENY`). The artifact never gets more than in review mode: no tokens, emails or bodies, the same message rules, and review responses keep `frame-ancestors 'self'` plus the app origin.
13. **The bar is not a security control.** Owners turn it off for everyone, and any visitor can leave it: "Open without the Portifact bar" (offered when the viewer cannot show the artifact with its tools) is `https://<id>.portifact.dev/__portifact/raw?to=<path>`, which only a top-level navigation (`isTopLevelVisit`) may use; it sets `__Host-pf_nobar=1` (`Secure; HttpOnly; SameSite=Lax; Path=/`, host-only, one hour) and continues to the page through `viewerPath`, and top-level visits that carry exactly that value get the artifact itself (through the read handoff for a protected one). The cookie grants nothing and is matched exactly like every Portifact cookie, so a sibling cannot set it (a `__Host-` name) and anything else (another value, a lowercase look-alike, two values) still opens the viewer; a site that sends a visitor to the path can only show them the artifact without the bar. Nothing that keeps users safe may depend on the bar being shown.
14. **Phishing through the viewer.** The viewer puts untrusted content under `app.portifact.com`, next to Portifact's real mark, which a hostile artifact can use: a name like "Portifact: session expired" over a page with a code form, under an address bar that reads `app.portifact.com/view/…`. The viewer limits what that buys: the artifact's name is never in the bar beside the mark but in the caption attached to the frame, set as user content (normal weight, in quotes), next to the artifact's own link (`https://<id>.portifact.dev/…`) and a strong "Published by a user, not by Portifact" badge; the frame cannot reach or restyle the bar, the caption or the sidebar; every Portifact form (sign-in, comments) lives outside the frame, and no Portifact page asks for credentials inside an artifact. What a page draws inside its frame can still imitate anything, as on its own origin; the human check, the report link in the bar and suspensions are the remaining controls, and the risk is accepted with the bar's default on (pending the maintainer's confirmation).

### Review mode

The viewer at `app.portifact.com/view/<id>` (see "The viewer" above) shows one pinned version of the artifact to a signed-in visitor in a sandboxed iframe on the artifact origin, with the bridge (`packages/bridge`) injected; comments are written and confirmed in the viewer's sidebar and posted through the annotations API. The code is in `apps/app/src/api/review.ts`, `apps/content/src/review.ts`, `apps/content/src/inject.ts`, `packages/services/src/review-access.ts` and `apps/web/src/dashboard/screens/viewer.tsx`, following [decision 0002](decisions/0002-review-mode-cookies.md).

1. The viewer calls `POST /api/v1/artifacts/:id/review`, which accepts only the dashboard session (exact `Origin`, `Sec-Fetch-Site: same-origin`; bearer tokens get 403), is limited per account and artifact (`REVIEW_START_LIMIT`, 60 per 10 minutes) with at most 10 unredeemed codes per account (see "The viewer") and applies the same `checkReadAccess` as reading the artifact, so a missing and a forbidden artifact both answer 404. It stores a one-use code (`review_handoffs`: only its SHA-256, the user, the current version, the dashboard session's ID and the policy generation, valid 60 seconds) and returns the iframe URL on the artifact origin, built from the validated ID, and the session tag (`reviewSessionTag`: 16 bytes of a domain-separated SHA-256 of the code, which reveals neither the code nor the session ID).
2. `/__portifact/review?code=…` redeems it only for a cross-site iframe navigation (`Sec-Fetch-Site: cross-site`, `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: iframe`), which stops a top-level visit and a sibling artifact's direct request. It does not prove that the viewer started the navigation: an artifact framed in the viewer can open a frame to a redirector on another site that lands on the exchange with a code of its own (for an artifact it can read), and that arrives with the same metadata, so the attacker's review session replaces the visitor's in the viewer's partition. That is why the claims carry the session tag, the bridge script gets it as `data-session-tag` and echoes it in `ready`, and the viewer refuses a `ready` whose tag is not the one it got with its code: it gives that page no nonce, turns the review tools off and offers to reload the review, which redeems a new code of the visitor's. Comments are not affected either way, because they are posted with the dashboard session. One guarded update marks the code used while the dashboard session is live, and the `review_sessions` row is inserted only if it happened. It sets `__Host-pf_review` (`Secure; HttpOnly; SameSite=None; Partitioned`, no `Domain`, 4 hours) with HMAC-signed claims (session, artifact, pinned version, user, policy generation, session tag, 60-second claims expiry, session expiry), sealed with `READ_SESSION_SECRET` under its own purpose, and redirects to `/__portifact/review/check`.
3. The check page redirects to `/` when the cookie came back. When it did not (the browser blocks partitioned cookies in frames), it answers a page whose one nonce-allowed script posts a fixed `status: unavailable` message to the viewer's exact origin, and the viewer offers general comments only.
4. The review cookie is honored only for `Sec-Fetch-Site: same-origin` or `cross-site` with `Sec-Fetch-Mode: navigate`, never for `Sec-Fetch-Dest: document` (the viewer's frame navigations are always `iframe`), matched exactly and case-sensitively, and requires exactly one value. A frame cookie on a top-level document navigation was planted, and every such response clears it (see "The review tab"). Siblings are `same-site` and get the normal public or sign-in answer. Claims are trusted without D1 only while unexpired and while the artifact's policy generation is unchanged; then `refreshReviewSession` rechecks the session, the dashboard session it came from and the access policy. The pinned version must still be current. Otherwise the response is a status page (`ended`) that clears the cookie with the same partition attributes, so revocation, archiving, signing out or a new version ends review within 60 seconds or at once.
5. Review responses serve the pinned version with `Cross-Origin-Resource-Policy: same-origin`, `frame-ancestors 'self'` plus the app origin (never `*`, even for an embeddable public artifact) and `Cache-Control: private, no-store`. HTML is rewritten on the way out with `<script src="/__portifact/bridge.js?v=<bundle version>">` appended; the stored bytes and downloads never change, and rewritten pages carry no `ETag` or ranges. For a page rendered by Portifact, the document's CSP `<meta>` is dropped and the header carries the same policy plus `script-src 'nonce-…'` for the bridge only. A site's own CSP is left as it is; if it blocks the bridge, the viewer stops waiting after 5 seconds and offers general comments.

The bridge and the viewer exchange `postMessage` only with each other's exact origin and window, within size limits (16 KiB from the bridge, 2 MiB of at most 200 markers to it) and strict schemas (`packages/bridge/src/protocol.ts`). The viewer gives each page load a fresh instance nonce after its `ready` message and drops every later message without it. The artifact's own scripts share the bridge's window and can overhear the nonce, so every bridge message stays untrusted data: a selection or a picked element only fills in a comment that the reader writes and confirms, and the server takes the author from the session. The frame receives targets, short labels and marker names, never bodies, author names, emails or tokens. Its sandbox is `allow-scripts allow-same-origin allow-forms allow-popups`, without top navigation. The bridge draws in a closed shadow root marked `data-portifact-ignore` and reads no form values, cookies or storage. The closed shadow root keeps the page's styles out of the overlay, not its scripts: they run in the same window and can patch the DOM APIs the bridge uses, hide or fake markers and send anything the bridge sends. The dashboard's CSP allows `frame-src https://*.portifact.dev` and keeps `frame-ancestors 'none'`.

What the frame can and cannot do to the viewer, given that the page can forge any bridge message:

- It cannot open or retarget a comment. The viewer accepts an `element` only while the reader is picking (the bridge sends `element` before `pick-ended`, which ends the wait), and ignores `selection` and `element` while a comment is open. The composer keeps the target it opened with. A forged selection only offers a comment.
- It sees only what the current page needs: markers for the threads whose target is on the page the bridge reports (at most 200), with targets and labels.
- `resolved` and `activate` count only for the markers the viewer last sent to that page, and only change where markers are shown or which thread is focused.
- `status` (`ended`, `failed`, `unavailable`) has no nonce because the content Worker's status pages send it, so any page of the artifact can forge it. It only changes the frame's notice and turns the review tools off; the viewer then refetches the threads, and whether the reader can comment, the threads and their state always come from the API. A forged status is a denial of service of the review tools, which a hostile artifact can cause anyway by not running the bridge.
- After every load of the frame the viewer must hear from the artifact's origin within 5 seconds: the new page's `ready`, or a `pong` to the `ping` it sends with the current nonce. Otherwise it warns that the frame stopped answering from the artifact, says not to trust what it shows, and turns the review tools off. A page can navigate its own frame to another artifact (a look-alike, or a file without the bridge); that navigation is `same-site`, so the review cookie is not honored there and the other artifact gets its public or sign-in answer. A bounce through a redirector on another site, which would arrive as the `cross-site` navigation the review cookie honors, is refused by the viewer's `frame-src https://*.portifact.dev` (Chromium shows an error page, Firefox keeps the page; `e2e/tests/review.spec.ts` checks both), so a page cannot make another artifact render in review mode inside this viewer. A nested frame is not covered by the viewer's `frame-src`, which is why planting a session (above) works, but a review response's `frame-ancestors` keeps it from rendering there.

Expired review codes and sessions are deleted by the maintenance job in bounded batches, like read sessions.

#### The review tab

Where the frame cannot run review mode (the check page reports `unavailable`, which Firefox with all third-party cookies blocked and WebKit on Linux do, or the bridge never answers), the viewer offers the fallback from decision 0002: the artifact in a top-level review tab. Comments are still written, confirmed and posted only in the viewer, as general comments; the tab has no bridge and no channel back to the viewer.

A hostile artifact in the viewer's frame can force this offer, by forging `status: unavailable` or by staying silent. The tab it leads to is the artifact itself, an untrusted page on the artifact origin that may imitate Portifact's UI (a fake sign-in, a fake comment box). The offer says so: the tab shows the artifact, written by its author, not Portifact, so nothing should be signed in to or entered there. No credential, session or comment form of Portifact ever lives on the artifact origin.

1. "Prepare a review tab" calls `POST /api/v1/artifacts/:id/review/tab`, with every check of the review code route (dashboard session only, exact `Origin`, `Sec-Fetch-Site: same-origin`, the same per-account limit and `checkReadAccess`). It stores a code like a review code with `kind = 'tab'` (`review_handoffs.kind`), and redemption is conditioned on the kind, so a frame code never opens a tab session and a tab code never opens a frame session.
2. The viewer shows the URL as a link (`target="_blank" rel="noopener" referrerpolicy="origin"`) and withdraws it 10 seconds before the code expires or once it is clicked. `noopener` keeps the tab from reaching or navigating the viewer (reverse tabnabbing); `referrerpolicy="origin"` overrides the dashboard's `no-referrer` for this link only, so the artifact origin receives just `https://app.portifact.com` as `Referer`. The link is a second click rather than `window.open` after the API call, which popup blockers stop and which would keep an opener or lose the referrer.
3. `/__portifact/review/tab?code=…` redeems the code only for a top-level cross-site navigation (`Sec-Fetch-Site: cross-site`, `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`) whose `Referer` origin is exactly the app origin. An artifact, in the viewer's frame, a popup or a tab of its own, starts navigations with its own origin as referrer (or none, and redirects keep the initiator's referrer), so it cannot redeem a tab code of its own in a visitor's browser, directly (`same-site`) or bounced through another site (`e2e/tests/review-tab.spec.ts`). The app's pages are the dashboard's own and never redirect to an artifact origin on input. A browser that strips cross-site referrers entirely cannot open review tabs; the viewer still offers general comments. A planted tab session would in any case only show the visitor the artifact's current version through an account that may already read it, and could post nothing. One guarded update marks the code used while the dashboard session is live, as for frame codes.
4. It sets `__Host-pf_review_tab` (`Secure; HttpOnly; SameSite=Lax; Path=/`, no `Domain`, no `Partitioned`, 15 minutes, `REVIEW_SESSION.tabSessionTtlSeconds`) with the same claims as the review cookie sealed under their own purpose (`pf_review_tab`), so neither cookie's value validates as the other, and redirects through `/__portifact/review/tab/check` to `/`. `Lax` keeps it out of the viewer's cross-site frame and out of every other site's subresource requests.
5. The tab cookie is honored for `Sec-Fetch-Site: same-origin` requests and for top-level navigations (`Sec-Fetch-Mode: navigate` with `Sec-Fetch-Dest: document`, from any site), and never without fetch metadata. Unlike the frame's cookie it lands in the artifact's own partition, so later visits in that browser carry it until the session ends; honoring their document too keeps the banner on every page that is served in review mode, instead of a normal page whose subresources come back in review mode. A sibling artifact's subresource or frame request carries it as `same-site` and gets the normal answer, and its top-level navigation shows the visitor the page and lets the sibling read nothing. Claims, renewal, the version pin, `Cross-Origin-Resource-Policy: same-origin`, `frame-ancestors` and `no-store` are those of the frame session, so signing out, revocation, archiving or a new version end the tab within 60 seconds or at once, with a status page that clears the tab cookie.
6. HTML in the tab gets a banner instead of the bridge, at the start of the body (or the end of a page without a body tag): plain markup in a declarative shadow root, so the page's styles cannot restyle it and it needs no script. It says the tab is in review mode, that comments are written in the viewer and that it ends within 15 minutes, and links to `/__portifact/review/end`. Rendered documents keep their script-free policy. The page's scripts can hide or fake the banner, which is why the session is short and the viewer also says how long it lasts and how to end it.
7. `/__portifact/review/end` ends the session only for a `GET` navigation from the artifact itself (`Sec-Fetch-Site: same-origin`, `Sec-Fetch-Mode: navigate`), so another site or a sibling cannot end a visitor's review: it deletes the `review_sessions` row named in the claims (`endReviewSession`) and clears the cookie, so the next request is a normal visit and a copied cookie is refused when its claims next need renewing. Ending twice or without a session only clears the cookie. The artifact's own scripts can follow the link too, which only ends review.
8. A sibling can plant a frame session in the artifact's own partition: it frames a redirector on another site that forwards to the artifact's exchange with a frame code of its own (for any artifact its author can read). The exchange sees the same `cross-site`, `navigate`, `iframe` request as the viewer's and redeems it, and because that frame sits under the `portifact.dev` top-level site, the partitioned `__Host-pf_review` lands in the partition of the artifact's top-level visits (Firefox keeps it even with all third-party cookies blocked, since the frame is first-party). Three rules keep it from reaching a visitor's top-level pages or review tab: the frame cookie is never honored for `Sec-Fetch-Dest: document`; every response to a top-level document navigation (`navigate` and `document`, including `/__portifact/review/end`) that carries a `__Host-pf_review` clears it with `Partitioned` (`strayFrameCookie`), before the page's same-origin subresources can carry it, which never touches a genuine frame cookie because that lives in the viewer's partition; and the tab cookie is tried before the frame cookie, so a frame cookie that does reach a request never outranks the visitor's tab. `e2e/tests/review-tab.spec.ts` reproduces the plant.
9. The app sends `Referrer-Policy: no-referrer` on every response (the global middleware in `apps/app/src/app-host.ts`), so app URLs never leave as `Referer`; the review tab link alone overrides it with `referrerpolicy="origin"`.

### Identity and the authorization server

`app.portifact.com` runs Better Auth in the `portifact-app` Worker as the only identity provider and OAuth authorization server ([decision 0001](decisions/0001-oauth-server.md)). The code is in `apps/app/src/auth`.

- The session cookie is `__Host-pf.session_token` with `Secure; HttpOnly; SameSite=Lax; Path=/` and no `Domain`. Every Better Auth cookie uses the `__Host-pf.` prefix, set through `cookiePrefix` with `useSecureCookies: false` so Better Auth does not add `__Secure-` in front.
- Only the endpoints Portifact uses are reachable under `/api/auth`; the allowlist in `apps/app/src/auth/routes.ts` answers 404 for everything else, including password sign-up, admin and client management endpoints, OIDC userinfo, HTTP introspection and `/device/token` (which would issue first-party session tokens). Adding a Better Auth endpoint means adding it to the allowlist with a test.
- Browser endpoints (sign-in, sign-out, consent, device approval) require the exact `Origin` of the app on every `POST`. Client endpoints (token, revoke, registration, device code) never see cookies: the Worker strips them, so a registration or token request cannot act on a browser session.
- The legal pages (`/terms`, `/privacy`, `/acceptable-use`) are served on `portifact.com` only, with the same strict CSP, `no-cache`, `nosniff` and `X-Frame-Options: DENY`, and load no script.
- Every `/api/auth` response sends `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. The dashboard and the auth pages (`/login`, `/device`, `/consent`) send a strict CSP (`default-src 'none'`, same-origin scripts, styles, images and requests, `frame-ancestors 'none'`), `no-store` and `no-referrer`. They are served only on the app host; `portifact.com` answers 404 for them. The dashboard is served only at its routes and only with a valid session of an account that accepted the current terms; without one it redirects to `/login?next=...`, and `next` accepts only the device page and the dashboard routes.
- Google and GitHub accounts are keyed by the provider's stable ID. A provider sign-in joins the existing account with the same email only when the provider vouches for the email and the account's own email is verified (`requireLocalEmailVerified`); otherwise it is refused with `account_not_linked`. A provider that does not mark the email as verified cannot create an account either (`email_not_verified`), so every account's email is proven and a later email code or provider sign-in for that address always lands in the account of whoever controls it. Provider accounts are never unlinked from the web yet, and `/link-social` (linking a provider with a different email) stays off.
- Google and GitHub tokens are not stored: the account row keeps only the provider and its user ID.
- No account is created and no session is issued without the current terms accepted ([legal.md](legal.md)). The login page shows a notice above the methods and, when the user chooses one, posts the acceptance to `POST /api/auth/accept-terms` (exact `Origin`, limited per IP) before starting it; before sign-in it gets `__Host-pf_terms`, HMAC-signed with a key derived from `BETTER_AUTH_SECRET`, 30 minutes, cleared when a session is created. Better Auth hooks verify it when creating a user or a session; `terms_version` and `terms_accepted_at` are not writable from any request body. The dashboard, the `/api/v1` session lookup and `/read/<id>` treat a session of an account without the current version as no session.
- No account is created without a solved human check (Cloudflare Turnstile); see "Human check" below. Existing accounts sign in without one.
- Email codes are 6 digits, valid for 5 minutes, single use, three attempts, and stored as hashes. Sending is limited per IP, per address (one per minute, five per hour) and by a global daily budget, in D1 counters keyed by an HMAC of the address, never the address itself. The answer is the same whether or not an account exists. Only sign-in codes can be requested.
- After those limits, the auth route asks `checkSignInEmail` (`packages/services/src/email.ts`): a suppressed address answers `403 email_suppressed` with an explanation (the login page shows it), and once the cycle's sign-in emails are spent (`SIGN_IN_EMAILS_PER_CYCLE`, the 20,000-email admission limit minus a reserve of 100 for budget alerts, `packages/domain/src/email.ts`) every send answers `503 capacity_unavailable`. Every email sent (codes and budget alerts) is counted in `email_counters`, one row per UTC day without recipient data, which the budget run reads as its `emails` metric. The suppression check runs after the rate limits, so it cannot test many addresses quickly, and it reveals only that mail to the address failed, never whether an account exists.
- Suppressions (`email_suppressions`) are keyed by a SHA-256 of the normalized address with a fixed prefix, unkeyed so the operator tool can look an address up without the Worker's secrets, plus a masked hint (`a***@example.com`); the full address is never stored or logged. They come from two sources: Cloudflare Email Service events (`message.bounced` with `bounce.type` `hard`, and every `message.complained`) delivered to the `portifact-email-events` queue and recorded by the jobs Worker, and a send the `EMAIL` binding refuses with `E_RECIPIENT_SUPPRESSED` because Cloudflare's own list holds the address (`provider`). Better Auth swallows delivery errors so the answer stays the same, which means a `provider` refusal shows its explanation from the next request on. They last 30 days (hard bounce), 180 days (complaint) or 7 days (provider), the stronger reason wins on a repeat, and the maintenance job prunes them. Cloudflare keeps its own list independently, so lifting ours does not lift theirs (see [operations.md](operations.md)). Code guesses, client registrations and device codes are also limited per IP.
- The device page binds a code to the first signed-in user who opens it; nobody else can approve it. A device request cannot name the user who approves it (`user_id` is refused).
- The CLI (`packages/cli`) signs in with the device grant as `portifact-cli`, requesting every product scope plus `offline_access` for `https://app.portifact.com/api/v1`. It keeps tokens per server origin in the OS credential store (`Bun.secrets`) or, when there is none, in a `credentials.json` written `0600` in a `0700` directory with a warning. It never prints tokens or the device code, does not follow redirects with tokens, opens or shows only verification pages on the server's own origin, and accepts a `PORTIFACT_APP_ORIGIN` override only for https or loopback http. `logout` revokes before deleting and keeps the credentials if the server cannot answer. A refresh that fails with `invalid_grant` deletes them, unless another process already stored newer ones.
- Access tokens are opaque and checked against D1 on every request. A resource accepts a token only if its audience contains that exact resource: CLI tokens work only at `/api/v1`, MCP tokens only at `/mcp`. The seeded CLI client is linked to the API only.

### Human check

Account creation and an account's first comments on other people's artifacts need a solved Cloudflare Turnstile challenge (plan section 13). Turnstile tokens are verified only on the server, with siteverify and `TURNSTILE_SECRET_KEY`, in `apps/app/src/turnstile.ts`; the page only renders the widget with the public `TURNSTILE_SITE_KEY`, which the app host puts in a `<meta>` of the login page and the dashboard (`withSiteKey` in `apps/app/src/app-host.ts`). Those two pages add exactly `https://challenges.cloudflare.com` to `script-src` and `frame-src`; no other page does. How the widget looks changes nothing on the server: an invisible challenge yields the same single-use token, verified the same way.

- **Fail closed.** Without the secret, or when siteverify fails, times out, answers an error or rejects the secret, every check is `unavailable` and nothing that needs one goes through: `/api/auth/verify-human` and the comment answer `503 capacity_unavailable`, and a sign-up without a valid check cookie is refused. The Worker logs that the secret is missing or rejected, never a token or the secret. There is no test-mode bypass in production code: tests and local development use Cloudflare's documented test keys, and the app tests replace the siteverify transport (`AuthDeps.siteverify`).
- **Sign-up.** The login page renders the widget with `appearance: "interaction-only"` from the moment it shows the methods (`apps/web/src/auth/human-gate.ts`): most visitors never see it and hold a token before they choose a method. Only when Cloudflare asks for an interaction does the challenge appear, below the methods, with an explanation and an announcement; a sign-in waits for it while it is visible, waits at most `HUMAN_CHECK_WAIT_MS` (8 seconds) for an invisible one still running, and goes on without a token when the challenge failed, so an existing account is never blocked by the widget. A token is used once; the next sign-in renders a fresh challenge. The page posts the token to `POST /api/auth/verify-human` (in the auth allowlist, exact `Origin`, 30 per IP per 10 minutes) after recording the acceptance and before the sign-in method. On success the Worker sets `__Host-pf_human` (`Secure; HttpOnly; SameSite=Lax; Path=/`, 30 minutes): a random 24-byte nonce and the time, HMAC-signed with a key derived from `BETTER_AUTH_SECRET` under its own purpose. Better Auth's `user.create.before` hook (`apps/app/src/auth/human.ts`), after the terms check, requires a valid cookie and claims its nonce once in the D1 counters (`human:<nonce>`), so one solved challenge creates at most one account whatever the method (Google, GitHub or email code); `session.create.after` clears the cookie. Refusals are `APIError` `FORBIDDEN` with code `human_verification_required`: the email-code sign-in answers 403 and provider callbacks redirect to `/login?error=human_verification_required`. Existing accounts never need the cookie.
- **First comments.** `createAnnotationThread` and `replyToAnnotationThread` take a `HumanCheck` (the token the request carried, if any, and a verifier bound to siteverify and the caller's `CF-Connecting-IP`) that every adapter builds the same way: the API reads the optional `turnstileToken` of the body, MCP never has one. When the caller is a participant (never the owner) with fewer than `ANNOTATION_LIMITS.humanCheckedComments` (3) `thread_created` or `message_created` events on artifacts it does not own, a comment without a token answers `403 human_verification_required` and a failed token the same with another message. The check runs after the permission, version and limit checks, so a refused request never spends a token, and a write that loses its claim and runs its checks again reuses the first verdict instead of verifying the single-use token twice. CLI and MCP callers cannot show the challenge, so those first comments must come from the viewer; the error message says so. Events go with their artifact, so deleting artifacts can make an account need the check again. The token is not part of the idempotency hash, and a refused comment's answer is stored for its key, so the viewer retries with a new key and a fresh token.

### Access control

- The API under `app.portifact.com/api/v1` accepts bearer tokens issued for the API resource and the dashboard's session cookie, checks one scope per route (`artifacts:read`, `artifacts:write`, `artifacts:share` or `artifacts:delete`) and takes the acting user from the token or session (`apps/app/src/api/access.ts`). A bearer token always wins over a cookie. A session holds every product scope (`SESSION_SCOPES`) and is honored only with `Sec-Fetch-Site: same-origin`, failing closed without fetch metadata, and, on every mutation, the exact app `Origin`; anything else answers 403. An unknown or expired session answers 401 like a request without credentials. Another account's artifact or upload answers 404 exactly like a missing one. Prepare requires an `Idempotency-Key`; a retry with the same key and body replays the stored response, and the same key with another body is refused. Access changes (`PATCH /api/v1/artifacts/:id/access`, scope `artifacts:share`) bump `policyGeneration` in the same transaction as the reader writes; those writes are conditioned on the generation the request read and the guarded update runs last, so of two concurrent changes exactly one applies. Making an artifact `public` is refused during the account's first 7 days; narrowing access is always allowed, also on archived artifacts. A reader list holds at most 500 addresses.
- The account endpoints under `/api/v1/account` (`apps/app/src/api/account.ts`) list the signed-in user's browser sessions and connected apps, sign out the other sessions and disconnect an app. They accept only the dashboard session, with the same fetch-metadata and `Origin` checks as above; a bearer token is refused with 403 even with every product scope, because no scope covers credential management yet. Every query is keyed by the session's user, so another user's grant answers 404 like a missing one. Responses never carry session or OAuth tokens, nor IP addresses. Signing out other sessions goes through Better Auth (`revokeOtherSessions`) and never deletes `sessions` rows directly: its session hooks revoke the access tokens issued through those sessions, which a direct delete would leave active (the foreign key only sets their `session_id` to null). As after signing out, those apps recover by refreshing, so only disconnecting ends an app's access: that deletes its access and refresh tokens and the consent for that user in one batch.
- The MCP endpoint `app.portifact.com/mcp` accepts only bearer tokens issued for the MCP resource. Before the SDK sees a request, it runs the same check as the API with the scope of the tool being called (`artifacts:read` for discovery and listing tools), so a missing scope answers 403 `insufficient_scope` with that scope for step-up; each tool also declares the scope to the SDK as a second check. Tools call the same services as the API and return the same errors, the acting user comes from the token, and the raw token is not passed to the tools. Inline publishing accepts at most 256 KiB of well-formed UTF-8 and the Worker writes the bytes to R2 itself, then commits through the same verification; `delete_artifact` needs `confirm` equal to the artifact ID. The annotation tools (`apps/app/src/mcp/annotation-tools.ts`) carry the annotation scope of their API route, call the same services and validate with the same contracts; `create_annotation` and `reply_annotation` require an `idempotencyKey` like the routes' `Idempotency-Key`, `delete_thread` needs `confirm` equal to the thread ID and `moderate_annotation` with `delete` needs `confirm` equal to the message ID. Their descriptions and the server instructions tell agents that bodies, quotes and author names are untrusted data. Request bodies above 1 MiB are refused with 413.
- Annotations live under `/api/v1/artifacts/:id/annotations` (`apps/app/src/api/annotations.ts`) with `annotations:read` for listing, reading and export, `annotations:write` for starting threads, replying, editing, deleting one's own messages and resolving, and `annotations:moderate` for the mode (`PUT .../annotations/mode`), hiding, unhiding and deleting other people's messages and deleting threads. The rules are in `packages/domain/src/annotations.ts`: only the owner and accounts the access policy admits take part, an account without access gets 404 like a missing artifact, visitors lose the threads when the artifact is archived or suspended and see only the current version's threads (older ones are the owner's history), `locked` lets visitors read and delete their own messages only, and the owner hides or deletes but never edits other people's words. The author always comes from the token or session; request bodies are strict, so an `authorId` field is refused. Every write in `packages/services/src/annotations.ts` claims its change with an `annotation_events` row inserted under the same checks evaluated inside the batch (artifact state and mode, current version, the visitor's policy generation, the author and artifact rate limits and the row's previous state), and the rest of the batch runs only if that row, found by a per-request `write_id`, exists; so a revocation, a new version, a lock or a concurrent edit that lands first wins, and a retry cannot apply effects twice. Starting a thread or replying needs an `Idempotency-Key`; edits carry the message `revision`. The owner's 5,000 messages and 50 MB, and the 200 messages per thread, are CHECK constraints kept by the triggers in `0007_annotation_usage_triggers.sql`. Bodies are plain text, at most 4,000 code points and 8 KiB, with control characters refused, and requests that create content are capped at 16 KiB. Annotation bodies, quotes and author names are untrusted data: clients render them escaped, exports start with a notice saying so, the Markdown export puts bodies and quotes in fences longer than any backtick run they hold and is served as an attachment with `nosniff`, and responses show other people's names and avatars, never their email.
- Every request to `portifact.dev` follows this order: rate limit, resolve artifact, check state and dates, authenticate, authorize the version, check traffic quota, resolve the path, and only then read bytes from cache or R2.
- The traffic quota (`TRAFFIC_LIMITS`: 1 million requests and 25 GB per account per UTC calendar month) is checked after authorization, so a visitor who cannot open an artifact never learns whether its owner is over quota, and anonymous refusals charge the owner nothing. Over quota, every artifact of that account answers 429 with `Portifact-Error: traffic_exceeded` and `Retry-After` until the next month, in every access mode and in review mode; other accounts are unaffected. The counter (`traffic_counters`) is read in the same lookup as the artifact, and the content Worker adds what it served in memory per isolate and writes it once per 5-second window through `waitUntil` (`apps/content/src/traffic.ts`), so delivery does no D1 write per request. The quota can therefore be overshot by what isolates serve within one window, and a write lost with an evicted isolate is not counted; both are accepted, since per-IP rate limiting in front of the Worker is the abuse control and the quota is a cost cap.
- While budget protection tightens traffic, a per-IP limit also applies after the traffic quota check and before any bytes are read, so a refused request charges no traffic (`apps/content/src/budget.ts`); it is counted exactly per IP by the `TrafficLimiter` Durable Object, answers `429` with `Retry-After` until the visitor's window ends and fails open, logging the failure.
- Every file is authorized, including CSS, JS, images, source maps and downloads.
- Cached bytes are looked up only after authorization and are keyed by artifact, version and path. No identity or access decision is cached in a shared cache.
- The acting user always comes from the session or token, never from input. An opaque ID never replaces an authorization check.
- Token scopes allow a class of action; ownership or permission on the specific artifact is always checked as well.
- R2 has no public bucket, no `r2.dev` and no custom public domain. Presigned upload URLs are bound to one object key, size, checksum and a short expiry. The `portifact-app` Worker signs them (`apps/app/src/api/presign.ts`) with an R2 token limited to that bucket: `content-length`, `host` and `x-amz-checksum-sha256` are signed headers, the key is `objects/<owner>/<sha256>`, and they expire after 15 minutes. Commit still verifies every pending object's size and SHA-256 in R2 before the version becomes current, so a client that skips the URL cannot publish other bytes. Only verified objects count as already stored; an object another open upload declared but never sent gets a new upload URL.
- Objects over 64 MiB, for a client that sends `multipart: true` at prepare, are uploaded with presigned multipart (`packages/services/src/multipart.ts`). The Worker opens the R2 multipart upload through the binding and signs one S3 UploadPart URL per part (`presignPart`), each binding the key, upload ID, part number, `content-length` and 15 minutes; parts are 16 MiB except the last. A part's SHA-256 is not signed because the server only knows the whole file's hash, so per-part integrity relies on the signed size and on the commit's rehash. The parts go to a staging key of the session (`uploads/<owner>/<session>/<sha256>`), never to the object's shared key: R2 does not check a whole-object checksum when it assembles parts, and assembling straight into `objects/<owner>/<sha256>` could overwrite bytes another publish already verified. The client reports each part's ETag (`POST /api/v1/publishes/:id/parts`, owner and open session only); the commit completes the upload with the reported ETags, streams the staged object through `crypto.DigestStream` (never buffered), refuses a wrong size or hash with `upload_incomplete` (opening a fresh upload for that object so the client can send it again), and only then copies it to the object's key with `sha256` set, so R2 checks it once more, and deletes the staging copy. A closed session (commit, abort, failure or expiry) writes an `abort_multipart` outbox job in the same batch, which aborts what was not completed and deletes the staging copies and rows; R2's default seven-day abort of incomplete uploads is the safety net for a prepare that failed before its batch. A client without the flag gets one PUT per object, as before.
- Downloads (`GET /api/v1/artifacts/:id/versions/:versionId/download`, MCP `get_download`) return presigned GET links signed by the same Worker and token (`presignGet` in `apps/app/src/api/presign.ts`): one object key each, `response-content-disposition=attachment`, valid 5 minutes, issued only after `getVersionDownload` in `packages/services/src/versions.ts` checked the caller. The owner may download published files and sources of any retained version. Anyone else gets only the published files of the current version of a `markdown` or `text` artifact that `checkReadAccess` admits right now; sources, previous versions and sites answer 404 exactly like a missing version. Version lists and manifests are owner-only. A link handed out before a revocation stays usable until it expires, so its lifetime is kept short.
- Manifests refuse any `.git` path segment, in any case and in the forms Windows resolves to it (`.git.`, `.git `, `git~1`; `isGitSegment` in `packages/domain/src/paths.ts`). `portifact pull` writes only into a folder it creates (refusing one that exists or lies inside a `.git` folder), validates every path again with the same rules before writing anything, refuses non-canonical paths and paths that leave the folder, writes with `wx`, checks each file's size and SHA-256, never sends the API token to storage, and removes the folder if the pull fails. `pull --source --git` (`packages/cli/src/history.ts`) also accepts a folder an earlier `--git` pull made, but only when it is a real directory (not a link) whose own `.git` folder is a directory (not a linked work tree), marked with the same artifact in `portifact.artifact`, on `main`, with Portifact's last commit and tag and no uncommitted changes. It writes objects only with git plumbing that runs no hooks and no filters (`hash-object --no-filters`, `update-index` on a separate index file, `commit-tree --no-gpg-sign`) and checks that git kept every path, updates the files with `read-tree -u -m`, which refuses to overwrite local changes or write through a link in the way, and moves the branch and creates the tags in one `update-ref --stdin` transaction, putting the files back if it fails.
- A rollback (`POST /api/v1/artifacts/:id/rollback`, MCP `rollback_artifact`) publishes a new version that references the retained version's objects. It changes only the current version and the expiry, never the access mode, readers or policy generation, so it cannot bring back access that was removed. It takes an `Idempotency-Key` (optional `idempotencyKey` on MCP) and the base version the client read.

### Comment visibility

Who sees which threads (plan section 8, decision of 2026-11-08 on comment visibility) is part of the access policy and is decided only by `commentScope` and `threadInScope` in `packages/domain/src/annotations.ts`, applied in `packages/services/src/annotations.ts`.

- **The setting.** `artifacts.comment_visibility` is `owner` (the default, also for artifacts that existed before) or `everyone`. With `owner`, a reader's scope is `own`: the threads they started and the threads the owner started, each with every reply in it, whoever wrote the reply. With `everyone`, the scope is `all`. The owner's scope is always `all`. It changes through `PATCH /api/v1/artifacts/:id/access` (`commentVisibility`), MCP `set_comment_visibility` and `portifact access comments` (`artifacts:share`), and does not move the policy generation: it never changes who can open the artifact, and every annotation request reads it again.
- **Exceptions.** `artifact_readers.comment_visibility` is null (inherit), `all` or `own`, set with `readerCommentVisibility` (`inherit` clears it), `portifact access reader-comments` or the menu beside each person in the dashboard's reader list, only for addresses already on the list (`invalid_input` otherwise; an addition and its exception can go in one change). It applies to the account whose verified email is that address, in every access mode: for `restricted` artifacts the list is also who may open it; for `authenticated` and `public` artifacts the list still exists (it is kept when the mode changes) and only serves the exceptions, and every other account follows the artifact's setting. An unverified address never matches. Removing a reader removes the exception; adding them again inherits.
- **Hidden means missing.** Listing, reading by ID, export and refresh never return a thread outside the caller's scope, and a thread or message ID outside it answers `not_found` with the same message as one that does not exist, for reads and for every write (reply, edit, delete one's own message, resolve). A reader therefore cannot reply in a thread they cannot see. Their own reply in a thread they can no longer see (written while the scope was wider) stays where it is, visible to whoever sees the thread, and they cannot edit or delete it until the owner widens the scope again; account deletion still erases it. A write that names a thread re-checks the scope inside its claimed batch (`scopeGuard`, the same rule on the live rows), so narrowing the visibility or dropping an exception wins over a reply or edit in flight.
- **Refresh cursors.** With the `own` scope, list pages, `removed` (deleted threads, found by the `thread_created` event that outlives them) and the cursor's upper bound only consider events of threads in scope, so another reader's activity never shows up as a removal or moves the cursor. `AnnotationPage.commentScope` tells the client which scope it holds; when it differs, the client starts again without a cursor, as for a change of mode or current version (`review/use-threads.ts`).
- **What follows.** Exports give the owner every thread and anyone else what they can see. Counts and markers in the viewer come from the threads the API returned. The artifact list's `activity` (open threads) is the owner's own view. The access log is unaffected. The account export holds the account's own messages wherever they are, with nothing else from threads it cannot see but their target.

### Access logs

The owner of an artifact sees who opened it (plan sections 11 and 13): the verified email of each signed-in visitor and when, one entry per visitor, artifact and 30-minute window, kept 30 days (`ACCESS_LOG` in `packages/contracts`, the rules in `packages/domain/src/access-log.ts`). The code is in `apps/content/src/access-log.ts`, `packages/services/src/access-log.ts` and `apps/app/src/api/access-log.ts`.

- **What is recorded.** Only a page load (`GET` with `Sec-Fetch-Mode: navigate`, top-level or in a frame) of a `restricted` artifact (its readers are the addresses the owner listed), which the content Worker answered below 400 (the viewer redirect included) after authorizing it with a read session or a review session (the viewer's frame or a review tab), by a visitor who is not the owner. Visits of public and `authenticated` artifacts are never recorded (`isLoggedOpening`): any site can send a signed-in visitor top-level to such an artifact, where the viewer opens a review session or the read handoff completes without a click, so recording them would hand the owner the email of whoever was sent there. The visitor is the `uid` of the session's signed claims, never request input. A frame that a sibling artifact opens (`Sec-Fetch-Site: same-site` with a `Sec-Fetch-Dest` other than `document`) is not an opening either: artifacts share one site, so the Lax read cookie goes along and the page is served, but `frame-ancestors` keeps it from rendering, and logging it would let a hostile artifact plant openings the visitor never saw. Subresources, the owner's own visits, refusals, sign-in steps and every request served without a session (public artifacts outside review mode) are not recorded, so anonymous visitors are never identified. On a `restricted` artifact a session counts because only listed readers get one; the redirect, the viewer's frame and its first page fall in the same window.
- **No write per request.** Each isolate keeps the openings it serves in memory, skips what it already wrote for the window, and writes once per 5-second batch after the response through `waitUntil`, like the traffic meter. A failed write keeps the batch for the next one; an evicted isolate loses what it had not written. The log therefore says it is not a complete audit (API description, CLI note, dashboard hint, skill). The email is never in the cookie or on `portifact.dev`: the batch reads it, and the artifact's owner and state, from the control database when it is written, and drops openings of artifacts that are no longer `active` or by accounts that no longer exist, so a batch held across a purge or an account deletion writes nothing for them.
- **Separate database.** The rows live in the `portifact-access` D1 database (`ACCESS_DB`, schema `packages/db/src/access-schema.ts`), keyed by artifact, window and visitor, so concurrent batches from several isolates keep one row (with the earliest time). No D1 batch spans both databases, so nothing in the access log is written in the same transaction as a control-database change; erasure goes through the outbox (below).
- **Owner only.** `GET /api/v1/artifacts/:id/access-log` (scope `artifacts:read`, through `guarded`, so the dashboard session works with its usual checks), the MCP tool `get_access_logs` and `portifact logs` call `getAccessLog`, which answers 404 `not_found` exactly like a missing artifact to anyone but the owner, including the artifact's readers, and for artifacts being purged; archived and suspended artifacts keep their log for the owner. The query is also keyed by the owner stored with each row. Entries past 30 days are never returned, even before the prune reaches them.
- **Retention and erasure.** The jobs Worker prunes rows older than 30 days on every run, in bounded statements. Purging an artifact (`deleteArtifactData`, whatever started it) writes an `erase_access_events` job for it in the batch that deletes the artifact; deleting an account writes one for the account's own openings with the request and again when the deletion finishes (so re-applied tombstones and openings recorded meanwhile are covered too). The jobs Worker runs them against `ACCESS_DB`; each deletes in bounded statements and asks to run again when there is more.
- Emails in the access log are personal data of the visitors: they are never logged, the MCP tool and the skill tell agents to show them only to the user, and the Privacy Policy describes them ([legal.md](legal.md)).

### Abuse reports, suspension and account deletion

- The report form is a trusted page on `app.portifact.com/report`; artifact origins only link to it (`/__portifact/report` answers a `303` there for any ID, so it reveals nothing, and sets no cookie). Pages rendered by Portifact (Markdown and TXT) end with a "Report this artifact" link to that path, in a `footer` outside `main` marked `data-portifact-ignore` (anchors skip it) and `data-portifact-chrome`; it is plain markup in a page without scripts, added at commit by `packages/render` (`reportLink`), never injected into a site's HTML. Review mode removes that footer (`injectBridge`), and the viewer's bar shows its own link to `/report?artifact=<id>` to everyone but the owner. Sites keep only the reserved path, which the Acceptable Use Policy documents. `POST /api/v1/reports` (`apps/app/src/api/reports.ts`) needs no credentials, so it accepts only the exact app `Origin` with `Sec-Fetch-Site: same-origin` and a JSON body (a sibling artifact cannot fake fetch metadata, and a cross-site form cannot send JSON), limits requests per IP, per artifact and globally in the D1 counters (`REPORT_LIMITS`), validates with the strict `AbuseReportInput` (reason enum, at most 2,000 code points of details without control characters, optional email, 8 KiB body) and answers `202` whether or not the artifact exists. Only reports about artifacts that exist are stored. Report text and emails are untrusted data and are never logged.
- Suspensions are applied only by the operator tool with the deploy credentials ([operations.md](operations.md)); no web route can suspend or reinstate. A suspended artifact is not servable, so every existing check refuses it: delivery answers it like a missing artifact, read-session claims stop at the next request because the Worker reads the state on every request, `/read/<id>` and `checkReadAccess` refuse it, `getVersionDownload` gives readers nothing and visitors lose annotations. Owners see only the reason category, never the operator's note. A suspended account cannot publish (`preparePublish` refuses it for every channel).
- Deleting the account (`POST /api/v1/account/delete`, dashboard session only, like every account endpoint) needs the account's email typed again and a session signed in within `FRESH_SESSION_MS` (10 minutes); an older session gets `403 reauthentication_required` and signs in again. One batch records the deletion in `account_deletions`, claims every artifact as `purging`, erases the address from abuse reports, deletes the user's device codes, writes an `erase_access_events` job for the account's openings of other people's artifacts and deletes the `users` row. The foreign keys then delete its sessions, identities, OAuth access and refresh tokens, consents, read sessions and handoffs, so no credential survives the request. This is the one place that ends sessions without Better Auth's API: the tokens those hooks would revoke are deleted by the same cascade.
- `advanceAccountDeletion` finishes it, run by the `account_deletion` queue job and by the maintenance job `processAccountDeletions`: `purgeArchived` purges the claimed artifacts (tombstone per ID), `eraseAuthorFromThread` removes the account's messages on other people's artifacts in batches (a message someone replied to after it becomes the deleted marker; a thread left without visible messages is removed; each change is claimed under the thread revision it read, so a reply that lands meanwhile wins and the next run looks again), late artifacts from an upload already in flight are claimed too, and when nothing is left the storage objects, counters, idempotency records and upload sessions are deleted and an `account` tombstone replaces the deletion row. Every step is idempotent and safe to run concurrently.
- The deletion request also writes an `account_deletion` outbox job and a `purge_artifact` job per claimed artifact in its batch, so the `portifact-jobs` queue advances the deletion right after the next scheduled relay; the scheduled scan stays as the safety net.
- Artifact IDs are never reused: a trigger (`artifacts_refuse_tombstoned_id`) refuses inserting an artifact whose ID has a tombstone, and `preparePublish` turns that into a retry.
- A D1 Time Travel restore rewinds the tombstones too, so purged artifacts and deleted accounts would come back. The operator exports the markers before restoring and applies them after it (`export-tombstones`, `apply-tombstones`, see [operations.md](operations.md)); applying claims every resurrected artifact for purging and deletes every resurrected account the way a deletion request does, deleting its `users` row directly like `requestAccountDeletion`.
- The account export (`GET /api/v1/account/export`, session only) is the account's own data as a JSON attachment with `no-store`: profile, sign-in methods, artifacts with access, versions and manifests, the threads on its artifacts and its own messages elsewhere. Other people appear by name only, never by email, and the file starts with a notice that comment text is untrusted. File bytes are fetched through the existing owner-only download links.

### Requests and responses

- No credentialed CORS for artifact origins on any `portifact.com` endpoint.
- Every mutation requires a valid session, CSRF protection and an exact `Origin` check. No mutations over GET.
- Auth callbacks never accept arbitrary redirect targets and respond with `no-store` and `Referrer-Policy: no-referrer`.
- Content responses set `X-Content-Type-Options: nosniff`, correct MIME types, `frame-ancestors` and `Cross-Origin-Resource-Policy` defaults, and `X-Robots-Tag: noindex`. User content cannot override these headers. The owner's options change them only while the artifact is public and never in review mode: `indexable` drops `noindex`, and `embeddable` allows any `frame-ancestors` and `cross-origin` CORP. A protected artifact stays `noindex` and unembeddable whatever its options say.
- Requests that register service worker scripts are blocked.
- Dashboard and viewer pages cannot be framed by user content (`frame-ancestors 'none'`, `X-Frame-Options: DENY`).

### Untrusted content

- Markdown is rendered by `packages/render` with markdown-it and `html: false`: raw HTML is shown as literal text, never parsed, and there is no MDX and no user plugins. Links and images keep only `http`, `https` and `mailto` URLs (plus paths on the artifact), checked with the WHATWG URL parser so `//host`, `/\host` and embedded tabs resolve as a browser resolves them. Links to other origins get `rel="nofollow noopener noreferrer"`. Remote images are off unless the document opts in; when off they become links. TXT is always escaped inside `<pre>`.
- Rendered documents carry a Content-Security-Policy `<meta>` (`default-src 'none'`, no scripts, frames or forms, `base-uri 'none'`) as defense in depth if markup ever slips through. Review mode replaces it with the same policy as a header plus a nonce for the bridge only (see "Review mode").
- Rendering must stay linear in the input, because a 5 MB document is allowed. remark/micromark is quadratic on nested emphasis, links and many footnotes (seconds to minutes on a few hundred KB), which is why the renderer uses markdown-it, and why `packages/render` patches markdown-it-footnote's quadratic token concatenation. Keep the hostile-size tests in `packages/render/src/security.test.ts` passing when changing the parser or adding plugins.
- The Markdown and TXT viewers run on the artifact origin, never on `portifact.com`. The one exception is the document editor's preview: `POST /api/v1/documents/preview` (scope `artifacts:write`, 120 per user per 10 minutes in the D1 rate-limit counters, nothing stored) returns the page the commit would render, and the dashboard shows it only in an `iframe` with an empty `sandbox` and `srcdoc` (`PreviewFrame` in `packages/ui`). The frame runs in an opaque origin with no scripts, forms, popups or navigation of the page, fetches nothing to load and inherits the dashboard's policy, whose only addition for it is the hash of the renderer's constant stylesheet (`DOCUMENT_STYLESHEET`) in `style-src`; `frame-src` stays `'none'`. The dashboard never inserts rendered markup into its own document.
- Documents are rendered once, at commit, never per request: hostile input can expand about ten times, and a 5 MB source is allowed. The commit reads the verified source from R2, rejects binary, invalid UTF-8 and oversized sources with `invalid_input`, and stores the page (and the Markdown block map) as content-addressed objects of the version. Their bytes count toward the version's 250 MB and the account's storage: the commit batch adds them before marking them verified, so the account limit's CHECK constraint refuses a rendering that does not fit and the upload is released. Rendering a 5 MB hostile document holds the source, the page string and its UTF-8 bytes in memory at once; watch the commit's memory and CPU in production.
- A document's root serves only its rendered page, with the document policy as a `Content-Security-Policy` header too (`default-src 'none'`, no scripts, plus the usual `frame-ancestors`). The original is served at its own path as a download (`Content-Disposition: attachment`), and prepare stores it with the document's MIME type (`text/markdown` or `text/plain`, UTF-8) whatever the client declared, so it can never be served as HTML. Both go through the same authorization as any file. Markdown assets are served as files, like a site's. A document without a rendering answers 503 rather than rendering on the fly.
- Renderer security fixes raise `SECURE_RENDERER_VERSION`; the maintenance job (`rerenderDocuments`) then re-renders every retained document version below it, also on an account at its storage limit (the new bytes are counted up to the limit, never refused), guarded on the version's recorded renderer so concurrent runs apply once. Annotation anchors on re-rendered versions will need to be re-verified when annotations exist.
- Annotation targets are untrusted input wherever they come from: they are validated with `AnnotationTarget` (strict keys, size caps, a CSS selector grammar without escapes or functions, same-origin routes); see [anchors.md](anchors.md).
- Messages from the bridge are untrusted data. Validate the exact origin, source window, instance nonce, schema and size. A selection alone never creates a comment; the user confirms it in the trusted viewer.
- The artifact iframe never receives tokens, email addresses or thread bodies.
- Comment bodies, artifact content and MCP tool results are user data. They never trigger actions or change permissions. Annotation events record who did what, never bodies.

### Uploads

- Paths are normalized and checked on the server: absolute paths, `..`, symlinks, special entries, collisions, reserved paths, size and entry limits are all rejected.
- The server verifies the real size and checksum before commit. A client-declared value is never trusted.
- Quotas are reserved in the same transaction that admits the work.
- The CLI (`packages/cli/src/manifest.ts`) also refuses links and special files instead of following them, applies the domain's path rules before uploading, and leaves out `.git` (any case), `node_modules`, caches and files that may hold secrets (`.env*` except templates, `.dev.vars`, `.npmrc`, `.netrc`, SSH keys, `*.pem`, `*.key`, Terraform state and similar), also when such a file or folder is named directly. These are conveniences for the user; the server still enforces every rule.
- ZIP files are expanded by the CLI (`packages/cli/src/zip.ts`), never by the server, with a minimal reader that trusts nothing in the archive: it reads the central directory and refuses symbolic links (Unix mode or Windows reparse point), special files, encrypted entries, names that are not UTF-8 or fail the domain's path rules (zip slip, absolute paths, drive letters, backslashes, control characters, `__portifact`), duplicates and case collisions, a name used as file and folder, local headers that disagree with the directory, overlapping entries, multi-disk archives and more than 10,000 entries, all before writing a byte. Declared sizes must fit the limit (250 MB published, 2.5 GB sources) and an entry over 1 MB may not expand more than 200 times; inflation stops as soon as an entry passes its declared size, and the CRC-32 must match. Entries land in a private temporary folder under numbered names, so no archive name becomes a path on disk, and the folder is removed when the command ends. The server still validates the resulting manifest like any other.
- Private sources from git (`packages/cli/src/git.ts`) run `git` as a child process with argument arrays, never a shell, with `core.fsmonitor=false`, no pager, no prompts and no optional locks. A `--ref` starting with `-` is refused, so it cannot become an option. The secret filter applies to the files git chooses. The remote attached to a version loses its user name (except on ssh), password, query and fragment in the CLI, and the server refuses any declared remote that still carries them (`checkSourceOrigin` in `packages/domain/src/sources.ts`), whichever client sent it. The origin is declarative: the server checks its form, cannot verify it, and shows it only to the owner, like the sources. A rollback copies it with the sources.
- The dashboard applies the same exclusions and path rules: they live in `packages/domain/src/files.ts` and both clients import them. It builds the manifest in a Web Worker (`apps/web/src/dashboard/publish`), hashing and expanding incrementally. ZIPs are read from their central directory before anything is expanded: links and special files (Unix modes), encrypted entries, ZIP64, split archives and compression other than stored or deflate are refused, declared sizes are checked against the limits first, and each entry must expand to exactly its declared size and CRC-32, so a lying archive stops at the size it declared. Documents must be one UTF-8 file without NUL characters, within 5 MB.
- The dashboard uploads with `XMLHttpRequest` straight to R2's S3 endpoint, sending every signed header except `host` and `content-length`, which the browser sets itself to the signed values. Its page policy adds exactly that origin to `connect-src` (`dashboardCsp` in `apps/app/src/app-host.ts`), and the bucket's CORS rule allows only `https://app.portifact.com` ([releasing.md](releasing.md)). Neither the session cookie nor any token goes to storage (`credentials: "omit"` on downloads). Cancelling deletes the upload; a failed one stays open so the same page can resume it with fresh URLs from `GET /api/v1/publishes/:id`, which lists the parts of large files already reported and signs only the missing ones. Parts are `Blob` slices, so the browser reads them from disk as it sends; reading a part's `ETag` needs the bucket's CORS rule to expose it. Downloads are checked against the manifest's size and SHA-256 before the browser saves them, and several files are packaged into a ZIP in the page.
- The CLI sends each object to the presigned URL with exactly the signed headers and never with the API token. A large file's parts are streamed from disk one byte range at a time, at most four uploads in flight, so memory stays bounded whatever the file size. Upload URLs are never printed. If anything fails after prepare, it cancels the upload with `DELETE /api/v1/publishes/:id` so the reservation is released.

### Secrets and logs

- No secrets in the repository. Local secrets live in `.dev.vars`, which is ignored by git. CI's `secrets` job scans every change's commits and the checked-out tree with gitleaks, and the whole history when its rules change ([releasing.md](releasing.md)); a false positive goes in the `.gitleaks.toml` allowlist with the reason it is safe, as narrow as the finding, never as a path exclusion. Public values (the Turnstile site key, the Google and GitHub client IDs, Cloudflare's documented Turnstile test keys and the e2e Worker's test-only values) are not secrets.
- Never log tokens, cookies, OTP codes, presigned URLs, private emails (the access log stores visitors' emails in its own database and never logs them), or full comment bodies. The email sender replaces provider errors with a generic one (or `RecipientSuppressedError`), because a provider error can echo the message that holds the code and the address. The email events consumer logs only the event type, ID and outcome, never the recipient.

## Review checklist

Before finishing a change that touches the areas above, confirm:

1. Which origin serves this, and does it hold credentials it should not?
2. Who is the actor, and where does that identity come from?
3. Is every path authorized before bytes or data are returned?
4. Can a hostile artifact on a sibling subdomain trigger, read or forge this?
5. Is there a test that tries to break it?
6. Does a top-level visit to an artifact still reach only what it did before, and does the viewer redirect stay out of frames, reserved paths and artifacts with the bar off?
