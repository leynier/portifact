# Releasing

Releases are fully automatic. Nobody edits versions, writes tags or uploads binaries by hand: merging `develop` into `main` is the only release action.

## Branches

| Branch    | Role                                              | How changes get in                                                                            |
| --------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `develop` | Default branch. All work targets it.              | Pull requests, squash-merged, with green CI and a Conventional Commit title.                  |
| `main`    | Release branch. Every push can produce a release. | Only pull requests from `develop`, merged with a merge commit, with green CI and smoke tests. |

Both branches are protected by repository rulesets. The only actor allowed to push directly is the release deploy key, used by the release workflow.

Use a merge commit (not squash) when merging `develop` into `main`, so the release tooling can read every individual commit.

## Commit messages decide the version

Pull request titles become the squashed commit on `develop`, so they must follow [Conventional Commits](https://www.conventionalcommits.org). CI checks them.

While Portifact is below 1.0.0:

| Commit                                                             | Release                                   |
| ------------------------------------------------------------------ | ----------------------------------------- |
| `fix:` or `perf:`                                                  | Patch, for example 0.3.1 → 0.3.2          |
| `feat:`                                                            | Minor, for example 0.3.1 → 0.4.0          |
| Breaking change (`feat!:` or a `BREAKING CHANGE:` footer)          | Minor, not major, until the public launch |
| `docs:`, `chore:`, `ci:`, `test:`, `refactor:`, `build:`, `style:` | No release                                |

The switch to 1.0.0 at launch is done by removing the `breaking` rule in `.releaserc.json` and merging a breaking change.

## What happens on merge to main

The `release` workflow (`.github/workflows/release.yml`):

1. Runs `bun run check` and `bun run test`.
2. Uses semantic-release to read the commits since the last tag and compute the next version. If there are no releasable commits, it stops here.
3. Writes the version to `packages/cli/package.json` and `bun.lock` (`scripts/set-version.ts`).
4. Compiles the CLI for all platforms with `bun build --compile` (`scripts/build-cli.ts`) and writes `SHA256SUMS`.
5. Commits `chore(release): vX.Y.Z [skip ci]` to `main` and tags it `vX.Y.Z`.
6. Publishes a GitHub release with notes, the archives, `SHA256SUMS`, `install.sh` and `install.ps1`.
7. Signs build provenance attestations for the archives through GitHub's OIDC token (Sigstore).
8. Syncs `develop` with `main`. This runs after every push to `main`, even when there is nothing to release, so `main` is never ahead of `develop`. It fast-forwards `develop` to `main`, leaving both on the same commit; only if `develop` received new commits during the run does it create a merge commit instead.

## Deploying portifact.com

Every push to `main` also runs the `deploy` job after `release`: it applies pending D1 migrations to `portifact-control` and to the access log database `portifact-access`, then to the EU region's `portifact-control-eu` and `portifact-access-eu` (`wrangler d1 migrations apply --remote`, from `apps/content`, whose configuration binds the four), deploys the `portifact-content` Worker (artifact origins on `*.portifact.dev`, D1 plus the private R2 bucket `portifact-artifacts`), deploys the `portifact-jobs` Worker (maintenance every 15 minutes and the consumer of the `portifact-jobs` and `portifact-email-events` queues, no routes), builds `apps/web` and deploys the `portifact-app` Worker, using the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets, then checks that `portifact.com` serves the landing page and the installer redirect and that `app.portifact.com` serves the authorization server metadata. The Worker owns `portifact.com`, `www.portifact.com` and `app.portifact.com` as custom domains and routes by host: the apex serves the landing and installers, `www` redirects to the apex, and `app` serves identity, OAuth and the auth pages (see [security.md](security.md)). Pull requests validate both bundles with `wrangler deploy --dry-run`. Migrations must stay backward compatible with the code still running during a deploy: add columns and tables first, remove them in a later release.

### Jobs Worker queue

The `portifact-jobs` Worker produces to and consumes from the Cloudflare Queue `portifact-jobs` (`queues` in `apps/jobs/wrangler.jsonc`): its schedule relays pending rows of the transactional outbox to the queue and its consumer runs them (see "Maintenance and the outbox" in [operations.md](operations.md)). Wrangler does not create queues on deploy, and deploying a Worker bound to a missing queue fails, so the maintainer creates it once before the first release that ships the binding, with the deploy credentials:

```bash
npx wrangler queues create portifact-jobs
```

It survives deploys. The deploy token already has Queues access. No dead-letter queue is configured: a message whose retries run out is dropped, and the outbox sends its job again an hour later because the row is still there. Pull requests validate the binding with `wrangler deploy --dry-run`, which does not check that the queue exists.

### Email events queue

Cloudflare Email Service reports bounces and complaints through an event subscription to a queue, which the `portifact-jobs` Worker consumes (the second consumer in `apps/jobs/wrangler.jsonc`) to keep the email suppression list (see "Email quota and suppressions" in [operations.md](operations.md)). Before the first release that ships this consumer, the maintainer, with the deploy credentials:

1. Creates the queue, because deploying a consumer of a missing queue fails: `npx wrangler queues create portifact-email-events`.
2. Subscribes it to the sending domain in the dashboard: Queues, `portifact-email-events`, Subscriptions, Subscribe to events, source Email Sending, domain `portifact.com` (the domain that sends from `noreply@portifact.com`), events `message.bounced` and `message.complained`.
3. After the deploy, checks the jobs Worker's logs for `email_event` lines once a bounce happens (sending a code to a non-existent mailbox at a domain you control produces one). `email_event_malformed` means the subscription delivers another body shape than the event JSON or a JSON string of it, which the consumer accepts; fix the parser before relying on it.

No dead-letter queue is configured: an event whose 5 retries fail is dropped, and Cloudflare's own suppression still refuses the next send, which records a `provider` suppression. Without the subscription nothing breaks: suppressions then come only from refused sends.

### Access log database

The owner's access log (see "Access logs" in [security.md](security.md)) lives in a D1 database of its own, `portifact-access`, bound as `ACCESS_DB` in `apps/content`, `apps/app` and `apps/jobs` (`wrangler.jsonc`) with migrations in `packages/db/access-migrations` (generated from `packages/db/src/access-schema.ts` with `bun run --cwd packages/db generate:access -- --name <change>`). The database exists since 2026-11-08 (ID `b5285aa9-aa8d-4c2c-9828-22e31c1aec9e`, in the three `wrangler.jsonc` files); the deploy job applies its migrations before deploying the Workers, and they are backward compatible like the control database's. To recreate it, run `npx wrangler d1 create portifact-access` with the deploy credentials and put the new ID in the three configurations.

Locally, `npx wrangler d1 migrations apply portifact-access --local` from `apps/app` or `apps/content` creates it next to the control database; the tests and the e2e stack create their own.

### Plan grace (migration 0060)

Migration `0060_owner_plan_grace` adds the nullable `owner_plans.grace` column ([decision 0022](decisions/0022-plan-grace.md)). The release before it never reads the column, so a rollback of the Workers needs nothing: rows stay readable, owners in a grace from a lowering or a removal lose the hold and are pruned as before the grace existed, and a removed plan's kept row (`free`, no end, no overrides) reads as free. Do not roll back the migration itself; the column is harmless to older code. A plan that ended within the 60 days before the deploy gets its grace at once (it is derived from `valid_until`), so versions and rows the previous release had not pruned yet are held. Access log rows the previous release dated for a plan with an end are re-dated by a one-time pass of the maintenance run after the deploy (`redatedPlans`), so nothing is needed by hand.

### Maximum life of artifacts (migration 0062)

Migration `0062_artifact_max_life` adds the nullable `artifacts.life_started_at` and `artifacts.uncapped_expires_at` columns ([decision 0023](decisions/0023-workspace-retention-policies.md)); the previous release ignores them, so never roll the migration back. A workspace's row stores `artifactMaxDays` and its effective date only while set (`storedPolicy`), so the previous release, whose policy schema is strict, reads every policy that sets none, and only workspaces that set a maximum are affected. For those, the previous release throws on the row wherever it parses it and answers 500 (`internal`): every API, MCP and CLI request acting on the workspace (all roles and its service tokens), the workspace list of each of its members (so the dashboard's space menu fails for them), its Policies page and its share links. Delivery of its artifacts keeps working. Before rolling back:

1. List them: `npx wrangler d1 execute portifact-control --remote --command "select id, slug from workspaces where json_extract(policy, '$.artifactMaxDays') is not null"`. If none, nothing else is needed.
2. `bun run --cwd apps/jobs operator export-policies --out "$HOME/portifact-policies.jsonl"` and keep the file.
3. Copy it, remove `artifactMaxDays` and `artifactMaxDaysFrom` from those workspaces' lines in the copy, and `apply-policies --file <copy>`: removing a maximum is always applied (no `--allow-lifting`) and is recorded as `policy.changed` by the operator. Tell those workspaces' admins.
4. Wait for the jobs to finish: in every region's database (`portifact-control`, and each regional one), `select topic, subject from outbox where topic in ('workspace_policy', 'retention_notice') and subject in (<the workspace IDs>)` must return nothing. The removal's job gives every capped artifact back the expiry its plan gave it, so nothing is archived by a maximum the previous release cannot see. The previous release reads a `workspace_policy` job this one writes (its payload is unchanged). It cannot run a `retention_notice` job: it acks the queue message as malformed, but the outbox row stays and is relayed again every `OUTBOX_REDELIVER_MS` (an hour), so an admins' email still pending at the rollback goes out late, after rolling forward, not never; waiting for it avoids the delay.
5. Roll back.
6. After rolling forward: in a copy of the export, set `artifactMaxDaysFrom` to `null` on each line, then `apply-policies --file <that copy>`. A null date gives the maximum a fresh notice period (7 days from the apply). Re-applying the export as it is keeps each stored effective date, and where that date has passed, every artifact whose deadline passed meanwhile is capped at now and archived at the next run with no expiry notice. Tell the admins the new date, since `apply-policies` sends no email. Delete the files when done.

Restores and moves made under the previous release do not set `life_started_at`; after rolling forward such an artifact's life counts from its last publish, so it may be archived sooner, and it stays restorable.

### Comment retention

Comment retention ([decision 0023](decisions/0023-workspace-retention-policies.md), "Comment retention") adds no migration: its fields live in `workspaces.policy` only while set, its tombstones are a new kind of `tombstones` row, and its epoch rows are `maintenance_cursors` rows. Rolling back past it:

1. Workspaces that set it: `select id, slug from workspaces where json_extract(policy, '$.commentRetentionDays') is not null`. The previous release answers 500 for every request that parses their policy (as for the maximum life above); remove the field from them first with the same `export-policies`, edited copy and `apply-policies` steps (removing it is always applied, and deletes nothing), and wait until no `comment_retention_notice` outbox row is left for them (the previous release acks such a queue message as malformed, the row stays and is relayed again every `OUTBOX_REDELIVER_MS`, so the email would only go out late). After rolling forward, re-apply the original export with `commentRetentionFrom` set to `null` on each line, so each rule takes effect after a fresh notice period, and tell the admins.
2. With a separate regional database, wait until no `comment_tombstones` outbox row is left in that region (`select count(*) from outbox where topic = 'comment_tombstones'` on its database): the previous release cannot run that job, so the tombstones of threads already deleted would only be written after rolling forward, and a restore in between would bring those threads back. The previous release runs no comment retention scan, so it deletes nothing. Its `export-tombstones` writes `comment_thread` lines that its own `apply-tombstones` refuses: drop them from the file before a restore under it (the threads they guard come back with that restore).
3. The `comment_retention_warned:<workspace>` rows in `maintenance_cursors` and the guard records `system/comment-retention/<workspace>` in each bucket are ignored by the previous release; leave them (after rolling forward, a record whose token still agrees with its policy keeps that rule in force; one that does not makes its admins save again).

### Third-party notices

`third-party-notices.md` and the CLI's embedded copy (`packages/cli/src/third-party-notices.ts`, printed by `portifact licenses`) list the licenses and notices of every production dependency of the Workers, the web pages and the CLI binary, generated from the installed packages by `bun run notices` (`scripts/third-party-notices.ts`). The app Worker serves the Markdown as plain text at `portifact.com/third-party-notices` (copied into `apps/web/dist` by the Vite build). `bun run check` fails when either file is stale, when a shipped package's license is not in `AGPL_COMPATIBLE` (`scripts/notices.ts`), or when it is AGPL compatible but not in `COMMERCIAL_COMPATIBLE`, the stricter list of permissive licenses that keep the commercial license possible ([licensing.md](licensing.md)). An expression passes when one side of an OR has all its identifiers in the list, so a dual-licensed package is used under its permissive side (DOMPurify, `MPL-2.0 OR Apache-2.0`). GPL, AGPL and other strong copyleft never go in `COMMERCIAL_COMPATIBLE`; weak copyleft (LGPL, MPL, EPL) stays out of it too and is accepted only for an exact version in `COMMERCIAL_EXCEPTIONS` with a written reason: each entry is the maintainer's reviewed decision, recorded with its reason. The only exception today is `elkjs@0.12.1` (`EPL-2.0 OR GPL-3.0-or-later`, Mermaid's ELK layout, bundled unmodified in the diagram script); an update of it fails `check` until the exception is reviewed again for the new version. Adding a license to either list or an exception is a license review, so say why in the change, and never add a strong copyleft package as an exception: replace it or ask the maintainer. A package whose manifest declares no license is refused as `UNKNOWN` until its license file is read and its exact version added to `REVIEWED_LICENSES` in the same file (Mermaid's dependency `khroma@2.1.0` is MIT); an update of that package needs the review again. Versions are left out so routine updates do not change the files, but a new or removed dependency, or a changed license text, does: run `bun run notices` after `bun install` and commit the result, including on Dependabot's pull requests, which fail `check` until then.

### Contributor license agreement

The `cla` workflow (`.github/workflows/cla.yml`) decides whether a pull request into `develop` has the contributor records `cla.md` section 13 asks for. The rules are `scripts/cla.ts` (unit tested, run by `scripts/cla-main.ts`). This check matches declared contributor identities to signature records; it does not authenticate signatures or establish ownership. Authenticated assent is the contributor's own pull request comment, and the maintainer verifies provenance before merge. Terms: the statement is the text a contributor posts (quoted in `cla.md` with a `<digest>` placeholder, `statementTemplate`); a signature record is the line in `cla-signers.md`. A pull request passes only when:

- the check read one identified head: the workflow reads the pull request (head SHA, commit and changed file counts) before and after reading the commits, comments, changed files, and `cla-signers.md` and `cla.md` at the event's head; the check refuses a head that changed during collection, a commit list that does not contain the head, a commit or file count that differs from the one the pull request reports, and more than 250 commits (`MAX_COMMITS`) or 3,000 files (`MAX_FILES`), the endpoints' limits; a failed API read fails the step;
- every contributor has signed: the pull request's author, every commit author and every co-author named in a `Co-authored-by` trailer, matched by numeric account ID, each with a signature record of a version accepting new submissions at the head and an unedited comment, by that same account, whose whole text (trimmed) is the statement. Anyone but the pull request's author adds a second line, `Head commit: <full SHA>`, which must name the current head: the author controls the branch, so their statement covers the commits they author whenever they push, while anyone else approves one head and posts again after a later push;
- co-author trailers resolve: each `Co-authored-by` line must be exactly one `Name <address>`, the address either a GitHub noreply address with the account ID or a commit email of an exempt account (`EXEMPT_EMAILS`, taken from the repository's history, so a contributor can apply the maintainer's review suggestions). Any other trailer is refused, tools and AI assistants included, in outside pull requests and in the maintainer's own; a commit whose author email belongs to no account fails too;
- an outside pull request (author not exempt) changes no protected file (`PROTECTED_FILES`: `cla.md`, `scripts/cla.ts`, `scripts/cla-main.ts`, `.github/workflows/cla.yml`; `cla.md` is also compared with the base's text, so a branch behind `develop` must be updated) and leaves `cla-signers.md` exactly as on `develop` with only `- ` record lines appended at its end;
- every pull request keeps every list item of `develop`'s `cla-signers.md` as written (malformed ones too), adds only records whose account posted the statement on it under the same login, and adds none while `cla.md` changes: an agreement change is published on its own, then signed.

The exempt accounts (`EXEMPT_ACCOUNTS`, by numeric ID: the maintainer `leynier` and `dependabot[bot]`, `github-actions[bot]` and `imgbot[bot]`) do not sign, but an exempt pull request still cannot remove or change a record or add one nobody confirmed. A commit attributed to an exempt account in a pull request someone else opened passes only when GitHub reports it verified and its committer is an exempt account or `web-flow` (ID 19864447) acting on a commit whose author account ID is exempt; anything the API data cannot establish is refused. So the maintainer signs the commits they push to a contributor's branch, or makes them on GitHub.

The check writes `evidence.json` (head SHA, commits, and for each contributor the account ID and login, the agreement version and digest, and the comment's ID, URL, timestamps and body digest) and the workflow uploads it as the `cla-evidence` artifact, kept 90 days. Before merging any pull request with an outside contributor, the maintainer:

1. downloads the `cla-evidence` artifact of the run on the head being merged (a force push invalidates earlier evidence; the check runs again on the new head);
2. stores it in the maintainer's private agreement archive under the pull request's number, with the statement comments, any ownership authorization and the mapping from the pull request's commits to the squash commit;
3. confirms a contact email privately with each new signer and records it in the archive.

The archive must exist before the first outside contribution is merged ([licensing.md](licensing.md)).

It runs on `pull_request_target` from the base branch, so a pull request cannot change the check that judges it: it checks out the base branch's tip (the commit the workflow itself comes from, never the pull request's older base commit), never runs code from the pull request and reads the pull request's data through the API with a read-only token (`contents: read` and `pull-requests: read`, which GitHub's permission table lists for the issue comments endpoint; no secrets). The actions it uses are pinned by full commit SHA with the tag in a comment. A consequence is that a change to the workflow or the check takes effect only once it is on `develop`, and the pull request that adds it is not checked by it. A comment does not start the workflow (a run started by `issue_comment` would not report on the pull request's head), so a contributor posts the comment and then pushes or closes and reopens the pull request.

Versions: each published version of `cla.md` is immutable and listed in `AGREEMENT_VERSIONS` with the SHA-256 of its text (LF line endings, kept by `.gitattributes`) and whether it accepts new submissions; a test fails when `cla.md` does not hash to the current version's digest or does not quote the statement, so changed text with an unchanged version number cannot pass. A new version is published on its own pull request by the maintainer: a new number in `cla.md`, a new entry in `AGREEMENT_VERSIONS`, `CLA_VERSION` and the statement and record example in `contributing.md` (a test checks them). Records are keyed by account ID and version, so a signer can hold a record of several versions; existing records are never rewritten to imply assent to new terms, and historical grants stay governed by the version actually accepted. Set `acceptsNewSubmissions` to false on an older version only when contributors should move to the new one; they then append a record of it and post its statement on their next pull request. Version 1.0 was never signed and is not listed (see "Agreement versions" in [licensing.md](licensing.md)).

`cla` is a required status check of the `develop` ruleset, with `quality`, `pr-title` and `build` (set by the maintainer on 2026-11-10, after the workflow had run once so GitHub listed it); a renamed check must be updated there by hand. Pull requests from forks run it without the first-time contributor approval, which is fine because it runs only base-branch code with a read-only token.

### Human check (Turnstile)

Account creation and a visitor's first comments need a Cloudflare Turnstile widget ([security.md](security.md), "Human check"). The code fails closed, so until both values exist the deployed app refuses new accounts (existing accounts keep signing in) and visitors' first comments. Both exist since 2026-11-08 (widget `portifact-app`, secret set on the Worker). To recreate them:

1. In the Cloudflare dashboard, Turnstile, add a widget named `portifact-app` in Managed mode with the hostname `app.portifact.com` only, and pre-clearance off.
2. Put its site key in `TURNSTILE_SITE_KEY` in `apps/app/wrangler.jsonc` (public; it ships with the next deploy).
3. Pipe its secret key to `wrangler secret put TURNSTILE_SECRET_KEY --name portifact-app` like the other secrets. Rotating it in the dashboard and here takes effect at once; tokens issued before stay valid only for the old key.

Local development uses Cloudflare's documented test keys in `apps/app/.dev.vars`: `TURNSTILE_SITE_KEY=1x00000000000000000000AA` and `TURNSTILE_SECRET_KEY=1x0000000000000000000000000000000AA` always pass (`2x...` keys always fail). Never put a test key in the deployed configuration. The app tests set the same test keys in `vitest.config.ts` and fake siteverify; the e2e Worker leaves `TURNSTILE_SITE_KEY` empty and seeds comments without the check.

### Storage CORS for the dashboard

The dashboard uploads to and downloads from the `portifact-artifacts` bucket's S3 endpoint directly from the browser, so the bucket needs a CORS rule. The maintainer applies it once in the Cloudflare dashboard (R2, `portifact-artifacts`, Settings, CORS policy) or with `npx wrangler r2 bucket cors set portifact-artifacts --file cors.json`; it survives deploys. Without it, browser uploads and downloads fail with a network error while the CLI keeps working.

```json
{
  "rules": [
    {
      "allowed": {
        "origins": ["https://app.portifact.com"],
        "methods": ["PUT", "GET"],
        "headers": ["x-amz-checksum-sha256", "content-type"]
      },
      "exposeHeaders": ["ETag"],
      "maxAgeSeconds": 3600
    }
  ]
}
```

`exposeHeaders: ["ETag"]` is required: multipart uploads (files over 64 MiB) read each part's `ETag` and report it to the API, and without it every large browser upload fails while small ones keep working. Part URLs sign only `content-length` and `host`, so the allowed headers need no change. Keep R2's default lifecycle rule that aborts incomplete multipart uploads after seven days; the `abort_multipart` job cleans up normally and that rule catches the rest.

Only the app origin is allowed: never add `*.portifact.dev` or `*`. The URLs are still presigned, so CORS only decides which page may read the answers. `host` and `content-length` are signed too, but the browser sets them and they are not CORS request headers. For local development against a real bucket, add `http://localhost:8787` in a separate rule and remove it afterwards. The dashboard's `connect-src` already allows `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com` (`dashboardCsp` in `apps/app/src/app-host.ts`).

### Custom domains (switched off)

Custom domains ([decision 0006](decisions/0006-custom-domains.md), "Custom domains" in [security.md](security.md)) ship switched off. The legal pages describe it under "Features not yet available"; move it out of that section of each page in the change that switches it on ([legal.md](legal.md), "Features not yet available"). Two things are switched separately:

- **Serving** is `CUSTOM_DOMAINS_ENABLED` exactly `"true"` (`customDomainsServing`), the same condition in `portifact-content` (serving custom hosts and redirecting old `.dev` links) and `portifact-app` (where codes, frames and the artifact views' addresses point). Off, the content Worker answers every other host 404 and serves `.dev` exactly as before, and the app names only `.dev` origins, whatever the tables hold.
- **Adding and checking domains** also needs `CF_CONTENT_ZONE_ID`, `CONTENT_DOMAIN` and the secret `CF_HOSTNAMES_TOKEN` on `portifact-app` (adding, "Check again") and `portifact-jobs` (activation, the daily check, the deletion job). Without them adding or checking a domain answers `503 capacity_unavailable`, the dashboard says custom domains are not available yet and the jobs skip every Cloudflare and DNS call. A Worker with the variable but not the rest logs `custom_domains_misconfigured` (error level) and keeps serving the domains that exist.

| Name                     | Kind   | Value                                                                                                                                                                                       |
| ------------------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CUSTOM_DOMAINS_ENABLED` | var    | Exactly `"true"` switches the feature on; anything else or nothing leaves it off. Needed on `portifact-app`, `portifact-jobs` and `portifact-content`; in no deployed `wrangler.jsonc` yet. |
| `CF_CONTENT_ZONE_ID`     | var    | The `portifact.dev` zone's ID (32 hex characters). Public, but added only together with the switch.                                                                                         |
| `CF_HOSTNAMES_TOKEN`     | secret | The API token `portifact-custom-hostnames`: Zone, SSL and Certificates, Edit, on the `portifact.dev` zone only, one year. Never on the content Worker; never logged (errors carry codes).   |

Once enabled, the platform makes these outbound requests and no others for custom domains: `POST`, `GET`, `DELETE` and a paginated `GET` (operator `reconcile-domains` only) on `https://api.cloudflare.com/client/v4/zones/<CF_CONTENT_ZONE_ID>/custom_hostnames`; DNS over HTTPS on `https://cloudflare-dns.com/dns-query`: `type=TXT` for `_portifact.<hostname>` when a domain is checked, `type=SOA` for the hostname when it is added or proven (to refuse the apex of a DNS zone), and `type=A` and `type=AAAA` for the hostname, and when it answers addresses instead of a CNAME to the target also for `domains.portifact.dev`, at activation, "Check again" and the daily check (where the name points). The content Worker makes no outbound request for custom domains.

### Content Worker configuration

`apps/content/wrangler.jsonc` holds `CONTENT_DOMAIN` and `APP_ORIGIN` as `vars`. One secret is set once on the `portifact-content` Worker and survives deploys:

| Secret                | Value                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `READ_SESSION_SECRET` | 32 random bytes, base64 (`openssl rand -base64 32`). Encrypts (and so authenticates) the cookies of artifact origins: read, review, link and sign-in transaction cookies. Rotate it at least once a year: one key seals every cookie with a random nonce, which is sound only up to a number of seals a busy year can reach (decision 0006, "Second review"). Rotating it ends every read session; readers sign in again without noticing. |

Set it with `wrangler secret put READ_SESSION_SECRET --name portifact-content` from `apps/content`, the same way as the app's secrets. Until it is set, protected artifacts answer `503` and public ones are served normally.

Keep Cloudflare from changing what the Workers serve: Web Analytics' Real User Measurements must stay disabled on both zones (Web Analytics, each site, Manage site, RUM set to "Disable"), and so must any other zone feature that rewrites HTML, such as Rocket Loader, Email Address Obfuscation or Zaraz. Automatic RUM injects a third-party beacon script into every HTML response, including user artifacts on `portifact.dev`. Our CSP blocks it, but it alters user content and loads a script the Privacy Policy does not describe. It was on by default for both zones and was turned off on 2026-11-08. On `portifact.dev`, Email Address Obfuscation (Security, Settings) and Automatic HTTPS Rewrites (SSL/TLS, Edge Certificates) were turned off the same day. Rocket Loader is off. Server-side Excludes is still on: the dashboard no longer shows it and the deploy token cannot change zone settings. It only hides content wrapped in `<!--sse-->` from visitors flagged as suspicious.

The Worker bundles the diagram script (the pinned Mermaid build and its runner, "Diagrams and highlighted code" in [security.md](security.md)), which `bun run build` generates in `packages/render/dist` before the deploy; Turborepo also builds it before the content Worker's typecheck, tests and dev server, and before the e2e workspace's typecheck, which compiles the content Worker's sources through `e2e/worker`: any generated module the content Worker imports (the bridge bundle, the diagram script) must be a dependency of `@portifact/e2e#typecheck` in `turbo.json` too, or a clean CI run typechecks before it exists. ### SSO

Single sign-on for workspaces ships switched off ([decision 0016](decisions/0016-workspace-sso.md)). The legal pages describe it under "Features not yet available"; move it out of that section of each page in the change that switches it on ([legal.md](legal.md), "Features not yet available"). Before setting `SSO_ENABLED="true"` on `portifact-app` (never in `wrangler.jsonc`), set the secret `SSO_KEY` (at least 32 random characters, `wrangler secret put SSO_KEY`; during a rotation the old one goes in `SSO_KEY_PREVIOUS` until every provider's secret is saved again) and run these checks on a staging deployment against real identity providers: **Okta**, **Microsoft Entra ID** (v2.0 issuer `https://login.microsoftonline.com/<tenant>/v2.0`) and **Google Workspace** (`https://accounts.google.com`).

1. **Discovery.** "Check the issuer" passes for each, and the redirect URI the dashboard shows registers there unchanged.
2. **PKCE and nonce.** A sign-in sends `code_challenge_method=S256` and a `nonce`; the ID token carries the nonce back. Entra does not list `code_challenge_methods_supported`; confirm it accepts PKCE anyway.
3. **Claims.** The ID token carries `email` for each (Entra needs the `email` optional claim or the user's mail attribute; Google needs the `email` scope). A user whose `email` is outside the workspace's verified domains is refused with `sso_email_outside_domain`.
4. **Key rotation.** Rotate the signing key at the provider (Okta lets you; for Entra and Google wait for or simulate a key roll): the next sign-in fetches the key set once and passes.
5. **Clock skew.** Sign-ins pass with the Worker's clock; a token older than an hour or with `nbf` in the future is refused.
6. **A user removed at the provider.** They can no longer sign in through it, but their Portifact membership and sessions stay until an admin removes them (no SCIM yet); confirm the dashboard's note says so and the customer accepts it.
7. **Terms and human check.** A new person needs both; after a `TERMS_VERSION` bump an existing SSO user is sent back to accept.
8. **Google.** With issuer `https://accounts.google.com` and the workspace's Google Workspace domain verified: a user of that Workspace signs in (the token carries `hd`); a personal Gmail account, and an account of another Workspace, are refused with `sso_email_outside_domain`; an unmanaged Google account whose address is at the domain (created with an email address, no Workspace) has no `hd` and is refused.
9. **Microsoft Entra.** Register the app with the `email` and `xms_edov` optional claims; save the tenant-specific issuer (`common` and `organizations` are refused). A member with a mailbox at the verified domain signs in; a guest (B2B) user or a user whose `email` was edited to an address the tenant does not own gets no `xms_edov: true` and is refused with `sso_email_unverified`.
10. **Unverified addresses.** In Okta (or Auth0) with self-registration on, register a user at the domain without verifying the address: if the token says `email_verified: false` it is refused; an existing Portifact account at that address is never linked without the claim (`sso_link_required`), and "Link single sign-on" from that account's session links it.
11. **No secrets in logs.** Tail the Worker during the flows: no code, token, ID token, client secret or claim appears.

12. **SSO required** ([decision 0021](decisions/0021-workspace-session-policies.md)). Only `portifact-app` reads `SSO_ENABLED`; the artifact origin enforces a stored requirement from the database alone. Against each real provider above, with a staging Enterprise workspace: an admin signs in through the provider from the Policies page and requires it; a member's code session is refused on the dashboard, the API, MCP and a read session of a `workspace` artifact (within a minute), "Sign in with single sign-on" brings them back to the same page, and their personal space keeps working; a `portifact login` approved from the SSO session works and keeps working after a token refresh, one approved from a code session is refused; an MCP client authorized from the SSO session works; removing the provider lifts the requirement at once. Check `sessions.sign_in_method` on each sign-in path (code, Google, GitHub, the provider). Do this before any customer uses the requirement.

Then add `sso` to `AVAILABLE_PLAN_FEATURES` in the same change that turns it on.

**Before switching SSO off again (read this first).** A stored "SSO required" keeps binding with `SSO_ENABLED` off (decision 0021, (e)): nobody can sign in through a provider, so every member of such a workspace without a live SSO session or grant is locked out, admins included. Before removing the variable, list them with `bun run --cwd apps/jobs operator workspaces --sso-required` (or `select id, slug from workspaces where json_extract(policy, '$.ssoRequired') = 1`), and for each either run `operator clear-request-policies <slug> --confirm <slug>` (recorded as the operator) or tell its admins and agree on a date. Then switch it off.

**Grants after a removed identity.** Removing a person's SSO identity, or the provider, does not revoke OAuth grants already issued from an SSO session: they keep `sso:<id>` until their refresh chain expires or the person loses the membership. When a customer needs one cut off now: an admin removes the member; the person can disconnect the app on the Apps page or with `portifact tokens revoke`.

Rolling back past "SSO required": migration 0061 adds nullable or defaulted columns, two triggers and an index that the earlier release ignores; it reads every policy that does not set `ssoRequired` (`storedPolicy` stores it only while set). Before rolling back, run `clear-request-policies <slug> --confirm <slug>` on every workspace whose stored policy sets it (`select id from workspaces where json_extract(policy, '$.ssoRequired') = 1`). After a later upgrade of Better Auth, check that the session hook still writes `sign_in_method` in the creating statement and that the provider still revokes the rotated refresh token right before inserting its successor with the same `created_at` (the triggers' predecessor match); `apps/app/test/sso-required.test.ts` and `packages/db/test/sign-in-method-triggers.test.ts` fail if either changes.

### Artifact data Worker

`apps/data` is the data Worker of [decision 0026](decisions/0026-artifact-data.md) (`portifact-data`): it exports the documents Durable Object `ArtifactDocuments` and answers `404` to every request, with no route, no binding to D1, R2 or a queue, and no secret; `workers_dev` and preview URLs are off, `limits.cpu_ms` is 200 and invocation logs are off. Its class has the legacy migration `v1` (`new_sqlite_classes`). Its callers are the jobs Worker's lifecycle and audit relay jobs and the app Worker's owner document API (delivery 5), each through `ARTIFACT_DOCUMENTS` (`script_name: "portifact-data"` in `apps/jobs/wrangler.jsonc` and `apps/app/wrangler.jsonc`); the content Worker binds it with the page's delivery. The app Worker's binding changes nothing a release creates: the owner routes answer `404` while `ARTIFACT_DATA_ENABLED` is unset, and their export reads only objects that exist, so no object is created. Rolling the app Worker back to a version without the binding removes the owner routes and nothing else.

1. **What a release creates.** The first release that includes it creates the Worker `portifact-data` and the Durable Object namespace of `ArtifactDocuments` (SQLite storage), with no object in it: nothing creates one while `ARTIFACT_DATA_ENABLED` is unset, which it is everywhere (`scripts/durable-migrations.test.ts` fails if any configuration sets a data switch). The release workflow deploys it first, before the content, jobs and app Workers, because a binding to a class that is not deployed is refused; CI validates its bundle with the others (`wrangler deploy --dry-run`). `PORTIFACT_RESOURCES.scripts` lists it; its Durable Object metrics join the collector with the data step of budget protection (delivery 8). An empty namespace starts no alarm and stores nothing. What it does cost: each run of a pending account deletion lists the account's journal prefix once per region (an R2 class A operation, one per run whatever the journal holds); the operator's `data-reconcile` lists the inventory and the journal and reads D1, and its control reads and exports are Durable Object requests with active time even on empty objects; the jobs' added SQL statements cost ordinary rows.
2. **Release checks.** Before merging the release: `bun run test` passes `apps/data` (the object, the lifecycle jobs, the crash schedules and the restore drill on the real object), `apps/jobs` and `apps/app` (both run the data Worker's own bundle, `bun run --cwd apps/data build`, as the binding's target). After deploying: `npx wrangler deployments list --name portifact-data` shows the version; the dashboard's Durable Objects page lists the `ArtifactDocuments` namespace with no objects; `npx wrangler deployments list --name portifact-jobs` and `--name portifact-app` show both callers deployed after it; `select count(*) from artifact_data` is 0 in every region's control database; the jobs Worker's logs show no `job_failed` for a `data_*` topic.
3. **How to roll back.** The first deployment has no earlier data Worker version, and Cloudflare refuses a rollback across a Durable Object class lifecycle change, so the data Worker cannot be rolled back after its first deploy: leave the class deployed and unreachable (roll the jobs Worker back to its previous version, `npx wrangler rollback --name portifact-jobs`, which removes the only caller), or ship a forward fix that keeps the class and its migration. Once a later data version exists, `npx wrangler rollback --name portifact-data` returns to an earlier compatible one. Never roll back with a `deleted_classes`, `renamed_classes` or `transferred_classes` migration: objects hold data and control records (barriers, ended erase intents, resolutions, audit obligations) that reconciliation reads. Never remove the tables of migrations 0079 and 0080. If data jobs exist, pause the queue and keep their rows before deploying a jobs version that does not know their topics. A deploy that fails partway leaves the steps before it done (migrations, perhaps the data Worker's version): inspect the deployment state before retrying.
4. **What it means for the EU region.** Stubs for an EU artifact are made in the EU jurisdiction (`namespace.jurisdiction("eu")`, `dataNamespaces`); the default region's carry a `wnam` location hint. workerd does not implement jurisdictions, so the tests cover the EU region with the plain namespace and check the stub's jurisdiction with a recorded namespace.

## Platforms

`linux-x64`, `linux-arm64`, `linux-x64-musl`, `linux-arm64-musl`, `darwin-x64`, `darwin-arm64`, `windows-x64` and `windows-arm64`. Unix archives are `.tar.gz` and Windows archives are `.zip`; each holds a single executable that does not need Node or Bun.

- Linux glibc builds need glibc 2.17 or newer, so they run on Debian, Ubuntu, RHEL and its rebuilds (Rocky, Alma, CentOS 7+), Fedora, Amazon Linux and openSUSE.
- Musl builds are for Alpine and need `libstdc++` and `libgcc` (`apk add libstdc++ libgcc`); the installer checks for them and says so.
- x64 builds use Bun's baseline targets, so they also run on CPUs without AVX2.
- `scripts/smoke-linux-distros.sh` installs and runs the CLI in containers of those distributions, all in parallel; CI runs it on every pull request that can affect the CLI.

## Installing

```bash
curl -fsSL https://portifact.com/install | bash
```

```powershell
irm https://portifact.com/install.ps1 | iex
```

`portifact.com/install` and `portifact.com/install.ps1` redirect to the scripts attached to the latest release. Both scripts verify the archive against `SHA256SUMS` before installing. They accept `PORTIFACT_VERSION`, `PORTIFACT_INSTALL_DIR` and `PORTIFACT_NO_MODIFY_PATH`; see the header of each script.

The pull request preview action (`action/`, [github-actions.md](github-actions.md)) needs no release step of its own: users pin it to the `vX.Y.Z` tags the release workflow creates, or to the commit those tags point to, and it installs the CLI of that same release by reading `packages/cli/package.json`, which the release commit sets, and running `scripts/install.sh` or `scripts/install.ps1` from the same commit. So the action reaches users with the first release after it changes, never edit its version by hand, and keep the installers' environment variables (`PORTIFACT_VERSION`, `PORTIFACT_INSTALL_DIR`, `PORTIFACT_NO_MODIFY_PATH`) and the CLI's `publish --json` and `delete --key --json` fields stable, because released tags of the action depend on them. `scripts/github-action.test.ts` checks the action and its documented workflows.

To verify that a downloaded archive was built by this repository's workflow:

```bash
gh attestation verify portifact-linux-x64.tar.gz --repo leynier/portifact
```

## Checks on pull requests

The `ci` workflow runs on every pull request and again on `develop` after each merge, which keeps the readme's CI and coverage badges current. It runs lint, typecheck, tests with coverage thresholds, `shellcheck` and a render of sample release notes with the configured preset (`scripts/check-release-notes.mjs`). It also builds every platform and smoke-tests the installers on Linux x64 and arm64, macOS, and Windows x64 and arm64, checking that each machine gets its native build, and across Linux distributions in containers. The `e2e` job is a matrix with one job per Playwright project (`e2e (chromium-3pc-blocked)`, `e2e (firefox-chips)`, `e2e (firefox-3pc-blocked)`, `e2e (webkit)`) running in parallel, because the suite runs with one worker per stack: run back to back, the four projects took about 14 minutes, five times `quality`. Each job installs only its own browser with its system libraries (`bunx playwright install --with-deps <browser>` in `e2e/`), in tries of at most five minutes, up to three: the runner's resolver sometimes cannot resolve Ubuntu's package hosts and apt then hangs until the job's timeout, so after a failed try the next ones use public resolvers (`resolvectl`), and runs `bun run test:e2e -- --project=<project>`, then decision 0026's grant handoff experiment in the same engine (`spikes/artifact-data-grant`, about half a minute, also when the suite failed). It does not retry failed tests, and a failure uploads that project's `e2e/test-results/` and the experiment's `test-results/` (traces) as the `e2e-traces-<project>` artifact. A new Playwright project needs a matrix entry, or CI never runs it. The `secrets` job downloads gitleaks (version and SHA-256 pinned in `ci.yml`, checked before it runs, with read-only repository permissions and no persisted credentials) and scans the change's commits (`gitleaks git --log-opts=<base>..<head>`) and the checked-out tree (`gitleaks dir`) on every run, plus the whole history its commit reaches when the scope asks for it (`--log-opts=HEAD`: never the other branches in the checkout, which belong to other pull requests and follow their own rules), with the rules in `.gitleaks.toml` (the default rules plus a narrow allowlist; findings are redacted in the log). To update gitleaks, change `GITLEAKS_VERSION` and `GITLEAKS_SHA256` together from the release's checksums file and run it locally on the repository first. Pull requests into `main` must come from `develop`. Pull requests into `develop` also run the `cla` workflow (see "Contributor license agreement" below) and check their title in a separate `pr-title` workflow (`.github/workflows/pr-title.yml`), which also runs when the title is edited; `ci` does not run on edits, because a title or description edit used to start a second full run that cancelled the first through the concurrency group and left a cancelled required check blocking the merge.

Mutation testing has its own `mutation` workflow, which runs only when started by hand; releases do not wait for it. See [testing.md](testing.md#mutation-testing).

A first `changes` job (`scripts/ci-scope.ts`) skips work the diff cannot affect, and skipped jobs satisfy required checks. The CLI build and the installer smoke tests run only when the CLI, a workspace package it depends on, its build or installer scripts, shared tooling (`package.json`, `bun.lock`, `bunfig.toml`, root tsconfig) or the workflows change. Lint, typecheck and tests are skipped only when every changed file is under `docs/`, `license` or issue templates; `readme.md`, `AGENTS.md` and `skills/` still run them because checks read those files. Pull requests into `main` always run everything, and if `changes` fails the other jobs run anyway. The end-to-end suite runs when `apps/app`, `apps/content`, `apps/web`, any workspace package but the CLI, `e2e/`, shared tooling (including `turbo.json`) or `ci.yml` change. The secret scan always runs; its scope only decides the whole-history pass, which runs when `.gitleaks.toml` or `ci.yml` change, for pull requests into `main` and when the range cannot be computed (`SECRET_SCAN_FILES`). `.gitleaks.toml` alone does not run lint and tests. When you add a file the CLI build or the installers depend on, add it to `CLI_FILES` in `scripts/ci-scope.ts` with a test, and likewise `E2E_FILES` for the end-to-end suite.

## Setup and recovery

- Secret `RELEASE_DEPLOY_KEY`: private half of a write-enabled deploy key. The `develop` and `main` rulesets allow this deploy key to bypass them. If you rotate it, update both the deploy key and the secret.
- A failed release leaves no tag. Fix the cause on `develop` and merge into `main` again.
- If the sync into `develop` failed, rerun the workflow or merge `main` into `develop` through a pull request.
- Keep `conventional-changelog-conventionalcommits` on the major version that matches the changelog writer bundled with semantic-release. Version 10 of the preset needs `conventional-changelog-writer` 9, while semantic-release 25 ships writer 8, so the preset stays on 9. `scripts/check-release-notes.mjs` catches a mismatch in CI.
