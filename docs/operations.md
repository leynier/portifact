# Operations

How the operator handles abuse reports and suspensions (plan section 13), how storage is verified and a database backup restored (plan section 10), the budget alerts and protection (plan section 12), the email quota and suppressions (plan section 17), and owners' plans (premium plan section 3, F1 and F2). There is no operator web UI: every operator action runs from the operator's machine through the operator tool.

## Why a local tool and not an operator account

The operator tool (`apps/jobs/scripts/operator.ts`) talks to the production D1 database through a Wrangler remote binding, authenticated with the deploy credentials. That was chosen over an allowlisted operator account in the dashboard because:

- No new privileged route exists on `portifact.com`. A stolen dashboard session, an XSS in the dashboard or a bug in a route guard cannot reach a suspension endpoint, because there is none.
- The credential is the one that can already deploy and migrate the database, so it adds no new secret and no new trust: whoever holds it could change the data anyway.
- Every command calls the same services in `packages/services/src/moderation.ts` that the tests cover, so suspensions follow the same guarded, idempotent writes as everything else, and each one is recorded in `lifecycle_events` (`suspended`, `reinstated`) and in `suspensions`.

## Running it

From the repository root, with `CLOUDFLARE_API_TOKEN` set to a token with D1 edit access on the account (or after `wrangler login`):

The script runs on Node (`--experimental-transform-types`), not Bun: Wrangler refuses remote bindings under Bun, whose `fetch` ignores the dispatcher Miniflare routes them through.

```bash
bun run --cwd apps/jobs operator reports                     # open reports, oldest first
bun run --cwd apps/jobs operator report <report-id>          # one report in full: address, notice parts, outcome email
bun run --cwd apps/jobs operator show-artifact <id>          # state, access, owner and account suspension
bun run --cwd apps/jobs operator suspend-artifact <id> --reason phishing --facts "what was found" --ground "the rule or law" --report <report-id> --note "private note"
bun run --cwd apps/jobs operator resolve-report <report-id> actioned        # emails the reporter the outcome
bun run --cwd apps/jobs operator reinstate-artifact <id> --facts "why it comes back"
bun run --cwd apps/jobs operator suspend-account <user-id|email> --reason malware --facts "..." --ground "..."
bun run --cwd apps/jobs operator reinstate-account <user-id|email> --facts "..."
bun run --cwd apps/jobs operator decisions artifact|account|brand <id|email>   # statements of reasons and who got them
bun run --cwd apps/jobs operator send-statement artifact|account|brand <id|email> [--facts "..." --ground "..."]   # when silence ends
bun run --cwd apps/jobs operator hold-artifact <id> --ground "the legal ground" [--until 2027-11-12 | --until 2027-11-12T10:00:00Z]
bun run --cwd apps/jobs operator hold <id>                  # an open hold and the people it keeps
bun run --cwd apps/jobs operator release-hold <id>
bun run --cwd apps/jobs operator holds [--all]
bun run --cwd apps/jobs operator storage-report [--limit N]          # what the storage reconciliation found
bun run --cwd apps/jobs operator export-tombstones --out <absolute file>   # before restoring a backup
bun run --cwd apps/jobs operator apply-tombstones --file <absolute file>   # after restoring a backup
bun run --cwd apps/jobs operator email-suppressions                  # addresses that get no sign-in codes
bun run --cwd apps/jobs operator lift-email-suppression <email>
bun run --cwd apps/jobs operator plan <owner>                        # row, effective plan, usage against limits and columns
bun run --cwd apps/jobs operator set-plan <owner> pro [--seats N] [--until 2027-01-31] [--note "why"] [--overrides '<json>']
bun run --cwd apps/jobs operator remove-plan <owner>                 # back to free
bun run --cwd apps/jobs operator workspaces                          # every workspace with its members count
bun run --cwd apps/jobs operator workspace <slug|workspace-id>       # members, invitations, seats, artifacts and plan
bun run --cwd apps/jobs operator workspace-create <slug> --name "Acme" --admin <user-id|email> [--plan team --seats 5 [--until 2027-01-31] [--note "why"]]
bun run --cwd apps/jobs operator workspace-delete <slug|workspace-id> --confirm <slug>
printf '%s' "$SECRET" | bun run --cwd apps/jobs operator find-service-token   # a leaked service token, from standard input
bun run --cwd apps/jobs operator revoke-service-token <st_…>          # revoke it, with a tombstone
bun run --cwd apps/jobs operator export-plans --out <absolute file>  # before restoring a backup
bun run --cwd apps/jobs operator apply-plans --file <absolute file>  # after restoring a backup
bun run --cwd apps/jobs operator export-policies --out <absolute file>  # workspace policies, before restoring a backup
bun run --cwd apps/jobs operator apply-policies --file <absolute file>  # after restoring a backup
```

`--local` runs against the local D1 state of `wrangler dev` in `apps/app` instead (apply the migrations there first with `wrangler d1 migrations apply portifact-control --local --persist-to apps/app/.wrangler/state`). The remote binding is defined in `apps/jobs/operator.wrangler.jsonc`, which is never deployed. `--config <file>` uses the `DB` binding of another Wrangler configuration instead, for example a scratch database in a backup drill; never edit `operator.wrangler.jsonc` to point it elsewhere. `bun run --cwd apps/jobs` runs the script in `apps/jobs`, so relative paths (`--config`, `--out`, `--file`) resolve from there, not from the repository root: pass absolute paths. Reasons are the `AbuseReason` values in `packages/contracts/src/moderation.ts`. Every suspension and reinstatement (of an artifact, an account or a brand) takes the statement of reasons: `--facts` (up to 2,000 characters) and, for a suspension, `--ground` (up to 500), plain text; `--source notice|review` (a notice when `--report` is given, the operator's own review otherwise); and `--withhold-notice`, which records the statement without emailing anyone, only where the law requires silence. `--report` must name a report that exists. Put `--withhold-notice` last or before another flag, never before a positional argument.

An `<owner>` is an account (`<user-id|email>`) or a workspace (`workspace:<slug>` or its `ws_` ID).

## What a suspension does

- An artifact is suspended from `active` or `archived`. It stops being served at once in every channel: delivery on `portifact.dev` answers it like a missing artifact, fresh read-session claims stop working on the next request (the Worker reads the state on every request), its share links stop opening and their sessions end on the next request, `/read/<id>` issues no handoff, readers get no download links and annotations are closed to visitors. The owner can still see it, export it and delete it, but cannot publish to it, change its access, renew, restore or roll it back.
- The owner sees `state: "suspended"` and `suspension.reason` in the API, MCP, CLI `info` and the dashboard, which explains it and points to `abuse@portifact.com`. The single artifact's view (`GET /api/v1/artifacts/:id`, MCP `get_artifact`, CLI `info`, the dashboard's artifact page) also carries `suspension.statement`: the facts, the ground, whether it followed a notice or the operator's own review and when, from the decision behind the open suspension (or its account's), unless it was withheld. The operator's note is never shown.
- A suspended artifact does not hold an active slot (triggers in `0010_moderation_triggers.sql`). Reinstating puts it back in the state it had; an artifact that was active goes to the archive instead when the account has no free slot.
- Suspending an account suspends every active or archived artifact it owns, each with its own row that points at the account suspension, and refuses new publishes. Reinstating the account reinstates exactly those artifacts; an artifact suspended on its own stays suspended. The account can still sign in, export its data and delete itself.
- Suspending twice, or two operators at once, keeps one open suspension (a unique index on open suspensions per target).

## Reports

Reports arrive through `POST /api/v1/reports` from the report form at `app.portifact.com/report` (linked from the landing footer and from `/__portifact/report` on every artifact origin), and by email to `abuse@portifact.com`. The form is limited per IP, per artifact and globally (`REPORT_LIMITS`), and only reports about artifacts that exist are stored; the answer is the same either way. Aim to respond within 48 hours, as the legal pages promise.

The form carries a full notice of illegal content: the exact address of the content, kept in full (`abuse_reports.address`; null when the reporter typed a bare ID), the reason and an explanation of up to 8,000 characters, the reporter's name (optional, never asked for and dropped for reports of child sexual abuse or exploitation), the reporter's email (optional) and the statement that the information is accurate and complete to the best of their knowledge and sent in good faith (`confirmed`; the form requires it, and a report from an older page without it is stored as `report`, not `full-notice`). The form's language is kept for the outcome email. The reporter's email and name are erased when an account with that email is deleted. An email notice may still come to `abuse@portifact.com`. Handle every report or notice in these steps:

1. **Read it.** `reports` lists open reports; `report <id>` shows one in full. Reply to an email notice when it arrives, saying it was received; a form report needs no acknowledgement (the form confirms receipt on screen).
2. **Escalate first if it is urgent.** A suspected crime that threatens someone's life or safety, or child sexual abuse or exploitation, is reported at once to the competent authority through its authorized reporting channel. Suspend at once (`suspend-artifact ... --withhold-notice` when the law or the authority requires silence), then place a legal hold (`hold-artifact <id> --ground "..." [--until <date>]`, "Legal holds" below): from then on nothing deletes, moves, prunes or serves the artifact, its owner included, until the hold is released. Record outside the product only what the hold does not cover (for example the report sent to the authority and its reference). Do not make unnecessary copies or send the material through ordinary email. Where 18 U.S.C. 2258A applies, report to NCMEC and keep the hold for one year after submission (`--until`), subject to any further lawful requirement.
3. **Decide.** A person decides: read the content, the notice and the rules, and choose no action, a restriction (suspend the artifact, the brand or the account) or removal. Rate limits, quotas and capacity protection are automatic and are not decisions about content. Limiting public sharing has no command; it stays a manual step with its own email.
4. **Record and send the statement of reasons** with the decision itself: `--facts` (the facts relied on, written for the reader: outside the default region describe the content without quoting its name, text or comments, decision 0005) and `--ground` (the law or the rule of the Terms or the Acceptable Use Policy, and why it applies). `--source` says whether it followed a notice (the default with `--report`) or the operator's own review. The command writes a `moderation_decisions` row in the batch of the change and a `moderation_notice` job, which emails the account of a personal space, or each admin of a workspace, in their language: what is restricted, that it applies everywhere and has no end date until lifted, the category, the source, that a person decided without automated detection, the facts and the ground as written, and how to ask for a review (write to `abuse@portifact.com`) and other redress. The same reasons show next to the category: for an artifact on its page in the dashboard and in the single artifact's view of the API, MCP and the CLI (for its admins and editors; a service token gets the category only), for a brand on the Branding page, and for an account on Settings (`GET /api/v1/account/suspension`, session only). `--withhold-notice` records the statement and emails nobody (and the dashboard shows only the category), only where the law permits, for example while an authority investigates. When silence ends, `send-statement <kind> <id>` sends the recorded statement of the open suspension, with the same recipients and rules, and the send is recorded like any other. With `--facts`/`--ground` it records and sends a new decision for the suspension on every call: run it once per statement you mean to send. `decisions <kind> <id>` shows each decision, its email state (`pending`, `sent`, `no_recipient`, `withheld`) and every person it was sent to and when: that is the proof of sending. A statement goes to people with an account only; when nobody could be told (`no_recipient`, for example a suppressed address), use another contact method.
5. **Tell the sender.** `resolve-report <id> actioned|dismissed` resolves the report and, when the report came with an email, emails the reporter the outcome (restricted, or no breach found and no action) and how to ask for a review, in the form's language, naming only the artifact's own origin and the date of the report: never who manages the content, the path or anything the reporter typed, because nobody verified the address (`report_outcome` job; `outcome` in `report <id>`). One address gets at most 3 outcome emails a day (`REPORT_LIMITS.outcomeEmailsPerRecipient`, counted in `rate_limits` under the keyed hash the sign-in limits use, computed by the app Worker when the report arrives and kept as `abuse_reports.reporter_email_key`); the rest are marked `undeliverable`, and so is a report from before the key existed. `--withhold-notice` resolves it without the email. Changing the status of a report already resolved emails nobody again. Reply by hand to a notice that came by email.
6. **Review** a decision when the affected person or the sender asks, by someone looking at it again, and reply with the outcome. A reinstatement records its own decision (`reinstate-artifact <id> --facts "..."`) and emails the people affected that the restriction is lifted.
7. **Copyright counter-notices** follow the Terms: forward a valid counter-notice to the sender of the notice and reinstate 10 to 14 business days after receiving it, unless the sender says a court action was filed. Count substantiated notices per account for the repeat infringer rule.
8. **The operator's mailbox.** Delete ordinary correspondence when it is no longer needed to handle the matter. Keep billing confirmations and payment records for the period required by tax and accounting law, and legally preserved records for the required period (step 2). Do not request artifact contents or unnecessary personal data by email. For legal notices and private contract details, request only the information the published procedure requires. Use the report form or the dashboard for other submissions where they support the request. Keep two-step verification on.

Statements of reasons and report outcomes are service notices: no opt-out, refused for suppressed addresses (the decision then counts nobody), counted in `email_counters`, and on the sign-in codes' rung (`checkModerationNoticeCapacity`): a full cycle leaves the job pending for the next one instead of dropping it. Each send claims its row in `moderation_notice_sends` (or, for an outcome, `outcome_notified_at`) before sending and gives it back if the send fails, so two runs that overlap send once and a failed send is retried for that person only. A D1 Time Travel restore rewinds `moderation_decisions` and `moderation_notice_sends` with everything else; the emails already went, so before a restore note `select id, target_kind, target_id, notice, notified_at from moderation_decisions where created_at > <restore point>` if the proof of sending must survive it.

### Legal holds

A legal hold preserves one artifact for an authority. Only the operator tool sets, lists and releases holds; the owner side is never told why (every refusal says only that the artifact cannot be changed, moved or deleted right now).

- `hold-artifact <id> --ground "..." [--until <date>]` holds a suspended artifact (suspend it first, so it is served to nobody). `--until` takes a UTC date (`2027-11-12`, midnight UTC) or a UTC timestamp (`2027-11-12T10:00:00Z`) and nothing else. On a held artifact the command refuses unless `--until` is given, and then only moves the release date and says so. The hold records the ground, the start, the planned release date and who it concerns (`legal_hold_identities`, in the artifact's region): the owner account, the account or token that created the artifact and the publisher of each committed version, with each account's email at that moment, so they stay known after their accounts are deleted. `hold <id>` prints them for the authority. They are deleted at release and never written to the restore file; `apply-tombstones` captures them again from the accounts as they are after the restore.
- While it is open: nobody but the operator reads its data. The people who manage it are refused deletion and every read of its files, comments, comment history (`get_comment_history`), review entries, access log (`portifact logs`), analytics and their exports with the same `forbidden` (`portifact export` and "Download your data" record those parts as skipped, one artifact at a time; the space's open feedback and the account export leave its comments out), and anyone else gets exactly what a missing or suspended artifact gives, with the same reads, so nobody outside learns that a hold exists; a transfer is refused (a suspended artifact never moves), downloads, `read_artifact` and version comparisons are refused to everyone, its owner included, reinstating it is refused (`reinstate-account` leaves it suspended and says how many), and the maintenance never archives, purges or prunes its versions. Its access log entries and analytics counts are kept past their expiry (the access prune skips held artifacts, `heldArtifactIds`), and when someone whose comments, review verdicts or openings are on it deletes their account, those stay on the held artifact while everything else of the account goes. Account and workspace deletions go on for everything else (the person's account, sessions, other artifacts, comments and the rest are deleted as usual) and leave the held artifact suspended, so the deletion stays pending (the deletion scans try a waiting deletion last, `attempted_at`). A restore's re-applied deletions leave it out too. Triggers in migration 0074 refuse any path the services miss: no state change out of `suspended`, no owner change, no delete of the artifact or of a committed version.
- `release-hold <id>`, or the maintenance scan at the `--until` date, releases it and forgets the addresses it kept. The release writes a `legal_hold_release` job in its own batch, which erases what the hold deferred for accounts deleted meanwhile (found by their `account` tombstones): their comments and review verdicts on the artifact and their openings of it; expired access log rows and counts go at the next prune. The artifact stays suspended until `reinstate-artifact`; a deletion that waited (the owner's account or workspace) claims and purges it at its next run, and the owner can delete it again.
- `holds` lists open holds in every region; `holds --all` adds released ones. `export-tombstones` writes every hold with the markers and `apply-tombstones` puts them back first, before any deletion is re-applied: a hold the restore lost comes back (its artifact suspended again if the restore brought it back served), one released before the export is released again through the same batch as any release (its release job, the addresses forgotten), and the output names any held artifact the restore could not bring back. With `--region <name>`, holds of artifacts in other regions are left alone. A file written before a release reopens that hold; release it again.

## Promises kept by hand

The legal pages promise these, and no code does them: the operator does each by hand, records when it was done and retains only the evidence needed for the applicable purpose and retention period. `docs/legal.md` ("Promises the operator keeps by hand") points here.

- **Paid plans.** The pre-contract information, the written confirmation, private seller's details, refunds and billing corrections: "Granting a paid plan" below.
- **Reports and notices.** Acknowledging notices sent by email, the 48-hour aim, reporting urgent crimes to the authorities, telling a person without an account or without a deliverable address, answering an email notice's sender, reviews and counter-notices: "Reports" above. Statements of reasons, outcomes sent to reporters who gave an email, and preservation through legal holds are done by the product once the operator runs the command.
- **Switching and leaving.** "A customer asks to switch or leave" below, including returning by hand what no export tool covers.
- **Changes to the legal texts.** For a materially adverse change, email every account's address and update the pages at least 30 days before it takes effect (the urgent security and legal exceptions in the Terms apply, explained as soon as allowed). Use an available contact method for an address on the suppression list.
- **Price changes.** Email every paying customer and update the pricing page at least 30 days before a new price can apply to a new period.
- **Shutdown.** Email every account at least 30 days before, unless something beyond our control makes that impossible, and refund unused paid periods in every case.
- **New sub-processors.** Watch Cloudflare's sub-processor announcements (its objection window is ten days from its notice). Update the DPA's Annex III and email every customer's contact (the data protection contact they named, else the workspace's admins, else the account holder of a personal space used for work) at least 14 days before the new provider receives customer data, or get the customer's specific written authorization for an earlier start. Resolve objections before the provider starts.
- **Breaches.** Tell each affected customer's contact without undue delay, with what is known and updates as you learn more. Where Portifact is the controller, notify the supervisory authority and the people affected when the law requires.
- **Privacy requests and complaints.** Answer requests to `privacy@portifact.com` within one calendar month (explain any lawful extension within that month), pass requests about a workspace's data to its admins, send the transfer safeguards and the private annex on request, and acknowledge complaints within 30 days and send the outcome without undue delay.
- **Workspace deletion.** Delete a workspace at its admins' request (`workspace-delete`) and confirm the deletion in writing once the jobs have finished.

## Share links

A share link (`app.portifact.com/s#<token>`, [decision 0008](decisions/0008-share-links.md)) lets anyone who holds it read one artifact without an account. Abuse handling does not change:

- **A reported link.** The visitor of a link lands on the artifact's own origin, so the address bar names the artifact ID, and the report form and `/__portifact/report` carry it as usual. When a report gives only the link, find its artifact without pasting the token on a command line: `printf '%s' '<link>' | bun run --cwd apps/jobs operator find-share-link` (or `operator find-share-link < file`) reads it from standard input, hashes the token locally and prints the artifact, the link's ID and state, and who created it, never the token. Do not keep the link in notes or tickets; it is a credential.
- **Suspending kills the links.** A suspended artifact is not servable, so every link to it stops opening and open link sessions end on their next request. Reinstating brings them back, unless they expired or were revoked meanwhile. There is no operator command to revoke one link: the owner revokes it, and a suspension is the operator's tool.
- **Plans.** Links need `shareLinks` in the owner's plan. Removing or lowering a plan pauses them without deleting them, and they work again when the plan includes the feature; the dashboard says so.
- **Maintenance.** Each run deletes spent link codes and expired link sessions in bounded batches (`shareLinks` in the `maintenance` log line), and links revoked or expired more than 30 days ago, writing a `share_link` tombstone first for the revoked ones.
- **Restores.** `export-tombstones` includes every revoked link and `apply-tombstones` revokes them again (`share link(s) revoked again` in its output), so a restore never reopens one. Links created after the restore point are lost; their owners create them again.

## Approval reviews

Approval reviews ([decision 0013](decisions/0013-approval-reviews.md)) need no operator action. The maintenance scan `recheckApprovalReviewers` (`approvalReviewers` in the `maintenance` log line) runs last in the run and re-checks up to 30 open requests (at most 243 D1 calls and 5 seconds), in ID order from the `approval_reviewers` cursor in `maintenance_cursors`; it drops reviewers who can no longer open the artifact from the count (or counts them again once they can) and deletes verdicts whose author no longer holds the address. A request goes with its artifact; a restore that rewinds a cancellation or a verdict needs nothing re-applied, because neither deletes anything.

### Review notices

When the artifact owner's plan includes both `reviews` and `commentNotices` (Team and above), people get review emails in their language ([decision 0013](decisions/0013-approval-reviews.md), "Emails"; rules in "Approval reviews" in [security.md](security.md)): each reviewer with a Portifact account and a standing relationship to the artifact (the owner side or a member of its workspace, its reader list, a listed group, or a verified domain in `domain` mode; never someone admitted only because the artifact is public or open to everyone signed in) when a person asks them (on a new request or when added to one; a service token's requests send none), and the owner side (the user of a personal space, or a workspace's admins and editors) when the version under review is approved or changes are requested, except the person whose verdict decided it.

- The write adds one `review_notice` event job (subject: the request) to its own batch. The consumer turns it into one send job per recipient account (subject: the account) and deletes it in one batch; a send job claims its row by deleting it before sending, like comment notices, checks everything again and skips with `review_notice_skipped` (a reason and a count, never the address): `stale` (the request was cancelled, moved to a new version or reached another status), `plan`, `no_account` (an address that never signed in), `opted_out`, `not_reviewer` (no longer listed, or no standing relationship), `not_owner_side`, `muted`, `suppressed`, `capacity`, `duplicate` or `recipient_cap` (the person already received 20 review emails today, counted under `approvals:notices:<user>` in `rate_limits`; dropped, not retried). A failed send puts the job back and frees its claim.
- At most one email of each kind per person, artifact and version: `review_notices` keeps the claim (it goes with the version, the artifact and the account). A status that goes back to pending and becomes final again on the same version tells nobody twice.
- Capacity: review notices stop first, at `REVIEW_NOTICE_EMAILS_PER_CYCLE` (4,900 emails sent in the cycle), 5,000 before comment notices, 10,000 before expiry notices and 15,000 before sign-in codes (`packages/domain/src/email.ts`). Every email counts in `email_counters`.
- Worst case: requests and changes that add reviewers are limited to 100 a day per owner and 30 an hour per actor (`APPROVALS`), each naming at most 10 reviewers, so at most 1,000 request emails a day and an hour for one owner and 300 an hour for one actor, all to people with a standing relationship to the artifact; status emails are at most one per owner-side person per artifact version; and one recipient gets at most 20 review emails a day from every space together (`APPROVALS.noticesPerRecipientPerDay`).
- Opt-out is the comment notices setting and its one-click unsubscribe link, the same as comment notices; the per-artifact mute stops status emails for that artifact.

To stop them in an emergency, with the deploy credentials: `wrangler d1 execute portifact-control --remote --command "delete from outbox where topic = 'review_notice'"` (nothing else changes; requests and verdicts stay), repeated until a fix is deployed, or delete `UNSUBSCRIBE_SECRET` from the jobs Worker as for comment notices, which keeps every send failing before it sends.

## Custom domains

Owners on a paid plan attach a hostname of their own to one artifact ([decision 0006](decisions/0006-custom-domains.md), "Custom domains" in [security.md](security.md)); the feature is switched off until the steps in "Custom domains (switched off)" in [releasing.md](releasing.md) are done. Every run of the jobs Worker brings domains whose certificate is pending forward (25 per run), re-checks each active domain once a day (its TXT record, where the name points and Cloudflare's status; three missed TXT checks in a row, three checks in a row that find the name not pointing at the CNAME target, or a hostname Cloudflare reports moved, deleted, blocked or missing, detach it; a domain is activated only while its name points at the target), detaches domains still provisioning after 2 days (Cloudflare bills them), detaches domains on the block list, applies lower plans (the oldest domains stay; an expired plan counts for 7 more days, and during those days the owner, or each admin of a workspace, gets one email naming the domains that will stop and when) and prunes claims older than 7 days. A detached domain stops serving at once and its `delete_custom_hostname` job deletes the Cloudflare hostname, then the row, which frees the name. Without the switch the run only prunes claims and applies plan limits.

Operator commands:

- `show-domain <hostname>`: the domain's state (and why it was detached), artifact, owner, checks and Cloudflare ID, and every pending claim of the name (owner and artifact, never the token).
- `detach-domain <hostname>`: stops serving the artifact on the domain and queues the deletion of its Cloudflare hostname. The artifact keeps its Portifact origin; the owner can add the domain again with a new DNS proof.
- `block-domain <name> --note <reason>`: refuses the name and every name under it as a custom domain from now on (adding and verifying answer that it cannot be used), detaches the domains it covers at once and drops their pending claims. `unblock-domain <name>` lifts it (detached domains stay detached; owners add them again with a new proof); `blocked-domains` lists the names with their reasons.
- `reconcile-domains`: after a restore (below), with `CF_CONTENT_ZONE_ID` and `CF_HOSTNAMES_TOKEN` in the shell's environment (the operator's own copy of the token; no other command reads them).

**Abuse on a customer's domain.** A report names the artifact, or a link on the customer's domain: find the artifact with `show-domain <hostname>`. Suspending the artifact (`suspend-artifact`) detaches its domain in the same step, so the Cloudflare hostname and its certificate are deleted and the name answers Cloudflare's error; reinstating does not bring the domain back. When only the domain is the problem (a lookalike of another brand on an otherwise acceptable artifact), `detach-domain` alone is enough. Phishing reported to Cloudflare about a customer hostname is a report against `portifact.dev`: handle it the same way and answer Cloudflare's abuse desk. To keep a name or a whole domain out for good (a lookalike of a bank, a domain used for phishing on several accounts), `block-domain` it; built-in refusals already cover Portifact's domains, any label with `portifact` and the apex of a DNS zone.

**What you see may not be what is stored.** The owner controls the name's DNS. Between two daily checks they can point it at a server of their own, and the viewer would then frame that server's page inside Portifact's bar (the bar still names the real origin). Before judging a report about a page on a custom domain, compare it with the stored artifact (`https://<id>.portifact.dev/`, or the download) and look at where the name points now (`dig +short <hostname>` should end at `domains.portifact.dev`; `show-domain` shows the last check's problem, `cname_elsewhere` when it pointed elsewhere). A name serving something Portifact does not hold is abuse of the domain, not of the artifact: `detach-domain` it at once rather than waiting for the third daily check, and `block-domain` it when the owner repeats it. Reports about a page that is the stored artifact are handled as any other report.

**Verifying after the switch is on.** With a test hostname you control: add it in the dashboard, publish the TXT record and the CNAME, press "Check again" until it is active (`show-domain` shows `active` and a Cloudflare ID). Then, in a private window: with the bar on, open `https://<host>/` and check it ends in the viewer on `app.portifact.com` framing `https://<host>`; turn the bar off and check `https://<host>/` serves the artifact with no `Strict-Transport-Security` header, `http://<host>/` answers `308` to `https`, and an old `https://<id>.portifact.dev/` link answers `308` to the custom host; make the artifact restricted and check sign-in comes back to `https://<host>/` with a `__Host-pf_read` cookie of that host only. Point the CNAME elsewhere and press "Check again": the dashboard shows that the domain does not point at Portifact; point it back. Check the next day that `checked` moved and `missed` stays 0; remove the domain and check that `https://<host>/` answers 404 at once, the row is gone after the queue runs and the hostname no longer appears in Cloudflare's custom hostnames.

## Budget alerts and protection

Cloudflare's budget alerts only inform, so Portifact protects its own budget. Every 15 minutes the jobs Worker (`apps/jobs/src/budget.ts`) measures the cycle (the calendar month in UTC), projects its spend at the reference prices in `REFERENCE_PRICES` (`packages/domain/src/budget.ts`), stores the result in the single `platform_budget` row and records alerts in `budget_alerts`. Counters are extrapolated linearly from what the cycle used so far (at least one day counts as elapsed); stored bytes are a gauge assumed to stay for the whole cycle. CPU time, logs and taxes are not measured: the budget's margin covers them.

| Projected spend | Level        | What happens                                                                                                                                                                                                                              |
| --------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| US$25           | `alert25`    | Alert to the operator.                                                                                                                                                                                                                    |
| US$50           | `alert50`    | Alert; review the largest consumers (D1 `objects` and `account_usage`, Cloudflare's analytics).                                                                                                                                           |
| US$75           | `slow75`     | Alert and `stop_new_artifacts`: publishes that create an artifact answer `capacity_unavailable`; updates still work.                                                                                                                      |
| US$100          | `protect100` | Alert and the plan's steps in order, each from its own spend: `block_uploads` (US$100, every new upload refused), `pause_annotation_writes` (US$110), `tighten_public_traffic` (US$125), `limit_protected_traffic` (US$150, last resort). |

Decision 0026 (artifact data, partly built, switched off) adds a `pause_data_writes` step at US$105 and a data admission limit; this table gains them when that feature is built.

Reaching a global admission limit (800 GB stored, 2 M class A operations, 20 M Worker requests or 20,000 emails in the cycle) adds `stop_new_artifacts` and `block_uploads` whatever the spend, and records an `admission_<metric>` alert. Reads, exports, deletion, access reduction, renewal, restore and rollback keep working at every level, comment moderation and deletion too, and nothing is ever deleted to contain costs. The traffic steps limit each visitor IP to `PROTECTION_TRAFFIC_LIMITS` (`packages/domain/src/budget.ts`: 120 requests per minute for public traffic, 240 for protected; calibrate with real traffic), counted exactly by the `TrafficLimiter` Durable Object of the content Worker (one object per IP and kind of traffic, a fixed window in memory, reached only while a traffic step applies); an isolate remembers a refused visitor until their window ends, so a flood is refused without a Durable Object request each time. The content Worker reads the protection at most once a minute and fails open, logging `budget_protection_unreadable` when the state cannot be read and `traffic_limiter_failed` when the limiter cannot answer. Workers Rate Limiting is not used for this: its counts are approximate per location, and on 2026-11-08 a deployed 240-a-minute binding refused none of 1,200 protected requests a minute from one IP (see [workers-sdk#16097](https://github.com/cloudflare/workers-sdk/issues/16097)). While uploads are blocked or new artifacts are braked, every account's usage reports a `capacity` block, which the dashboard shows as a notice and the CLI and MCP report like any other block.

The D1 rows it counts include the restore markers of app tokens: an MCP client that refreshes every hour writes 24 `oauth_token` markers a day (each insert also writes its primary key and `tombstones_kind_deleted_idx` entries), and 30 days later the prune reads and deletes the same 24 rows a day through the index; a CLI that refreshes on use writes one per refresh.

Each alert is recorded once per kind and cycle. Without email configured, alerts stay "not emailed" and are visible with the commands below and in the jobs Worker's logs (`budget_alert` events). A failed analytics query never lifts protection: counters it missed keep their last values of the cycle.

```bash
bun run --cwd apps/jobs operator budget                      # state, projection, metrics, protection and this cycle's alerts
bun run --cwd apps/jobs operator budget-alerts --limit 20    # recorded alerts, newest first
bun run --cwd apps/jobs operator budget-override protect100 --steps 2 --note "traffic spike under review"
bun run --cwd apps/jobs operator budget-override none --hours 12 --note "projection wrong after a migration"
bun run --cwd apps/jobs operator budget-override clear
```

An override replaces the automatic decision at once, in both directions, until `--hours` passes or it is cleared; `--steps` (1 to 4) says how many protection steps a `protect100` override applies. It can be set before the first measurement. The note is required and only the operator sees it.

### Cloudflare analytics

The jobs Worker measures R2 operations and storage, Worker requests and D1 rows through Cloudflare's GraphQL Analytics API (`apps/jobs/src/analytics.ts`). In production the `portifact-jobs` Worker has both settings below, so the collector runs on every budget run; without either of them it stays off and the projection uses only what D1 knows (the bytes of every stored object and the objects created this cycle, one class A upload each). Emails always come from D1 (`email_counters`), with or without analytics.

| Name                 | Kind   | Value                                                                                                                           |
| -------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `CF_ANALYTICS_TOKEN` | Secret | A Cloudflare API token with only **Account > Account Analytics > Read** on the Portifact account. No edit permission is needed. |
| `CF_ACCOUNT_ID`      | Secret | The account ID the token can read.                                                                                              |

Rotate or set them with `wrangler secret put <NAME> --name portifact-jobs` from `apps/jobs`, piping the value so it never appears in the shell history. The collector queries `r2OperationsAdaptiveGroups`, `r2StorageAdaptiveGroups`, `workersInvocationsAdaptive` and `d1AnalyticsAdaptiveGroups` on `https://api.cloudflare.com/client/v4/graphql`. The account also hosts other projects, so each dataset is filtered to Portifact's resources (`PORTIFACT_RESOURCES`: the `portifact-artifacts` and `portifact-artifacts-eu` buckets, the second named `eu_portifact-artifacts-eu` in the R2 datasets, whose latest storage samples are added together, the `portifact-app`, `portifact-content` and `portifact-jobs` Workers and the `portifact-control`, `portifact-access`, `portifact-control-eu` and `portifact-access-eu` databases, whose rows read and written are added together); keep that list in sync when a Worker, bucket or database is renamed or added. The plan's included amounts are per account, so the projection credits all of them to Portifact and can understate its share of the invoice when other projects use them too. The collector's errors carry only a code and a number, and the jobs Worker logs `budget_analytics_failed` with that label: `Error:ANALYTICS_HTTP:401` or `:403` (the token was revoked or lacks Account Analytics read: set a new one), `Error:ANALYTICS_HTTP:429` (rate limited: the next run retries), another status (Cloudflare's side), `Error:ANALYTICS_GRAPHQL_ERRORS:<count>` (the query was refused: check the datasets above still exist) or `Error:ANALYTICS_ACCOUNT_NOT_VISIBLE` (the token is not scoped to this account). `operator budget` shows `analytics failed` when the last query failed, and the counters it missed keep their last values of the cycle.

### Alert emails (optional)

Alert emails need the `portifact-jobs` Worker's `send_email` binding `BUDGET_EMAIL` and the vars `BUDGET_ALERT_TO` (the operator's address) and `BUDGET_ALERT_FROM` (a sender verified in Cloudflare Email Service); without any of them they are a no-op. `apps/jobs/wrangler.jsonc` sets all three: alerts go to `hello@portifact.com`, which Email Routing forwards to the operator (like `abuse@`, `privacy@` and `legal@`), from `noreply@portifact.com`. Changing the operator's inbox is a routing change, not a deploy. With all three, each run emails the cycle's alerts that were not emailed yet and marks them; a failed send is retried on the next run. The email (`budgetAlertEmail` in `packages/emails`) has an HTML version and a plain-text alternative with the projection, level, protection in effect, the new alerts and the `operator budget` command; `bun run --cwd packages/emails preview` shows it.

## Email quota and suppressions

Sign-in codes stop for the rest of the month once `SIGN_IN_EMAILS_PER_CYCLE` (19,900) emails were sent in the UTC month, below the 20,000-email admission limit so codes alone never stop publishing; the login page then suggests Google or GitHub. The daily budget (600 codes) normally keeps the month far below it. `operator budget` shows the cycle's `emails`, counted as they are sent (`email_counters`).

Addresses whose mail bounced permanently or was reported as spam get no more codes (see "Identity" in [security.md](security.md)). Cloudflare Email Service reports them through the `portifact-email-events` queue (set up in [releasing.md](releasing.md)), and a send it refuses because its own list holds the address is recorded too. The person sees an explanation that points to Google, GitHub and `privacy@portifact.com`.

```bash
bun run --cwd apps/jobs operator email-suppressions [--limit N]     # suppressions in effect: id, masked hint, reason, dates
bun run --cwd apps/jobs operator lift-email-suppression <email>     # after checking with the person that the address works now
```

Only the masked hint is stored, so lifting needs the address from the person who wrote in. Lifting ours does not lift Cloudflare's: if sends still fail (the next request records a `provider` suppression again), remove the address from the sending domain's suppression list in the Cloudflare dashboard (Email Service, Suppressions) or through its API, unless the entry is `read_only` (complaints and missing mailboxes usually are; only Cloudflare Support can review those). A complaint means the person marked our mail as spam: lift it only at their request. The consumer logs `email_event` (type, event ID, outcome), `email_event_malformed` and `email_event_failed`; malformed events are dropped and failed ones retried up to 5 times, after which Cloudflare's own suppression still blocks sends and the next refused send records it.

## Expiry notices

An active artifact archives 30 days after its last publish or renewal. Three days before (`EXPIRY_NOTICE.windowMs` in `packages/domain/src/expiry-notices.ts`), its owner gets an email, in their language (`account_settings.locale`, English when they chose none), listing every artifact of theirs that expires within the window, each with its address, its expiry in UTC and a link to its page in the dashboard to renew it, plus a link to Settings to turn the notices off (`account_settings.expiry_notices`, on by default and part of the account export). For a workspace whose data is in the EU (decision 0005), the notice names nothing: it says how many artifacts expire and when the first does, and links the dashboard's list of the workspace's artifacts expiring soon (`/?workspace=<slug>&expiring=soon`, the same list as `portifact list --expiring soon`); the job knows the region from its message and the slug comes with the admins' read. Comment and review notices for an EU workspace likewise say "An artifact" instead of its name (`noticeDetail` in `packages/domain/src/notices.ts`).

- The maintenance scan (`scheduleExpiryNotices`, `packages/services/src/expiry-notices.ts`) picks up to 25 owners a run whose artifacts are due and who did not turn notices off, and for each writes one `expiry_notice` outbox job (subject: the owner; payload: the artifacts and the expiry each was scheduled for) and marks the artifacts (`artifacts.expiry_notice_for`, the expiry notified, and `expiry_notice_at`) in one batch conditioned on the artifacts still being due, so overlapping runs schedule each expiry once. A publish, a rollback, a renewal or an unpin sets a new `expires_at`, which is due for its own notice; a pinned artifact has none, so it is never due.
- An owner gets at most one notice a day (`ownerCooldownMs`), so artifacts that enter the window hours apart go out together; every artifact still gets at least two days of warning.
- The consumer claims the job by deleting its row before sending, so a duplicate or concurrent delivery sends nothing: notices are sent at most once. Before sending it drops artifacts renewed, archived or expired since, and skips (logging `expiry_notice_skipped` with a reason and a count, never the address) when the account is gone, the owner turned notices off, the address is suppressed or the cycle's notice emails are spent (`NOTICE_EMAILS_PER_CYCLE`, 14,900: notices stop 5,000 emails before sign-in codes do). A refusal because Email Service's list holds the address records a `provider` suppression. Any other failure puts the job back in the outbox for the next run and logs `job_failed`; only a Worker dying between the claim and the send loses a notice.
- Every notice sent is counted in `email_counters` like sign-in codes. The `portifact-jobs` Worker sends through its `send_email` binding `EMAIL` from `noreply@portifact.com`, with `APP_ORIGIN` and `CONTENT_DOMAIN` in its `vars` for the links.

`select owner_id, count(*) from artifacts where expiry_notice_at > <ms a day ago> group by owner_id` shows who was notified in the last day. There is no operator command to resend a notice.

## Comment notices

On artifacts whose owner's plan includes `commentNotices` (Pro and above, from `PLANS`; never free), people get an email digest of new comment activity, in their language, at most every 10 minutes (`COMMENT_NOTICE` in `packages/domain/src/comment-notices.ts`). It lists each artifact with how many threads are new, how many replies came in and how many threads were resolved, with a link to its comments in the viewer. It never holds comment text, quotes or who wrote anything. Recipients are the owner side (the user of a personal space, or a workspace's admins and editors) and the participants of a thread (its author and everyone who wrote in it) when someone else replies or resolves it; nobody hears about their own writes.

- A comment, reply or resolution adds one statement to its own claimed batch (`markCommentActivity`, `packages/services/src/comment-activity.ts`), only when the owner's plan has the feature: one `comment_notices` row per recipient and thread with counts and IDs, never text. Rows go with their thread and artifact by foreign keys, and with the recipient's account in the deletion batches.
- The maintenance scan (`scheduleCommentNotices`, `packages/services/src/comment-notices.ts`) picks up to 25 recipients a run whose oldest pending activity is at least 10 minutes old and who have no job waiting, and per recipient writes one `comment_notice` outbox job carrying up to 200 rows and deletes those rows, conditioned on the job's unique claim, in one batch. Rows of people who turned the notices off are deleted instead. The schedule runs every 15 minutes, so a digest usually arrives 10 to 25 minutes after the first comment.
- The consumer claims the job by deleting its row before sending (at most once, like expiry notices). It then checks again the account, the opt-out (`account_settings.comment_notices`), the per-artifact mutes (`comment_notice_mutes`), the owner's plan and, with the same rules as every read path, which threads the recipient may still see; it skips with `comment_notice_skipped` (a reason and a count, never the address or names) when nothing is left, the address is suppressed or the cycle's comment notice emails are spent (`COMMENT_NOTICE_EMAILS_PER_CYCLE`, 9,900: they stop 5,000 emails before expiry notices and 10,000 before sign-in codes; review notices stop 5,000 before them). Any other failure puts the job back and logs `job_failed`.
- Every email carries a one-click unsubscribe link (`/unsubscribe?token=...`, and `List-Unsubscribe` with `List-Unsubscribe-Post` for mail clients), signed with the `UNSUBSCRIBE_SECRET` both the `portifact-app` and `portifact-jobs` Workers hold ([releasing.md](releasing.md)). Without it on the jobs Worker the jobs fail and wait; without it on the app the endpoint answers 503.

To stop these emails in an emergency (a bug that sends too many, a complaint wave), with the deploy credentials: delete the pending work, `wrangler d1 execute portifact-control --remote --command "delete from comment_notices; delete from outbox where topic = 'comment_notice'"`, and repeat it after each scheduled run until a fix is deployed; or deploy the jobs Worker without `UNSUBSCRIBE_SECRET` (`wrangler secret delete UNSUBSCRIBE_SECRET --name portifact-jobs`), which keeps every job failing before it sends. Budget protection that pauses annotation writes also stops new activity, since nothing is marked without a write. Nobody's comments or preferences change either way.

## Webhooks

Owners whose plan includes `webhooks` (Pro and above) send events about their artifacts to their own HTTPS endpoints, Slack or Discord ([decision 0009](decisions/0009-webhooks.md); rules in "Webhooks" in [security.md](security.md)). Up to 10 per owner (a personal space or a workspace), managed by its admins in the dashboard's Webhooks page (with the space chosen in the space menu) and with `portifact webhooks` (`--workspace <slug>` for a workspace; MCP agents can only list them). A workspace's webhooks, counters and plan gate are the workspace's; they go with the workspace when it is deleted, and a transfer drops the artifact's events still waiting for the source's webhooks. Events include `review.requested` and `review.completed` (decision 0013). They ship switched off: the deployed Workers do not set `WEBHOOKS_ENABLED`, so nothing is created or delivered until the release checks in [releasing.md](releasing.md) ("Webhooks") pass.

- A write that causes an event adds its pending row (`webhook_events`, counts and IDs, never text) and a `webhook_delivery` outbox job, available a minute later, to its own batch; a burst lands in the same row and job. The outbox relay runs every minute (`RELAY_CRON` in `apps/jobs/src/index.ts`), so a delivery usually arrives one to two minutes after the first write.
- The job (`deliverWebhook`) sends one signed `POST` with up to 50 events, with a 5-second timeout and no redirects, alongside the batch's other jobs, and records each attempt in `webhook_deliveries` (outcome, status or error kind, never a body; pruned after 7 days). Network errors, timeouts, 408, 429 and 5xx are retried after 1 minute, 5 minutes, 30 minutes, 2 hours and 6 hours, with the same delivery ID; other answers are not. 15 failed attempts in a row disable the webhook (`failures`), a 410 at once (`gone`), a URL that no longer passes validation too (`invalid_url`), and a value sealed with a key the Worker no longer holds (`key_unavailable`, after a restore past a key rotation: put that key back in `WEBHOOK_KEY_PREVIOUS`, or the owner removes and adds the webhook again). The admin sees the reason and enables it again, an hour after an automatic disable at the earliest and at most 3 times a day; a re-enabled webhook is disabled again after 3 failures until it has a success.
- Each owner gets at most 1,000 attempts per UTC day (`WEBHOOK_LIMITS.attemptsPerOwnerPerDay`), counted in `rate_limits` under `webhook:attempts:<owner>:<day>` before each send; past it, jobs wait for the next day with one `daily_cap` entry in the log. Creates (20 a day), tests (20 an hour) and enables (20 a day) are counted per owner under `webhook:create:`, `webhook:test:` and `webhook:enable:`. While budget protection blocks uploads (US$100, or `budget-override protect100`), deliveries wait 15 minutes at a time and keep their events; the writes that cause them are never refused.
- A plan that loses `webhooks` stops deliveries and drops what was pending; nothing is deleted, and the webhooks work again when the plan returns.
- The maintenance run prunes the log (`webhooks.prunedDeliveries`) and gives any webhook with pending events and no job a new one (`webhooks.requeued`). It also re-seals webhooks of a rotated key (`webhookKeysRewrapped`, `webhookKeysLeft`; see [releasing.md](releasing.md)).
- Suspending an account or an artifact does not stop webhooks by itself: a suspended artifact has no new activity, and a suspended account cannot publish. To stop one owner's webhooks, disable them with `wrangler d1 execute portifact-control --remote --command "update webhooks set disabled_at = unixepoch() * 1000, disabled_reason = 'manual' where owner_id = '<owner>'"`.

To turn webhooks off for good (or keep them off), leave `WEBHOOKS_ENABLED` unset on both Workers: the app refuses new ones and the jobs Worker's next maintenance run disables every enabled webhook with the reason `unavailable` (`webhooksStopped` in its log line); admins enable them again once the variable is back. To stop every delivery in an emergency without disabling anything (a receiver complains, a bug sends too much), set the emergency stop on the jobs Worker: `echo 1 | npx wrangler secret put WEBHOOKS_PAUSED --name portifact-jobs` from `apps/jobs`. A secret change takes effect without a code deploy; jobs then wait 15 minutes at a time, keeping their events. `npx wrangler secret delete WEBHOOKS_PAUSED --name portifact-jobs` resumes them. Deleting `WEBHOOK_KEY` from the jobs Worker also stops them (every job fails before sending), but it is a key, not a switch: prefer `WEBHOOKS_PAUSED`.

## Issue integrations

Owners whose plan includes `integrations` (Team and above) create GitHub, Linear or Jira Cloud issues from comment threads ([decision 0018](decisions/0018-issue-integrations.md); rules in "Issue integrations" in [security.md](security.md)). Admins connect a service on the dashboard's Integrations page with a credential they paste (a GitHub fine-grained token limited to Issues on chosen repositories, a Linear API key, or a Jira API token with scopes with its account's email, the site and its cloud ID); the owner side creates issues from the viewer's thread menu, the API, MCP (`create_issue_from_thread`) or `portifact issue`. They ship switched off: the deployed Workers do not set `INTEGRATIONS_ENABLED`, so nothing is offered until the checks in [releasing.md](releasing.md) ("Integrations") pass.

- A request writes its `thread_issues` row and a `thread_issue` outbox job in one batch; the jobs Worker creates the issue (`runThreadIssue`) and the thread then links it. Retries after 1, 5, 30 and 120 minutes; before each retry the job looks for an issue the previous attempt created and lost the answer of. Failed requests stay on the thread for the person who asked, with the reason.
- A credential the service refuses (401) marks the connection `credential_rejected`; one sealed with a key the Workers no longer hold, `key_unavailable` (after a restore past a key rotation: put that key back in `INTEGRATIONS_KEY_PREVIOUS`). Issues stop through it until an admin pastes a new credential or a test passes.
- Per owner and UTC day, 200 issue requests (`integration:issues:<owner>:<day>`) and 1,000 attempts (`integration:attempts:<owner>:<day>`) in `rate_limits`; past the attempts, jobs wait for the next day. Connection creates (20 a day) and credential checks (30 an hour) are counted under `integration:create:` and `integration:check:`.
- The maintenance run gives a pending request whose job went missing a new one (`threadIssues`) and re-seals credentials of a rotated key in every region (`integrationKeysRewrapped`, `integrationKeysLeft`).
- To stop one owner's issues, mark its connections: `wrangler d1 execute portifact-control --remote --command "update integration_connections set attention = 'credential_rejected', attention_at = unixepoch() * 1000 where owner_id = '<owner>'"` (the owner's region's database for an EU workspace). To stop all of them, unset `INTEGRATIONS_ENABLED` on both Workers: pending jobs then fail with `unavailable` and send nothing.
- A leaked credential is the customer's to revoke at GitHub, Linear or Atlassian; removing the connection deletes it from Portifact and writes a tombstone, so a restore cannot bring it back.

## Slack connections

A workspace's admins connect their own Slack app ([decision 0025](decisions/0025-slack-integration.md); "Slack connections" in [security.md](security.md)). Connections are rows of `integration_connections` with `service = 'slack'`, so the issue integrations' tombstones, deletions, export and key rotation cover them.

- A started connection is `pending` until an admin pastes the bot token and signing secret; the maintenance run deletes pending rows older than 24 hours in every region (`pendingConnections` in its result). They hold no credential and write no tombstone.
- `app_uninstalled` means Slack told Portifact the app was uninstalled or its tokens revoked; `credential_rejected`, that `auth.test` refused the token on Test or `chat.unfurl` refused it for a preview; `key_unavailable`, that the sealing key is gone. Each needs an admin to paste a new token and secret. One `integration.failing` is recorded for each.
- To stop one owner's Slack connections at once, mark them like any connection: `update integration_connections set attention = 'credential_rejected' where owner_id = '<owner>' and service = 'slack'`. To stop every Slack connection, unset `SLACK_ENABLED` on `portifact-app`: the endpoint answers 404 and Slack disables the subscription after its failures, which the admins re-enable with "Verify" later.
- Removal revokes the bot token at Slack only while `SLACK_ENABLED` is on: with Slack switched off nothing calls Slack, so a connection removed meanwhile is deleted from Portifact (row, sealed value and, after the tombstone, any restored copy) but its token stays alive at Slack until the customer deletes or reinstalls the app. Before switching Slack off, tell the admins of every owner with a Slack connection (`select owner_id, id from integration_connections where service = 'slack' and attention is distinct from 'pending'`, in each region) that removing one while it is off does not revoke the token, and that deleting the app in Slack does. The token can only read and change link previews (`links:read`, `links:write`), so this is a cleanup step, not an incident.
- A leaked bot token or signing secret is the customer's to rotate in Slack (reinstall the app, or "Regenerate" the secret) and paste again. Removing a connection revokes its bot token at Slack (`auth.revoke`, logged as `slack_token_revoke`); the app itself stays in the customer's Slack workspace until they delete it.
- The endpoint's log line is `slack_event` with `connectionId` and `outcome` (`refused`, `verified`, `ignored`, `team_mismatch`, `uninstalled`, `failed`, and for previews `nothing_to_unfurl`, `unfurled`, `slack_error`, `rate_limited`, `credential_rejected`, `timeout`), plus `candidates` and `unfurled` counts for an event. A burst of `refused` for one connection is someone without its signing secret, or a secret pasted wrong (the admin's "Verify" in Slack fails too). `slack_error` is usually `cannot_unfurl_url` (the Slack workspace blocks the domain) or Slack failing; nothing counts them, nothing is retried, and the connection is not marked. `rate_limited` is Slack's limit per Slack workspace (Tier 3); previews are dropped, never queued.
- Previews show only the name and type of public, active artifacts of the connection's own owner. Slack keeps a preview in the message it was added to and Portifact keeps no record of where it unfurled, so a customer asking to take back a preview of an artifact that is no longer public deletes or edits the message in Slack; Portifact cannot. A preview of an abusive artifact goes when the artifact is suspended only for new posts, the same way.

## Brands

Owners whose plan includes `branding` show a name, logo, color and link on the viewer's bar ("Owner branding" in [security.md](security.md)). A brand that impersonates someone, imitates Portifact or links to phishing is handled like an abusive artifact, but its suspension is separate:

- `brand <owner>` (user ID, email or workspace ID) prints the brand with its text on one quoted line each, the logo's type, size and hash, whether it is suspended and whether the viewer shows it.
- `suspend-brand <owner> --reason <reason> --facts "..." --ground "..."` sets `owner_brands.suspended_at`: the viewer shows the default bar on every artifact of the owner at once and the logo stops being served; the brand is kept, the owner sees "Your brand is suspended" with the category and the statement of reasons on the Branding page and cannot delete it. Suspend the artifacts too when they are abusive themselves. `reinstate-brand <owner> --facts "..."` lifts it. Both are idempotent; there is no web route for either.
- When the owner's plan stops including `branding`, the default bar shows and the brand is kept; nothing needs doing. A logo counts in the owner's storage and is released when it is replaced, removed or the brand is deleted, through a `delete_objects` job.
- Logos are stored at `brands/<owner>/<sha256>` in R2, which the storage reconciliation does not scan (it lists `objects/`). Deleting an account deletes its brand and logo when the deletion finishes.
- A D1 Time Travel restore rewinds `owner_brands`: brands changed since come back as they were (a logo deleted since then is missing and the viewer shows the brand without it), and so do suspensions, like artifact suspensions. Before restoring, note the suspended brands (`npx wrangler d1 execute portifact-control --remote --command "select owner_id, suspension_reason from owner_brands where suspended_at is not null"`) and suspend them again after `apply-tombstones`. `apply-tombstones` deletes the brand of a deleted account the restore brought back.

## Account deletions

Deletions need no operator action: the request removes the user at once and the scheduled jobs finish the rest (see "Account deletion" in [security.md](security.md)). `select * from account_deletions` lists the ones still in progress.

## A leaked service token

A service token (decision 0011) leaked: in a log, a public repository, a compromised CI. Revoking it stops it at its next request.

1. The workspace's admins revoke it on the workspace's Service tokens page in the dashboard. If they cannot be reached, the operator finds it from the secret and revokes it: `printf '%s' "$SECRET" | bun run --cwd apps/jobs operator find-service-token` (standard input, never the command line; it prints the token ID, label, workspace and expiry, never the secret), then `bun run --cwd apps/jobs operator revoke-service-token <st_…>`, which deletes the row and writes the `service_token` tombstone.
2. Check what it did: versions whose author is the token ID (`select artifact_id, number, created_at from versions where author_id = '<st_…>'`), `lifecycle_events` with that `actor_id` (renewals, archives, deletions and access changes), and artifacts whose `created_by` is it. Its last use is on the Service tokens page, to the hour. If it held `artifacts:share`, check the workspace's artifacts that are `public` or have share links; if it held `artifacts:delete`, check `purging` artifacts of the workspace (a deletion cannot be undone).
3. Tell the admins to create a new token for the job, with the narrowest scopes and a key prefix restriction.

## GitHub Actions trust

GitHub repositories a workspace trusts through OIDC ([decision 0024](decisions/0024-github-oidc-federation.md)), shipped switched off (`GITHUB_OIDC_ENABLED`).

- **Revoking.** An admin removes the repository on the workspace's Service tokens page, section GitHub Actions: the rule and every credential issued from it are deleted in one batch, with a `github_trust_rule` tombstone, so a run holding a credential is refused at its next request. Without an admin, the operator deletes the rule with `wrangler d1 execute` (`delete from github_trust_rules where id = '<gtr_…>'`, after inserting `('github_trust_rule', '<gtr_…>', <now>)` into `tombstones`); its credentials go by the cascade. A single leaked credential (`pfst_…` labelled `GitHub owner/name run N`) is found and revoked like any service token ("A leaked service token"); it expires within 15 minutes anyway.
- **What a run did.** Each exchange is a `github_trust.exchanged` event in the workspace's audit log, with the repository, event, run ID and attempt; the credential is the actor of everything it changed (`versions.author_id`, `lifecycle_events.actor_id` and `artifacts.created_by` hold its `st_` ID).
- **GitHub's keys unreachable.** Each isolate tries GitHub's key set at most once a minute, whether the last attempt worked or not, and shares one fetch among concurrent requests. A set that once worked keeps verifying for three hours, so exchanges keep working through a short outage; an isolate that never got one refuses them and logs `github_oidc_jwks_unavailable` (and `github_oidc_refused` with `reason: "jwks_unavailable"`). Credentials already issued keep working until they expire. Nothing to do on Portifact's side: check GitHub's status; workflows can fall back to a `PORTIFACT_TOKEN` secret meanwhile. Many `reason: "signature"` lines may be someone sending tokens with made-up keys, which cost no extra fetch. After GitHub starts signing with a key the cached set lacks, a run may be refused for up to a minute; re-run it.
- **GitHub signing key compromised.** You learn of it from GitHub (its security advisories, the GitHub Changelog or status page) or from the workspace's admins; Portifact has no feed for it. A cached key set is not fetched again for a key it already holds, so a key GitHub has removed keeps verifying in an isolate until its cache expires (up to an hour) or, while GitHub is unreachable, for up to three hours. To stop it at once: remove `GITHUB_OIDC_ENABLED` from `portifact-app` however it was set (`wrangler secret delete GITHUB_OIDC_ENABLED --name portifact-app` for a secret, or the Worker's variables in the Cloudflare dashboard; the exchange answers 404 from then on, and the change itself starts new isolates), or redeploy the app Worker unchanged, which starts new isolates with empty caches that fetch GitHub's current key set. Credentials issued before that live up to 15 more minutes; to end them at once, delete them: `wrangler d1 execute portifact-control --remote --command "delete from service_tokens where trust_rule_id is not null"` (their exchanges stay in the audit log), or have the affected workspaces' admins remove their trust rules, which ends that rule's credentials in the same batch. Then check the audit log's `github_trust.exchanged` events since GitHub says the key was exposed, and what those credentials changed ("What a run did"). Switch the variable back on once GitHub's key set no longer holds the key.
- **Restore.** Rules are global rows: `export-tombstones` before a D1 Time Travel restore carries the `github_trust_rule` markers, and `apply-tombstones` deletes restored rules that were removed or changed (a change replaces the rule with a new ID and tombstones the old one), with their credentials by cascade. Rules created or changed after the restore point are lost: tell the workspace's admins to add them again. Used ID tokens (`github_used_tokens`) are rewound too; a token used after the restore point could be exchanged once more only within its own remaining life (minutes), which is shorter than a restore takes, so nothing is exported for them. Credentials the restore brings back have long expired.
- **Pruning.** `runMaintenance` deletes run credentials an hour after they expire and used ID tokens once their `exp` plus a minute has passed, at most 500 each per run (`federatedCredentials` and `usedGitHubTokens` in the run's log line).
- **A changed rule.** A change saves the rule under a new ID; the dashboard and the audit log (`github_trust.changed` names the new ID) follow it, and the old ID answers like a missing rule.

## Workspaces

Workspaces are created and deleted only by the operator while there is no billing (premium plan T1): every workspace has its own quotas, so free self-service workspaces would multiply the free quota. Self-service arrives with billing.

- `workspace-create <slug> --name <name> --admin <user-id|email>` creates it in the default region with that account as its first admin (`createWorkspace`). `--plan team|enterprise --seats N [--until] [--note]` grants the plan in the same command; the plan is checked before anything is written, and if granting it fails afterwards the command says so and `set-plan workspace:<slug>` grants it. Without a plan the workspace is on `free`, with one seat, so its admin can invite nobody. Slugs are 1 to 40 lowercase letters, digits and inner hyphens, unique, and `personal` is reserved.
- A plan's `seats` cap the members (admins, editors and members) plus pending invitations; external readers of an artifact do not count. Lowering the seats or letting the plan expire removes nobody: new members and invitations are refused until the workspace is back under the cap.
- Admins manage members and invitations from the dashboard (session only; there is no operator command for them). The last admin of a workspace can never be removed or demoted and cannot leave or delete their account (`sole_workspace_admin`): when an admin must go, make another member admin through them, or delete the workspace. To recover a workspace whose only admin is unreachable, insert the new admin's membership with `wrangler d1 execute` (`insert into workspace_members (workspace_id, user_id, role, updated_at) values (...)`) only after verifying the request, and record why.
- `workspace <slug>` shows members (addresses masked), pending invitations, seats in use, the artifacts count and the plan; `workspaces` lists them.
- `workspace-delete <slug> --confirm <slug>` deletes it (`deleteWorkspace`): in one batch it records the deletion with a `workspace_deletion` job, claims every artifact for purging (they stop being served at once) and deletes the workspace row, its memberships and its invitations. The jobs release its custom domains and claims, finish it once the artifacts are purged and leave a `workspace` tombstone; `select * from workspace_deletions` lists the ones in progress. There is no undo.
- Invitation emails count in the month's email budget and stop at the same capacity as expiry notices. An address gets at most 5 invitations a day across workspaces (the `rate_limits` key holds a hash of it, never the address). A suppressed address gets no email, but the admin gets the same answer as for any other address (an `invitation_not_sent` log line says so, with the reason only); the invitation expires unanswered. To help an admin whose invitee never got the email, check the address with `email-suppressions` and lift it if appropriate (see "Email quota and suppressions").
- Moving an artifact (`portifact transfer`, MCP `transfer_artifact`, the API) needs an admin of a source workspace. The move bumps the artifact's generations, so its open read, review and share link sessions end; its access log and view counters follow it through the `access_history_move` job, which re-owns the rows in `portifact-access` and sets their expiry from the target's plan. An artifact in the `workspace` or `domain` access mode becomes `restricted` in the same batch.

### Workspace email domains

Admins verify email domains on the Members page (premium plan T2, [decision 0010](decisions/0010-workspace-access-modes.md)); artifacts in the `domain` access mode are then read by anyone signed in with a verified address at one of them. There is no operator command and no CLI or MCP path for them.

- Rows live in `workspace_domains` (global): `pending` claims with a fresh token for 7 days, then `verified`. At most one workspace has a domain verified (a partial unique index); at most 10 domains per workspace.
- The maintenance run re-checks every verified domain whose last check is more than 24 hours old (50 per run, `recheckEmailDomains`) through DNS over HTTPS, and drops pending claims past their expiry. A missing record counts a miss (`failed_checks`, `problem = 'txt_missing'`, which the Members page shows with the misses left), a found one resets it, and the third miss in a row deletes the row with a `workspace_domain` tombstone. A resolver failure counts nothing; the run's log line carries `emailDomains` with `checked`, `removed`, `unavailable` and `expiredClaims`, or `failed`.
- A workspace that proves a domain another workspace holds takes it over only when the holder's record is gone from the same answer; otherwise the claimant is told another workspace still proves it. A complaint that a domain was verified by the wrong workspace is answered by asking the domain's DNS operator to remove that workspace's `_portifact-email.<domain>` record: the next daily checks remove it, and the rightful workspace can then verify. In an emergency (an employer reports a former workspace keeping its domain) delete the row with `wrangler d1 execute` after verifying the request, insert a `workspace_domain` tombstone with its ID, and record why: readers who matched it stop within a minute.
- Deleting a workspace removes its domains with it.

### Workspace single sign-on

Admins set up one OpenID Connect provider per Enterprise workspace on the Members page ([decision 0016](decisions/0016-workspace-sso.md)); there is no operator command and no CLI or MCP path. It ships switched off (`SSO_ENABLED`, [releasing.md](releasing.md), "SSO").

- The row is `workspace_sso` (global): issuer, client ID, the sealed client secret and the verified domains it serves. Identities linked through it are Better Auth `accounts` rows with `provider_id = 'sso:<id>'`.
- People who sign in through it join the workspace as members (or with a pending invitation's role) while it has a free seat; nobody is removed when they leave the identity provider. To cut someone off, remove them from the members list and, if needed, end their sessions.
- Removing a member writes a `workspace_removals` row, so their next single sign-on does not bring them back (`sso_removed`); inviting them again lifts it. A person whose existing account the provider cannot vouch for (`sso_link_required`) signs in once with an email code and uses "Link single sign-on" on the login page.
- A customer who lost their identity provider can still sign in to Portifact with an email code, but that sign-in does not satisfy a workspace's active single sign-on requirement (decision 0021); the operator may need to clear the requirement (`clear-request-policies`).
- Removing the provider writes a `workspace_sso` tombstone, so a restore cannot bring it back (`apply-tombstones` deletes it and its linked identities again). A provider whose secret was sealed with a retired `SSO_KEY` stops signing in until an admin enters the secret again.

### Workspace SCIM provisioning

Admins create a SCIM token in the Directory sync section of the Members page and paste it, with the base URL `https://app.portifact.com/scim/v2`, into their identity provider ([decision 0017](decisions/0017-workspace-scim.md)). Switched off until `SCIM_ENABLED="true"` ([releasing.md](releasing.md), "SCIM").

- Rows are global: `scim_tokens`, `scim_users` (the directory's copy of each person: the address, `externalId`, the names it sent, `active`, the linked account and `removed_at`), `workspace_scim` (whether provisioned people get the invitation email; off by default) and pending memberships in `workspace_invitations` with `source = 'directory'`. They go with the workspace.
- A provisioned person without an account holds a seat until they sign in or for 90 days after the directory's last write (`SCIM.pendingDays`); the maintenance run then drops the pending row and, once nothing links it to an account, the directory's copy (`pruneDirectoryUsers`).
- The directory deactivating someone removes them from the workspace, signs them out everywhere and blocks single sign-on (`workspace_removals`). An admin removing a SCIM-provisioned member by hand holds against the directory's routine syncs; the directory brings them back only by deactivating and reactivating them, or deleting and creating them again. A person who left by themselves comes back only through a delete and a new create. An existing account the directory adds gets one `directory_notice` email (skipped lines log `directory_notice_skipped` with the reason only). A `429` on authentication is the per-IP limit on failed attempts (20 in 10 minutes): the directory's own requests are never counted.
- A directory that gets `403` on create is out of seats: grant more (`set-plan`) or free some. `400 mutability` on a deactivation is the last admin: another member must become admin first. `401` after it worked: the token was revoked or expired; the admin creates a new one.
- The audit log names the directory by the token's label (`Okta (directory)`).
- Groups the directory pushes are workspace groups marked as directory-managed (`scim_groups`). The Groups page shows them as "Managed by your directory" and does not change them, so an admin who needs a change makes it in the directory. The directory's own view of each group, pending people included, is `scim_group_members`. A group a customer made in the dashboard is never taken over: the directory's `POST` with that name gets `409`, and the customer renames one of the two.
- A directory-managed group that must change while the directory cannot (a revoked token, a lapsed plan, SCIM switched off): an admin chooses "Stop syncing" on the Groups page. The group becomes an ordinary group, its mapping is cleared, and the people it gave a role keep it. A later push of a group with that name answers `409`.
- **After a D1 Time Travel restore**, `apply-tombstones` also recomputes roles from the current directory groups for every workspace with a role mapping, so a role the directory took away does not come back with a rewound row. The result's `directoryRoles` counts the workspaces; when there are more than 500, run `apply-tombstones` again (it is idempotent) until it reports fewer. A workspace it skips because the recompute would leave no admin needs an admin by hand first.
- Role mapping (Members page, Directory sync): one directory group for `editor`, one for `admin`. A `400 mutability` on a group push, a group delete or an unmapping means the change would demote the last admin: make someone else an admin by hand first. The directory only takes back a role it gave: a role an admin changes by hand is the admin's from then on (the directory can still raise it if the person's groups give more).

## A leaked SCIM token

A SCIM token (decision 0017) leaked. Whoever holds it can provision and deactivate the workspace's people at its verified domains (never create accounts, never change roles, never reach artifacts). Revoking it stops it at its next request.

1. The workspace's admins revoke it in the Directory sync section of the Members page. If they cannot be reached: `printf '%s' "$SECRET" | bun run --cwd apps/jobs operator find-scim-token` (standard input, never the command line; it prints the token ID, label, workspace and expiry, never the secret), then `bun run --cwd apps/jobs operator revoke-scim-token <sc_…>`, which deletes the row and writes the `scim_token` tombstone.
2. Check what it did: the workspace's audit events with `actor_type = 'directory'` and that `actor_id` (`select kind, target_id, at from audit_events where owner_id = '<ws_…>' and actor_id = '<sc_…>' order by at`). People it deactivated were signed out; an admin re-adds them or the directory re-provisions them.
3. Tell the admins to create a new token and paste it into the identity provider.

## Workspace policies

A workspace's admins set its policies on the dashboard's Policies page ([decision 0015](decisions/0015-workspace-policies.md)); there is no operator command to set them, only `export-policies` and `apply-policies` around a restore. A save that changes existing artifacts runs the `workspace_policy` outbox job, 50 rows of each kind per step until done. Every 15-minute run also scans: one global query reads up to 500 workspaces with a policy (from a cursor when there are more), one regional query finds those whose artifacts break their policy, and up to 20 of them get a step, public access first, so a violation is corrected within one run. The `maintenance` log line reports `workspacePolicies: {checked, corrected, failed}`; a failure logs `workspace_policy_enforce_failed` or `workspace_policy_unreadable` (a stored policy that no longer parses: fix the row, its workspace is skipped meanwhile) with the error's name only, and never stops the run. Each step records `policy.enforced` in the workspace's audit log with counts, and each changed artifact its own `access.changed` by the system. To see a workspace's policy: `npx wrangler d1 execute portifact-control --remote --command "select policy, policy_revision from workspaces where slug = '<slug>'"`. A customer whose plan ended keeps its policies; an admin loosens or removes them from the page, without the plan. After a restore of only the regional database (artifacts, readers and links rewound, policies kept), nothing needs running: the next scheduled run finds and corrects every workspace in violation; check its `workspacePolicies.corrected`.

### Maximum life of artifacts

A workspace can archive its artifacts a number of days after their last publish, restore or move into it ([decision 0023](decisions/0023-workspace-retention-policies.md)). It never deletes anything by itself: it only brings `expires_at` forward, and `archiveExpired` archives what reaches it, as any expiry. What the scans do: the `workspace_policy` job (written by every save while one is set, run on the workspace's own region) and the 15-minute `enforceWorkspacePolicies` scan unpin pinned artifacts and cap each active artifact's expiry at its deadline, never earlier than the date the maximum takes effect (7 days after it was set or shortened) and never earlier than now, 50 a step, with `policy.enforced` (`deadlinesSet`) and an `artifact.unpinned` by the system per unpinned artifact in the workspace's audit log. Each capped artifact keeps the expiry its plan gave it (`artifacts.uncapped_expires_at`), and every step first gives back to `min(that expiry, the current deadline)` what the policy no longer asks for (`deadlinesExtended`), so after any sequence of saves nothing stays capped by a rule that changed, and a removal returns every artifact to its plan's expiry. Owners the steps do not visit (a workspace whose maximum was removed, a personal space a capped artifact moved to) are covered by the stale-cap sweep in the same scan: one call per run while nothing is capped, otherwise at most 20 owners and 200 artifacts a run, 50 per owner per pass, from a cursor (`stale_caps` in `maintenance_cursors`, logged as `stale_caps_sweep_failed` if it fails), and the expiry run gives a stale cap back instead of archiving by it. Until that run, an artifact whose stale cap passed reads as archived (at most 15 minutes); its row stays active and nothing is deleted. To see what the policy caps in a workspace now: `select id, expires_at, uncapped_expires_at from artifacts where owner_id = '<workspace ID>' and uncapped_expires_at is not null`. An artifact moved into the workspace starts a new life there (it is never archived sooner than the maximum's days after the move). An artifact archived while a cap held it records `artifact.archived` by the system with `policy: artifactMaxDays`. Every admin gets one email when it is set or shortened (`retention_notice` job; `retention_notice_skipped` logs only the reason). What a customer who lost something can still recover, and until when: an artifact archived by the policy is an ordinary archived artifact, restorable by an admin or editor from its page until its `purge_at` (the plan's archive months, 6 on free and 12 on paid plans, counted from the archive and never shortened by the policy); a restore gives it a new life of at most the maximum. After `purge_at` it is gone like any purged artifact. A customer who set a maximum by mistake removes or lengthens it on the Policies page (no plan needed); artifacts already archived stay archived until restored. To see which artifacts the policy archived: `select target_id, at from audit_events where owner_id = '<workspace ID>' and kind = 'artifact.archived' and json_extract(detail, '$.policy') = 'artifactMaxDays'`.

### Comment retention

A workspace can delete its comment threads a number of days after their last activity ([decision 0023](decisions/0023-workspace-retention-policies.md), "Comment retention"). Unlike the maximum life, this deletes for good: nobody, the operator included, can recover a deleted thread or its messages, and no restore brings it back (that is the point of its tombstones). What the scan does: `enforceCommentRetention`, every 15 minutes per region, deletes whole threads whose clock is older than the period (a resolved thread's last activity; an open thread's last activity or the moment its version was replaced, whichever is later; never open threads on an artifact's current version, never on a suspended artifact, never within 7 days of an artifact moving in, never before the rule's effective date), at most 50 per workspace and 200 per run and region, from a cursor (`comment_retention:<region>` in `maintenance_cursors`). The `maintenance` log line reports `commentRetention: {checked, threads, suspended, paused, failed}`; `comment_retention_failed` (one workspace, the error's name only) never stops the run. Each batch records `policy.enforced` with `threadsDeleted` and `messagesDeleted` in the workspace's audit log. With a separate regional database the tombstones are written by a `comment_tombstones` job from the region's outbox; one left failing (`outbox` rows of that topic with growing `attempts`) means deleted threads a restore could bring back, so treat it before any restore. A workspace whose plan no longer includes `policies` has its rule removed by the system (`policy.changed`, reason `plan_lapsed`) and nothing is deleted; its admins set it again once the plan is back. To see what a workspace's rule would delete now, ask its admins to open the preview on the Policies page (it shows counts). The restore guard (decision 0023, "Restores"): each workspace's rule carries a random token, saved in its policy and in a record in its region's bucket (`system/comment-retention/<workspace>`); the scan deletes for a workspace only while the two agree, read right before each batch. `paused: true` with `heldBack` counts the workspaces with threads due that did not agree this run, and `comment_retention_held` logs why (`missing`, `different`, `unreadable`, `unavailable`). That is expected after a restore of the global database, and after a save whose record could not be written; the workspace's Policies page then says the rule is set but not in force, and an admin fixes it by saving the rule again (a new notice period, like any new rule). Never write a record by hand: the token's only job is to tell the policy saved last from a restored one, and a record written by hand would arm whatever the database holds. A lengthening is refused while the region's R2 cannot be written, and any change of the rule (but a removal) while its record cannot be read (the admin sees "The comment retention rule could not be changed right now, so nothing was saved. Try again in a few minutes."; the API answers `capacity_unavailable` with `details.reason` `comment_retention_guard`); deletions are held back meanwhile, since the scan cannot read R2 either. A removal is never refused: it deletes the record before and after its D1 write. A record can outlive its rule whenever a guard write fails (both of a removal's deletes, a new rule's confirmation, a lengthening's write that landed although R2 answered with an error, a workspace deletion's cleanup; each logs `comment_retention_guard_write_failed`). The scan sweeps such records by itself (decision 0023, "The sweep"): every run, per region, one R2 list of `system/comment-retention/` (at most 100 keys, from the `comment_retention_guard:<region>` cursor in `maintenance_cursors`) deletes any record at least 10 minutes old whose workspace no longer exists, is in another region, sets no rule or a rule with another token, days or date, unless the workspace's row changed in the last 10 minutes. The `maintenance` line reports `commentRetention.guardSweep: {listed, deleted, young, foreign, failed}`. The sweep only deletes, so it can only pause a rule (the Policies page then says it is set but not in force). A key under the prefix that is not a workspace ID is left alone and logged once (`comment_retention_guard_foreign`): delete it by hand after checking what wrote it. The manual delete is the fallback for when the sweep cannot run: `comment_retention_guard_sweep_failed` with `reason: list` (or `comment_retention_scan_failed`) on every run of a region for more than an hour while `comment_retention_guard_write_failed` was logged. Then read the stored policy (`npx wrangler d1 execute portifact-control --remote --command "select json_extract(policy, '$.commentRetentionDays'), json_extract(policy, '$.commentRetentionToken') from workspaces where id = '<workspace-id>'"`) and the record (`npx wrangler r2 object get portifact-artifacts/system/comment-retention/<workspace-id> --remote --pipe`); if the policy sets no comment retention, or a token other than the record's `token`, delete the record once R2 answers: `npx wrangler r2 object delete portifact-artifacts/system/comment-retention/<workspace-id> --remote` (`portifact-artifacts-eu` and `--jurisdiction eu` for a workspace in the EU region, in both R2 commands). Deleting a record never arms anything; at worst it pauses a rule its admins save again. The record holds the rule's token, days and date, so a policy edited by hand never agrees with it. What it costs: one R2 read per workspace per run, only for a workspace with threads due in that run; the sweep's one R2 list per run and region (class A, about 2,900 a month per region, whether or not the prefix holds a record), plus a global read, a `get` (class B) and a `delete` only for records old enough to judge; no R2 write on any scan; one write per save that changes the rule, per lapse and per operator plan change of a workspace with a rule. A workspace whose stored policy is not valid JSON is skipped (`workspace_policy_unreadable`), never the region.

### Network allowlists and the escape hatch

A workspace's policies can limit the networks its people and its service tokens act from ([decision 0020](decisions/0020-workspace-request-policies.md)). Members outside them get `policy_refused` naming the network policy and their own address; the dashboard shows "Not reachable from this network" for that workspace. Saving a list that excludes the saving admin's address is refused, but an office or VPN change can still leave every admin outside. Then, after confirming with the customer who asks (an admin of the workspace, through the usual support channel), run `bun run --cwd apps/jobs operator clear-request-policies <slug|workspace-id> --confirm <slug>`. It lifts both network allowlists and nothing else (public access, reader domains, share links and the default access stay), records `policy.changed` by the operator in the workspace's audit log with counts, and takes effect at once (within a minute for an EU workspace's artifacts). It answers that nothing changed when there is no list. The admins set a correct list again from the Policies page. When a customer reports a lock-out, check first: whether their list covers both address families (a list of only IPv4 ranges refuses everyone whose request arrives over IPv6, and the app and the artifact origin are different zones that a dual-stack browser may reach over different families; the Policies page and the save confirmation warn about it, but an admin can confirm it anyway); whether the address the refusal message shows is in a 240.0.0.0/4 range (then Pseudo IPv4 is overwriting headers on that zone: [releasing.md](releasing.md), "Client addresses"); and whether the jobs or content Worker logs show `workspace_network_policy_unreadable` with the workspace's ID (a stored list that does not parse refuses everyone, by design; `clear-request-policies` lifts it). The lists are part of `export-policies` and `apply-policies`. `apply-policies` validates and normalizes every line before applying any (one invalid policy refuses the whole file, naming its line, and nothing is applied), and never lifts a restriction a workspace has now that the file does not have (an export older than an allowlist, a public-access ban or a link rule): it lists those workspaces and the fields and leaves them as they are. Pass `--allow-lifting` only when lifting them is the intent, for example after confirming with the customer that a restriction set after the export was a mistake. After a restore, check that the restored lists still admit the admins' networks, since a list from before the restore point may name an old office.

### Sign-in policies and lock-outs

A workspace can also limit how long a sign-in may act on it and which kinds of app may act ([decision 0021](decisions/0021-workspace-session-policies.md)). A member refused for an old sign-in gets "Sign in again" in the dashboard and `policy_refused` naming `portifact login` in the CLI or "reconnect this app" in MCP; signing in again fixes it, nothing is signed out. An admin cannot save a maximum their own sign-in already exceeds, and the dashboard is always an allowed client, so a lock-out needs every admin unable to sign in at all; then `clear-request-policies` lifts the network lists and both sign-in policies (and nothing else) as above. When a customer reports that the CLI keeps being refused right after `portifact login`, check that the token rows have `auth_time` (migration 0058's triggers): `select auth_time from oauth_access_tokens where user_id = ? order by created_at desc limit 1` must be recent; a 0 means a grant from before the release, which `portifact login` replaces. `export-policies`/`apply-policies` carry both fields, validate them and report a longer or missing maximum, or more allowed kinds, as a lifted restriction applied only with `--allow-lifting`.

### SSO required and lock-outs

A workspace can require that people act on it only through its own single sign-on ([decision 0021](decisions/0021-workspace-session-policies.md), "SSO required"). Admins are bound like everyone: there is no admin exemption by design. A member refused gets "Sign in with single sign-on" in the dashboard, `policy_refused` telling the CLI user to sign in to the dashboard through single sign-on and then run `portifact login` and approve it from that browser, and an MCP refusal asking the user to sign in through single sign-on and reconnect the app. Lock-outs come from the identity provider: when it is down, misconfigured (a rotated client secret, a changed redirect URI, a deleted app) or no longer issues the `email` claim, nobody can act on the workspace. What to tell a customer whose provider is down: their people keep their accounts, personal spaces and other workspaces; nothing is lost; the workspace becomes reachable again the moment the provider works, or at once if an admin asks us to lift the requirement. After confirming with an admin of the workspace through the usual support channel, run `bun run --cwd apps/jobs operator clear-request-policies <slug|workspace-id> --confirm <slug>`: it lifts "SSO required" with the network lists and the sign-in policies, records `policy.changed` by the operator, and takes effect at once (within a minute on the artifact origin). The admins require it again from the Policies page once the provider works (which needs one of them to sign in through it first). Switching single sign-on off for the whole service does not lift it: the requirement keeps binding and nobody can meet it, so the release step lists those workspaces first (`operator workspaces --sso-required`). The requirement suspends itself, without anyone acting, while the provider serves no verified domain (an admin removed it, or the daily re-check did: `domain.removed` by the system in the audit log) or the plan lacks `sso`; removing the provider clears it (`policy.changed` by the system, reason `sso_removed`). Each suspension and resumption is in the workspace's audit log as `policy.sso_suspended` / `policy.sso_resumed` by the system, with its cause. A person removed from the identity provider keeps their CLI and app grants until the refresh chain expires; to cut them off now, an admin removes the member. When a member reports being refused right after signing in through single sign-on, check the session row: `select sign_in_method from sessions where user_id = ? order by created_at desc limit 1` must be `sso:<the workspace's provider ID>`; a null means the session was created by an endpoint that does not record a method. `apply-policies` refuses to apply the requirement to a workspace whose provider cannot sign anyone in (it lists them; set the provider up again first) and never lifts it silently.

## Traffic quota

An account whose artifacts served its plan's traffic in the current UTC month (1 million requests or 25 GB on `free`, the plan of every account without an `owner_plans` row; `PLANS` in `packages/contracts/src/plans.ts`) gets 429 on all of them until the next month ( see "Access control" in [security.md](security.md)). Its counters are in `traffic_counters`, one row per account and month, for example `select owner_id, requests, bytes from traffic_counters where cycle_start = <month start in ms> order by bytes desc limit 20` to see the largest consumers during a budget review. There is no operator command to raise or reset a counter; a higher quota comes with a plan (see "Plans" below). Counters older than the previous month are pruned by the maintenance job.

## Plans

Every owner has a plan (`free`, `pro`, `team` or `enterprise`, `PLANS` in `packages/contracts/src/plans.ts`); without an `owner_plans` row it is `free`, exactly the limits every account had before plans. Payment does not exist yet: the operator tool is the only way to grant, change or remove a plan, and there is no web route, API endpoint, MCP tool or CLI command for it, nor may there be one. A future billing webhook writes the same row through the same service.

- `<owner>` is an account (`<user-id|email>`) or a workspace (`workspace:<slug>` or its `ws_` ID); a workspace's Team or Enterprise seats are also its member cap (see "Workspaces").
- `set-plan <owner> <plan>` grants or changes it (`setOwnerPlan`, `packages/services/src/plans.ts`): `--seats` multiplies Team and Enterprise's per-seat limits, `--until` (an ISO date, UTC) ends it, after which the owner reads as `free`, `--note` records why, and `--overrides` takes JSON such as `{"limits":{"activeArtifacts":5000},"features":{"sso":true}}`, totals applied after seats (an Enterprise contract). It refuses an unknown plan, seats outside 1 to 10,000, an end in the past, invalid overrides, accounts that do not exist or are being deleted, and workspaces that do not exist (a deleted workspace's row is gone). It records `granted_by` as `operator`.
- The grant writes the row and the four limit columns the database's CHECK constraints compare usage against (`account_usage.active_limit` and `bytes_limit`, `annotation_usage.messages_limit` and `bytes_limit`) in one batch, creating the usage rows if the owner has none yet, so a later publish or comment finds the plan's limits. A column is never set below what the owner already uses: it holds the larger of the plan's limit and the usage. The rules that admit new work read the plan, not the columns, so the columns are only the safety net against races.
- `remove-plan <owner>` lowers the columns toward the free values in the same batch and, when the plan kept anything above free, keeps the row as `free` with its grace (see "Plan grace") instead of deleting it; `plan <owner>` shows the row, the effective plan (an expired plan shows as `free`), the features, each usage against its limit and column, and the grace.
- The maintenance scan `alignPlanLimits` (`alignedPlanLimits` in the `maintenance` log line) brings the columns back in line for owners whose plan expired, was removed or lowered, or whose usage fell: up to 50 owners a run, reading only owners with a plan row or a column off the free values and writing only those out of line, each conditioned on the plan row it read being unchanged.
- For a workspace in a region with its own database (the EU), the row and its audit event are written globally with a `plan_region` job, then the region's limit columns and `owner_retention` job. If that region cannot be written, `set-plan` and `remove-plan` exit with code 1 and say the change is half applied: run the same command again to complete it (the job also completes it within minutes). The alignment, unpinning and pruning scans read a bounded number of pages per run and resume from `maintenance_cursors`, so a large number of owners is covered over several runs (decision 0005, "Scan bounds").
- When a paid plan ends or is lowered, its listed retention rules continue for 60 days (see "Plan grace"); data keeps ageing under those rules and archive deletion dates do not move, so the grace does not guarantee that every item stays for another 30 days. Above its limits, new artifacts, restores, updates that add storage and new comments are refused with `quota_exceeded`, naming the plan's limit where the owner reads the message (comments say only that the owner has no room, because the commenter is someone else). Reading, listing, exporting, downloading, deleting, archiving, reducing access, renewing and rolling back keep working; a rollback is not held to the per-artifact size, since the version already fit the plan it was published under.

Safety caps that are not plan tiers stay constants: files per version, publishes and new files per 24 hours, open uploads, readers per artifact, the boundaries' file, offset and anchor cap (`LIMITS.fileBytesCap`, 5 GB, above every plan's per-artifact size) and the artifacts one expiry notice lists (`EXPIRY_NOTICE_ARTIFACTS_MAX`, 1,000). Version retention is applied from `PLANS` by `pruneVersions` (see "Version retention"); access log retention (`accessLogRetentionDays`) applies to the access log and the analytics view counters (see "Access logs"). Budget protection does not look at plans.

### Granting a paid plan

Paid plans are sold by email (`hello@portifact.com`) and paid outside Portifact. Before the customer becomes bound by the order or pays, send a written confirmation by email, and grant the plan with `set-plan` only once paid. The confirmation must state:

- [ ] Who the customer is: the person or organization, its contact address and, for a workspace, its slug.
- [ ] The plan and, for Team or Enterprise, the fixed number of seats (a seat is a member of any role or a pending invitation).
- [ ] The currency and the total payable, including any tax Portifact must collect.
- [ ] The start and end dates (`--until`), and that nothing renews or adds seats without the customer's written agreement.
- [ ] How to pay (the method and, if a payment provider is used, its name).
- [ ] The refund terms of the Terms: in full within 14 days of the first purchase, pro rata by day when Portifact ends the plan without the customer's breach, withdraws a paid feature or shuts down, billing errors refunded in full, paid within 14 days of a valid request or of ending the service, to the original payment method (another method only if agreed with the customer, with no refund fee; any stricter statutory rule applies), asked for by replying to the confirmation or at `legal@portifact.com`.
- [ ] For a consumer, the withdrawal information their law requires (the right of withdrawal, its period and how to use it, with the model form where the law gives one), and, if the plan starts before the withdrawal period ends, the customer's express request to start it then.
- [ ] For a consumer entitled to the seller's geographical address and contact details, provide them privately on request before the consumer becomes bound, with any telephone number or other contact information their law requires. Do not conclude the order or accept payment while required pre-contract information is missing.
- [ ] For a customer that needs the standard contractual clauses (the DPA's "International transfers"), the completed party details with the operator's postal address and country, sent privately, before the clauses are relied on.
- [ ] For Enterprise, the signed agreement that sets limits, liability and any `--overrides` (for example `auditRetentionDays`).

Keep the confirmation and the payment record as long as tax and accounting law requires (the Privacy Policy says so). Correct a billing error and refund an overpayment in full as soon as it is found.

### A customer asks to switch or leave

A switching or erasure request under the EU Data Act, or any customer leaving, arrives at `legal@portifact.com` (the Terms, "Taking your data out and switching", with its export register):

1. Acknowledge it and agree the dates in writing: any preparation notice is at most two months, and the transition normally takes at most 30 calendar days. If switching within 30 calendar days is technically impossible, tell the customer within 14 working days of the request, explain why and give an alternative transition period of at most seven months. The customer may extend the transition once. Explain known continuity risks.
2. Keep the paid plan in force through the transition and for 30 days afterwards (`set-plan <owner> <plan> --until <date>`). Extending the plan does not stop normal expiry. Identify the data to be transferred and its deletion dates (`plan <owner>` shows the retention in force; the "Download your data" page and `portifact export --dry-run` show what goes on which date). Before those dates, create and verify a separate export, including data the export tools omit, and include changes needed to complete the switch. Keep the export secure (encrypted, outside the repository, readable only by the operator) and available to the customer throughout the retrieval period, then delete it under step 5.
3. Make the separate export with these, as the owner's admin or with the deploy credentials:
   - Files, versions, access logs, the audit log, each artifact's records (`artifacts/<id>/records.json`: settings and access rules, share link settings, the approval review, analytics, comment threads and the comment action history) and the space's records that bearer routes read (`space.json`): `portifact export <folder> --workspace <slug>` (signed in as an admin of the workspace, or the account for a personal space), then check its `manifest.json` says `"complete": true`, lists no `skipped` item and no records part says `rate_limited` (run it again until it exits 0). Each artifact's records cost 7 requests, plus one per extra page of 500 history entries and one per extra 366 days of analytics, made one after another; a resumed run (after exit 8 or an interruption) keeps the records files it already wrote and verified in that export, and a run after a complete one reads them all again.
   - The workspace's members and roles, groups and their members, invitations, verified email domains, full policies, service tokens, single sign-on, SCIM and GitHub trust settings, branding and its logo, webhooks, integrations and audit streams: the "Space records" download and the logo link on the dashboard's "Download your data" page (`/data?workspace=<slug>`), signed in as an admin. A part that says `unavailable` is a feature switched off on the deployment: nothing to return.
   - Usage and plan: `portifact usage --workspace <slug> --json` and `operator plan <owner>`.
   - What no tool covers is a manual query against the control database with `npx wrangler d1 execute portifact-control --remote --json --command "select ..."` (the EU databases for an EU workspace), filtered by the owner or its artifacts: cancelled approval requests (`review_requests` where `cancelled_at` is set, with their `review_reviewers`), and the plan and usage records (`owner_plans`, `account_usage`, `usage_events`, which keep only the last 7 days; see "History retention").
   - Verify each file against its source (counts and, for artifact files, the checksums in the manifest) before telling the customer it is ready.
4. Send the customer the export through a channel agreed in writing, protect it in transit, and return on request any other exportable data and digital assets the tools do not cover, whether or not they contain personal data.
5. The affected service contract ends when switching succeeds; notify the customer then. If they asked for erasure without switching, it ends no later than the end of the preparation notice period. After successful switching and the retrieval period (at least 30 calendar days after the transition), delete the separate export, the workspace or account, and anything returned by hand, unless the law requires keeping something, and confirm the deletion in writing. The ordinary refunds apply.

### Plan grace

[Decision 0022](decisions/0022-plan-grace.md). When an owner's plan ends (`valid_until` passes), is removed or is lowered (another plan, fewer seats, lower overrides), what the old plan kept is held for 60 days (`PLAN_GRACE_DAYS`) from the drop: previous versions, access log rows and analytics counters, audit events, pins and the archive length of artifacts archived meanwhile. The owner can still read, download and export them: the version list, downloads, `portifact pull`, comparing versions if the old plan had it, rollback, the analytics, the access log and its export, the audit log and its export. Everything else follows the plan the owner has now from the moment of the drop: new pins, share links, webhooks, search, policies and anything over the new quotas are refused as before. After the 60 days the usual scans prune what the plan the owner has now does not keep. Nothing is deleted to fit a quota: an owner above the new limits keeps everything, and only new work is refused.

- `set-plan` and `remove-plan` start a grace by default when the new plan keeps less than the old one did. `--no-grace` (after the owner and plan) ends every running hold and starts none: use it only for abuse, it is recorded in the owner's audit log as the operator. Granting a plan that keeps at least what was held ends the grace early with nothing lost (recorded as renewed).
- `plan <owner>` shows `grace       until <date>, holding <plan>: ...`, the reads still open (`held reads`) and one line per hold (each drop is its own hold with its own end; a second drop never extends or shortens the first). Past eight running holds the two ending first are folded into the later one, shown as `(folded: N holds)`: it keeps the highest of them until its own end, so a fold lengthens a value's hold by at most 60 days after the newest drop folded in, and holding forever would take a real drop at least every 60 days indefinitely.
- `grace       UNREADABLE` (and a `plan_grace_unreadable` log line with the owner's ID, every maintenance run) means the stored grace could not be read. Nothing is deleted for it: the owner is held at the most any retention may be. Fix it by running the plan the owner should have with `set-plan` (or `remove-plan`), which stores a readable 60-day hold in its place; `--no-grace` drops it instead.
- The grace scan (`planGraces` in the `maintenance` log line) stores a natural expiry's hold once and removes holds whose days passed, recording `plan.grace_started` and `plan.grace_ended`; a removed plan's `free` row is deleted with its last hold. At most three pages of 100 rows a run, from `maintenance_cursors`.
- What to tell a customer whose plan lapsed or was lowered: the personal-space owner and workspace admins can see the dates on the Plan and "Download your data" pages, and admins and editors also see a notice on other pages, which they can hide for the day. `portifact export <folder> [--workspace <slug>]` downloads retained artifact files and versions, access logs, the audit log and each artifact's records (settings, access, share links, the approval review, analytics, comment threads and their action history) the caller's role and plan allow (resumable; `--dry-run` first shows the counts, bytes and dates); the "Download your data" page adds the workspace's members, invitations and other settings only the dashboard reads, and the operator returns data the tools omit. Renewing the plan preserves its retention limits but does not freeze existing data: versions and log entries keep ageing. The search index and custom domains are not held: the index is rebuilt on a new grant, and domains follow their own 7-day rule (see "Custom domains").
- Grace emails (decision 0022, third delivery): each hold on whose end a step of the forecast falls is announced by email when it starts, 14 days before it ends and 3 days before it ends, to the account of a personal space or each admin of a workspace, in their language (a hold whose end deletes nothing, such as Enterprise lowered to Team, gets none; several holds due at once share one email). The scan (`graceNotices` in the `maintenance` log line, in every region's run, right after the grace scan in the default one) reads the plan rows of the region's owners whose stored grace has a hold due an email, three pages of 100 a run from `maintenance_cursors` (`plan_grace_notices:<region>`), and writes one `plan_grace_notice` job per owner in the owner's region, with a token of its own, marking the hold and the token on the plan row (`owner_plans.grace_notices`: `select owner_id, grace_notices from owner_plans where grace_notices is not null` shows what each hold got). A scan that comes late sends only the most urgent moment due, once. The job sends only while the mark holds its token and the email is still due (a plan granted again or `--no-grace` makes it moot, logged as `plan_grace_notice_skipped` with reason `moot`), skips suppressed addresses and stops on the expiry notices' rung of the capacity ladder (`checkNoticeCapacity`). A `start` or 14-day email refused for capacity is dropped; a 3-day email waits instead: it goes back to the outbox for an hour and is tried again until it is sent or the hold ends. While warnings wait on capacity, the Worker logs `plan_grace_notice_waiting` (warn, `reason: capacity`, `moment: three_days`) on each try and `select subject, available_at, attempts from outbox where topic = 'plan_grace_notice' and available_at > <now>` lists them; the cycle's email budget is then nearly spent (see the budget alerts), and the warnings go out once the cycle turns or the operator raises the budget. When capacity runs out after some admins of a workspace got the 3-day email, it goes back naming only the admins not told yet (an admin removed meanwhile gets nothing, a new one is not added). A failed first send goes back to the outbox; once one admin got it, a failed send for another is dropped (`plan_grace_notice_failed`). There is no opt-out and no `--no-email`: a grace that must not be announced is ended with `--no-grace`. With a separate regional database (an EU workspace) the job is written first, available two minutes later, and the mark after it. A job that runs before its mark has landed waits five minutes and tries again, at most six times (`plan_grace_notice_waiting` with `reason: mark`); a Worker dying between the two writes leaves a job that waits and then finds another scan's token, so the email is never lost for good and never sent twice. Start emails can wait behind plan rows whose grace cannot be read (`plan_grace_unreadable` in the logs): with D of them ahead of an owner, ceil(D / 300) more runs of 15 minutes; fix those rows (see above).
- A restore: `export-plans` and `apply-plans` carry each row's holds and grace emails (`graceNotices`), so a grace is neither shortened nor restarted and no email already sent goes again; a job pending at the export that the restore rewound is lost (its mark says sent). A file exported before the grace emails has no marks: each live hold then gets one email, for its most urgent moment (see "Restoring a backup").
- After the deploy that added graces, a one-time pass per region (`redatedPlans` in the `maintenance` log line) writes `owner_retention` jobs for owners whose plan has an end, so access log rows the previous release capped at the plan's end are kept into the grace. It marks itself done (cursor `plan_grace_redate:<region>`); delete that cursor row to run it again.

### Version retention

- How many previous versions an artifact keeps and for how long come from its owner's plan (`retainedPreviousVersions` and `previousVersionRetentionDays` in `PLANS`: 2 for 7 days on free, 50 for 90 days on Pro, 100 for 365 days on Team), read whenever a version is listed, read, compared, rolled back to or pruned (`previousVersionRetained` in `packages/domain/src/versions.ts`, `retainedVersionSql` in `packages/services/src/retention.ts`). A version records when it was replaced (`versions.superseded_at`), never a fixed expiry, so an upgrade keeps longer the versions not pruned yet. A lower or expired plan normally preserves the earlier retention limits for 60 days. Versions and log entries continue to age under those limits and can expire during grace. After grace, the current plan's limits apply. Existing archive deletion dates do not move. If the operator explicitly disables grace, the lower limits apply immediately.
- The maintenance scan `pruneVersions` (`prunedVersions` in the `maintenance` log line) deletes up to 50 versions a run that the owner's plan no longer keeps, then releases the objects only they referenced through `releaseOrphans`, which is when the owner's storage goes down. Owners without a plan row are pruned with the free values in one query; each owner with a row gets its own query, and each delete is conditioned on the plan row it was decided from, so a grant that lands meanwhile is never pruned with stale values. Owners with a plan row are read 50 a run from a cursor that wraps, so a lapsed or lowered plan's extra versions go within `ceil(plan rows / 50)` runs (15 minutes each) instead of the next one: never earlier than the plan allows, and their storage stays counted until then. Nothing else is deleted, and the current version never is. Retained versions count in the owner's storage until they are pruned, so the plan's storage limit bounds them.
- A lower or expired plan normally preserves the earlier retention limits for 60 days. Versions and log entries continue to age under those limits and can expire during grace. After grace, the current plan's limits apply. Existing archive deletion dates do not move. If the operator explicitly disables grace, the lower limits apply immediately. (See "Plan grace".)
- To keep an owner's versions longer, grant the plan before the grace ends; versions already pruned cannot come back.

### Pins and archive length

- Pinning (feature `pin`, Pro and above) keeps an active artifact published with `artifacts.pinned` set and no `expires_at`, so the archive scan and the expiry notices never pick it. There is no separate cap on pins: a pinned artifact holds an active slot, so the plan's active-artifact limit bounds them. Unpinning gives it 30 days from that moment and works on any plan. A publish or rollback keeps the pin, archiving (by hand, or a reinstatement that sends it to the archive for lack of a slot) clears it, a restore comes back unpinned, and a suspension keeps it until the artifact is reinstated.
- When an owner's plan stops including `pin` (expired, removed or lowered) and its grace has ended (60 days, see "Plan grace"; pins stay during it, but new ones are refused), the maintenance scan `unpinLapsedPlans` (`unpinned` in the `maintenance` log line) unpins its active artifacts with 30 days from the scan, which also makes them due for the normal expiry notice: up to 50 artifacts a run, never archiving or deleting anything, writing nothing for owners that still have the feature, each owner's batch conditioned on the plan row it read being unchanged so a grant that lands meanwhile keeps the pins. Each unpinned artifact gets an `unpinned` lifecycle event with `{"reason":"plan"}`. Granting the plan again does not re-pin them; the owner pins again.
- An archive is kept for the owner's plan's `archiveMonths` at the moment it is archived (6 on `free`, 12 on paid plans; during a grace the held plan's), by the scan, by hand or by a reinstatement: `purge_at` is set then and never moves. A later downgrade does not shorten it and an upgrade does not extend it; restoring and archiving again under the new plan sets a new date. The expiry notice names the owner's current archive months.

### Content search

- The index (decision 0012) is `search_artifacts`, `search_chunks` and the FTS5 table `search_text` in each regional database. Only the `search_index` outbox job writes it: a commit, rollback, restore or transfer of an artifact whose owner's plan includes `contentSearch` writes the job in its batch, and the job reads the version's text from R2 and replaces the artifact's rows in one batch while that version is still current. Caps (`SEARCH_LIMITS`): 2 MiB read and 512 KiB of text per file, 200 files and 4 MiB per version, 32 MiB per owner; over a cap, or with an object missing from R2, the artifact is marked `partial`.
- One job reads at most 8 MiB and 40 objects from R2 (`jobReadBytes`, `jobFiles`) and holds at most the version's remaining text budget plus the one object it is reading. A version larger than that is written in parts: the job writes what it read and a continuation job (`from`, the next file) in the same batch, and `search_artifacts.next_file` says where the pass stands (null once complete). The jobs Worker runs up to 10 queue messages per invocation one after another, so an invocation reads at most 80 MiB with at most 400 R2 reads, under its 1,000 subrequests; `max_batch_size` stays 10.
- Searches are rate limited per actor (60 a minute) and per owner (300 a minute, `search-owner:<owner>` in `rate_limits`, whoever acts), and a query holds at most 8 different words and 16 characters per Chinese or Japanese run (`invalid_input` above that). The worst accepted query on an owner at its 32 MiB cap took about 20 ms in local workerd (`content-search-limits.test.ts`, budget 1.5 s).
- Two scans run every 15 minutes, each from a cursor in `maintenance_cursors` and with four queries a run whatever the number of owners: `dropLapsedSearchIndexes` (`droppedSearchIndexes` in the `maintenance` log line, cursor `search_index_drop`) reads one page of 100 indexed owners and drops up to 100 indexed artifacts of those whose plan lost the feature, each owner's on the plan row it read; `scheduleSearchIndexing` (`scheduledSearchIndexing`, cursor `search_index_schedule`) reads one page of 100 `owner_plans` rows and writes up to 200 jobs for active artifacts of entitled owners whose current version is not fully indexed and that have no job waiting, which covers a plan granted later, a reinstated artifact and a lost job or continuation. A page that still had more due is read again next run. A 1,000-artifact workspace that gains the plan is scheduled in five runs, about 75 minutes, plus the queue's time; publishes after the grant are indexed by their own job within minutes.
- To rebuild an owner's index, delete its rows and let the scan write the jobs again: `npx wrangler d1 execute portifact-control --remote --command "delete from search_artifacts where owner_id = '<id>'"` (the cascade and the trigger delete the chunks and the full-text rows). To check an owner: `select count(*), sum(text_bytes), sum(partial) from search_artifacts where owner_id = '<id>'`.
- Backups: Time Travel restores the index with the artifacts (FTS5's shadow tables are ordinary tables). Checked on 2026-11-10 against Cloudflare, on a scratch database with migrations `0044` and `0045`: an indexed artifact was deleted after a bookmark, the restore to that bookmark brought back the artifact, its chunk and its text, the restored index answered a `MATCH` with its snippet, FTS5's `integrity-check` passed and the three triggers were still there. The full backup drill (tombstones exported and re-applied over an indexed artifact) has not been run with the index: do it in the next drill (see "Backup drill"). `apply-tombstones` claims resurrected artifacts for purging, which drops their rows through the trigger. `wrangler d1 export` refuses a database with a virtual table; export the other tables with `--table` (one per table) and rebuild the index after an import.
- Size: the index lives in the regional database today. When it nears 1 to 2 GB in a region (`select sum(text_bytes) from search_artifacts` times about 1.3), move it to a search database of its own per region (decision 0012, "Alternatives rejected", is the starting point) before it crowds the artifacts' database.
- A later migration that rebuilds the `artifacts` table must recreate the `artifacts_search_inactive` and `artifacts_search_moved` triggers of the `content_search_fts` migration.

## Artifact data

[Decision 0026](decisions/0026-artifact-data.md) gives an artifact a document database in its own Durable Object (`ArtifactDocuments`, exported by the `portifact-data` Worker). Nothing creates one yet: every path that would is off until the release that switches artifact data on, so in production these jobs find no `artifact_data` rows and do nothing. What is built is the lifecycle that reaches an object once one exists, run by the jobs Worker through its `ARTIFACT_DOCUMENTS` binding:

- **Jobs.** A hold, its release and a transfer raise `artifact_data.epoch` and write a `data_fence` job in their own batch; a purge (which is also how an account's or a workspace's deletion ends its artifacts) writes a `data_erase` job from the row the purge deletes; an account deletion retires the account's author journal entries (`system/data-authors/<user>/<artifact>` in each region's bucket) and writes a `data_author_erasure` job for each. A held or quarantined object keeps its erasure jobs waiting a day at a time (`kept`), never erasing; the hold's release job (`legal_hold_release`) sends them again at once. A fence that must wait for an earlier change answers `pending` and comes back. `data_job_refused` in the logs names the job, its topic and the object's refusal code.
- **The inventory.** Every object that may hold something has an entry at `system/data-objects/<artifact>` in its region's bucket, written before D1's row. A purge's committed erase retires the entry; a retired entry is deleted 31 days later (longer than D1 Time Travel can rewind) by the reconciliation walk.
- **After a restore** (step 7 of "Restoring a backup"): `data-reconcile --region <region>` writes one `data_reconcile` job that walks the region's inventory a page at a time and compares each object with D1 by the record's field authority table, then walks the journal and writes again the author erasures a rewound outbox lost (from the retired entries). `data-findings [--region <region>]` lists what it did per artifact: `raised` (D1 was behind the object and was raised to it), `resumed_erase` (a prepared erase was committed under its own ID), `quarantined` with the reason (`owner`, `hold`, `orphan` for an object D1 has no row for, `generation`), `awaiting_operator` (already quarantined). A hold D1 and the object disagree on is converged rather than quarantined when D1's records settle it (a corrective hold for a hold D1 has open, a corrective release for a hold D1 records as released, written as a new `data_fence` job; reconciliation answers `converge`, or `converging` when such a job is already waiting); an object holding a hold D1 has no record of is quarantined (`hold`), because releasing it could end a hold the restore lost. A quarantined object refuses everything but the operator.
- **Resolving a quarantine.** Export first if in doubt: `data-export <artifact>` writes the object's documents to `system/data-exports/<artifact>.<time>/` in the region's bucket as JSON Lines, a page per file, under a hold or a quarantine too. `data-findings` prints each quarantine's `state`: `<artifact>:<region>:<incarnation>:<reason>:<owner>:<generation>:<epoch>`, where the incarnation counts the object's quarantines, so a later quarantine with the same reason is a different state. Resolve exactly what you reviewed: `data-resolve <artifact> adopt|erase --state <state>` with that state. The object refuses a resolution whose state is no longer the one you reviewed (`refused (conflict)`: read `data-findings` again), and a retried job finishes the same resolution, never a later quarantine. A state of another artifact or region is refused before the object is read (`refused (forbidden)`), and an `identity_mismatch` refuses the resolution until it is fixed. A resolution's receipt becomes eligible for pruning 24 hours after it, so a retried job replays it for as long as it exists; after it is pruned a retry is refused as a conflict and changes nothing. If D1 did not follow the object, `data-reconcile` raises it when D1 has the artifact's data row; an orphan whose adoption stopped before its row was written is quarantined again as an orphan, and needs a new reviewed `data-resolve`. `adopt` needs D1 to name the owner the object recorded (repair the artifact's ownership rows first, or it records `refused (stale)`) and keeps any hold: the object keeps its own, or takes the one D1 has. `erase` moves the object to its next generation and is refused while D1 or the object holds (`refused (held)`): release the hold first, which needs its own authorization. The finding becomes `adopted` or `erased`, and the artifact's waiting data jobs run again.
- **Owner findings from the jobs.** `refused (owner)`: a fence ended while the object's owner is not D1's and no transfer to D1's owner was waiting, including a transfer the object refused because it holds with no release left to free it (a restore re-opened a hold without its fence, so the object keeps the old hold). The jobs record it themselves (there is no scheduled reconciliation); nothing is quarantined until you run `data-reconcile`, which then records `quarantined (owner)`. Repair the artifact's ownership rows in D1, or adopt after reconciliation, as for an owner quarantine. Once D1 and the object agree on the owner, `data-reconcile` clears the finding.
- **Other findings.** `identity_mismatch` (with `key`, `inventory_region`, `directory_region` or `control`): the inventory, the directory and the object disagree about which artifact or region this is; nothing was followed, so check the directory row and the entry by hand. `superseded`: a purge's erase reached an object at a newer generation without D1 proving the artifact's permanent deletion; the job and the inventory entry are kept, a day at a time, until D1 proves it (its tombstone). The object is not quarantined, so `data-resolve` does not apply to it, and `data-reconcile` alone does not finish the job: it raises D1 when the object is ahead with the same owner and hold, and quarantines only when D1's generation is ahead, neither of which changes the waiting purge's generation or proves the deletion. Repair D1's metadata (the artifact's tombstone, with no artifact row left but a purging one) so the job erases the object's generation; until then the job waits a day at a time and erases nothing.
- **A job that keeps failing** without the binding (`artifact data binding` in its error) means the jobs Worker was deployed without `ARTIFACT_DOCUMENTS`: deploy `portifact-data` and then the jobs Worker again (docs/releasing.md, "Artifact data Worker").

## Maintenance and the outbox

Every control database has its own outbox, relayed once a minute into the one `portifact-jobs` queue; a message from a region other than the default names it (`region`) and runs on that region's database, bucket and access log. The scans of an owner's data run once per region (`runRegionalMaintenance` for the others: archive, expiry notices, comment notices, uploads, version pruning, purge, orphan objects, re-rendering, operations, read and review sessions, artifact groups, share links, traffic counters, plan alignment, grace emails, unpinning, both search scans, webhooks, workspace policies, the region's audit events, history retention (lifecycle and moderation records, upload and usage history, stale storage findings), and the approval reviewers' re-check last), each bounded per run as in the default region and limited to the owners of that region; the global ones (account and workspace deletions, invitations, directory users, restore markers, expired sign-in records, email counters and suppressions, the global audit events) once (decision 0005, "Second delivery", lists the D1 calls of each with a separate database). A job about an owner (`owner_retention`, `expiry_notice`, `plan_grace_notice`, `search_index`, `review_notice`, `webhook_delivery`) is written in the outbox of the owner's region and runs with that region's database, bucket and access log.

State changes that need follow-up work write a job to the `outbox` table in the same D1 batch (`packages/services/src/outbox.ts`): `purge_artifact` when an artifact is claimed for purging (deletion by its owner, the purge when its archive ends, account deletion, re-applied tombstones), `account_deletion` with a deletion request, `workspace_deletion` with the operator's deletion of a workspace, `access_history_move` with a transfer (it gives the artifact's access log and view rows to its new owner), `delete_objects` with the R2 keys whose rows a release just deleted, `erase_access_events` when an artifact is purged or an account is deleted (it deletes their rows, and a purged artifact's view counters, from the separate `portifact-access` database), `owner_retention` when the operator grants or removes a plan (it moves the expiry of the owner's access log and view counter rows to the new plan), `plan_region` with a plan change for an owner whose region has its own database (written in the global batch, it writes that region's limit columns and `owner_retention` job from the owner's current plan; the command withdraws it once it has done the same inline), `expiry_notice` when the maintenance scan schedules an owner's expiry notice (see "Expiry notices" below), `plan_grace_notice` when the maintenance scan schedules a grace email (see "Plan grace"), `webhook_delivery` when a write records a webhook event (see "Webhooks" above), `search_index` when a commit, rollback, restore or transfer makes a version current for an owner with content search (see "Content search" above), and `abort_multipart` when an upload session with multipart uploads closes (it aborts the R2 uploads not completed and deletes their staging copies under `uploads/`, which the storage reconciliation does not scan). Every minute the jobs Worker relays due rows to the `portifact-jobs` queue; every 15 minutes it runs the maintenance scans and reconciles a slice of storage. The consumer deletes a row once its job is done; a job whose row is gone is already done, a purge whose artifact is no longer in the `purging` state and generation it was claimed with is stale and dropped, and a `delete_objects` job keeps any key that has a row again. A row still there an hour after it was sent is sent again.

`select topic, subject, attempts, dispatched_at from outbox order by id` shows what is pending. Rows with many attempts point at a job that keeps failing; the Worker logs `job_failed` with the row's ID, topic, region and the error's label (see "Reading the Workers' logs" below), never its message. The scans in `runMaintenance` still archive, purge, prune and finish deletions on their own, so a queue outage only delays the work.

### Reading the Workers' logs

Workers observability is global, outside every region (decision 0005), so every log line is `{"event": ..., fields}` written by `logEvent` (`packages/domain/src/logs.ts`) with IDs, counts, enum values, a region and, for a failure, an error label: never a name, an address, a URL path or an error's message, which can hold any of them (`scripts/log-fields.test.ts` enforces it). A label is the error's name followed by codes that cannot carry content:

| Label                                                                                                        | Meaning                                                                         | What to do                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Error:D1_ERROR:SQLITE_CONSTRAINT` (or another `SQLITE_*`)                                                   | A D1 statement failed with that SQLite result code                              | `SQLITE_CONSTRAINT` on a job usually means a row changed under it; it retries. A repeated `SQLITE_BUSY` or `D1_ERROR` alone: check D1's status, then reproduce locally |
| `Error:r2_<number>`                                                                                          | An R2 binding call failed with that R2 error number                             | Look the number up in R2's error codes; `10001`-class errors are R2's side and retry                                                                                   |
| `Error:ANALYTICS_HTTP:<status>`, `Error:ANALYTICS_GRAPHQL_ERRORS:<n>`, `Error:ANALYTICS_ACCOUNT_NOT_VISIBLE` | The budget collector's call (see "Cloudflare analytics")                        | As there                                                                                                                                                               |
| `Error:CF_HOSTNAMES_HTTP:<status>[:<codes>]`                                                                 | Cloudflare's custom hostnames API refused a call, with Cloudflare's error codes | `401`/`403`: `CF_HOSTNAMES_TOKEN`; `409` with codes: the hostname's state in Cloudflare                                                                                |
| `Error:DOH_HTTP:<status>`, `Error:DOH_RCODE:<rcode>`                                                         | A DNS over HTTPS lookup failed (custom domains, email domains)                  | Transient on `5xx` and `SERVFAIL` (`2`); the daily check retries                                                                                                       |
| `Error:BUCKET_NOT_BOUND`                                                                                     | A region's bucket binding is missing in the jobs Worker                         | Fix the deployment's bindings ("EU region" in releasing.md)                                                                                                            |
| `Error:E_RECIPIENT_SUPPRESSED` and other `E_*`                                                               | Email Service's code                                                            | See "Email quota and suppressions"                                                                                                                                     |
| `Error`, `TypeError` and other bare names                                                                    | Anything without a code: the message is never logged                            | Reproduce locally with the job's row (`select * from outbox where id = <id>`) and `wrangler dev`, or run the operator command that covers it                           |
| `string`, `object`                                                                                           | Something other than an error was thrown                                        | Reproduce locally                                                                                                                                                      |

Events an operator reads: `job` and `job_failed` (row ID, topic, region, outcome or label), `outbox_relay_failed`, `preview_prune_failed` and `access_log_prune_failed` (region, label), `preview_prune_behind` (region and counts, see "Preview prune"), `custom_domains_failed`, `email_domains_failed`, `email_event_failed`, `budget_analytics_failed`, `multipart_complete_failed` (label), `maintenance` and `budget` (the run's counts), `email_event` (`bounced`, `complained` or `other`, the event ID and the outcome), the notices' `*_skipped` events (a reason and a count), `workspace_network_policy_unreadable` (the workspace ID), `traffic_write_failed`, `access_log_write_failed` and `view_write_failed` (the content Worker kept the batch for the next window), and `turnstile_secret_missing` or `turnstile_secret_rejected`.

### Preview prune

Built previews of edit suggestions ([decision 0027](decisions/0027-edit-suggestions.md)) leave a document in each region's bucket under `previews/` and a row in `preview_codes`. While `SUGGESTIONS_ENABLED` is on, the jobs Worker deletes both every minute (`runPreviewPrune`, beside the outbox relay but in its own `waitUntil`), once a document is 2 minutes old, and every maintenance run does the same. A run deletes up to 5,000 documents and 5,000 rows per region (`PREVIEW_PRUNE`: five pages of 1,000). `preview_prune_behind` (region, `documents`, `rows`) means a run reached that cap, so more may remain (a run that deletes exactly the cap logs it too): the next minute continues, and the line repeating for many minutes means previews are issued faster than they are pruned, a real capacity condition to investigate, since the planning rate limits are per person and do not bound a region's total; check `select count(*) from preview_codes` in the region and the size of `previews/` in its bucket, and look for an account issuing previews in bulk. `preview_prune_failed` (region, label) means a region's run failed; the other regions and the relay are not affected, and the next minute retries.

## Access logs

Openings of artifacts by signed-in visitors and the daily view counters of analytics live in the `portifact-access` D1 database (see "Access logs" and "Artifact analytics" in [security.md](security.md)). Every row carries `expires_at` from the owner's plan (`accessLogRetentionDays`: 30 days on free, 365 on paid plans), and each scheduled run prunes rows past it, both tables, in bounded statements (`prunedAccessEvents` in the `maintenance` log line counts both, or `failed` with an `access_log_prune_failed` line; the rest of the run goes on).

Retention follows the plan. `set-plan`, `remove-plan` and `apply-plans` write an `owner_retention` job in the same batch as the plan change; the job recomputes the expiry of every row of the owner from the plan at that moment, in bounded statements. A lower plan (a removal, a lowered plan, an override of `accessLogRetentionDays`): A lower or expired plan normally preserves the earlier retention limits for 60 days. Versions and log entries continue to age under those limits and can expire during grace. After grace, the current plan's limits apply. Existing archive deletion dates do not move. If the operator explicitly disables grace, the lower limits apply immediately. The job dates each row by the steps of retention in force (the held plan's until the grace ends, then the new plan's), so a row already older than the held limit can expire during the grace, and after it the prune deletes the rows the new plan does not keep (a downgrade from Pro keeps the last 30 days). A higher plan extends the rows still there; rows already pruned do not come back. A plan that reaches its `valid_until` needs no job: rows written under it already expire no later than 60 days after its end, or 30 days after their start if that is later. Each row keeps the expiry it got when written until a job moves it, so a grant with no job (a row written by hand) leaves existing rows as they were. To check an owner: `npx wrangler d1 execute portifact-access --remote --command "select count(*), min(expires_at), max(expires_at) from artifact_views where owner_id = '<id>'"`. Only the artifact's owner reads them through the product; there is no operator command, and a visitor's request about their own entries goes through `privacy@portifact.com`: `npx wrangler d1 execute portifact-access --remote --command "select artifact_id, opened_at from access_events where user_id = '<id>'"` lists them, and deleting the account erases them. The database is not part of the control database's Time Travel restore: restoring `portifact-control` does not bring access log rows back, and the erase jobs of re-applied tombstones delete any rows of resurrected accounts or artifacts again. It has its own Time Travel, but restoring it would bring back entries that were erased, so do not. A restore of `portifact-control` rewinds `owner_plans`; `apply-plans` grants them again through `setOwnerPlan`, which writes the `owner_retention` jobs that set the access database's expiries back in line with the plans.

## Audit log

Every owner's changes are recorded in `audit_events` (see "Audit log" in [security.md](security.md)): in the owner's region, and for members, invitations, plans and custom domains in the global database. The 15-minute maintenance run deletes events past the owner's `auditRetentionDays` (90 days on every plan; an Enterprise contract sets another value, see below) at most 1,000 rows per statement and 50 statements per pass (50,000 rows per database and run), first for owners on the default retention and then for each owner whose plan keeps another number of days; a plan row changed after the scan read it is left for the next run. Plan grants and removals made with `set-plan`, `remove-plan` and `apply-plans` are themselves recorded, with the operator as actor and without the operator's name or note; a grant that changes nothing records nothing. A D1 Time Travel restore rewinds the audit log like everything else: events after the restore point are lost, and `apply-tombstones` erases the events of deleted accounts and workspaces that the restore brought back.

### Audit retention and exports

An Enterprise contract sets how long an owner's audit events are kept, from 30 days to seven years (2,557 days, `AUDIT_RETENTION_BOUNDS`), with the operator tool only; there is no self-service setting:

```bash
bun run --cwd apps/jobs operator set-plan workspace:acme enterprise --seats 25 --overrides '{"limits":{"auditRetentionDays":730}}'
```

`set-plan` refuses a value outside the bounds, and `plan` shows the effective value (`audit log   kept 730 days`), as do the usage body (`plan.limits.auditRetentionDays`) and the Audit page. Raising it keeps events longer from then on; it cannot bring back events the scan already deleted. Lowering it with `--no-grace` is destructive at once: reads and exports stop listing older events, and the next 15-minute scan deletes them for good (in bounded statements, so a very large backlog can take a few runs). The same happens 60 days after the plan ends, is removed or the override is lowered without `--no-grace` (see "Plan grace"), since the owner falls back to the 90 days of every plan; during those 60 days the log and its export stay readable. Confirm a lowering with the customer in writing before running it, and export first if they want a copy. A D1 Time Travel restore rewinds the plan row with everything else; `export-plans` and `apply-plans` carry the override across like any other.

Exports are rate limited per owner (30 starts an hour) and per person (10 an hour) through `rate_limits`; a customer who hits the limit waits for the hour to pass, and each start appears in the log as `audit.exported`.

E3's retention policies (a maximum artifact life and comment retention) are built ("Maximum life of artifacts" and "Comment retention" above). Streaming the log to a SIEM is built and switched off ("Audit streams" below).

### Audit streams

An owner's admins point its audit log at an HTTPS endpoint from the Audit page ([decision 0019](decisions/0019-audit-stream.md)). Streams are switched on and off with webhooks (`WEBHOOKS_ENABLED` and `WEBHOOK_KEY` on both Workers); `WEBHOOKS_PAUSED` on the jobs Worker holds them too, and budget protection from `block_uploads` defers them 15 minutes at a time.

- **What the customer gets.** Signed JSON Lines, the export's bytes, at least once, ordered within each source (`portifact-audit-source: regional` or `global`) by when the database recorded each event, sent about 2 to 8 minutes after that: tell customers to keep each event ID once (a retry can carry more events than the first attempt, so the batch key is not a dedupe key) and to merge the two sources by `at` if they need one order. Lines with a `record` field are a gap (`"record":"gap"`: events recorded in that range were or will be deleted by retention and may be missing; anything still kept was sent anyway, and a quiet stream that sat paused past retention reports one even if nothing was deleted) or a test.
- **The scan.** Per region and 15-minute run, while switched on, one batch prunes the delivery log past 7 days (500 rows at most) and gives a job to up to 100 active streams that lost theirs; the run's log line has `auditStreams` with `prunedDeliveries`, `armed`, `keysRewrapped` and `keysLeft`. Streams sealed with `WEBHOOK_KEY_PREVIOUS` are re-sealed by the same run as webhooks are, in every region (the re-seal reads nothing when no previous key is set); keep the previous key until `keysLeft` and `webhookKeysLeft` are both 0. During a rotation, setting `WEBHOOK_KEY_PREVIOUS` on `portifact-app` too lets admins change a stream that is not re-sealed yet.
- **A stream in `attention`.** It failed for 72 hours, its URL no longer passes the checks, or no key opens it. The admin sees why on the Audit page (unreachable, refused with a status class, timed out, redirected, certificate) and in the log (`audit_stream.paused`); they fix the endpoint, send a test and resume, and it goes on from its position, with a gap record if retention passed it meanwhile. An endpoint down for longer than the owner's retention loses events to the stream; say so plainly, the gap record is the evidence.
- **Daily cap.** 2,000 requests per owner and UTC day (`audit-stream:attempts:<owner>:<day>` in `rate_limits`); a capped stream waits for the next day with one `daily_cap` row in its log. A large backfill takes several days by design.
- **Restores.** A restore that rewinds a stream's position makes it send again what it had sent since; nothing is skipped. Removed streams stay removed through their `audit_stream` tombstones (`export-tombstones` and `apply-tombstones` as for every restore).
- **Never log** a stream's URL, its path, a secret or a body; the consumer logs only the job's ID, topic and outcome.

## Storage reconciliation

Each region's bucket is reconciled against that region's database, with its findings in that region's `storage_findings` (`storage-report --region <name>`). Each scheduled run checks the next 50 object rows against R2 and the next 100 R2 objects under `objects/` against D1, resuming where the previous run stopped (`maintenance_cursors`). It records in `storage_findings`, and never deletes:

- `missing`: a verified object row whose R2 object is gone. Versions that reference it serve errors for that file. Look for a restore that brought back rows of bytes deleted after the restore point; if the artifact must keep the file, its owner publishes it again.
- `size_mismatch`: the R2 object has another size than the row. Treat it as corruption and ask the owner to publish again.
- `orphan`: an R2 object at least 24 hours old that no row references, for example after a restore to a point before it was uploaded, or a delete that never ran. If a restore is not the cause, delete it with `npx wrangler r2 object delete portifact-artifacts/<key> --remote`. Do not delete orphans right after a restore until the reconciliation has seen the restored rows: they may be the only copy of bytes the restored database references.

A finding disappears once a later pass sees the key fine again or no longer sees it at all, and any finding no pass has seen for 90 days (`STALE_FINDING_DAYS`) is deleted by `pruneStaleFindings` (a pass that still sees the problem records it again). A full pass takes `rows / 50` and `objects / 100` runs of 15 minutes.

## History retention

Records that outlive what they describe are pruned by every region's maintenance run (`packages/services/src/history-retention.ts`, rules in `packages/domain/src/history.ts`), each statement bounded per run:

- **Lifecycle and moderation records.** `lifecycle_events` of a purged artifact and `suspensions` of a purged artifact or deleted account are kept one year (`HISTORY_RETENTION_DAYS`) after it went, then deleted (`pruneGoneHistory`). An artifact's year counts from its `purged` event, walked oldest first through `lifecycle_events_purged_at_idx`, 90 artifacts per run, resuming from the `gone_history` cursor past the ones it keeps (an artifact a restore brought back). A suspension's year counts from `suspensions.target_gone_at`, set in the purge's batch and in the batch that finishes an account deletion (migration 0070 filled it for what was gone before). A year covers the six months in which a person can complain about a moderation decision, the appeal or out-of-court settlement after it, and the reports that show the same abuse coming back; the `artifact` and `account` tombstones keep the IDs from reuse after it. Abuse reports themselves are not pruned by this. To keep a record past its year (a legal hold), `historyHeld` is the one place to answer: every deletion above asks it first, and today it holds nothing.
- **A deleted account's traces.** Once an account's comments are erased, `eraseAccountTraces` replaces its ID with `deleted` in comment actions (`annotation_events`), in the "message deleted" markers and threads others replied to, and clears it as who resolved a thread and who acted in lifecycle records, 500 rows per statement per run; the deletion stays pending until none is left. The comment action history (`GET /api/v1/artifacts/:id/annotations/history`, MCP `get_comment_history`, the exports' `records.json`) shows such an action with `actor: null`, both before the ID is replaced (the account row is gone) and after (`deleted` is never looked up).
- **Moderation records and legal holds.** The operator's decisions (`moderation_decisions`) go once they are a year old and what they are about is gone from the region (a purged artifact, a deleted brand, an account whose suspension was pruned), with the records of who they were sent to (`moderation_notice_sends`); a released hold's row goes a year after its release (its addresses went at the release, `legal_hold_identities`). While a hold is open, `historyHeld` keeps everything about its artifact and its owner: lifecycle records, suspensions, decisions and their sends, and, in `eraseAccountTraces`, the comment actions and markers of deleted accounts, which the release job (`legal_hold_release`) erases once the hold ends. Comment deletion markers re-applied by a restore never reach what a hold deferred: comment writes need an active artifact, so none is written while it is held, and an account deletion's erasure writes none.
- **Upload and usage history.** `usage_events` older than 7 days (the quotas only count 24 hours) and closed `upload_sessions` 30 days after they expired, once no multipart upload is left for the abort job and, for one that never committed, no version is left for the version pruning (`pruneUploadHistory`, 500 rows each).
- **Storage findings.** See "Storage reconciliation".

The run's log line has `goneHistory` (`artifacts`, `suspensions`), `uploadHistory` (`usageEvents`, `uploads`) and `staleFindings`.

## Expired sign-in records

The default region's maintenance run deletes, a day after they expired (`EXPIRED_AUTH_GRACE_MS`), at most 500 of each per run (`pruneAuthRecords`, `packages/services/src/auth-records.ts`, log field `authRecords`): verification records (sign-in codes, whose identifier holds the address, and Better Auth's other short-lived records), OAuth access and refresh tokens, device codes and client assertions; browser sessions with their IP address and browser, but only those Better Auth's sign-out would leave exactly as they are (`sessionHooksHaveNothingToDo`: no live access token or live refresh token without `offline_access` bound to them, no token of a client with a back-channel logout URI), so a session whose token is still live waits until it expires; and app registrations made without an account (`oauth_clients.user_id` null, never the seeded `portifact-cli`) once 30 days old when no consent, token or device code refers to them: registrations nobody approved, and those whose app every person disconnected. What a client that cached such an ID then sees is in [mcp-compatibility.md](mcp-compatibility.md), "Deleted registrations". Consents stay until the person disconnects the app.

## Restoring a backup

The database backup is D1 Time Travel (30 days on Workers Paid). R2 is not rewound, so a restore can bring back rows of artifacts and accounts deleted since, and lose the tombstones that recorded those deletions. Re-applying the tombstones afterwards deletes them again. With the deploy credentials, from the repository root:

Before restoring, stop requests and background work that could read or disclose restored data. Reapply deletion markers, current access restrictions and recorded deletion requests before reopening access. Do not reopen affected data if its deletion history cannot be reconstructed. Step 4 re-applies the markers of: deleted artifacts, accounts and workspaces; comment and thread deletions (by their authors, by the people who manage the artifact or by comment retention); memberships ended by an admin, a directory or leaving; revoked or declined invitations; email notices turned off and per-artifact mutes; ended sessions, revoked or deleted app tokens and disconnected apps; and the other kinds listed in step 4. Two changes write no marker and a restore can undo them until they are made again: a reader removed from an artifact and a group removed from an artifact (with a separate regional database, both live in the region's database); check with the artifacts' owners after a restore of a regional database.

0. **Legal holds and the jobs Worker.** A restore to before a hold leaves the artifact unheld, and possibly unsuspended and served, until step 4 puts the hold back, and R2 deletions cannot be rewound. Pausing the jobs Worker narrows that window but does not close it: the app Worker purges inline when someone deletes an artifact (`deleteArtifact`), and any request that reaches the restored database meanwhile acts on what it holds. So: export the holds in step 2 (they are in the same file), run step 4 at once after step 3, holds first (it applies them before anything else, releases before re-opened holds, so a hold listed before an older hold's release is never dropped; a stated limit, not a guarantee: a restore run while the jobs Worker still consumes can re-open a hold with no fence after an in-flight release read the hold level, and that release then frees the object, so pause it as below), and know that the window lasts as long as you take between the two. Pause the jobs Worker too, from the repository root with the deploy credentials (`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` set):
   - Read the schedules: `curl -s "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/workers/scripts/portifact-jobs/schedules" -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN"` (keep the output).
   - Clear them: the same URL with `-X PUT -H "Content-Type: application/json" --data '[]'`. Cloudflare's reference does not say that an empty list clears them, so read them again with the first command and go on only when the list is empty; otherwise remove them in the dashboard (Workers, `portifact-jobs`, Settings, Triggers).
   - Stop the consumer: `bun run --cwd apps/jobs wrangler queues pause-delivery portifact-jobs` and `bun run --cwd apps/jobs wrangler queues pause-delivery portifact-email-events` (messages wait in the queues); check with `bun run --cwd apps/jobs wrangler queues info portifact-jobs`.
   - After step 4: `bun run --cwd apps/jobs wrangler queues resume-delivery portifact-jobs`, `bun run --cwd apps/jobs wrangler queues resume-delivery portifact-email-events`, and the schedules from the configuration with a normal deploy, `bun run --cwd apps/jobs wrangler deploy` (`wrangler triggers deploy` also applies them, but Wrangler marks it experimental). Read the schedules again to confirm both are back.
   - Then check every hold of the file: `bun run --cwd apps/jobs operator holds` lists each as open, and `show-artifact <id>` shows each artifact still there and suspended. `apply-tombstones` names any held artifact it could not bring back: one deleted in the window has lost its files for good; record which, when and how, and tell whoever asked for the preservation.
1. Note the current state so the restore can be undone: `bun run --cwd apps/jobs wrangler d1 time-travel info portifact-control` prints the current bookmark.
2. Export what the restore must not bring back from the live database: `bun run --cwd apps/jobs operator export-tombstones --out "$HOME/portifact-tombstones.jsonl"`. The file lists tombstones, account and workspace deletions in progress, artifacts already claimed for purging, revoked share links and every legal hold, one JSON object per line. It holds user and artifact IDs: write it outside the repository (a relative path lands in `apps/jobs`, which is not ignored) and delete it when done.
3. Restore: `bun run --cwd apps/jobs wrangler d1 time-travel restore portifact-control --timestamp <RFC 3339 time>` (or `--bookmark <bookmark>`). It asks for confirmation (there is no `--yes`; without a terminal Wrangler proceeds on its own), cancels queries in flight and prints a bookmark that undoes it; note that one too.
4. Re-apply the tombstones: `bun run --cwd apps/jobs operator apply-tombstones --file "$HOME/portifact-tombstones.jsonl"`. It stores the markers as tombstones, claims every artifact that has a tombstone or belongs to a tombstoned account or workspace for purging, and deletes every tombstoned account and workspace the restore brought back the way a deletion does, each with its outbox job (a tombstoned account is deleted even when it is the only admin of a workspace). It then puts back the `artifact_directory` rows the restore rewound, for every artifact still in the database, so no restored ID can be handed out again ([decision 0005](decisions/0005-regions.md), section 2). Running it again changes nothing. Without `--file` it applies the tombstones the restored database still has. Deleted workspace groups and removed group memberships (`workspace_group` and `workspace_group_member` tombstones, decision 0014) are deleted again (`group(s) and group membership(s) removed again` in its output), so a restore never gives someone back a group's access. So are deleted comments and threads (`comment_message`, `comment_thread`: a message becomes the "message deleted" marker again, a thread goes with its messages), memberships an admin or a directory ended (`workspace_member`, with the single sign-on block of `workspace_removals`) or their member left (`workspace_member_left`, no block), invitations revoked or declined (`workspace_invitation`), email notices turned off (`notice_opt_out`, `<user>:comment_notices` or `<user>:expiry_notices`: turned off again, never on) per-artifact mutes (`comment_notice_mute`, `<artifact>:<user>`: set again on artifacts still there, for accounts not deleted), and, written by triggers on the identity tables (migration 0071) whatever path made the change: sessions that ended before they expired (`session`: deleted again), OAuth tokens revoked or deleted before they expired (`oauth_token`: revoked again) and deleted consents (`oauth_grant`, a disconnected app: deleted again). Every refresh of an app's token writes one `oauth_token` marker: Better Auth rotates the refresh token by revoking the old one, which stays unexpired, and that marker is what keeps it dead after a restore. A family invalidation (a reused refresh token) marks only the rows still live, never the revoked ones. The prune reads each kind through `tombstones_kind_deleted_idx` (migration 0072), oldest first, at most 100 rows per kind per statement and four statements per run, so it reads only what it deletes. A membership is ended again only when it is not newer than its marker and never when that would leave its workspace without an admin: such an admin stays, and the workspace's admins settle it. These kinds (`WINDOW_TOMBSTONE_KINDS` in `packages/services/src/workspace-groups.ts`), and only those, are pruned after 30 days (`GROUP_TOMBSTONE_RETENTION_MS`, the D1 Time Travel window) by the maintenance run's `pruneGroupTombstones` (at most four statements of 500 rows per run, oldest first, with a cursor): a restore cannot reach further back, so anything removed or turned off before that is already so at every point a restore can bring back, and its tombstone guards nothing. Turning notices back on or unmuting deletes the marker, so a change made after the restore point and undone before the export is not re-applied. Every other kind of tombstone is kept for good.
5. The jobs Worker purges the claimed artifacts and finishes the deletions within the next runs; an account deletion stays pending until its artifacts are purged, so it finishes one run after them. Check with `select count(*) from artifacts where state = 'purging'`, `select * from account_deletions` and `select * from workspace_deletions`.
6. Run `storage-report` after a full reconciliation pass and handle `missing` and `orphan` findings as described above.
7. Reconcile artifact data, in every region, after step 4 and once the jobs Worker runs again: `bun run --cwd apps/jobs operator data-reconcile --region <region>` (see "Artifact data" below). Until a region's walk has finished, an object D1 no longer vouches for is not yet quarantined.

Workspaces, memberships and invitations are rewound too: members added and invitations sent since the restore point are lost, while members removed or who left and invitations revoked or declined since are removed again by `apply-tombstones`; tell the workspaces' admins about the lost ones. Workspaces deleted since are deleted again by `apply-tombstones`.

Comment notice activity is rewound too: pending `comment_notices` rows and `comment_notice` jobs from before the restore point come back, so some people may get a digest of activity they were already told about. Rows of accounts deleted since go again when step 4 re-runs their deletion, and rows of purged artifacts go with them by the foreign keys. Unsubscribes, email notices turned off and mutes made since the restore point are applied again by `apply-tombstones`; other settings changed since are lost with the rest of `account_settings`.

Workspace email domains are rewound too: a domain removed or lapsed since the restore point comes back from the backup, and `apply-tombstones` removes it again (every removal writes a `workspace_domain` tombstone with the row's ID, which `export-tombstones` exports, so a claim of the same name made later is kept). Domains verified since are lost; their admins verify them again.

Webhooks are rewound too: a webhook removed since the restore point comes back from the backup, and `apply-tombstones` removes it again (removals write a `webhook` tombstone, which `export-tombstones` exports); webhooks of tombstoned accounts go with them. Webhooks created since the restore point are lost; their admins add them again. Pending events and delivery jobs from the restore point come back, so a receiver may get a delivery again, with the same delivery ID.

Custom domains are rewound too, but Cloudflare is not: after step 4, run `reconcile-domains` (with `CF_CONTENT_ZONE_ID` and `CF_HOSTNAMES_TOKEN` in the environment). It detaches restored rows whose Cloudflare hostname is gone or names another host, deletes Cloudflare hostnames without a row (attached after the restore point), and clears `custom_host` from artifacts that hold a host no active row gives them. Until it runs, a restored domain serves only if its artifact row came back with it. Running it again changes nothing.

Plans are rewound too: `owner_plans` and the limit columns go back to the restore point, consistent with each other, so the database stays correct but plans granted, changed or removed since are lost or back. Plans are not tombstones, so they have their own export: in step 2 also run `export-plans --out "$HOME/portifact-plans.jsonl"` (one JSON object per plan, with owner IDs and notes: keep it outside the repository and delete it when done), and after step 4 run `apply-plans --file "$HOME/portifact-plans.jsonl"`. It writes each exported plan back exactly as it was, its end, its running grace and the grace emails already sent included (so a grace is neither shortened nor restarted and no grace email goes twice), with its limit columns and `owner_retention` job; it skips plans that ended and hold nothing any more and accounts that are gone or being deleted (so run it after `apply-tombstones`), and lists owners that have a plan the file does not, which the restore brought back; remove each with `remove-plan` if it was removed after the export. It never removes a plan by itself. Running it again changes nothing.

Workspace policies are rewound too ([decision 0015](decisions/0015-workspace-policies.md)): a policy an admin set or tightened after the restore point is lost, which could make public access possible again. They are not tombstones, so they have their own export, like plans: in step 2 also run `export-policies --out "$HOME/portifact-policies.jsonl"` (one JSON object per workspace with a policy: workspace IDs and the policy, no personal data; delete it when done), and after step 4 run `apply-policies --file "$HOME/portifact-policies.jsonl"`. It sets each exported policy again with the operator as actor (`policy.changed` in the audit log), writes the `workspace_policy` job that narrows whatever the restored artifacts break, skips workspaces that are gone or already as exported, and lists workspaces that have a policy the file does not; review each with its admins, since it was set before the restore point and lifted after it. It never lifts a policy by itself. Running it again changes nothing. Comment retention ([decision 0023](decisions/0023-workspace-retention-policies.md), "Comment retention" and "Restores") deletes for good, so more things hold around a restore. The threads it deleted come back with a restore and `apply-tombstones` deletes them again (their `comment_thread` tombstones are in the export; under the previous release, drop those lines from the file first, since its `apply-tombstones` refuses the kind). After a restore of the global database, every workspace whose rule changed after the restore point (removed, lengthened, set again, lapsed, or its plan changed by `set-plan`/`remove-plan`) holds a token that no longer agrees with its record in R2, so the scans delete nothing for it, by themselves, with no step to run. Take `export-policies` before the restore: `apply-policies` writes the exported policies with their tokens, so a workspace whose exported token is the one in R2 deletes again by itself, and every other one stays paused until an admin saves its rule again (its Policies page says so). An export taken after the restore is harmless but useless: it re-applies the restored rules, which keep disagreeing, so nothing deletes until the admins save. `apply-policies` writes no guard record and has no arming step; it still always applies a file's removed or longer retention, and never a stricter one (shorter, new, or taking effect earlier): it keeps the stored rule, applies the rest of the item and lists the workspace ("kept their comment retention because the file's is stricter"). `set-plan` and `remove-plan` delete the record of a workspace with comment retention before changing a plan that loses `policies`; when R2 refuses, or no bucket is bound (`--local`, `--config` drills: the guard is not maintained there), the command says so, keeps the plan change, exits 1 and prints how to delete the record by hand. `operator.wrangler.jsonc` binds `ARTIFACTS` and `ARTIFACTS_EU` as remote R2 bindings for that. A restore of only a regional database changes nothing for the guard: the policies were not rewound. The maximum life of artifacts ([decision 0023](decisions/0023-workspace-retention-policies.md)) is the exception, because there the restored, tighter rule is what archives: `apply-policies` always applies a file's longer or removed maximum (alone when the rest of the item waits for `--allow-lifting`), applies a shorter one with the effective date the file stores (never sooner), and removes a restored maximum from a workspace the file does not list (`retentionCleared` in its output). Run it right after `apply-tombstones`: until then the scan may cap or archive with the restored rule. Anything it archived is restorable from its page, and the query above lists it.

The block list is rewound too and has no export: before step 2 run `blocked-domains` and keep its output, and after step 4 run `block-domain` again for every name the restore dropped (running it detaches whatever the restore reattached under that name) and `unblock-domain` for every name lifted after the export.

If the live database cannot be read for step 2, restore to the latest point that can, export from it, then restore to the point you need and apply. Migrations applied after the restore point are rewound too: apply them again with `wrangler d1 migrations apply portifact-control --remote` before step 4. A restore to before migration 0027 also rewinds the per-row limit columns of `account_usage` and `annotation_usage`; reapplying it gives every row the free plan's defaults again, and `apply-plans` sets the granted plans' columns again.

### With more than one region

Each control database has its own Time Travel: `portifact-control` is the global database and the default region's, `portifact-control-eu` the EU region's (and `portifact-access-eu` its access log, which no restore of a control database touches). Restore only the databases that need it; `export-tombstones` and `apply-tombstones` then need `--region <name>` or `--region all`, so the restore is named on purpose.

What each database holds decides what a restore rewinds. The global database: accounts, sessions and identities, workspaces, members and invitations, workspace groups and their members, single sign-on providers, SCIM tokens, users, groups and the role mapping, workspace policies, plans, email domains, custom domains and claims, tombstones, the artifact directory, and the global audit events. A region's database: its artifacts and versions, readers and `artifact_groups`, share links, comments and `comment_notices`, review requests, reviewers, verdicts and `review_notices`, webhooks and their events, the search index, usage and limit columns, its outbox and its audit events.

1. Before exporting, drain the regions' comment markers. A comment or thread deleted in a region with its own database gets its tombstone from a `comment_tombstones` outbox job in that region, which the relay sends a minute or two later; a restore of the global database rewinds the tombstones, and a restore of the region rewinds the job, so a deletion whose job has not run yet would come back. After stopping requests, keep the jobs Worker's relay and queue running until `select count(*) from outbox where topic = 'comment_tombstones'` is 0 in every region with its own database, then export. A row that will not go (its job keeps failing, `job_failed` with its ID): run its payload by hand, `insert or ignore into tombstones (kind, id, deleted_at) select 'comment_thread', value, <at> from json_each('<ids>')` and the same with `comment_message` for `messages`, on the global database, then delete the row; if neither works, note the thread and message IDs in the payload and delete them again after the restore before reopening access.
2. From the live databases, before any restore: `export-tombstones --region all --out "$HOME/portifact-tombstones.jsonl"` (tombstones and deletions from the global database, purges and revoked links from every region), and, when the global database will be restored, `export-plans`, `export-policies` and `blocked-domains` as above. Export with `--region all` even when only one database will be restored: the markers come from both sides.
3. Restore each database that needs it with `bun run --cwd apps/jobs wrangler d1 time-travel restore <database> --timestamp <RFC 3339 time>`, noting the bookmark each prints. Restore the global database first when both are restored.
4. Re-apply. Restoring the default region means restoring `portifact-control`, which is the global database: it rewinds the global rows and the artifact directory of every region, so it is always `apply-tombstones --file "$HOME/portifact-tombstones.jsonl" --region all` (the tool refuses `--region default` while another region has its own database, because the other regions' directory rows and the evidence of resurrected owners would be left out). A single-region flag is only for a region whose own database was restored alone, such as `--region eu` after restoring `portifact-control-eu`. Each separate region is done first (purges, link revocations, webhook removals, audit events), then the global half, which also deletes again an account or workspace whose only rows left are in a separate region. If it stops in between, run it again. Then, when the global database was restored, `apply-plans` (each plan goes to its owner's region, with its limit columns and `owner_retention` job), `apply-policies` and the block list, as above.
5. Check per region: `select count(*) from artifacts where state = 'purging'` in each restored regional database, `account_deletions` and `workspace_deletions` in the global one. A second `apply-tombstones` with the same `--region` reports `0 restored, 0 artifact(s) claimed for purging, 0 account(s) and 0 workspace(s) deleted again`.

What comes back, by database restored:

- **Only a region's database.** Its artifacts, versions and webhooks deleted since return and step 3 removes them again; artifacts created since are lost, while their directory rows stay and answer like a missing artifact. Review notices: pending `review_notice` jobs and `review_notices` claims come back, so a reviewer may get the same review email again; requests and verdicts since the restore point are lost, so tell the workspace's admins. Comment notices behave as above. `artifact_groups` rows naming a group deleted since grant nothing (`canRead` needs a live group) and `pruneArtifactGroups` removes them. A plan granted since keeps its global row while the restored limit columns are older: the region's `alignPlanLimits` sets them again within 15 minutes, and the region's `owner_retention` job is lost, so run `set-plan` again for owners whose retention changed. The search index is rebuilt by its scans.
- **Only the global database.** Workspaces, members, invitations, groups and memberships, SSO providers and their identities, SCIM tokens, users and groups, policies and plans return to the restore point; tombstones (`workspace_group`, `workspace_group_member`, `workspace_sso`, `scim_token`, `scim_user`, `workspace_invitation`, `workspace_member`) remove what was deleted since, and the directory roles are recomputed. The regions keep their rows; step 3 with `--region all` rebuilds the directory rows of every region and purges artifacts of owners deleted since.
- **Both.** Restore the global database first, then the regions, then `apply-tombstones --region all` once.

### Backup drill

Rehearse the restore on a scratch database, never on `portifact-control`. With the deploy credentials:

1. `bun run --cwd apps/jobs wrangler d1 create portifact-drill-<date>`, then a Wrangler configuration outside the repository with a `DB` binding to it (`"remote": true`, `migrations_dir` pointing at `packages/db/migrations`) and `bun run --cwd apps/jobs wrangler d1 migrations apply portifact-drill-<date> --remote -c <that file>` (an absolute path, and an absolute `migrations_dir`: the command runs in `apps/jobs`).
2. Seed it through the services (users, active and archived artifacts with versions and objects, annotation threads), for example with a throwaway Node script that binds the configuration with `getPlatformProxy` and a local R2 bucket. The publish commit uses the Workers-only `crypto.DigestStream`, so such a script needs a small polyfill on Node.
3. `bun run --cwd apps/jobs wrangler d1 time-travel info portifact-drill-<date>` for the bookmark, then delete as production does: an artifact deleted by its owner, an account deletion left in progress, and an account deletion finished by its jobs.
4. Follow "Restoring a backup" with `--config <that file>` on every operator command and the scratch database's name in the Wrangler commands. Check that the restore brings the deleted rows back without their tombstones, that `apply-tombstones` claims the resurrected artifacts and deletes the accounts again, that a second run reports `0 restored, 0 artifact(s) claimed for purging, 0 account(s) deleted again, 0 artifact directory row(s) rebuilt`, and that the outbox jobs finish the purge.
5. Delete the database (`bun run --cwd apps/jobs wrangler d1 delete portifact-drill-<date>`), the configuration, the export and any local state.
