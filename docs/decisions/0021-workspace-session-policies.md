# 0021 Workspace sign-in policies

- Status: accepted for the maximum session age and the allowed clients; "SSO required" is designed here and ships in a follow-up
- Date: 2026-11-11
- Feature: premium plan E4, rest (`policies` in `PLANS`, Enterprise), after [decision 0020](0020-workspace-request-policies.md); the open half of E1 ([decision 0016](0016-workspace-sso.md))

## Question

Decision 0020 put the request context on the global handle and applied the network allowlists where the role is decided. Organizations also want to bind how a person's request authenticated: only with a recent sign-in, only through the clients they trust, and only through their own single sign-on. What does the server know for a fact about how a request authenticated, how does that reach `actorOn` without a D1 read, what does each policy mean for every credential (the dashboard, the CLI, MCP clients, service tokens, the artifact origin's read and review sessions), how does a refusal look, and how do admins avoid locking themselves out?

## Scope of this change

This change extends the request context with the credential and ships two policies end to end: the maximum session age and the allowed clients, in the app Worker, the content Worker, the dashboard, the CLI and MCP, the operator's escape hatch and restores. "SSO required" needs one more fact, the method a session signed in with, which Better Auth does not record today (its `sessions` row has no method column), plus decisions about break-glass and provider removal that deserve their own review; its design is in "SSO required" below and it ships separately, so nothing about it is offered or stored yet. All three at once would not have been one reviewable pull request.

## Decision in short

- **The credential is a fact on the request context.** `RequestContext` (`packages/contracts/src/request-context.ts`) gains `credential`: `{ kind: "session", userId, signedInAt }`, `{ kind: "oauth", userId, clientId, client, signedInAt }` or `{ kind: "service_token", userId }`. It is recorded where the request authenticates (`recordCredential`, on the request's own context object that every handle built for the request shares), from rows the lookup already read, never from a header. Absent until then; a request that presents two different credentials gets `null` for the rest of the request. Frozen and background contexts never take one.
- **Where each is recorded, and from which read.**
  - The dashboard's session: `sessionOf` (`apps/app/src/auth/credentials.ts`) wraps Better Auth's `getSession`, which reads the `sessions` row; `signedInAt` is its `created_at`. Every session lookup of the app goes through it (the API's session path, the account, workspace, audit stream and integration routes, the read entry, terms acceptance).
  - An OAuth access token: the in-process introspection (`apps/app/src/auth/introspection.ts`) already reads the `oauth_access_tokens` row through the provider; it captures that row as the provider's adapter returns it (a view over the endpoint's context whose `findOne` remembers the row) and adds `portifact_auth_time` from its new `auth_time` column. `introspectFor` records `{ clientId: payload.client_id, signedInAt }`. That covers `/api/v1` bearer tokens, `/mcp`, `/api/v1/me`, the CLI's `credentials:manage` routes.
  - A service token: `authenticateServiceToken`'s result, in `guarded` (`apps/app/src/api/routes.ts`).
  - Read and review sessions on the artifact origin: their renewal (`refreshReadSession`, `refreshReviewSession`) already checks that the app session behind them is live, in its own read with one database (a scalar subquery on `sessions` now selects `created_at` instead of only testing existence) or in its one global read with a separate regional database (which now returns `created_at`); then `recordSessionRenewal` records it before `checkReadAccess` decides the role.
- **No added D1 read.** Every fact comes from a row the path already read. Proved by call counts: services `test/sign-in-policies.test.ts` ("D1 calls": resolving a role and listing workspaces cost 2 statements with and without the policies), the content Worker (`apps/content/test/workspace-modes.test.ts`: a warm request and a renewal prepare the same statements with and without the policies), and the existing `write-costs.test.ts`, `scan-costs.test.ts` and two-region delivery counts unchanged. With a separate regional database the renewal's global read and the access check now run one after the other instead of side by side (same count, one more round trip once every 60 seconds per read session), because the access check needs the sign-in time.
- **One choke point, unchanged.** `bound` in `actorOn` passes the actor's user and `Date.now()` to `checkRequestPolicy`, which checks the network first (decision 0020), then `signInVerdict` (`packages/domain/src/workspace-policies.ts`). No service checks a sign-in policy itself. `requestRefusal` gives the workspace list its `blockedBy` from the same rules. A refusal is `policy_refused` with `reason: "session_age"` or `"client"` on the `Result` (additive; network refusals keep no reason), so the read entry can send a person to sign in again.
- **Fail closed.** A policy that needs a fact the context lacks refuses: no credential, a credential of another user than the one the role is decided for, a service token's credential for a person, or a token whose record does not say when its sign-in happened. Background work is never bound, service tokens are never bound by these two, and the personal space never is.
- **Guard.** `scripts/request-context.test.ts` now also checks that only `credentials.ts` reads a session in the app, and records it; that only `introspectFor` introspects and records the token; that the service token check records the token; that both renewals record the session before the access check; and that the context reads no header but `CF-Connecting-IP`.

### Alternatives rejected

- **A D1 read for the sign-in time in `actorOn`, only when a policy needs it.** Simple, and it would cost nothing to workspaces without the policy, but every request of a workspace that sets one would pay a read, and the brief for this feature is no added read on the request path. The facts are on rows already read.
- **Reimplementing the provider's token validation in one joined query.** Fewer reads, but Portifact would own the security of token validation (expiry, revocation, client state, session liveness) instead of the pinned provider. The adapter view keeps the provider's code path intact and only remembers what it read.
- **Putting the sign-in time in `reference_id` or another provider column.** `reference_id` keys consents; any other column would be a misuse the next provider upgrade could break. A column of our own, filled by a trigger, is explicit.
- **A list of allowed client names or IDs.** Dynamically registered MCP clients choose their own names, and anyone can register a client, so a list of names is theater. See "Allowed clients".
- **Ending sessions that are too old.** The policy binds acting on one workspace, not the account: the same session keeps working in the person's other spaces, so nothing is signed out or deleted.

## The maximum session age

`WorkspacePolicy.sessionMaxHours`: null, or an integer from 1 to 720 (`WORKSPACE_POLICIES.sessionMinHours`/`sessionMaxHours`). A person acts on the workspace only while `now - signedInAt <= hours`. Service tokens have no sign-in and are not bound; the Policies page says so.

### What "sign-in time" means, per path

- **The dashboard session.** Better Auth's `sessions.created_at`. Checked in the installed better-auth 1.7.18: `getSession` extends a session by calling `updateSession` with only `expiresAt` and `updatedAt` (`api/routes/session.mjs`), so `created_at` survives every refresh; Better Auth's own "fresh session" rule reads the same column. A new sign-in is a new row. Last activity (`updated_at`) is not a sign-in and is not used.
- **An OAuth access token.** The sign-in its grant descends from, never the token's own issue time, so refreshing never resets the clock. The pinned `@better-auth/oauth-provider` 1.7.18 writes the rows itself and keeps a sign-in time only on the refresh token: `auth_time` is the session's `created_at` for the authorization code grant, and every rotation copies it to the new refresh token (`createRefreshToken(..., originalRefresh, authTime)`). Access tokens carry no such column, and the device flow (the CLI's `portifact login`) keeps no session and writes no `auth_time` at all. So migration 0057 adds `oauth_access_tokens.auth_time` and 0058 adds two triggers:
  - a refresh token inserted without `auth_time` is the first of a new grant (the authorization code grant always carries one), so it takes its session's `created_at`, or 0 ("not known") without a session (migration 0059 replaced 0058's fallback to its own `created_at`; see "The device flow" below);
  - an access token takes its refresh token's `auth_time`, or its session's `created_at` when it has no refresh token, or stays null.
    Grants from before the release are backfilled with their session's `created_at` when that session still exists, and otherwise with 0, "not known", which every maximum age refuses: those people sign in again once instead of an old grant looking recent. For a CLI that stays logged in for months: once its `portifact login` is older than the workspace's maximum, every command on that workspace answers `policy_refused` with "Run `portifact login` to sign in again"; the personal space and other workspaces keep working.
- **The device flow (`portifact login`).** A device login inherits the sign-in of the session that approved it, exactly as an authorization code inherits its session's. The first version of this change took the refresh token's own `created_at` (the poll), which a review found to be a bypass: a member refused for a 9-hour-old session could approve a new device code from that same session and get a CLI token that looked fresh, so a stolen or long-lived session cookie could keep itself alive forever. What the pinned provider does (`better-auth` 1.7.18, `plugins/device-authorization/routes.mjs`, and `@better-auth/oauth-provider` 1.7.18 `exchangeOAuthDeviceCode`): `/device/approve` reads the session (`getAuthoritativeSessionFromCtx`), checks the code is pending and claimed by that user and sets `status: "approved"`, storing no session; the poll finds the code by `device_code`, then `consumeOne` deletes it, and only then calls `issueTokens` with no `sessionId`, no `authTime` and nothing that names the code. So no trigger can join a token to its approval: the row is gone and the tokens carry user and client only, which two concurrent codes of one person for one client share. The mechanism (migration 0059, `apps/app/src/auth/device.ts`, called from the auth routes around the two endpoints):
  - **At approval**, the one moment the server knows the approving session, the app reads that session (`sessionOf`) and writes its `created_at` on the code (`device_codes.approver_signed_in_at`), before the provider approves it, on the row with that user code, claimed by that user and still pending. Written before the approval, so a poll can never find an approved code without it; of two attempts on one code the older sign-in wins (`min`), so the value is never fresher than any session that tried to approve it.
  - **At the exchange**, the app reads the code's value by its `device_code` before the provider consumes the row, lets the provider issue the tokens, and writes the value onto the exact access token and refresh token it issued, found by the provider's own lookup of the returned access token (`tokenRecordOf`, a SERVER_ONLY endpoint of the introspection plugin, through the same adapter view). Every later rotation copies it. Two codes approved at once are keyed by their own `user_code` and `device_code` and their own returned token, so they never swap or share values (tested).
  - **Fail closed.** The refresh trigger now gives a sessionless new grant 0, so if the app's write fails, or a code was approved before 0059 (its column is null), the tokens read as "not known" and the person approves again. Considered and rejected: refusing device approval from a session older than a freshness bound (sound, but every `portifact login` would need a fresh sign-in, and it would still not be the approving session's time); a trigger on the code's approval update (it cannot know which session approved).
  - **Upgrades.** This relies on the provider keeping `/device/approve` and the device grant at `/oauth2/token`, finding the code by `device_code`, and storing access tokens findable by `validateAccessToken`; `apps/app/test/sign-in-policies.test.ts` fails if any of that changes.
- **Read and review sessions on the artifact origin.** They reference `sessions.id`; their 60-second renewal enforces the age from the app session's `created_at` read in the renewal's own query. Which modes: every mode in which `checkReadAccess` decides a member's role at renewal, so `workspace`, `restricted` and `domain`; a member reading a `public` artifact reads it as anyone. Not bound: the outsiders a `restricted` or `domain` artifact names (no role), share link sessions and public visitors. Within a session's 60-second claims nothing is re-checked (no read per delivery request), so the delay is at most a minute. A refused renewal sends the visitor to the app's read entry, which sends them to `/login?reauth=session_age&next=<the entry>`.

### Refusals and what fixes them

The message names the policy and the fix of the client that asked (`POLICY_MESSAGES.sessionAge`): the dashboard and read entry "Sign in again to continue", the CLI "Run `portifact login` to sign in again", other OAuth apps "Ask the user to reconnect this app to Portifact, which signs them in again". A record that does not say when (`sessionUnknown`) gets the same fixes. The dashboard shows one page for the workspace ("Sign in again to continue") whose action opens `/login?reauth=session_age&next=<this page>`: the login page then offers the sign-in although a session exists, signs in alongside it (the old session is not ended; the other spaces keep working with it) and returns to the page. The workspace list keeps the workspace with `blocked: true, blockedBy: "session_age"`; `portifact workspaces` prints the fix; `list_workspaces` tells the agent the user must reconnect. The policy never ends or deletes a session or token.

## The allowed clients

`WorkspacePolicy.allowedClients`: null (every kind), or a list of `CLIENT_KINDS` besides the dashboard, which is always allowed: `cli` and `oauth_apps`. An empty list allows only the dashboard (and read and review sessions, which descend from it).

- **What the server knows for a fact.** The token's `client_id` comes from its row. `cli` is exactly the seeded record `portifact-cli` (`CLI_CLIENT_ID`, the one record that lists `credentials:manage`, decision 0003): dynamic registration generates client IDs, so no one can register that ID. Every other OAuth client registered itself (or was registered by a Client ID Metadata Document) and is `oauth_apps`.
- **Why not specific clients.** Allowing client IDs picked from those the workspace's members authorized was considered and not built: the ID is the server's record, so it is real, but the only thing an admin can recognize it by is a name the client chose for itself, so a list would let an attacker who registers "Claude" next to the real one be indistinguishable in the picker, and a person can register a new client in a minute. Categories are what the server can stand behind. If customers need it, it can come with verified publishers (Client ID Metadata Documents on a domain the admin trusts).
- **What it does not protect against.** It does not stop a person from copying what they can read into another app, or from using the dashboard; it binds acting with a person's authorization, not the data afterwards. The dashboard copy says so.
- **Refusals.** `POLICY_MESSAGES.client("cli" | "oauth_apps")` ("does not allow the Portifact CLI / apps connected through OAuth, such as MCP clients, to act on it. Use the dashboard, or ask a workspace admin."), `reason: "client"`, `blockedBy: "client"`. The client is checked before the age: signing in again would not help.

## Shared rules

- **Plan.** Setting or tightening needs `policies` (Enterprise, live); loosening (a longer maximum or none; a superset of kinds or none) never does, and a lapsed plan keeps them applying (decision 0015's rule).
- **Who.** Only admins, only through the dashboard session (`/api/v1/workspaces/:slug/policies`); no bearer route, MCP tool or CLI command.
- **Reading.** Every member reads both values (the Policies page, the workspace list, `describePolicy`): unlike a network list, they are rules members must follow, and every refusal names the hours anyway. The admin's own sign-in time (`yourSignInAt`) is shown only to admins.
- **Lock-out.** `checkPolicyKeepsCaller` refuses (`invalid_input`, in the preview too) a maximum the saving admin's own sign-in already exceeds (`sessionLocksOut`), and fails closed when their sign-in time is unknown. The allowed clients cannot lock the dashboard out (it is always allowed), and saving happens only through it.
- **Impact.** The preview returns `signIns: { members, staleMembers, clientMembers }` when either is set: every member bound, members who would have to sign in again (no live dashboard session younger than the maximum, or a live CLI or app grant whose sign-in is older or not known: they sign in again at their next action there), and members holding a live OAuth grant of a kind the policy would refuse. One batch of the global database, on the preview only. The dashboard confirms a new or tighter policy with these counts; nobody is signed out.
- **Stored shape.** `storedPolicy` writes each field only while it is set, so a row that sets neither stays readable by the previous release's strict schema; a rollback breaks only workspaces that set one (docs/releasing.md, "Sign-in policies").
- **Audit.** `policy.changed` carries `sessionMaxHours` (hours or null) and `allowedClients` (the kinds or null): enums and counts only.
- **Escape hatch and restores.** `clear-request-policies` lifts the network allowlists and both sign-in policies, nothing else. `export-policies`/`apply-policies` carry them, validate and normalize every line, and report a wider or missing value as a lifted restriction (`liftedFields`), applied only with `--allow-lifting`.
- **Blocked is never an outsider.** A refused member reads nothing of the workspace through their account but a public artifact (decision 0020's rule, unchanged: the refusal comes from `actorOn` before `canRead`). They can still leave the workspace and decline invitations, which never decide a role on it.
- **Races.** A policy saved while a request is between its role decision and its write binds from the next role decision, as in decision 0020; a request that decides the role again later is refused inside the same request (services test "races"). The policy changes no stored data, so no job or scan is needed.

## What this protects against, and what it does not

- It bounds how long a stolen session, a forgotten CLI login or a long-lived MCP connection can act on the workspace, and which kinds of client can act at all, through every interface, without a read per request.
- It does not bound what a person already copied or shared, service tokens (bound only by their network list, decision 0020), share links, or the person's other spaces.
- The CLI's sign-in time is the sign-in of the session that approved its device code, and an app's the sign-in of the session that authorized it; neither is reset by approving or connecting again from the same session.
- An MCP client that keeps refreshing its tokens is refused once its authorization is older than the maximum, and the person reconnects it.

## SSO required (next)

Designed here, shipped separately. The setting `ssoRequired` would let members act on the workspace only through a session that signed in with the workspace's own provider (the `sso:<provider id>` identity of decision 0016), and OAuth tokens only when they descend from such a session.

- **The missing fact.** Better Auth's `sessions` row does not say how it signed in. The follow-up adds a session column (Better Auth `session.additionalFields`, set by Portifact's SSO plugin when it calls `setSessionCookie`, and `null` for every other method), read with the session in `sessionOf`; tokens take it through the same trigger path as `auth_time` (refresh token, then access token). Until then nothing about it is offered, stored or enforced.
- **Admins.** Exempt by default (break-glass: if the identity provider is down or misconfigured, an admin can still sign in with a code and fix the provider); a workspace can opt admins in, after a confirmation that names the lock-out and the operator's `clear-request-policies` as the only way back.
- **Members the provider cannot serve.** Members whose verified address is not at a domain the provider serves cannot sign in through it: the save is refused while any exist, naming the count, unless the admin exempts them explicitly, and the Policies page lists them.
- **Pending, directory and invited members.** A pending membership is not a role, so it is not bound until it is claimed; accepting an invitation from a non-SSO session works (it changes only the person's own membership) and binds from the next request.
- **Service tokens** are not bound. **A blocked member** sees the workspace in the list with a "Sign in with single sign-on" action that starts the provider's flow and returns them.
- **Provider removed or SSO lapsing.** Removing the provider clears the setting in the same global batch, with its own audit event; a plan without `sso` (or `SSO_ENABLED` off) stops enforcing it and the dashboard says so, so a required method nobody can use can never remain. With `SSO_ENABLED` off the setting cannot be set and nothing about it is shown.
