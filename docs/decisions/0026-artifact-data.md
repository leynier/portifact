## Question

An artifact is a static site today. The maintainer wants it to be able to be a small app: its JavaScript, running in a visitor's browser, stores and reads data that outlives the visit (forms, votes, lists, boards), and the owner and their agents read and manage the same data through the API, the MCP server and the CLI. How can Portifact give each artifact a database without letting a visitor reach another visitor's data, letting a page act as a person without their consent, letting one artifact reach another's, letting a hostile owner or visitor spend Portifact's budget without a bound, or breaking any rule the platform already keeps (regions, deletion, restore, holds, quotas, the three interfaces' parity)?

From the fourth review and the maintainer's answer to it:

45. **No owner ledger and no leases.** Every limit is per artifact, kept in the artifact's own object, checked and charged synchronously in the same transaction as the work. An owner's exposure is the number of data artifacts the plan allows times the per-artifact daily limits. The limits arrive with every command from the plan the Worker already holds; a plan change applies from the next command. Nothing is awaited between a command's admission and its work.
46. **Charging by measured work after the fact.** After each operation the object adds the rows it read and wrote (the cursors' counters plus its own bookkeeping) to the day's counter for that class, in the same transaction, and refuses further work of that class once the counter is spent. One operation's overshoot is bounded by stated, tested per-operation caps. Reads are counted in memory and persisted in batches. Refusals cost as little as possible. The one exception is a storage failure the object cannot record at all ("Implementation notes for delivery 4", note 11).
47. **No proven worst month.** The record states the per-artifact limits, the arithmetic of what they imply, which numbers were measured locally and which must be measured in production, and that global budget protection is what stops spending when the estimates are wrong, with a new step for data.
48. **Lifecycle repairs**: a hold refuses every payload erasure, quarantine resolution included, until a separately authorized release is acknowledged; erase steps carry a durable erase ID with its target; a repeated transition must match its original contents; a request's newer epoch never consumes the epoch a pending fence needs; an alarm is set only for maintenance that can run; the first durable write on an empty object binds its identity or is refused.
49. **Terminal author erasure**: the barrier governs every path that could recreate author-associated state; completion ends with an atomic check and cleanup; the journal has one retention rule; the minimal evidence kept is listed.
50. **The design phase ends.** Delivery 3 is the contracts as production code with property and fault-schedule tests and its own adversarial code review; every protocol property the four reviews found is in "Acceptance tests for delivery 3". Nothing is reachable by a user until the last delivery's switch.

Alternatives rejected by the issue (Turso Cloud, Turso's engine in Workers, D1 per artifact, shared tables in the regional D1, SQLite in the browser with sync) stay rejected for the reasons it gives.

## Decision in short

- **One object per artifact**, `ArtifactDocuments`, holding the collections and speaking only the document API, to the page through the content Worker and to the owner side through the app Worker. No second object, no owner ledger.
- **A control record** in the object: artifact, region, owner, owner epoch, generation, epoch, an independent hold, a quarantine, a prepared erase with its ID, the last ended erase, the last transition with its ID and contents, a storage sequence and a payload revision. One validator, `admit`, with four modes, decides every command.
- **One transaction per command, nothing awaited before it**: admission, replay, issue-time horizon, authorization, the class's spent check, the work and the charge of what was measured, all synchronous.
- **Per-artifact daily counters** for growth, reads, cleanup, export, the visitor's own rights and live messages, from the plan sent with the command.
- **Operation records** keyed by actor, generation and operation ID, bound to a hash of the request, holding no body; IDs carry their issue time; audit obligations under the same key.
- **Erasure** in two steps under an erase ID for the whole data, and per author behind a terminal barrier in bounded, replayable chunks; the author journal and the object inventory in R2.
- **A grant on the app origin** before any identity.
- Shipped off behind four switches; nine deliveries, the feasibility experiments first and the contracts' code review before any adapter; option B recommended as the smallest exposure.

## One object

`ArtifactDocuments`, named by the artifact ID, in the jurisdiction of the artifact's region, holds every collection of the artifact and its control tables. No SQL from anyone reaches it: every statement it runs is written by Portifact, so no owner schema, constraint, trigger or reference exists that could block an erasure or make a statement's cost unbounded.

| Worker                 | Exports             | Binds                | `limits.cpu_ms` |
| ---------------------- | ------------------- | -------------------- | --------------- |
| `portifact-data` (new) | `ArtifactDocuments` | itself               | 200 proposed    |
| `portifact-content`    |                     | `ARTIFACT_DOCUMENTS` | default         |
| `portifact-app`        |                     | `ARTIFACT_DOCUMENTS` | default         |
| `portifact-jobs`       |                     | `ARTIFACT_DOCUMENTS` | default         |

The new Worker has no routes, no D1, R2 or queue bindings and no secret; legacy `migrations` with tag `v1` (`new_sqlite_classes`), never `deleted_classes`, `renamed_classes` or `transferred_classes` (a `scripts/` test refuses them). Deploy order: `portifact-data`, then jobs, content and app. `dataNamespaces(env, region)` in `packages/services` is the only place a stub is made (`locationHint: "wnam"` for the default region, `jurisdiction("eu")` for the EU), from the directory's region only. The CPU limit stops runaway work; it does not bound billed wall time (see "Cost").

## The control record and the validator

The object keeps a control record (`spikes/artifact-data/src/envelope.ts`) in `pf_meta`: `artifactId`, `region`, `ownerId`, `ownerEpoch`, `generation`, `epoch` (the admission floor: no request older than it is admitted), `boundEpoch` (the epoch the first durable write bound the object at), `fencedEpoch` (the epoch of the last fence applied, null before any), `hold` (the transition that set it, independent of everything else), `quarantine` (set only by reconciliation, cleared only by the operator), `erasing` (a prepared erase: its ID, target generation and epoch), `lastErase` (the last erase intent that ended and how), `last` (the last transition: its ID from D1's batch, kind, epoch, owners before and after, time), `storageSeq` (raised by every durable write) and `payloadRevision` (raised when documents or declarations change, and at a generation boundary; implementation note 14). Every command carries an envelope `{ artifactId, region, ownerId, generation, epoch, opId? }` filled by the calling Worker from D1.

**One validator, four modes.** `admit(stored, envelope, mode)`:

| Check, in order            | `request` (page, owner side)                      | `operator`  | `erase` (prepare, commit, cancel) | `maintenance` (settle, acknowledge) |
| -------------------------- | ------------------------------------------------- | ----------- | --------------------------------- | ----------------------------------- |
| No control record          | Admitted; only an authorized first write binds it | Admitted    | Admitted; prepare binds it        | Admitted; the first write binds it  |
| Another artifact or region | `forbidden`                                       | `forbidden` | `forbidden`                       | `forbidden`                         |
| Quarantined                | `quarantined`                                     | Admitted    | `quarantined`                     | Admitted                            |
| Another owner              | `stale`                                           | `stale`     | `stale`                           | Admitted                            |
| Older epoch                | `stale`; a newer one is admitted, never adopted   | `stale`     | `stale`                           | Admitted                            |
| Another generation         | `stale`                                           | `stale`     | Older: done; newer: `stale`       | Admitted (the key names it)         |
| Held                       | `held`                                            | Admitted    | `held`                            | Admitted                            |
| Erasing                    | `stale`                                           | Admitted    | Admitted                          | Admitted                            |

A newer epoch is admitted but never written into the control record: only a fence moves the epoch, so a request that arrives first never consumes the epoch the fence it precedes needs. **The first durable write on an empty object binds its identity**: a declaration (after authorization), an erasure step, an author erasure, a fence or a settlement writes the control record from its envelope in the same transaction; every other command on an empty object writes nothing; a later command naming another artifact is refused.

**Fences.** `fence(envelope, { state, toOwner?, transition })` applies a hold, a release or a transfer. It checks the artifact, region and generation; a repeat of the same transition ID must carry the same contents (kind, epoch, new owner) and is acknowledged without change, anything else under that ID is `conflict`; then it requires the current owner and an epoch newer than the last transition's. It is persisted before it is acknowledged, on an empty object too. A hold or a transfer ends a prepared erase (recorded as cancelled); a transfer records the new owner and its epoch; both close live connections; a quarantine survives every fence. A release re-arms maintenance. D1's side: the hold or transfer batch raises the epoch in `artifact_data` and writes a `data_fence` job carrying the transition ID and contents; the change is in force when the object acknowledged it.

**Erasing the whole data, under an erase ID.** `prepareErase(envelope, eraseId)` records `erasing { id, generation, epoch }` (binding an empty object's identity) and closes live connections at that barrier; the same ID and target repeat, another ID while one is prepared is `conflict`, and an ID that already ended answers how it ended. `commitErase(envelope, eraseId)` commits only the prepared ID: one transaction deletes every payload table (documents, collections, fields, indexed values, author counts, sequences, operation records), writes the next generation and records the ID as committed; counters, barriers and audit obligations stay. `cancelErase(envelope, eraseId)` cancels only that ID. A retried step answers the intent's terminal result; a delayed step of an earlier intent changes nothing. Every erase step is refused while a hold stands.

**Restore.** A D1 Time Travel restore rewinds D1, not the object. After `apply-tombstones` puts holds and revocations back, `data_reconcile` reads each object's control record (the R2 inventory lists them) and applies `reconcile(row, control)`:

| Field                                                       | Authority after a restore                                                                                                                     |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Artifact and region                                         | The directory and the inventory; a mismatch goes to the operator                                                                              |
| Owner and owner epoch                                       | The object's last verified transfer transition                                                                                                |
| Generation and epoch                                        | The object; D1 is raised to them only when owner and hold agree                                                                               |
| A prepared erase                                            | The object's `erasing`, with its ID and target; resumed under that ID, never skipped by raising numbers                                       |
| A hold                                                      | The object's hold record against D1's re-applied holds; disagreement quarantines                                                              |
| A quarantine                                                | The object; only the operator clears it                                                                                                       |
| Grants, codes, sessions, memberships, tokens, policies      | D1 plus its non-rewound revocation evidence (window tombstones, including `data_grant` revocations), never the object                         |
| Artifacts, grants and codes created after the restore point | Gone from D1. The inventory finds objects with no D1 row; each is quarantined for the operator. Visitors whose grants were lost consent again |
| Pending account deletions and author erasures               | Re-derived from the tombstones and the journal's retired entries, never from a rewound outbox                                                 |

The operator exports under a quarantine and resolves it with `resolveQuarantine(envelope, "adopt" | "erase")`. `adopt` needs an envelope naming the owner the object recorded, after the operator repaired and verified the directory, ownership and authorization rows; it clears the quarantine. `erase` moves to the next generation and is **refused while a hold stands**: the hold keeps its evidence until a separately authorized release was acknowledged, and only then can the operator erase.

## One transaction per command (decision 45)

Every command of the object is synchronous: nothing is awaited between its admission and its work, so a hold, a transfer or a duplicate delivery is ordered wholly before or wholly after it. A mutation is one transaction:

1. admit the envelope (and bind an empty object's identity if this is an authorized first write);
2. look the operation record up: the same request replays after the caller's current authorization was checked, another request under the key or an aborted one is `conflict`;
3. refuse an operation ID older than the horizon or from the future;
4. authorize, the author barrier included;
5. refuse if the counter of the operation's class is already spent (writing nothing);
6. count the rate attempt;
7. do the work, record the operation and its audit obligation, raise the storage sequence;
8. add the rows the cursors measured, plus the charge statement's own, to the day's counter for the class.

A failure after step 6 rolls the transaction back and then, in a second synchronous transaction, counts the rate attempt and charges what the work measured before it failed, so failed work is never free. Reads are the same without steps 2, 3, 6 and 8: their rows are added to an in-memory count. The spike proves the methods return synchronously (`invariants.test.ts`: every command's answer is not a promise) and that a hold racing twenty writes, or five copies of one operation, leaves exactly the writes that landed before it and one applied copy. No await remains on any command's path; the only awaits are in the alarm (rescheduling) and in the live upgrade after its transaction, so there are no fault schedules to keep. The request hash is computed by a synchronous SHA-256 (`spikes/artifact-data/src/hash.ts`).

## Operation records and replay

Every mutation (document writes, declarations, index steps, bulk deletes, author erasure chunks) carries an operation ID of the form `<issue time in ms>.<random>`, which the Worker stamps from the client's idempotency key. The object records it in the mutation's transaction under `actor | generation | opId`, with a SHA-256 of the request, the state (`committed` or `aborted`), the kind, what it named and, for erasure chunks and bulk deletes, the small result (counts). Never a body. A replay never applies again, never charges and never notifies. Records are pruned 24 hours after they were written; an ID issued more than 23 hours before the command's time, or more than 5 minutes after it, is refused as `conflict`, so a pruned ID can never apply again (spike: D18). Author erasure deletes the author's records.

## Audit with durable states

An owner-side mutation and every author-erasure chunk write their audit obligation (`pf_audit`) in their own transaction under the operation's full key, the same as the mutation record, the D1 audit event's uniqueness and the acknowledgement. Obligations are control data: a whole erase keeps them. The jobs Worker calls `settle(envelope, actor, opId)` (maintenance admission): it answers a committed obligation and whether it was delivered, a committed operation without one, or records the operation as `aborted` so a late arrival cannot commit; for an erased author it writes nothing (the barrier already refuses their late writes). `acknowledge` marks the obligation delivered; delivered obligations are kept 7 days for late settlement, then pruned. Pending obligations are bounded by the owner-side mutations the artifact's growth counter admits per day times the days the relay is down; the daily sweep walks the R2 inventory for obligations pending longer than an hour.

## Author erasure (decision 49)

1. **The journal.** Before a grant's code is issued, the app claims `system/data-authors/<user ID>/<artifact ID>` in the artifact's region's bucket with a conditional put; of two racing first grants one writes, the other reads the winner's visitor ID. **Its one retention rule**: the account deletion job retires the entry first, before any erasure chunk runs; a retired entry refuses every claim; it is deleted 31 days after retirement, longer than any grant or code issued before the deletion can live (30 days and 60 seconds). After that the account no longer exists in D1 and its ID is never reused, so no issuance can name it.
2. **The barrier** is written by the first chunk, on an empty object too (binding its identity), before anything is deleted; it closes the author's live connections and deletes their sequence. From then on the barrier governs every path that could recreate author-associated state: the author's creates, replaces and connections are refused before their rate row is written; nobody edits a document whose creator is barred (`conflict`, so no edit recreates the author's sequence); a sequence in a barred author's scope is never written; a settlement naming the author writes nothing.
3. **Bounded, replayable chunks.** Each chunk deletes at most 500 of the author's documents through an author-first index (each through the sequence and live invalidation, indexed values and counts included), marks at most 500 of the author's edits on other people's documents `_editedBy: "erased"` (each through the sequence and invalidation), and deletes at most 500 of the author's operation and rate rows, then answers `more`. A repeated chunk replays its recorded counts. Chunks are counted against cleanup and never refused for it.
4. **Completion** is the chunk that finds nothing left: in the same transaction it checks that no document is created or last edited by the author, deletes any remaining sequence and count of the author and marks the barrier complete.
5. **Shared edits.** A document belongs to its creator. Erasing the creator deletes the document, including later edits others made to it; erasing an editor keeps the creator's document and its current content and replaces the attribution with `erased`.
6. **The minimal evidence kept**, deliberately: the barrier row (the opaque per-artifact visitor ID and the time; for as long as the object exists, so a late write is refused forever; one per erased author, counted in storage outside the data cap); the erasure chunk's operation record (until the 24-hour horizon); its audit obligation (counts only, until delivered and 7 days); the D1 audit event (counts); the retired journal entry (31 days). None holds a body.
7. A held artifact defers the chunks to the hold's release.

## Limits and counting (decisions 45, 46)

### The classes

| Class         | Counter (per UTC day)                        | Spent by                                                                                                              | Refusal                        |
| ------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| Growth        | rows written (and their reads), per artifact | creates, growing replacements, declarations, index build steps, live connects                                         | `quota_exceeded`               |
| Reads         | rows read, per artifact, in memory           | gets, queries, counts, describe, replays (the erasure job's are protected) and the lookups of refused work            | `quota_exceeded`               |
| Cleanup       | rows read and written, per artifact          | owner deletes and bulk deletes, shrinking replacements, deleting others' documents in `shared`, author erasure chunks | `rate_limited`; erasure never  |
| Export        | rows read and written, per artifact          | owner export pages                                                                                                    | `rate_limited`; operator never |
| Rights        | rows read and written, per visitor           | that visitor deleting a document they created, and exporting their own documents                                      | `rate_limited`                 |
| Protected     | rows read and written, per artifact          | fences, erase prepare, commit and cancel, settlement, acknowledgement, pruning, quarantine cleanup, live reservations | never                          |
| Live messages | messages, reserved 100 at a time             | every message sent, acknowledgements and errors included                                                              | connection closed `4029`       |
| Rates         | durable rows per author and minute           | writes, deletes, connects (attempts admitted; refusals at the limit write nothing)                                    | `rate_limited`                 |

The rights class is a small allowance of each visitor's own, kept in a row per visitor and day (pruned with the day counters), so neither the owner nor other visitors can spend it and block a person deleting or exporting what they created; it needs neither write permission nor the current terms. A spent growth day never stops reading, deleting, shrinking or exporting. Erasure is counted but never refused. The protected class records lifecycle and legally required work with its measured rows; it draws on no visitor's or owner's allowance and is never refused.

### How it is counted

- **Measured, after the work, in its transaction**: the rows the cursors reported plus the charge statement's own two read and two written. A failure after the work began charges what it measured in the next synchronous transaction; when storage fails that one too, or fails a command that has no second transaction, the rows measured and not yet charged are lost and debited to nobody (delivery 4's note 11).
- **Refused before the work** when the class's counter is already spent. Such a refusal writes nothing; refusals are counted in memory and persisted with the next counter write. Every ordinary read or document mutation attempt by a visitor or reader, refusals at any stage (admission, authorization, the horizon, a replay conflict) and replays included, counts once against the caller's minute (`readsPerCallerPerMinute`, in memory and shared with reads), so a caller who spent the minute on refusals is refused next without a durable row per refusal. An own export and the live operations do not count against it: they keep their own admission rules (the per-visitor rights allowance, and the connection and message limits).
- **Reads write no row of their own**: their rows, a replay's and the lookups of refused work are added to an in-memory count that reaches storage with the next counter write, synchronously from the command that reaches 10,000 rows or 1,000 refusals, and from an alarm aimed 30 seconds after the first of them (a target the platform's alarm lateness can miss; it never wakes a held or quarantined object). An eviction therefore loses at most 10,000 rows and 1,000 refusals. Usage of an earlier UTC day is written into that day before today's is counted.
- **The overshoot** of a spent counter is at most one operation, bounded by its caps:

| Per-operation cap                                | Value                       | Measured in the spike                      |
| ------------------------------------------------ | --------------------------- | ------------------------------------------ |
| Documents a page returns                         | 100                         | at most 116 rows read at 100,000 documents |
| Documents a bulk create, replace or delete names | 100                         | under 2,000 rows for a bulk delete         |
| Documents an index build step covers             | 500                         | under 3,000 rows a step                    |
| Documents an author erasure chunk deletes        | 500                         | 368 rows for a chunk of 20 documents       |
| Rows and bytes of an export page                 | 500 and 1 MiB               | 106 rows read for 100 documents            |
| Rows a pruning pass deletes per class            | 500, six retained classes   |                                            |
| Document size                                    | the plan's (16 KiB on Free) |                                            |

- **Row bounds.** `OPERATION_ROW_BOUNDS` turns these caps into the most rows each operation kind may measure, written from per-element constants that name the work (implementation note 5); an operation past its bound is a defect.
- **Index builds are incremental.** Declaring an indexed field records it as `building`; each step (the declaration's own, then `buildIndexStep` calls the owner side's service makes until none is building) adds the values of the next 500 documents in primary key order to `pf_values`; writes keep values for every field meanwhile; queries on a field are refused until it is `ready`. No statement touches more than one step's documents.
- **Counts come from maintained counters** (`pf_collections.documents`, `pf_author_counts`), so a count reads one row whatever the collection holds, a downgrade's retained documents included.
- **Plan changes** apply from the next command: every command carries the limits; a renewal of a live connection carries the current daily message limit.

### What the owner side can do without SQL

Describe (collections with mode, unique key, indexed fields and their build state, document counts and bytes, the artifact's counters); read any collection with one equality on `_by` or a built indexed field, ordered by `_created` either way, in pages of up to 100 with a cursor, in the same bounded shapes as the page; count a collection or one author from maintained counters; create, replace and delete one document; delete up to 100 by ID in one operation (`bulkRemove`, one operation record and one audit obligation, every deleted document through the sequence and live invalidation); build declared indexes in steps; export everything exactly. Bulk create and replace of up to 100 (one operation, all or nothing), counts by an indexed value (from maintained value counts, one row) and describe are built in delivery 3 as rules, contracts and tests (`BulkCreate`, `BulkReplace`, `DataCount`, `DataDescription`, `bulkBodies`, `planCount`, `describe`). It deliberately does not do joins, aggregates beyond counts, range filters on arbitrary fields, full-text search or arbitrary sort orders: each needs SQL or a scan that grows with the data; an agent that needs them exports and analyzes locally ("Later").

## Cost (decision 47)

This section states what the limits imply; it does not claim a proven worst month. What stops spending when these estimates are wrong is global budget protection ([docs/operations.md](../operations.md), "Budget alerts and protection"), which gains a data step (below).

### What the limits imply, per owner and month

If every data artifact an owner may have spends every per-artifact limit every day of a 31-day month, with every live connection sending its 4 messages a minute and the owner's whole traffic quota spent, nothing included, the formulas are, for `N` data artifacts, daily per-artifact limits `W` (growth rows), `C` (cleanup), `G` (rights), `R` (reads), `X` (export), `L` (live messages), connections `K` per artifact, size `S` MB, monthly traffic quota `T`, and active wall time `t` seconds per request:

- rows written: `31 × N × (W + C + G + 2 × L / 100) / 1,000,000` dollars (two rows per live reservation of 100 messages);
- rows read: `31 × N × (R + X + C + G) / 1,000,000,000`;
- Durable Object requests: `(T + M / 20 + A) × 0.15 / 1,000,000`, with incoming live messages `M = N × K × 4 × 1,440 × 31` and alarms `A = 31 × N × (1,440 + 2 × (W + C) / 15)` at most: one a minute per artifact with connections, as first written, plus about two pruning wakes per mutation a day after it (its operation record and its rate row expire at different moments), with at most `(W + C) / 15` mutations a day at about 15 rows each (delivery 2; the first version counted only the connections' minute);
- Worker requests: `T × 0.30 / 1,000,000`; Worker CPU: `T × 2 ms × 0.02 / 1,000,000`;
- duration: `(T + M + A) × t × 0.128 × 12.50 / 1,000,000`, where delivery 2 observed `t` at 11 to 16 ms for reads, 42 to 50 ms for writes and 108 ms for a pruning alarm on a cold object, inside the 5 and 100 ms sensitivities;
- storage: `N × (S + 0.256) / 1,000 × 0.20`;
- R2: one class A write per first grant, per retirement and per new object (US$4.50 per million), class B reads by the jobs.

### Account-level rounding

Billing is per account. Durable Object requests and duration are billed in whole million-unit blocks, so the data feature's share of a month's invoice can exceed its proportional cost by less than one block of each (at most US$0.15 and US$12.50) for the whole account, however many owners there are; Worker requests and CPU are billed fractionally. This bounds only the rounding, not the bill: total additional usage can cross many blocks, and its cost is the difference between the account's rounded totals with and without the data workload.

### The data step of budget protection

Budget protection gains a step `pause_data_writes` at US$105, between `block_uploads` and `pause_annotation_writes`: page and owner writes, live connects and index steps answer `capacity_unavailable`; reads, deletes, exports, the visitor's rights, erasure and restore keep working, as for every other step. The collector adds the data Worker's Durable Object requests, duration and rows to its metrics, and a global admission limit (100 million data rows written in the cycle) adds `pause_data_writes` whatever the spend. The step is designed here and built in delivery 8; [docs/operations.md](../operations.md) points to it.

## The grant (decisions 10, 17, 35)

A grant is one person's consent, for one artifact host and one browser, that the page may know them by an opaque per-artifact ID and their display name and save what they enter. Without a grant a page reads what the artifact's access allows and learns nothing about who is there: `GET /__portifact/data/me` answers `{ granted: false }` for everyone. Review, read and link sessions authorize reading only.

**The control** is drawn by Portifact on `app.portifact.com`: the artifact's host and owner, what the page will learn (display name and an ID for this artifact, never the email), that the people who manage the artifact read everything saved there, that the data moves with the artifact if it changes owner, how account deletion treats shared edits, how long the grant lasts, a link to the rights request page; "Allow" and "Not now".

**Two gates**: `beginGate` admits `GET /__portifact/data/grant/begin` only as a top-level navigation from the artifact's own page (`same-origin`, `document`) or the viewer's navigation of its frame (`cross-site`, `iframe`); `redeemGate` admits `GET /__portifact/data/grant?code=…` only as a `cross-site` navigation from the app (`document` or `iframe`). A sibling's `same-site` navigation passes neither. The API gate stays same-origin only.

**Three flows**, one rule: the one-use code redeems only with the transaction cookie of the browser that began, on the host it was issued for. (1) In the viewer's frame, with a sealed, partitioned transaction cookie, the nonce's hash posted to the viewer (exact target origin), the code bound to the hash and host, and a partitioned `__Host-pf_grant`. (2) The top-level tab, the fallback where partitioned cookies are refused, as decision 0002 verified for review. (3) A direct visit (no bar, a custom host, or the tab above): `begin` opens top-level in a popup or the same tab, the app shows the control and redirects to `grant?code=…`, and the Worker sets `__Host-pf_grant` (`SameSite=Lax`).

**Atomic codes**: consumed with one guarded D1 update. **Storage, expiry, renewal, revocation**: `data_grants` and `data_grant_codes` (regional); the grant cookie holds sealed claims (grant, artifact, visitor ID, 60-second claims, the grant's expiry, at most 30 days and never past the app session); renewal every 60 seconds checks the grant, the app session and the account's terms version; writes need the current terms (reads, the person's own deletes and export do not). Revocation from the dashboard, the viewer or sign-out applies within 60 seconds, live connections included, and writes a `data_grant` window tombstone. **The ID**: random, claimed in the journal, reused by later grants for the same person and artifact, never revived after retirement; it promises that Portifact never gives a page or an owner an account ID or email through this feature and that two artifacts get unrelated IDs; it does not stop an owner from correlating people through names, content, timing or a restricted artifact's access log. Cookie sealing keys are versioned and rotated.

**Anonymous writers** (decision 21): the same control with the human check and a per-IP issue limit; offered in a personal space and in a workspace with `policies` whose policy allows it; elsewhere `dataWriters: "anyone"` answers `plan_required`.

## Requests from the page

All on the artifact's own origin (and its custom domain), reserved under `/__portifact/data/`, routed before the `GET`/`HEAD` check, after the API gate, the artifact lookup, the servable check, the reading session, the grant claims, the network policy, the traffic quota and budget protection; then the envelope and the object. Requests are charged to traffic through the per-isolate meter. Routes: `me`, queries and gets under `c/<collection>`, `POST`/`PUT`/`DELETE` under `c/…`, `mine` (the grant holder's own documents and their export), `live` and `live/renew`, `grant/begin` and `grant`, and the client script `data.js`. Rendered Markdown and text documents run no scripts and are out of scope.

## The document model

The owner side declares collections with a mode (`own` default, `append`, `read`, `shared`), an optional unique key and up to the plan's indexed fields. Server fields: `_id`, `_by` (the grant session that created it: attribution, not proof), `_editedBy` (the last editor other than the creator, or `erased`), `_created`, `_updated`, `_seq` (scoped to the author in `own`, to the collection elsewhere). The unique key is a scalar, required, recomputed on replacement. Queries come only in seek-bounded shapes with their index named; an equality on an indexed field seeks `pf_values` and joins documents by primary key (spike: at most 116 rows read for a page of 100 and 15 to 24 for an empty or sparse match at 100,000 documents). `deleteScope` lets the owner side delete anything, a visitor always delete what they created, and any writer delete in `shared` mode.

## Export (decision 43)

`exportPage` (owner side, export class; the operator under a hold or quarantine, counted, never refused) returns documents in primary key order (collection, ID) after a cursor that is the last row's key, each with its server fields and its body exactly as stored, stopped at 500 rows or 1 MiB of encoded rows (a single document over the byte cap still makes a page of one). `exportMine` (a grant holder, rights class, without write permission or the current terms) returns the documents the caller created through the author index, in the same form and bounds. Every page carries the payload revision, which changes only when documents change, so pages that start and end with the same revision are a consistent snapshot and a quiet export never moves it. A declaration moves it too (what an export contains includes the collections and their indexed fields), and so does a generation boundary (implementation note 14).

The file the CLI and the dashboard write is JSON Lines: a header `{ format: "portifact-data", version: 1, artifact, generation, revision, collections: [{ name, mode, uniqueKey, indexed }] }`, one line per document `{ collection, id, by, editedBy, created, updated, body }` with `body` the stored JSON, and a footer with the revision at the end and `consistent`. It is stable (versioned, never reordered), typed (fixed server fields, bodies as stored) and complete (every document and every declaration), so it loads into SQLite with one table per collection or one table with `json_extract`. Writing and loading the file are delivery 3 and 5 tests.

## Live updates (decisions 5, 29)

A connection is accepted only on an object with data; it holds in its attachment the author, the principal that opened it, the generation, an absolute deadline, its per-minute counters, its reserved messages and the plan's daily message limit. Every message it receives and every message sent to it first re-admits it against the control record (a hold, quarantine, prepared erase or new generation closes it `4003`) and checks the deadline (`4001`). `renew(envelope, socketId, principal, deadline, limits)` requires the same principal, may shorten the deadline and updates the daily limit to the current plan's. Every message sent, acknowledgements and errors included, spends a message reserved against the artifact's day 100 at a time (two rows written per reservation: the day's counter and the control record's sequence); a refused reservation closes the connection `4029`, more than 256 KiB in a minute `4009`, more than 4 messages in or 1 KiB a message `4008`. Every document mutation, bulk deletes and author erasure chunks included, goes through the sequence and fan-out; a replay never notifies. Prepared erases, holds, transfers, quarantine and author erasure close connections at their barrier.

## Storage accounting

Every answer, refusals included, carries `{ generation, seq, bytes }`. `seq` rises with every durable write (mutations, counters, rate rows, live reservations, settlements, acknowledgements, pruning, fences, erase steps); a refusal that wrote nothing leaves it. The calling Worker keeps the newest report per object (`newerReport`: later generation, or same and later sequence) and writes it every 5 seconds into `artifact_data.documents_bytes`; the owner's usage is the sum over its artifacts. The object refuses growth when the documents' own bytes pass the plan's size, or when the database file passes it plus a 256 KiB reserve for control records. Control records are bounded by their retention: operation records 24 hours, delivered audit 7 days, rate rows a day, day counters 3 days, each pruned through an index that leads with its age, at most 500 a pass, resuming at the next alarm. Barriers (one per erased author) and pending audit obligations (bounded above) are kept as evidence, counted in storage and never deleted to meet the cap.

## Housekeeping

One alarm per object: it closes connections past their deadline, prunes every retained class in bounded passes, persists counted reads and sets the next alarm at the earliest moment any eligible maintenance can run (a connection's deadline, counted reads' 30 seconds, a minute later when a pass was full, or the oldest operation record, delivered audit obligation, rate row or day counter reaching its age, rounded up to the hour so one alarm prunes everything due within it). An alarm's own pruning is recorded with the next counter write, never by writing a day row of its own, so an idle object stops waking once its retention has run out. Under a hold or a quarantine nothing is pruned and only connection deadlines can set an alarm, so a held object with no connections sleeps; a release or a resolution re-arms it. An alarm that fails is retried by the platform; its work is idempotent. Delivery 2 measured that setting the next alarm at the oldest retained row's expiry wakes an object about twice per mutation ("Feasibility results"); with delivery 3's batching, 120 writes spread over an hour wake it once for retention the next day and twice in all (Implementation notes, 16).

## Lifecycle

Publish and rollback never touch the object. Archive and suspension raise the epoch (the fence is wired with the page and live paths it protects, deliveries 6 and 7); the page gets nothing; the owner side reads, exports and erases. A legal hold is a fence; only the operator exports (`data-export`, to the region's bucket); erasures and pruning wait. A transfer (same region) fences the object to the new owner, keeps visitor IDs and moves the data; the Privacy Policy and the grant control say so. Purge and account or workspace deletion run the two-step erase; account deletion runs author erasure for the account's journal entries. No point-in-time recovery for owners. Plan grace deletes nothing; the new limits refuse new work only.

## Interfaces, scopes and parity

New scopes `data:read` and `data:write`, a role action `data` (admins and editors, in `TOKEN_ACTIONS`); existing tokens gain nothing until an admin grants the scopes. The operations (describe, collections, documents, queries, counts, bulk writes and deletes, index steps, export, erase an author or all, data writers) have one service each with API, MCP and CLI parity, the terms classification, `confirm` on destructive tools and untrusted-data notes.

## Moderation and law

The owner is the controller of what visitors write, Portifact the processor; the Terms give Portifact the standing instruction to erase on account deletion the documents the account created (with later edits others made to them) and to let a grant holder delete and export their own. Not covered: the content of edits the account made to other people's shared documents (their attribution becomes `erased`), anything exported elsewhere; the rights request page (session only) lists the artifacts the journal names and notifies their admins. Reports name a collection, a document and its revision; `_by` is never alone evidence against a visitor. Legal texts need a new `TERMS_VERSION`: the Terms' "runs no … databases" sentence, a Privacy Policy category (visitor data, IDs, grants, the journal and its 31 days, location, transfer, the shared-edit rule, the minimal evidence kept after erasure), the Data Processing Addendum (the category, Annex III, the instruction) and the Acceptable Use Policy (no credentials or payment data, no file hosting or relays, no cross-site tracking, no command channels).

## Acceptance tests for delivery 3

Every protocol property the four reviews found, to be checked against the production code of delivery 3 by its code reviewer. References are review and finding: R1-11 is the first review's finding 11. Findings about owner SQL, copies, the owner ledger and leases are closed by removal and not listed.

Identity, replay and authorization:

1. A visitor never reads, lists, changes or deletes another visitor's `own` documents by ID, filter, cursor or live fan-out, and sequence numbers reveal nothing about other authors (R1-11, R1-15).
2. An operation ID is scoped to the actor and the generation and bound to a hash of the request; another actor's reuse never returns the first result; a replay answers only after the caller's current authorization; no record holds a body (R2-1, R2-5).
3. A replay never applies, charges or notifies twice; concurrent duplicates of one operation apply once (R2-1, R3-1, R4-9).
4. An operation ID past the horizon or from the future is refused; a pruned ID never applies again, for committed and aborted records, across a reset and a restore (R3-14, R4-9).
5. The unique key holds on create and on replace (R1-13).
6. Every command, maintenance included, is refused for another artifact or region (R1-27, R3-6, R4-8).

Lifecycle:

7. A fence is persisted before it is acknowledged, on an empty object too; it checks the generation; a repeated transition ID must carry the same contents (R2-2, R3-6, R4-2).
8. A request with a newer epoch never consumes the epoch a pending fence needs (R4-2).
9. A hold refuses every payload erasure, quarantine resolution included, until a separately authorized release was acknowledged (R4-1).
10. Erase steps carry an erase ID and its target; prepare, commit and cancel match it; a delayed step of another intent changes nothing; a retry answers the terminal result (R2-3, R3-5, R4-2).
11. A commit deletes the payload and writes the next generation in one transaction, keeps the control state, and a retry of an earlier erase never deletes data created after it (R1-4, R2-3).
12. After a D1 restore, the field authority table holds: a former owner is refused at any epoch, an owner or hold mismatch quarantines, a prepared erase resumes under its ID, and objects without a D1 row are found and quarantined (R1-5, R2-4, R3-5).
13. The first durable write on an empty object binds its identity; an unauthorized caller writes nothing on an empty object (R3-6, R4-8).
14. Nothing is pruned and no pruning alarm is set under a hold or a quarantine; a release re-arms maintenance (R3-6, R4-6).
15. No command awaits anything between its admission and its work, or, if a later implementation adds an await, the work's transaction re-admits and re-authorizes and a fault schedule injects a hold, a transfer and a duplicate at that await (R3-1).

Erasure:

16. Author erasure is terminal: the barrier is written before anything is deleted, on empty objects too; afterwards no path recreates the author's documents, edits, sequences, rate rows, operation rows, counts or connections; completion checks and cleans atomically; only the listed minimal evidence remains (R2-6, R3-8, R4-7).
17. The shared-edit rule: erasing a creator deletes the document with others' later edits; erasing an editor keeps the document and marks the attribution `erased` (R1-18, R3-8).
18. Two racing first grants get one identity; a retired journal entry refuses every claim for its retention; a delayed first grant cannot revive the person (R2-6, R3-8, R4-7).
19. Author erasure chunks are bounded by work, not by deleted rows, and a repeated chunk replays its counts (R2-17, R3-10).

Counting and limits:

20. Every operation's measured work, the counter's own row included, lands in its class's counter in the work's transaction, or for a failure after the work began, in the next one; the sum over random sequences is at least the measured work (R1-10, R2-7, R3-9, R4-3, R4-4). This is about refusals and failures the rules produce; a storage failure is delivery 4's note 11.
21. A spent class refuses before any work and writes nothing; refusals are counted in a bounded counter (R4-4).
22. One operation's overshoot is at most its caps: page, bulk operation, index step, erasure chunk, export page, pruning pass (R1-11, R4-3).
23. An index over existing documents is built in bounded steps, and queries on it are refused until it is built (R4-3).
24. Reads write no row per request; an eviction loses at most the stated flush (R4-4).
25. Cleanup, export and rights never meet the growth counter; a visitor deletes and exports their own documents when the shared counters are spent, without write permission or the current terms (R1-12, R1-22, R2-10, R4-12).
26. Shrinking replacements are under the author's write rate (R3-16).
27. Counts come from maintained counters, retained data after a downgrade included (R4-3).

Live, storage, audit, export:

28. Every message sent is reserved against the artifact's day; renewal requires the same principal, can shorten and carries the current plan's limit; deadlines survive hibernation; every mutation, bulk and author operations included, goes through the sequence and invalidation; connections close at a prepared erase and at every fence; message handling re-admits the control record (R1-8, R1-14, R2-8, R2-16, R3-15, R4-11).
29. The storage sequence advances on every durable write and the payload revision only on document or declaration changes and at a generation boundary; reports are ordered by generation then sequence (R1-17, R2-13, R3-14, R4-10).
30. Every retained control class is pruned through an index that leads with its age, in bounded resumable passes, and the next alarm covers every class (R3-14, R4-10).
31. An audit obligation's key equals its mutation's; delivered and aborted are distinct; obligations survive a whole erase; an erased author's late settlement writes nothing (R1-21, R2-14, R3-11, R4-7).
32. The export is exact, in primary key order, byte-bounded, with a revision that a quiet export does not move; the visitor's own export works through the author index; the JSON Lines file loads into SQLite (R1-20, R3-12, R4-12).
33. Visitor and owner queries read at most the page plus a few rows in every allowed shape, dense, sparse or empty (R1-11).
34. The grant's start and redeem gates and its one-use, browser-bound codes (R1-3, R1-9, R1-16, R2-15); the browser flows themselves are delivery 6.

## Implementation notes

Delivery 3 builds the record's protocols as pure code, and these notes record what the record left open and how the code decided it, including the rework after its adversarial code review. The wire and storage shapes are `@portifact/contracts/artifact-data`; the decisions are `@portifact/domain/artifact-data`; `packages/domain/src/testing/artifact-data-object.ts` is an in-memory documents object that composes them the way delivery 4's object must (read state, call the decisions, write their result in one transaction, an undo log replayed on a throw, every terminal outcome metered by `meter`) and that the tests drive. Every access to durable state goes through one instrumented store: each storage map counts its own reads and writes while object code runs, a seek through an index counts the rows it returns and its probe, and metering's own writes are bookkeeping, recorded as the stated fixed overhead of each counter write (`COUNTER_WRITE_ROWS`, four rows). The outermost scope of every entry point fails when the store saw rows that no metering step took, and the tests assert after every step of the property sequences, and directly, that what the day counters, pending usage and retired rows account for equals exactly what the store saw plus four rows per counter write. The bookkeeping writes themselves are modelled at that fixed cost, not observed: the store does not count them, so the oracle proves that every instrumented work access reaches metering, not that every primitive access is seen (a counter row written twice inside the bookkeeping would pass). This is the in-memory model's evidence; delivery 4 must measure its SQL cursors (obligation 3). Each item of "Acceptance tests for delivery 3" is a test named after its number in `acceptance.test.ts` (A01 is item 1); `properties.test.ts` runs random sequences of commands, fences, erases, holds, transfers, author erasures, plan changes, retries, clock moves, alarms and evictions and checks the record's invariants and the oracle after every step; `model-check.test.ts` runs every delivery order of small sets of lifecycle, replay, erasure and first-binding messages against reference models written apart from the rules; `review-findings.test.ts` carries the four design reviews' reproductions, `review-254.test.ts` the first code review's and `review-254-r2.test.ts` the second's.

1. **Fences are typed by kind**: `hold`, `release`, `epoch` (archive, suspension, access changes) and `transfer`. A repeat of the last transition must carry the same kind, epoch and new owner. **A transfer of a held artifact is refused (`held`)**: only a release ends a hold. An `epoch` fence does not end a prepared erase; every applied fence closes live connections.
2. **Binding is not a fence.** The control record keeps the epoch the first durable write bound the object at (`boundEpoch`) apart from the epoch of the last fence applied (`fencedEpoch`, null before any); `epoch` is the admission floor. A fence needs an epoch past the last fence, or before any fence, at least the bound epoch, so a hold, transfer or erase that D1 ordered before a request read its epoch still applies when the request arrives first (a declaration, a failed first write, a settlement or an erasure chunk alike).
3. **Erase intents.** Erase IDs have the operation ID's form. The issue-time horizon applies only to starting an intent the object does not know: a prepared intent is repeated, committed and cancelled under its ID after any delay, and reconciliation resumes it. Every ended intent is kept under its ID as control data for `replayMs` after it ended (with only the last ended one remembered, a delayed duplicate of an earlier intent could be prepared again). An intent's target (generation and epoch) never changes, and a step whose envelope is older than the target is `stale`; a newer one (after a restore) is accepted. At most `erase.intentsPerDay` (20) distinct optional intents (owner resets) start per artifact and UTC day. A whole erase the lifecycle requires (purge, account deletion, workspace deletion) says so in its trusted envelope (`requiredErase`) and is never rate limited; `admit` refuses that field on a document command, so a caller cannot claim it. An intent the object already knows, prepared or ended, is never a new one.
4. **Reconciliation** also quarantines an object the inventory found without a D1 row (`orphan`) and a D1 generation ahead of the object (`generation`). It raises D1 only when D1 is behind (an older generation, or an older epoch), past the object's epoch; a second run with nothing new answers `none`. A prepared erase is resumed at an epoch no older than the object's, the target's and D1's.
5. **A collection's mode and unique key are fixed once declared**; a declaration can only add indexed fields. A collection holds at most `MAX_INDEXED_FIELDS` (8) indexed fields under any plan, retained ones after a downgrade included, and an artifact at most `MAX_COLLECTIONS` (32); every per-operation row bound (`OPERATION_ROW_BOUNDS`) derives from them and from per-element constants that name the work: `COMMAND_ROWS` (a command's fixed rows), `DOCUMENT_ROWS` (one document's write or delete, with `VALUE_ROWS` per indexed value), `INDEX_STEP_ROWS`, `EDIT_ROWS`, `ERASED_ROW_ROWS` and `RETAINED_CLASSES`, the six classes the alarm's pruning walks. The in-memory object fails any operation that measures more than its bound, a failure after work included (it is checked with its operation's kind); a test runs every kind at its densest legal shape and the property sequences check every operation.
6. **Index values are canonical scalar text** (`scalarText`), computed in the Worker by `indexEntries` for writes and build steps alike; a value over 256 bytes is not indexed. Value counts per collection, field and value are kept with every write, delete and build step (`valueCountDeltas`), so a count by indexed value reads one row. A value-count row is deleted when its count reaches zero (`nextValueCount`), so no indexed value of a removed, replaced or erased document stays anywhere.
7. **Queries are planned, not written as SQL** (`planQuery`, `planMatches` as the reference meaning delivery 4's statements must match). Counts (`planCount`) and describe are the owner side's only. Every bulk command names 1 to 100 distinct documents and authorizes each target with the single command's rule (`authorizeTarget`), the creator's erasure barrier included; one refused target refuses the whole command and nothing changes.
8. **One metering path.** Every terminal outcome the rules produce goes through `meter` (a storage failure on real storage is delivery 4's note 11): work that ran, failed after it began, an export page or protected work is charged in its own transaction; reads, replays, empty answers and refusals at any stage are counted in memory (`counted`) and written with the next counter write or synchronously at a flush bound. Every class counts rows read and written plus the charge's own two and two. A flush is a counter write like any other: its overhead is recorded under `protected` (`flushWrite`).
9. **The protected class** records fences, erase prepare, commit and cancel, settlement, acknowledgement, pruning, quarantine cleanup and live reservations with their measured rows, never refused and drawing on no allowance. A whole erase is measured row by row like any other work. An alarm's pruning is deferred (`PendingReads.deferred`) to the next counter write instead of writing a day row of its own: otherwise an idle object writes a row only to record pruning, must prune that row three days later, and wakes forever. Deferred usage never schedules an alarm, a flush with nothing else pending writes nothing (it stays pending until an eligible counter write, across midnight included) and it is lost on eviction, bounded by the retained rows left to prune.
10. **A replay is a read attempt**: it passes the caller's minute (visitors and readers) and the read class like any read and is counted as reads; it never repeats the original operation's effect or its charge. The erasure job's replays are charged to `protected` (`replayCharge`), with no repeated effect, cleanup charge or notification.
11. **Reads and the day boundary**: an earlier day's pending reads are written into that day before today's are counted (into today when that day's row may already be pruned); the first pending read arms an alarm 30 seconds later, except on a held or quarantined object; the command reaching 10,000 rows or 1,000 refusals flushes synchronously.
12. **Rights are per visitor**: a row per visitor and UTC day, pruned with the day counters; the day row's `rights` is their sum, for accounting only. Author erasure deletes the author's rights rows in bounded steps, counted in `more` and in the completion check (`completes`); the day rows' aggregate stays.
13. **Live credits belong to their UTC day**: on a day change they expire and the connection reserves again against the new day's limit; a renewal with a lower daily limit drops the credits held. A reservation takes `min(100, limit - used)` and a refused one writes nothing. Deadlines are at most 60 seconds ahead.
14. **The payload revision** rises only when a document changes or a declaration creates a collection or adds an indexed field (a declaration is part of what an export contains); index steps, deletes that found nothing and erasure chunks that changed nothing leave it alone. The one exception is a generation boundary: a whole erase's commit and a quarantine's erase start a new generation and raise the revision even when the payload was empty.
15. **Audit obligations** are decided by `auditObligation`: every owner-side mutation, index steps included, and every erasure chunk, counts only.
16. **Alarms are batched** to the hour for retention: 120 writes spread over an hour wake the object once for retention the next day and once more when the day counters expire, two wake-ups in all (`review-254.test.ts`). That fixture has visitor writes and no pending owner audit obligations; it is an example, not a bound on the alarms of every workload.
17. **Settlement writes nothing where no late arrival is possible** (an erased author, an older generation, an ID past the horizon) and refuses IDs from the future.
18. **Storage headroom for protected records.** Ended intents (at most 20 a day, kept a day after they end, about 150 bytes each), author barriers (one per erased visitor, about 100 bytes) and pending audit obligations (one per owner-side mutation until delivered) are control records the data cap does not refuse; `controlReserveBytes` (256 KiB) is their headroom, enough for the ended intents of any day plus about 2,000 barriers. A hold or quarantine stops pruning, so delivery 4's growth checks must leave this reserve for them. The in-memory model's file size counts documents and every control and value-count row at a fixed size; it is not a storage-growth proof (obligation 8).
19. **The export file's footer** is `{ footer: true, revision, consistent, documents }`; document lines splice the stored body text in unchanged; a reader ignores unknown fields and refuses a newer version. `parseExportFile` is a local format helper, not an untrusted importer.
20. **The request hash** is SHA-256 of the forwarded request's JSON (`[kind, ...arguments]`), computed synchronously. The journal's retention outlasting a grant's lifetime is left to the delivery that issues grants (6), which owns that lifetime.

## Implementation notes for delivery 4

The first half of delivery 4 builds the documents object on real storage; the second half adds the R2 journal and inventory, the D1 tables, the purge, account and workspace deletion jobs, the outbox topics, reconciliation against D1 and the restore drill with the real object.

1. **Where it lives.** `apps/data` is the record's `portifact-data` Worker ("One object"): `src/store.ts` is the store (every command, synchronous, over `ctx.storage`), `src/documents.ts` the Durable Object class `ArtifactDocuments` that adapts the platform (the alarm, hibernatable WebSockets, the wake), `src/schema.ts` its tables. The class has no fetch handler and no RPC method, the Worker answers `404`, and no workflow deploys it: a deployed class can only be removed by deleting every object of it, so it is deployed with its first caller in the second half ([releasing.md](../releasing.md), "Artifact data Worker"). Its `wrangler.jsonc` already has the class and the `v1` `new_sqlite_classes` migration, so the tests run it as configured; `scripts/durable-migrations.test.ts` refuses `deleted_classes`, `renamed_classes`, `transferred_classes` and non-SQLite classes in every configuration. The jurisdiction is chosen per stub from the artifact's region (`dataNamespaces`), a seam of the second half.
2. **The thin shell.** Each command is the reference's: the same decisions in the same order, with maps replaced by statements. Every statement goes through one `#exec` that consumes the cursor and then adds its final `rowsRead` and `rowsWritten` to the command's cost and to an oracle no charge reads; the outermost scope of each entry point fails when a statement's rows reached no metering step. After a storage fault that equality is kept by counting the uncharged remainder as lost (note 11), so on a faulted entry point the oracle shows that the counters, the pending usage and the lost rows add up, not that the work was debited. Metering's own statements (the day row, a visitor's rights row, the control record when only counters moved) are measured apart and must stay within `COUNTER_WRITE_ROWS` per counter write (tested). File usage is `sql.databaseSize`.
3. **Transactions.** Admission, authorization, the work, the audit obligation, the control record and the charge run in one `transactionSync`; a throw rolls storage back and a mutation's failed work is charged in a second one with its rate attempt (reads, exports and control commands have no second transaction; note 11 says what a storage failure costs). What the object caches from storage (the control record, whether the schema exists) is dropped on every rollback, and what it keeps in memory about storage (pending usage and the oracle's meters) goes back to what it was before that transaction, so memory follows storage; attempts and sockets are not storage and are not rolled back. The size check belongs to the growth class: every command charged to growth (a create, a bulk create, a declaration, an index step, a replacement that grows its documents, a live connect) is judged against the file measured after every write of its transaction, the charge's included, and a refusal rolls it back whole and charges its work to growth like any failed work. Work charged to cleanup, rights or protected (a replacement whose documents do not grow in total, a removal, an erasure) is never judged, so it always finishes at the cap. That work can still grow the file: its own operation and audit records, and index entries when a replacement of the same size changes indexed values. It is bounded by its per-operation caps and its class's daily allowance, not by the file cap, so the cap is the limit of growth-class work and not a ceiling on the file; `MAX_ARTIFACT_BYTES` leaves a gigabyte under the platform's limit for it. At the cap a connect that needs a new page is refused like any growth, until rows are pruned or data is removed.
4. **Schema and the cold start.** The first binding write creates the schema in its own transaction; a read on an object no write bound creates nothing. A wake reads one row, the schema version in `pf_meta` (`SCHEMA_PROBE`), instead of scanning `sqlite_schema` (24 rows in delivery 2), and that row is deferred protected housekeeping. A newer stored version fails closed; an older one runs `MIGRATIONS` (none yet).
5. **One scheduler.** At the end of every entry point the object computes the next alarm with the domain's `nextAlarm` (retention from one seek through each class's age index, only when pruning is allowed; the pending flush; connection deadlines) and sets it only when it moved; a set that fails leaves it unknown, so the next entry point sets it again. The alarm handler re-admits through the control record in its own transaction, so a hold that landed after the alarm was set prunes nothing.
6. **Live connections.** Sockets are hibernatable; each attachment is serialized on every change and refused past 16,384 bytes (the largest legal one, 20 subscriptions of 32-character names and a 200-byte principal, is about 1 KiB). A wake rebuilds connections from the runtime's open sockets and their attachments. A close lost before a wake is caught by the control record's new `liveEpoch` (a domain change, below): a connection carries the value it opened under, and `liveCheck` closes it at its next message after any closing transition, a transfer, an epoch fence or an adopted quarantine included, which leave no other trace. Until the second half adds the upgrade route, the client end of a connection is held in the object.
7. **Payload-only erase.** A whole erase deletes `PAYLOAD_TABLES` (documents, collections, fields, indexed values, value counts, author counts, sequences, operation records) in the transaction that writes the next generation; `pf_meta`, barriers, day counters, rights, rate rows, audit obligations, ended intents and the alarm stay. `deleteAll()` is never called. `DELETE FROM` a whole table measures each row as written, so the erase is charged by its rows.
8. **Domain changes made here, each with tests.** `DataControl.liveEpoch` (raised by `applyFence`, `quarantine`, `resolveQuarantine`, `prepareErase` and `commitErase`) and `LiveAttachment.liveEpoch`, checked by `liveCheck`; `DELETED_ROW_ROWS` = 3 (a row deleted by age or author costs its seek, its lookup and its delete on real SQLite) for the pruning bound and `ERASED_ROW_ROWS`, where the bound had 2; `MAX_DOCUMENT_BYTES` (1 MiB, under the platform's row limit) and `MAX_ARTIFACT_BYTES` (9 GB, so the file stays under 10 GB with the control reserve) as caps of `ArtifactDataLimits`, which the object checks on every command, refusing impossible plans with `invalid_input`. The reference object now takes an erasure chunk's rows in key order, as the real index seeks do, so the two take the same subset when more remain. The shared suites assert a few facts only of the reference (its per-access counts, its file-size model); A25 and A33 now state their property without the reference's per-row figures (a seek through the values index reads each match's document too, two rows per match); A15's check that a command's answer is not a promise runs before any await on the reference, and for the real object inside the object, for every command (`storage.test.ts`), because its driver is an asynchronous transport.
9. **Measured on real SQLite** (local workerd, `test/storage.test.ts` and the suites, 2026-11-12). Rows read and written per operation at the largest legal shapes, against `OPERATION_ROW_BOUNDS`: create with 8 indexed fields 60 (bound 156), replace 98 (212), remove 66 (156), get 3 (100), count by value 11 (100), bulk create 100 3,326 (5,700), bulk replace 100 7,226 (11,300), bulk remove 100 4,917 (5,700), describe at 32 collections of 8 fields 290 (420), declare with a 500-document index step 2,517 (3,116), index step of 500 2,512 (3,100), export page of 500 503 (601), author erasure chunk of 500 documents 8,011 (35,600), pruning pass over six full classes 9,001 (9,106). Queries of 100 at 500 and 4,000 documents measure the same: by creation 104, by author 3 to 4, by indexed value 205 dense, 7 sparse, 3 empty. A visitor create is 12 read and 14 written warm (the spike's table: 11 and 13). A wake reads 1 row. 120 writes spread over an hour wake the object twice in the following days (delivery 2: 241 in one hour). Every statement's plan is a search through an index except seven, each bounded by `MAX_COLLECTIONS` and `MAX_INDEXED_FIELDS` or a whole erase; no statement binds more than 11 parameters. `DELETE ... WHERE key IN (SELECT ... LIMIT n)` measured six rows a row and `ORDER BY` without an index two reads a row, so the object selects then deletes by key and orders by declaration position in memory. Not measured here: CPU time (workerd stops the clock during synchronous work), and billed rows and active time deployed, which the second half's scratch run repeats.
10. **Comparing the two objects.** `apps/data/test/pair.ts` sends every command to the reference and the real object with the same IDs and fails at the first step whose answer or state differs. It found four real divergences, each fixed or explained: closed sockets revived by a rebuild (the object now wakes only open sockets), an erasure chunk's subset (now key order in both), and the storage sequence and day rows, which follow flush timing and therefore the measured rows (by design; the property tests check their rules on each object, and a test of the real object alone asserts that a flush only a read triggered moves the sequence). `describe` answers today's measured usage, so the pair compares its day and not its counts.
11. **Storage faults.** When a statement throws, nothing is held for later. The entry point ends, the transaction it was in rolls back and memory about storage follows it; transactions the entry point had already committed stay committed and charged. A mutation's failed work is charged by its second transaction when that commits. What is left uncharged (that second transaction failing too, or a read, an export, a control command, a connect or an alarm ended by the fault) is lost: no counter holds those rows and no allowance is debited for them, the visitor's rights included. The oracle counts them (`Instrument.lost`), so the tests still add up; they show the counters agree with what was measured, not that faulted work was paid for. The loss is the measured and uncharged remainder of one entry point per failure (at most its operation's bound; a whole erase's is its size), besides what an eviction already loses from memory. No liability accumulates and no command is refused because an earlier one failed, protected work included; the total lost over many failures is not bounded by a daily figure. A fault while the scheduler computes the next alarm, after the command committed, does not fail the command. Two limits of this evidence: only rows a cursor finished reporting are measured, so whatever a failing statement itself did before throwing is unknown to the object; and the tests inject the failure before a statement runs. No input a caller controls was found to make a statement throw: conflicts, sizes, cursors and query values are refused by the rules and metered, statements are fixed text with bound values, and bulk work loops inside one transaction. The policy does not rest on the platform restarting the object: a durable write that fails behind the output gate does restart it, a statement that throws (a full database, for one) need not. An earlier version held failed work in memory to charge it later; the review showed that it needs a day, a class and an author per held row and a bound that protected work cannot keep.

### The second half

12. **The interface other Workers call.** `ArtifactDocuments` has seven RPC methods, all lifecycle: `lifecycleControl` (the control record, a read that writes nothing), `lifecycleFence`, `lifecycleErase` (`prepare`, `commit` or `cancel` with a `RequiredErase` reason), `lifecycleEraseAuthor` (one chunk of 500 under the operation ID it is given), `lifecycleQuarantine`, `lifecycleResolve` (a reviewed resolution, note 16) and `lifecycleExport` (the operator's page); a test asserts the class's prototype holds only these and the platform's handlers. Each parses every argument at the boundary with the contracts' schemas (`LifecycleEnvelope`, which refuses an envelope carrying `opId` or `requiredErase`, `DataTime`, `EraseStepName`, `QuarantineResolutionRequest`) and answers an invalid one `invalid_input` as a value without any storage access, not even a read of the control record (its report is the empty one, never newer than another; a cold-store fault probe tests it), never as an exception across RPC. Valid commands read the control record to be admitted. Fences and quarantine use their own domain decisions (`applyFence`, `quarantine`), erase steps, author erasure, resolution and export go through their admission rules. Only `lifecycleErase` sets `requiredErase`, so a required erase can only come from it; document commands get their own methods with deliveries 5 and 6. The binding is the credential: only the jobs Worker binds the class (`ARTIFACT_DOCUMENTS`, `script_name: "portifact-data"`), and `dataNamespaces` in `packages/services/src/artifact-data.ts` is the only place a stub is made (`jurisdiction("eu")` for the EU, `locationHint: "wnam"` for the default region, chosen when a job reaches an object, since workerd implements no jurisdictions). The switch is a guard of the callers, not of every RPC: a valid fence, required erase or author erasure on an empty object binds it, and the jobs skip those while `ARTIFACT_DATA_ENABLED` is off. The platform's handlers (`alarm`, `webSocketMessage`, `webSocketClose`) are prototype methods too; a bound Worker calling the alarm runs work that is idempotent and re-admitted.
13. **D1.** `artifact_data` (regional, one row per artifact whose object may hold something, cascading from `artifacts`): the generation and epoch every envelope carries, and the newest storage report (`recordStorageReport`, `newerReport`'s order in SQL). The owner is `artifacts.owner_id` and a hold is an open `legal_holds` row, never duplicated here. `data_findings` (regional, no foreign key) is what reconciliation and the operator's resolutions did per artifact, with the quarantined state the operator resolves against (`state`, migration 0080); a finding is a diagnostic, rewound by a restore, never the proof that a step ran. The grant tables (`data_grants`, `data_grant_codes`) and the `data_grant` window tombstone belong to delivery 6, which issues grants; nothing writes them before.
14. **The R2 inventory and journal.** `registerDataObject` writes `system/data-objects/<artifact>` with a conditional put (create only, so a repeat keeps the first entry), then D1's row; the owner API's first write calls it (delivery 5). A missing entry for an object would hide it from reconciliation, so the entry is always first; an extra entry (no object, or no control record) reconciles to nothing. A purge's erase retires the entry only once the object confirmed that this erase committed (note 15); retirement is a write conditional on the entry it read, retried on a race, so the first retirement is the one kept; the reconciliation walk deletes a retired entry 31 days later (`ARTIFACT_DATA.inventoryRetiredMs`, longer than D1 Time Travel's window), and a retired entry whose artifact has no D1 row reconciles to nothing. The journal's retirement is a put conditional on the entry it read (`etagMatches`, or `etagDoesNotMatch: "*"` for an absent one, written retired without an ID), retried on a race, with `customMetadata.retired` so a walk skips retired entries from the listing; retired entries are deleted 31 days after retirement (`journalPrunable`) by the reconciliation walk, which runs only when the operator starts it (no periodic cleanup is wired yet).
15. **The jobs.** The lifecycle's jobs are written in the batch of the change they follow, on the same condition, in the artifact's region, and only for an artifact with an `artifact_data` row (an insert from a select): a hold (`placeLegalHold`) and a release (`release`, every path to it, on the hold still being open) raise the epoch and write `data_fence` with the hold's ID (`<hold>:release` for the release) as the transition; a transfer raises the epoch and writes `data_fence` with a random `transfer_<hex>` transition, under the owner the object knows, on the transfer's own `unchanged` condition; the purge (`deleteArtifactData`, the path of a deletion, an archive's end and an account's or workspace's deletion) writes `data_erase` from the row it deletes, only for an artifact still `purging`. The account journal step and the operator's jobs are written on their own (below). `data_fence` sends D1's current generation with the job's epoch; `fenceRefused` decides a refusal from the object's answer and one piece of evidence, whether D1 still has the data row: done when the object is past the fence, or when it names a generation the object has left and D1 has no row (a purge's erase overtook it: it can never apply), retry while an earlier change must land, and `reissue` when the object is already at or past the fence's epoch while D1 still wants the change (`fenceStillWanted`: the hold D1 has open and the object lacks, the release of the hold the object still has with none open in D1, a transfer D1 made and the object has not) and still has the data row: the job takes a new epoch from D1 in a guarded update (`max(D1, object) + 1`, conditioned on the epoch it read), rewrites its payload and applies it, so a hold released in D1 is always released in the object (a restore that rewound D1's epoch under the object's is the case). D1's epoch never goes backward: every write of it is a raise or `max(D1, object)`, conditioned on the row read. `data_erase` keeps its erase ID in its own row before the first prepare (a prepared erase is resumed under its own ID), so a retry after a crash past the commit recognizes its erase committed; it targets `purgeEraseTarget`: the job's generation, or the object's own once D1 proves the artifact's permanent deletion (`permanentlyDeleted`: its tombstone and no row left but a purging one), the epoch `purgeEraseEpoch`'s, the reason from the owner's deletion row or tombstone (`eraseReason`). Only this erase's commit retires the inventory entry (`purgeAnswered`); `superseded` (an old intent without that proof) keeps the entry and the job, a day at a time, with a `superseded` finding for the operator. A cancelled intent (a hold or a release cancelled it) is terminal for its ID: once the object confirms the cancellation and no other intent is prepared, a purge still authorized stores a new ID in its outbox row and prepares it after `DATA_ERASE_FRESH_MS` (one minute); an ID the horizon refuses is replaced the same way and retried by the queue. `advanceAccountDeletion` calls `scheduleAuthorErasures` in each region: one listing per run of the account's journal, resumed from a `maintenance_cursors` row (`data_journal:<user>`) across capped runs, written only while the account's deletion is pending (the condition is in the cursor's own statement, so a late scan cannot recreate it after the deletion ended), deleted by the batch that ends the deletion, and a leftover (a restore that rewound the deletion's end) removed by the maintenance scan `pruneJournalCursors`; per entry not yet retired, the `data_author_erasure` job (unless one is waiting), then the retirement; the scan completes (`nextJournalScan`) only after a whole pass that found nothing left to retire, a pass that retired something being followed by another from the start, so an entry written behind a pass's cursor is found by the next (delivery 6's issuance must still check the account after its claim). The author erasure job retires again first, then reads the object whatever D1 holds: only an absent object ends it without a chunk; an object D1 has no row for is erased under its own identity (erasure only removes the person's data), and a held or quarantined one keeps the job waiting a day at a time until its release or resolution wakes it (`wakeDataJobs`, from `runHoldRelease` and `runDataResolve`); chunks go until the object answers `more: false` (eight per run, then it gives the queue back). Every job throws without the binding, so its row stays. With artifact data off (`createsObjects`), a job that finds no control record ends without binding the object.
16. **Reconciliation.** The operator writes a `data_reconcile` job per region (`data-reconcile`); it walks the inventory a page of 50 at a time (resuming after the last key it reached), then the journal. Per object, `reconcileObject` first checks the authority table's artifact and region row (`identityDisagreement`): the inventory key against its entry, the entry's region and the directory's against the job's, the control record's identity against them; a disagreement is an `identity_mismatch` finding and nothing is followed. Then it applies `reconcile` with D1's row (owner from the artifact, hold from an open `legal_holds` row): a quarantine and a raise record their finding before acting, so a run that stops after acting leaves the operator's line, and a quarantine's finding then records the reviewed state (`reviewedState`, printed by `formatReviewed`); D1's raise is conditioned on the numbers it read; a resumed erase commits under its ID, records its finding, then raises D1 from the control record read again (`followObject`). The journal phase writes the author erasures a rewound outbox lost from the retired entries. A resolution is an operation with an identity (`resolveReviewed`, beside `resolveQuarantine` in the domain, with the mechanism of erase intents): `data-resolve <artifact> adopt|erase --state <state>` writes a `data_resolve` job with a new resolution ID and the state the operator reviewed, which names one quarantine of one object: the artifact and region, the quarantine's incarnation (a counter the control record keeps and every quarantine raises, never a time), its reason, and the owner, generation and epoch. A time the caller supplies is never an authorization condition. The service refuses a state whose artifact or region is not the job's before any read of the object, then runs `identityDisagreement` before any row write, object command or inventory retirement (an unresolved mismatch keeps its finding and refuses the resolution); the object compares the whole state atomically, refuses a different one, records its outcome under the ID in the ended-intent table, and answers a retry with the same outcome, so another artifact's state, a stale state, a second quarantine with the same reason and time or a delayed row conflicts and never resolves a later quarantine. The object resolves first and D1 follows it (the generation is the object's, the epoch `max(D1, object)`, conditioned on the row read). Resolution receipts are kept for the replay window (`replayMs`, 24 hours), like ended erase intents; a retry after that finds no receipt and is checked against the object's state as a new resolution: the quarantine it reviewed is gone, so it is refused as a conflict and changes nothing, and if the first attempt stopped before D1 followed, reconciliation raises D1 to the object. A hold disagreement never lets the less restrictive side win: `erase` is refused while D1 or the object holds, and `adopt` makes the object keep its own hold or take D1's in the transaction that clears the quarantine; erasing held data needs the hold's own release, acknowledged by the object. `adopt` also needs D1 to name the owner the object recorded, and D1's numbers follow the object before and after; the artifact's waiting data jobs are woken. `data_export` (`data-export`) writes the operator's export page by page to `system/data-exports/` in the region's bucket. Tombstones: no new kind of permanent deletion needs one. A purge's erase is covered by the artifact's tombstone (a restore that brings the artifact back has it purged again, and that purge erases whatever generation the object is at), an author erasure by the retired journal entry, and the object and R2 are never rewound.
17. **Deployment.** The data Worker is deployed with its first caller: the release workflow deploys `portifact-data` before the content, jobs and app Workers, CI validates its bundle, `PORTIFACT_RESOURCES.scripts` names it, and `limits.cpu_ms` is 200 with invocation logs off. Nothing sets `ARTIFACT_DATA_ENABLED` (a scripts test refuses any data switch in a configuration), so the release creates the namespace and no object. The first deployment has no earlier data Worker version and a class lifecycle change cannot be rolled back across ([releasing.md](../releasing.md), "Artifact data Worker").
18. **Measured.** The crash schedules are 58 injected crash cases (each pinned step crashed before and after) plus nine clean step checks and one retirement check; they retry cleanly and do not interleave a second lifecycle operation, which the review's reproductions (`review-261.test.ts`) and guard tests (`review-261-guards.test.ts`) cover for the compositions found. The two key prefix mutants are killed (the review's fresh Stryker run scored 100% on them). The lifecycle tests control the object's scheduler: `test/lifecycle.ts` replaces the object's `setAlarm` and `deleteAlarm` with a recorder before any lifecycle command reaches it, so no real alarm is ever set, and each test checks afterwards that none is. The quarantine model check (`quarantine-model-check.test.ts`) runs every delivery order of a hold's fence, its release, an adopt and an erase of the reviewed state, a second quarantine and either the release's fence apart or a purge (720 orders in two families of 360, 180 tests of four orders) against the real object and services, and after each order checks that held data is never erased, a resolution applies only to the quarantine it reviewed, D1's epoch never decreases, a hold released in D1 ends released in the object, and no job waits forever once the operator answers what is left; it fails when D1's epoch follows the object without `max`. Not measured: anything deployed (this delivery ran no deployment).

## Delivery 4's obligations

The in-memory object proves the protocols' decisions, not a Durable Object. Delivery 4 must not copy it literally; it must establish each of these against the real runtime, and its acceptance repeats delivery 3's tests through the real object:

1. **Real transactions and fault boundaries**: `transactionSync` for admission, authorization, reads and writes (its callback never returns a promise); the second transaction that charges failed work; faults injected at the real storage failure points. A snapshot restores storage only, not memory, meters or sockets.
2. **Input and output gates**: no external I/O between admission and the work (load grants and policies before the transaction, or re-admit after a wait); no acknowledgement before the write is durable; messages reserved durably before they are sent; failure tested between mutation, charge, notification and answer.
3. **Measured SQL cursors**: charges from the cursors' final `rowsRead` and `rowsWritten`, file usage from `sql.databaseSize`; real statements and indexes with their query plans asserted, and dense, sparse and empty costs measured within `OPERATION_ROW_BOUNDS`.
4. **One alarm scheduler** combining retention, pending flushes and connection deadlines, re-checked after every control change, tested with late, duplicated and failed alarms, a hold between scheduling and running, and a failure to re-arm after a committed write; a running handler still re-admits.
5. **Hibernation and socket invalidation**: every changed attachment serialized (at most 16,384 bytes), constructors rebuilding state, and an invalidation token persisted with fences so a socket recovered after a lost close cannot outlive a transfer or an epoch fence.
6. **Payload-only erase**: never `deleteAll()` (it clears control records and the alarm); a whole erase deletes payload tables only, atomically with the next generation, tested at the largest supported artifact.
7. **Platform limits**: 10 GB an object, 8 MB a row, 100 bound parameters and 100 KB a statement, the CPU limit; bulk operations bind their IDs within the parameter limit in one transaction; impossible plans refused independently of commercial tiers.
8. **Real file-size checks**: growth checked against the measured file size after the whole transaction, every index and control record included, with the protected headroom of note 18 kept.
9. **D1, R2 and object crash schedules**: conditional R2 claims and retirements, D1 inventory and tombstones, job retries and relay acknowledgements are separate systems; crash schedules across them, account checks at issuance, resuming prepared erases past the horizon, and no D1 repair published before the fence it needs is durable. Storage reports include every write a command caused, notifications' reservations included.
10. **Rights-row cleanup on real storage**: author erasure deletes the author's rights rows in bounded steps, counted in `more` and the completion check, asserted against the real tables.
11. **Value-count cleanup on real storage**: a value-count row is deleted when its count reaches zero on every path (single and bulk removal, replacement, index build, author erasure), asserted against the real tables, with the rows counted in the file size.
12. **Protected admission of required erases**: `requiredErase` is set only by the Worker paths of purge, account deletion and workspace deletion, never forwarded from a request, and those erases pass the daily gate on real storage while an optional reset at the gate is refused.

Delivery 2's three experiments are throwaway code, never imported by apps or packages and never deployed with the product: the grant handoff in `spikes/artifact-data-grant` (Playwright), the restore drill and the billing measurements in `spikes/artifact-data` (`src/drill.ts`, `test/restore-drill.test.ts`, `test/billing.test.ts`) and, for the halves only a deployment can show, the runbook `spikes/artifact-data/drill/runbook.ts` with its scratch Worker `drill/worker.ts`. Local runs: Chromium 156 and Firefox 157 with Playwright 1.64.1 on Linux, workerd through `@cloudflare/vitest-plugin`, 2026-11-12.

**One assumption is disproved, with a counterexample: alarms.** The cost formulas count alarms only for artifacts with live connections, at most one a minute (`A = N × 1,440 × 31`), and "Typical use" counts only an hour of deadline alarms. In the spike an object with no connection wakes once for every expiring operation record and once for every expiring rate row: 120 visitor writes spread over one hour made the object wake 241 times in one hour the next day (`billing.test.ts`, "an object with a steady write history"), because the next alarm is set at the oldest retained row's expiry (at most one a second). So pruning alarms are about two per mutation a day after it, in addition to the connections' alarms: on option B Free's limits (about 330 writes and 330 deletes a day) up to about 1,300 alarm requests a day per data artifact with no visitor connected, each about 108 ms on a cold object (deployed), and in "Typical use" about 100 more Durable Object requests per active artifact a day (382 assumed, so about a quarter more requests and duration from alarms). This does not change the architecture; it changes the alarm line of the arithmetic and points at a lever for delivery 3: retention is "at least", so pruning can be batched (for example at most one pruning alarm an hour, or pruning at the next write), which bounds alarms per artifact independently of writes. Not redesigned here.

Two smaller findings: re-running `reconcile` raises D1's epoch again every time (it answers `raise` with the larger epoch plus one whenever the numbers differ, and after a raise they always differ), harmless for access since a newer epoch is admitted and never adopted, but not the fixpoint "raised to them" describes, so delivery 3 should raise only when D1 is behind; and the consent control's page must not send `Referrer-Policy: no-referrer`, or its form's `POST` carries `Origin: null` and the exact-origin check refuses Allow (found by experiment 1, fixed in the stand-in).

## Alternatives rejected

### Owner SQL

The issue gave the owner side SQL, read and write, from the first release, and three versions of this record designed it: first one database with a SQL allowlist, then a second object per artifact as a sandbox with copies, a shape-bounded write ceiling, a CPU-bounded read ceiling, debt in a per-owner ledger and a lossless SQL export. After three reviews the write ceiling was still not a bound, overdrafts and debt could be taken twice or moved to the next owner, accepted owner DDL could block erasure, copies had no consistent paging and two objects could not be reconciled after a restore. The maintainer removed owner SQL (decision 38); what an owner's agent wanted from it is analysis, which "Later" answers. The removed design and its spike code are in commit `c5b84930`. Owner SQL can be reopened later with its own record, which must answer those findings first.

### An owner ledger with leases

Versions three and four kept each owner's daily allowances in a per-owner object and leased chunks of them to artifacts, so one owner's spending was bounded across artifacts. The fourth review showed the leases surviving plan changes, refunds from an old day funding a new one, lost lease acknowledgements spending twice, read bookkeeping and refusals escaping the pools, and every lease await opening a window for a hold, a transfer or a duplicate. The maintainer removed the ledger (decision 45): limits are per artifact and an owner's exposure is the plan's data artifact count times them. The ledger's code is in commit `65b85f06`.

| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Charging an upper bound before the work                  | The bound has to be proved for every statement, index and retained population; measured work in the same transaction needs no proof. |
| Building an index in one statement                       | Its work grows with the documents; steps of 500 do not.                                                                              |
| Identity from review or read sessions                    | They can be planted; no consent.                                                                                                     |
| Inferring an aborted operation from a missing obligation | A call still in flight would commit after; `settle` aborts explicitly.                                                               |
| Deleting the journal entry when erasure completes        | A delayed first grant would get a fresh identity; the entry is retired and kept 31 days.                                             |

## Later

What an owner's agent wanted from SQL is analysis: joins, sums, groups over the artifact's data. It can have that without server-side SQL by exporting the documents and querying them in a local SQLite database on the owner's machine, where the cost and the risk are the owner's. The export format in "Export" is designed for it: stable, typed and complete. A CLI command that does the load (for example `portifact data sqlite <artifact> --out data.db`) is a possible later change, not part of this design.

## Open questions for the maintainer

### The plan limits (open)

The options are the per-artifact table in "Cost". **Recommendation: B for the first release**, the smallest exposure that keeps live updates in every plan: Free 1 data artifact of 5 MB with 5,000 rows written, 500,000 read and 2,000 live messages a day; Pro 10 of 25 MB with 2,000, 500,000 and 5,000; Team 50 of 50 MB with 2,000, 1,000,000 and 10,000. B Pro's arithmetic is US$3.00 a month at 5 ms if all ten artifacts are saturated every day, above its US$2 price, and Team passes from 4 seats. Delivery 8 measures active wall time and real use on staging and fixes the numbers; if the measured month is over the price, Pro's growth and cleanup come down first, and budget protection's data step stops spending meanwhile. Every option keeps, per artifact, documents of at most 16 KiB, 1,000 documents a collection, 10 collections and 3 indexed fields on Free (more on paid plans), 30 writes and 60 deletes per author a minute, 300 reads per caller a minute, and the rights class at 500 rows a day.

### Engineering choices the record follows

1. **Per-caller read rates in memory**: they shape traffic; the spend is counted.
2. **The top-level tab** as the grant fallback, as review does today.
3. **`cpu_ms: 200`** for `portifact-data`: delivery 2 measured 1 to 4 ms of CPU per command and per pruning alarm on the scratch deployment, so 200 ms leaves ample room; it stops runaway work and does not bound billed wall time (writes spent about 45 ms active for 3 ms of CPU).
4. **Write cost levers** (fewer bookkeeping rows per write) are left for after measurement; they are the main lever on the 100,000-artifact cost.
