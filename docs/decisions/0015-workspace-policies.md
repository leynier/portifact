# 0015 Workspace policies

- Status: accepted
- Date: 2026-11-10
- Feature: premium plan E4 (`policies` in `PLANS`, Enterprise)

## Question

An organization wants rules that hold for every artifact of its workspace whoever acts on it: no artifact may be public, new artifacts start shared with the workspace, readers only at the company's own email domains, share links only with a password or not at all. Where do the rules live across the global and regional databases, how are they applied without a new read on every write (and none on delivery), what happens to existing artifacts that break a new rule, who sets them, what does a lapsed plan do, and what keeps a restore from lifting one?

## Decision in short

- A workspace's policies are one validated JSON value on its global row (`workspaces.policy`, null for the defaults) with a revision (`workspaces.policy_revision`). The shape is `WorkspacePolicy` in contracts, the rules are `packages/domain/src/workspace-policies.ts`, the use cases `packages/services/src/workspace-policies.ts`. A personal space has none.
- The policy is read in the same query as the membership (`actorOn`, `tokenActorOn`), so `Actor.policy` carries it and no write path gains a round trip. Measured with the recording proxy against develop: `preparePublish` 11, `updateAccess` 11, `createShareLink` 4 and `openShareLink` 3 D1 calls, before and after, with the defaults and with a restrictive policy (`packages/services/test/workspace-policies.test.ts`).
- The policies bind everyone acting on the workspace's artifacts: admins (the dashboard says so), editors and service tokens. A refusal is the new error code `policy_refused` (403, CLI exit 7) whose message names the policy, the same through the API, MCP, the CLI and the dashboard.
- Only admins set them (role action `policies`, never a token's), only through the dashboard session (`GET`/`PUT /api/v1/workspaces/:slug/policies`, `POST .../policies/preview`; a bearer token gets 403). Every member reads them there, and every client reads the policy in effect in the workspace list (`GET /api/v1/workspaces` with `artifacts:read`, MCP `list_workspaces`, `portifact workspaces`), so agents and the CLI can explain a refusal before trying.
- Setting or tightening any field needs `policies` in the workspace's plan; loosening (or changing nothing) never does. When the plan lapses the policies keep applying, because lifting a restriction silently would widen access; an admin can still loosen or remove them.
- A save that would change existing artifacts is refused with the counts (`policy_refused`), unless it carries the impact the admin confirmed after the preview (`confirmed`). The confirmation holds only for what the admin saw: a save whose counts grew since is refused again, with a message to review it. A confirmed save writes a `workspace_policy` outbox job in its global batch, which applies the policy in bounded steps.

## The policies

| Field              | Values                                                                                                          | Applied in                                                                                                                                                                                                                                                                    | Existing artifacts                                                                                                                                                                 |
| ------------------ | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `publicAccess`     | `allowed` (default), `forbidden`                                                                                | `updateAccess` (before the account-age rule), `transferArtifact`                                                                                                                                                                                                              | Public artifacts become `workspace` (generation moves, sessions end), after confirmation                                                                                           |
| `defaultAccess`    | `restricted` (default), `workspace`, `domain` (needs a verified domain when set); never `public`                | `preparePublish`'s workspace path (`newArtifactDefaults`), never wider than the workspace can give now: `domain` without a verified domain (one lapsed or was removed) starts as `workspace`, and without `workspaces` in the plan both workspace modes start as `restricted` | Never changed                                                                                                                                                                      |
| `readerDomains`    | null (default) or 1 to 20 plain ASCII domains, matched exactly against an address's domain like `emailDomainOf` | `updateAccess` when readers are added, `transferArtifact`                                                                                                                                                                                                                     | Readers outside are removed (generation moves), after confirmation. Members and groups are not readers and are not affected                                                        |
| `shareLinks`       | `allowed` (default), `password_required`, `disabled`                                                            | `createShareLink`, `openShareLink`, `transferArtifact` (`disabled` only)                                                                                                                                                                                                      | `disabled`: active links are revoked by the job. `password_required`: links without a password stop opening at once (checked at open time) and their sessions are ended by the job |
| `shareLinkMaxDays` | null (default) or 1 to 365                                                                                      | `createShareLink` (an expiry is required and must be within it), `openShareLink`                                                                                                                                                                                              | Links older than the lifetime stop opening at open time; their sessions are ended by the job                                                                                       |

Open-time enforcement for links costs no round trip: `openShareLink` already read the owner's plan from the global database, and now reads the plan and the workspace's policy in one `batch` (`ownerEntitlementsAndPolicy`). Redeeming the one-use code on the artifact origin (`redeemShareHandoff`) and renewing a link session's claims every 60 seconds (`refreshShareSession`) apply the same rule in the statement they already run (`liveLink`, the SQL twin of `policyLinkOpens` reading the workspace's row in the same query; with one region the workspace and the link share a database, as the delivery lookup's plan join does) and answer exactly like a link that does not open. So a code issued before a save and redeemed after it is refused, and an open link session ends at its next renewal, within 60 seconds, whether or not the job ran. The content Worker's request path is otherwise unchanged.

The domain default needs a verified domain when it is saved, but a domain can lapse or be removed later. The verified-domain state is read with the policy in the membership's own query, only when the default is `domain`, and a new artifact then starts as `workspace`: never a mode `updateAccess` would refuse to set, never wider. The Policies page says so.

Transfers into a workspace are refused, never narrowed, when the artifact is public where public access is forbidden, lists a reader outside the allowlist, or has active share links where links are disabled: the admin narrows the artifact first. The batch of the move is conditioned on the same facts (`access_mode <> 'public'`, no reader outside, no live link), so a concurrent change makes the move a no-op (`version_conflict`). A link a stricter link rule refuses simply stops opening in the target.

## Races

Workspaces are global rows and artifacts regional ([decision 0005](0005-regions.md)): no batch spans both, so a regional write cannot be conditioned on the policy. Instead the tightened policy wins after the fact:

- Every save of a policy that restricts existing artifacts writes the `workspace_policy` job in its batch, even when nothing was counted, so a request that read the old policy and writes just after the save is narrowed when the job runs.
- A request that writes after the job ran is caught by the maintenance scan `enforceWorkspacePolicies`, which is cheap and complete. Each 15-minute run, per region: one global query reads the workspaces with a policy (up to 500, `WORKSPACE_POLICIES.scanWorkspaces`, from a cursor when there are more); one regional query, with their restricting flags as a single JSON parameter (4 bound parameters whatever their number), returns the workspaces whose artifacts break their policy, public artifacts where public access is forbidden first, at most 20 (`scanSteps`); and one bounded step runs for each. A clean state costs a constant four queries (the cursor, the two queries, the cursor's write). A violation among the first 500 workspaces with a policy is found and corrected within one run: the bound for a race is one scan cycle, 15 minutes. With more than 500 workspaces with a policy, the cursor moves through them 500 a run; with more than 20 workspaces in violation at once, the rest are found on the next runs, worst first. A workspace whose step fails is logged (`workspace_policy_enforce_failed`, the error's name only) and counted in the maintenance result (`workspacePolicies.failed`), and never stops the others or the maintenance steps after the scan.
- Share links need neither: a link created against the old policy is refused when it is opened, redeemed or renewed.
- The policy write itself is conditioned on the caller still being an admin (`stillAdmin`) and on the revision it read, so an admin demoted before the write changes nothing and of two concurrent saves the later one is a `version_conflict`.

## The job

`enforceWorkspacePolicy` reads the workspace's current policy and, in one regional batch, changes at most 50 rows of each kind (`WORKSPACE_POLICIES.enforceBatch`): public artifacts narrowed to `workspace`, readers outside the allowlist removed, active links revoked with their sessions while links are disabled (revoked links are covered by `share_link` tombstones like any revocation), and sessions of links the policy stops opening ended. It answers `pending` while a kind filled its limit and the queue delivers it again; `done` once nothing is left; `stale` for a workspace that is gone.

Every statement selects the rows it changes itself, with a statement bounded by the batch size (`order by ... limit 50`), never a list of IDs: D1 allows at most 100 bound parameters per statement. Readers are matched by the domain rule in SQL (`substr(email, instr(email, '@') + 1) not in (<the allowlist>)`, at most 20 parameters), never by listing addresses, the same rule the preview, the scan and transfers use. The widest statement, the step's `policy.enforced` event, binds at most 78 parameters (its four selections twice, in its detail and its condition, plus its own values); the webhook statements at most 47; every other one at most 28. The batch size does not change those numbers. Each statement is conditioned on the row still breaking the policy, so a retried or concurrent step changes nothing twice.

A change by policy leaves the trail of a manual change: each changed artifact gets an `access.changed` event with actor `system` and `policy` naming the policy (`publicAccess` with the new mode, or `readerDomains` with the count of readers removed), one `insert ... select` per batch over the changed rows; the `artifact.access_changed` webhook event (one set-based upsert, `markWebhookEvents`); its generation moves, so sessions end; and approval reviewers who no longer take part are dropped as `updateAccess` drops them (`approvalAccessStatements`, for the changed artifacts that have an open request: one read finds them, usually none). The Policies page says after a confirmed change that the artifacts' pages and the audit log show what changed.

## Audit

`policy.changed` (global, target `policy`, the workspace's ID) records the fields that changed, their new values (enums, numbers and domains, never addresses) and whether the admin confirmed changes to existing artifacts. `policy.enforced` (regional, actor `system`) records what one step changed, as counts read in the step's own statement; a step that changes nothing records nothing.

## Restore

A restore of only the regional database brings back artifacts, readers and links as they were, while the policies stay: the next scheduled run finds and corrects them (one scan pass, see "Races"), with nothing to run. A D1 Time Travel restore of the global database rewinds the workspace rows and with them the policies, which could lift a restriction an admin set after the restore point (for example re-allow public access). Policies are not tombstones, so they get the same treatment as plans: `export-policies --out <file>` before the restore and `apply-policies --file <file>` after it (`applyWorkspacePolicies`), which sets each exported policy again with the operator as actor, writes the job, and lists workspaces with a policy the file does not have for the operator to review; it never lifts one. See [operations.md](../operations.md).

## Next

Out of scope here, because each needs the content Worker or the auth layer. [Decision 0020](0020-workspace-request-policies.md) adds the request context and the network allowlists, and designs the other two:

- `sessionHours`: a maximum length of read, review and link sessions for the workspace's artifacts. Needs the content Worker to cap the session cookies and claims it issues by the owner's policy, which its delivery lookup would have to carry without a new read.
- `allowedClients`: the OAuth clients allowed to act on the workspace (for example the CLI and one MCP client). Needs the token's client in `Actor` and a check in `authorizeResourceRequest` or `actorOn`, and a way to list clients an admin can recognize.
- An IP allowlist for reading and acting on the workspace's artifacts. Needs the client IP in delivery and API authorization, a CIDR rule in the domain, and an answer for share links and the viewer's frame.
