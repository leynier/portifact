# 0006 Custom domains

- Status: accepted; first part of P7 implemented on 2026-11-10 (see "Implementation notes")
- Date: 2026-11-09
- Spike: [spikes/custom-domains](../../spikes/custom-domains)

## Question

Paid owners will serve an artifact from their own hostname (for example `docs.example.com`) instead of `<id>.portifact.dev`: Pro gets 1 custom domain and Team 5 (`customDomains` in `PLANS`). Artifacts are served by the content Worker on the `portifact.dev` zone, and every artifact having its own origin is the core of the security model. How do custom domains work on Cloudflare, how does the content Worker find the artifact without a D1 read per request beyond today's one, and what changes in each rule of [security.md](../security.md)?

## What was tried

`spikes/custom-domains` models the tables and code paths custom domains touch, in workerd with two local D1 databases (`GLOBAL`, which also holds the default region as production would, and `DB_EU`, a regional database of decision 0005). Cloudflare's custom hostnames API and DNS are fakes behind two small interfaces; the real client (`src/cloudflare.ts`) is checked only against a fake `fetch`.

Verified by running code (`bun run spike:custom-domains`, 72 tests, 99.6% of lines and 97.4% of branches):

1. **Resolution** (`src/host-directory.ts`, `src/delivery.ts`): on a custom host, two reads on a cold isolate (the global hostname row and the regional artifact), then one per request, today's cost, in both regions. On `<id>.portifact.dev` it stays one read, which also returns the artifact's active custom host. An unknown host costs one read and is never cached. A global row alone serves nothing: the regional artifact row must carry the same host.
2. **Removal and moves take effect at the next request** with the hint still cached: after a detach the stale hint misses the regional row, is dropped and the global row no longer answers. A hostname moved to another owner's artifact in another region is followed in three reads on the first request after the move, and the old artifact is never served on it.
3. **Ownership proof** (`src/domains.ts`): nothing reaches Cloudflare before the TXT record of this claim's token is published; a squatter's claim does not block the real owner, another owner's token does not verify a claim, every claim of a name is spent when one verifies, and expired claims are refused. A valid proof by a new DNS holder takes the hostname from the previous owner, whose artifact stops serving first, and keeps the one Cloudflare hostname.
4. **Lifecycle**: activation only once Cloudflare reports the hostname and certificate active, and only if the artifact is still the owner's and active (otherwise it detaches); a failed Cloudflare create is retried once; a detach retried or run concurrently writes one deletion job, and the job is idempotent; suspension withdraws the hostname and reinstating does not bring it back; purges detach; a lost TXT proof detaches after three missed checks in a row; a downgrade keeps the oldest domains; after a restore, rows whose Cloudflare hostname is gone are detached and Cloudflare hostnames without a row are deleted.
5. **Handoffs and the viewer** (`src/handoff.ts`): the read entry names the host only from a custom host; the app chooses only between the artifact's two origins; read and review codes redeem once, only for their kind, artifact and exact host; the viewer's `frame-src` names the custom host only for a visitor who may read the artifact, so a missing or protected artifact's policy is byte-identical with or without a domain. Old `<id>.portifact.dev` links redirect to the custom host only for top-level page visits after authorization, the viewer wins while the bar is on, and plain `http` on a custom host is upgraded without HSTS.

Mutation checks run by hand, each made the expected tests fail and was reverted: not checking the regional row's host, taking the callback host from input, not binding codes to their host, framing the custom host without the access decision, skipping the TXT proof, not spending other claims, not conditioning the deletion job on the old state, redirecting on the custom host itself, deciding the canonical redirect before the viewer, allowing lookalike names and keeping a lapsed proof.

Only read, not run: everything in "Facts checked", the wrangler route change, the DNS over HTTPS lookup against the real resolver, and the e2e flows in a browser.

## Recommended design

### 1 One domain, one artifact

A custom domain maps to exactly one artifact, and an artifact has at most one custom host. An owner with paths (`docs.example.com/a` and `/b` as two artifacts) would put several artifacts in one origin, sharing cookies, storage and script access, which is what `<id>.portifact.dev` exists to prevent. Pro and Team limits count domains per owner (`entitlements(...).limits.customDomains`, resolved in the services).

### 2 Cloudflare setup (maintainer, once)

- Enable Cloudflare for SaaS on the `portifact.dev` zone (Free plan: 100 hostnames included).
- Fallback origin `domains.portifact.dev`, an originless proxied `AAAA 100::`, which is also the CNAME target customers use: `docs.example.com CNAME domains.portifact.dev`. The content Worker answers it with 404 like any non-artifact label.
- The content Worker's route becomes `*/*` on `portifact.dev` (today `*.portifact.dev/*`), so custom hostnames reach it. The apex `portifact.dev` and every non-artifact label already answer 404.
- Certificates use HTTP DCV: Portifact creates the Cloudflare hostname only after its own TXT proof, when the customer's CNAME is already in place, so the certificate validates with no further record. Subdomains only: apex domains need apex proxying (Enterprise add-on); an apex at a DNS provider with CNAME flattening may work but is not offered. No wildcards.

### 3 Secret and token

A new account API token `portifact-custom-hostnames` with only Zone, SSL and Certificates, Edit, limited to the `portifact.dev` zone, expiring after a year like `portifact-ci-deploy`. Set as `CF_HOSTNAMES_TOKEN` on `portifact-app` (create at verify) and `portifact-jobs` (activation, deletion, re-checks, reconciliation), with the zone ID as a `vars` entry `CF_CONTENT_ZONE_ID`. Client IP filtering does not fit Workers' egress. The permission also covers the zone's other SSL settings and certificates of `portifact.dev` (never `portifact.com`), which is the residual blast radius of a leak; the client never logs the token, and errors carry only Cloudflare's codes. The content Worker gets no token.

### 4 Data model

Global (decision 0005's global database; hostnames must be unique across regions):

- `domain_claims (hostname, owner_id, artifact_id, region, token_hash, expires_at)`, primary key `(hostname, owner_id)`: several owners may hold a claim for one name, each with its own token, so squatting blocks nobody. Claims last 7 days and never reach Cloudflare.
- `custom_domains (hostname primary key, owner_id, artifact_id, region, state, token_hash, cf_hostname_id, verified_at, checked_at, missed_checks)`, state `provisioning`, `active` or `detaching`. No foreign keys (owner may be a workspace; the artifact may be regional). A row is deleted only by the `delete_custom_hostname` job after Cloudflare's delete.

Regional: `artifacts.custom_host` (nullable, unique). It is the authority for serving: delivery on a custom host matches it, attaching sets it last, detaching clears it first. It is on `artifacts`, not on versions, so a rollback keeps the host.

Handoffs: `read_handoffs` and `review_handoffs` gain `host` (the exact hostname the code was sent to), and redemption is conditioned on it.

States and transitions:

| From           | Event                                                                                                                                                                                                   | To                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| (claim)        | TXT proof of this claim holds                                                                                                                                                                           | `provisioning`, Cloudflare hostname created, all claims of the name deleted |
| `provisioning` | Cloudflare `status` and `ssl.status` active, artifact takes the host                                                                                                                                    | `active`                                                                    |
| `provisioning` | Artifact can no longer take it (archived, purged, has one)                                                                                                                                              | `detaching`                                                                 |
| any            | Owner removes, suspension, purge, account or workspace deletion, three missed TXT checks, Cloudflare reports Moved, Deleted or missing, plan limit lower than the count, reconciliation after a restore | `detaching` (artifact row cleared first, job written once)                  |
| `active`       | A new holder proves DNS control                                                                                                                                                                         | previous artifact cleared, row to the new owner, `provisioning`             |
| `detaching`    | Job deleted the Cloudflare hostname                                                                                                                                                                     | row deleted, the name is free                                               |

### 5 Resolution in the content Worker

```ts
// <id>.portifact.dev: today's lookup by ID; the row now also returns custom_host.
// Any other host: hint (isolate LRU, 10,000 entries) -> regional row checked on the host.
select ... from artifacts where id = ? and custom_host = ?
```

The isolate caches `hostname -> { artifactId, region }` from `custom_domains` (`state = 'active'`) with no expiry and no invalidation message, because it is only a hint: every request reads the artifact row anyway (`findDeliveryArtifact` with its traffic and plan joins), and the custom-host variant adds `custom_host = ?` to it. A stale hint misses, is dropped, the global row is read again once, and the request is answered from that or 404. So: one read per request warm, two on a cold isolate per hostname, three on the first request after a move, nothing cached on a miss, and a removal is effective on the very next request in every isolate. Custom metadata (`request.cf.hostMetadata`) would save the cold read but needs Cloudflare's account team and lags 30 seconds; it is not needed.

Relation to decision 0005: `custom_domains` sits next to `artifact_directory` in the global database and plays the same role for custom hosts (host to ID and region), with one difference: a directory row never changes, a hostname row does, which is why its cache is validated on use rather than trusted. Today, with one database, both reads hit `portifact-control`; the code is already shaped for regions. A hostname of an EU workspace is global data, like workspace names: stated in the EU promise.

### 7 Abuse and lifecycle

- **Phishing.** Only paid plans attach domains. Names under Portifact's domains and any label containing `portifact` are refused (`normalizeHostname`); the operator can block more names. Abuse reports work as today (the report link and `/__portifact/report` on every origin); a suspension clears the artifact's host in the same regional batch and detaches the domain, so the Cloudflare hostname and its certificate are deleted. Reinstating does not reattach.
- **Dangling DNS.** After a removal or a lapsed plan, the customer's CNAME may still point at `domains.portifact.dev`. Cloudflare would validate a new custom hostname for that name in real time, so Portifact never creates one without its own proof: a TXT record `_portifact.<host>` holding a fresh random token of that claim (only its SHA-256 is stored), checked through DNS over HTTPS. Whoever does not control the DNS cannot publish it. Without a Cloudflare hostname the name answers Cloudflare's error, never another artifact.
- **Re-verification.** The jobs Worker re-checks every domain daily: the TXT record must stay, and Cloudflare's status must not be Moved, Deleted or missing. Three missed checks in a row detach it.
- **Domains that change hands.** A valid proof by another owner moves the name: the previous artifact stops serving on it first, then the row changes owner and artifact, the Cloudflare hostname is kept and the certificate reissue is Cloudflare's. A domain moved between the owner's own artifacts is a detach and a new attach; there is no in-place move, to keep one path.
- **Account and workspace deletion, purges.** `deleteArtifactData` and the account deletion detach the artifact's domains in their batches (regional clear plus the outbox job in the global batch); `advanceAccountDeletion` also drops the owner's claims. Hostnames need no tombstone: a released name is meant to be claimable again, with a fresh proof.
- **Tombstones around a restore.** A Time Travel restore can bring back a row whose Cloudflare hostname was deleted, or lose a row whose hostname exists. Cloudflare is the record: `operator reconcile-domains` (next to `apply-tombstones` in the drill) detaches rows whose Cloudflare hostname is gone or names another host and deletes Cloudflare hostnames without a row. Until it runs, a restored row serves only if its regional row also came back.
- **Downgrade or lapse.** `enforceDomainLimit` keeps the oldest domains and detaches the rest, after a grace period of 7 days past `valid_until` with an email to the owner. Nothing is deleted and every artifact keeps its Portifact origin.
- **Pending hostnames are billed**, so a `provisioning` domain that is not active after 7 days is detached.

## Alternatives rejected

- **One owner domain with a path per artifact**: several artifacts in one origin share cookies, storage and scripts, breaking the isolation model.
- **A subdomain per artifact under the customer's domain (`<id>.example.com`)**: needs wildcard custom hostnames (Enterprise) and gives nothing a one-artifact domain does not.
- **Trusting Cloudflare's own hostname validation**: real-time validation succeeds for anyone once the CNAME points at Portifact, so a dangling CNAME would let any paid account take a released domain. Portifact's own per-claim TXT proof is required before any Cloudflare call.
- **Custom metadata in `request.cf.hostMetadata` to resolve without D1**: needs Cloudflare's account team, lags 30 seconds behind a removal and still needs the artifact read; the hint cache already gives today's cost.
- **Caching the hostname answer with a TTL, or invalidating isolates**: a TTL delays removals and Workers have no broadcast to isolates; validating the hint on the read delivery already does is immediate and costs nothing warm.
- **Disabling `<id>.portifact.dev` once a domain is attached**: breaks every shared link and the fallback when a domain lapses; a redirect after authorization keeps them.
- **Redirecting `.dev` before authorization**: would tell anonymous visitors which domain a protected artifact uses.
- **The viewer always framing `<id>.portifact.dev`**: simpler policy, but the artifact would run on a different origin in the viewer than on its own address, so its CORS allowlists, storage and sign-ins would differ between the two.
- **A separate SaaS zone for custom hostnames**: another zone and token for nothing; `portifact.dev` already holds only user content.
- **HSTS on custom hosts**: commits the customer's domain beyond Portifact's control.

## Open risks

- Product decision for the maintainer: with the bar on, a custom domain's visitors still end in `app.portifact.com/view/<id>`. The recommendation is to keep `bar` as is and have the dashboard offer turning it off when a domain is attached; the alternative is to never redirect custom hosts to the viewer.
- An owner can point their domain at their own server and collect the read and review cookies and one-use codes Portifact sends readers there. They grant only reading the owner's own artifact, which the owner can already do, and the signed claims name the reader's opaque user ID. This must stay true for anything ever set on artifact origins.
- Customers whose own zone is on Cloudflare (Orange-to-Orange) and who proxy their CNAME may skip the content Worker if their record matches a more specific route on our zone; the `*/*` route and no other route on `portifact.dev` avoid it, to be checked.
- The `hard_cap` of a Free zone is undocumented; Cloudflare could refuse creation before 50,000.
- The SSL and Certificates permission of the new token can change `portifact.dev`'s certificates and SSL settings.
- Cloudflare's own abuse handling applies to customer hostnames on our zone: a phishing domain reported to Cloudflare is a report against `portifact.dev`.

## Implementation notes

The first part of P7 (2026-11-10) covers the data model, the proof, the operations in the API, MCP, the CLI and the dashboard, the jobs, the lifecycle and the operator commands; it ships switched off ([releasing.md](../releasing.md), "Custom domains (switched off)"). Delivery on custom hosts (section 5, the content Worker rows of section 6, `host` on `read_handoffs` and `review_handoffs`, the viewer's `frame-src`, the review iframe origin, the `.dev` redirect, the `http` upgrade, cookie cleanup only on `.dev`, the document policy from the request host, `customHost` in the artifact list and info) is the second part. Where the code differs from the record above:

- **Product decision since the record.** With the bar on, a visit to the custom domain still ends in the viewer. The bar is never changed automatically: the dashboard explains it when a domain is attached and offers to turn the bar off; the CLI and the MCP tools say the same.
- **The TXT token is stored, not hashed.** `domain_claims.token` and `custom_domains.token` keep the value. It is the content of a public DNS record and proves control only by being found there, and the dashboard, the CLI and MCP must show the record again for the daily check to keep passing. It is still never logged, exported or put in an error.
- **A claim keeps its token while it lasts.** Adding the same name again for the same owner keeps the token (and moves the claim to the artifact named), so a retry never invalidates a record already published; a new token comes only once the claim expired.
- **Verifying is gated too**, on the plan of the owner whose claim or domain it is; listing, reading and removing never are.
- **The count is enforced in the proof's write**, conditioned on the owner's domains, so two proofs at once cannot pass the limit; adding checks it too for an early answer.
- **Apex domains are refused in the domain rules** as names with fewer than three labels. A registrable domain under a two-label public suffix (`example.co.uk`) passes the rule but cannot validate without apex proxying; it is detached after the 7 days of provisioning.
- **One region.** The `delete_custom_hostname` job is written in the global batch, as the record says; today the global and regional databases are the same binding, so the relay sees it. A second region (E5) must relay the global outbox too.
- **Purges and account deletion** release domains in a separate step before their own batches (detach, then the artifact or account goes), because no batch spans the global and regional databases; the order keeps the host from serving first. Suspension clears `custom_host` in its own regional batch, as the record says.
- **Downgrade grace without email.** The grace of 7 days past `valid_until` is applied (`domainLimitAt` reads the plan as it was a week earlier); the email to the owner before the grace ends is not written yet.
- **States in the API.** Views show `pending` for a claim and `removing` for `detaching`, and carry `problem` (`txt_missing`, `certificate_pending`, `cloudflare_unavailable`), stored on the row for proven domains.
- **Extra surface.** `get_custom_domain` mirrors `GET /api/v1/domains/:hostname` and `portifact domains info`; `GET /api/v1/domains` and `list_custom_domains` take an optional `artifactId`, which the dashboard uses with the owner's plan.
- **Not yet.** The operator block list of names (section 7) and an email when a daily check starts missing are not implemented.
