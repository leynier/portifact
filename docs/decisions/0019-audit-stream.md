# 0019 Audit streams

- Status: accepted
- Date: 2026-11-10
- Feature: premium plan E3, second half, first part (`auditExport` in `PLANS`, Enterprise). Retention policies for artifacts and comments are not part of this record.

## Question

Enterprise customers keep their audit trail in a SIEM. The file export (`GET /api/v1/audit/export`) gives them the log on request; they also want it continuously, without polling, without gaps they do not hear about and without Portifact touching the paths that write events. How does Portifact deliver an owner's audit log to an HTTPS endpoint the customer runs, in order and without silent loss, reusing what webhooks already proved, and within the per-region and cost rules of decision 0005?

## Decision

A stream is its own destination, not a webhook event type. Portifact reads the owner's audit events after a stored position in each database the owner's events live in and posts them in batches, moving the position only after the endpoint answered 2xx. Delivery is at least once, ordered per database by when the database recorded each event, and never skips: a consumer keeps each event ID once. When retention may have deleted events the stream has not delivered, the stream says so with a gap record, never hiding it.

### Why not a webhook event

A SIEM needs every event, in order, with no loss it is not told about. Webhook events are coalesced per artifact and type, best effort (dropped after their retries or when a webhook is disabled), one request per window, and carry a summary of activity, not the record. Making the audit log one more event type would either weaken those guarantees for the log or strengthen them for every webhook. A stream reuses the webhook machinery (below) with its own delivery state.

### What a stream is

- Per owner (a personal space or a workspace), at most 2 (`AUDIT_STREAM.perOwner`, a safety cap). A label, an HTTPS URL (only the host is shown after it is set), a signing secret (shown once at creation and at each rotation, never returned again), a state (`active`, `paused`, `attention`) with the reason (`manual`, `plan`, `failures`, `invalid_url`, `key_unavailable`), a position per database, failure counters, the last gap reported and a pending test.
- `audit_streams` and `audit_stream_deliveries` are regional (`TABLE_HOMES`), next to the owner's webhooks: the job that delivers runs in the owner's region with the region's database (decision 0005, "Two-region audit"), the stream's deletion goes with the owner's other regional rows, and an EU workspace's stream never leaves the EU database. The global position is a column of the same regional row: positions are recorded times (below), so a restore of either database never makes a position point past events written afterwards.

### Recorded time (the stream's order)

The first version ordered a stream by an event's `at` and only sent events older than 20 minutes, assuming every writer commits within one Worker invocation of its `now`. An independent review showed that assumption does not hold: the operator tool takes one `now` per process and loops (`apply-plans`, `apply-policies`, `reconcile-domains`), the scheduled run passes one time to every scan in turn, the queue consumer one per batch, and isolates' clocks differ. An event written with an old `at` landed behind a position that had already moved, and was never sent.

The stream now orders and positions itself by `audit_events.recorded_at`, set by the database's own clock (`recordedNow`, `julianday('now')` in milliseconds) inside the same `insert ... select` that writes the event. Every writer already runs that insert, so the audit write path gets no extra statement, read or round trip, and the pinned counts in `write-costs.test.ts` did not move. `at` stays what the reader, the export and the stream's lines show; `recorded_at` is never sent or shown. A guard test (`scripts/audit-recorded.test.ts`) scans the shipped source and fails for any insert into `audit_events` that does not set it, because a row left at the column's constant default (0) would sort before every position.

A position is `(recorded_at, id)` of the last event delivered from a database. The job reads events recorded at least `AUDIT_STREAM.settleMs` (2 minutes) before the database's clock, read in the same query, so no Worker clock is involved anywhere in the order. The window is only the time a D1 batch takes between reading the clock (when its statement runs) and committing (when the row becomes visible), which is well under a second for the batches that write events and bounded by D1's statement limits; two minutes leaves room for a slow batch and for the clock of the host that runs the database moving slightly. Delivery lag drops from 20 to 26 minutes to about 2 to 8 (the window, the 5-minute idle interval and the one-minute relay). Tests cannot move the database's clock, so the window is injectable (`AuditStreamDeps.settleMs`, as `MultipartConfig` is for uploads) and tests set `recorded_at` directly where they need a past row.

The migration adds the column with a constant default (SQLite refuses an expression in `ALTER TABLE ADD COLUMN`), then backfills existing rows from `at` in one set-based `UPDATE` before creating the index `(owner_id, recorded_at, id)` the stream reads by, so the index is built once. On a large table that update rewrites every row once (one pass, no reads per row); production's table is small (the log started with premium plan T10 and keeps 90 days by default). Both databases get the column: every control database runs the same migrations, and the global rows record the global database's clock.

A D1 Time Travel restore rewinds rows, not the clock: rows recorded after the restore point are gone (and were already delivered, or are lost with the restore itself), and every row written afterwards is recorded later than any position, so a rewound position only makes the stream send again; it never skips.

Each database (the owner's regional one and the global one, `GLOBAL_AUDIT_KINDS`) has its own position and its own batches, each named in the `portifact-audit-source` header (`regional` or `global`). Order is guaranteed within a source. Across sources the two clocks are different databases' clocks, so a consumer can assume only that each event carries its `at`: merging the two sources by `at` and `id` gives the reader's order. With one region both sources are the same database, read for disjoint kinds, so no event is sent twice.

Rejected: positions by SQLite `rowid`, which is reused when the newest row is deleted; an `AUTOINCREMENT` column, which would need a table rebuild and gives no clock to compare a window with; fixing every writer's `now`, which leaves the guarantee resting on a convention nothing can check.

### Delivering

The jobs Worker delivers; nothing else fetches a stream's URL. A stream's job (`audit_stream` outbox topic, subject the stream) is its chain: each run sends what is settled and moves its own row to its next time, `now` while more is waiting (after `batchesPerRun` requests), `idleMs` (5 minutes) when caught up, the backoff after a failure, or the next UTC day at the daily cap. It ends only when the stream stops delivering (paused, attention, removed, the plan lapsed, switched off, no key). A job that runs without the switch or without `WEBHOOK_KEY` ends (`stale`) instead of being redelivered forever, and the scan gives the stream a job again once both are back. Creating and resuming a stream write its first job in their own batch.

The maintenance scan `maintainAuditStreams` is the safety net: per region and run, one batch that prunes at most 500 delivery log rows past 7 days and gives a job to at most 100 streams that should have one and have none (`armPerRun`). It runs from the jobs Worker only while streams are switched on. The key re-seal (`rewrapAuditStreamKeys`) reads nothing unless `WEBHOOK_KEY_PREVIOUS` is set, so outside a rotation streams add exactly one D1 call per region per 15-minute invocation, whatever the number of owners or streams; during a rotation, a read and a count per region plus one update per stream it re-seals (at most 100). These counts are pinned in `scan-costs.test.ts`; `runMaintenance`'s is unchanged.

One run of the job: reads the stream with its owner's plan (one joined read with one database, two with a separate one), checks the switch, the key, the state and the plan (a lapsed plan pauses the stream with the reason `plan`, keeps its position and records `audit_stream.paused`), waits while `WEBHOOKS_PAUSED` or budget protection holds deliveries (15 minutes, like webhooks), claims the run on its outbox row (one run at a time, taken over after 5 minutes), opens the URL and secrets, checks the URL again (`checkWebhookUrl`), sends a pending test, then up to 4 batches. Before each batch it reads the stream's revision and state again (below). A batch reads at most 500 settled events of one source after its position, presents them as the reader does (`presentAuditEvents`, the export's `auditJsonLine`), counts one request in the owner's daily counter, posts, and on a 2xx moves that source's position in one batch with its log row, conditioned on the position it read and on the revision the run started with. Bounded worst case per run: about 45 D1 calls (4 batches of the revision read, the event read, at most five presentation reads, the counter and the write, plus the stream, protection, claim and test).

The queue consumer runs stream jobs concurrently with webhook deliveries and issues and alongside the batch's other jobs, so a slow endpoint holds only its own job (10-second timeout, held even if the network ignores the abort signal), never a purge, a deletion or a notice.

### Changes during a run

Every change of what a stream is (its URL, secret, key, state or label, by an admin, the platform's pause or the key re-seal) bumps the row's `revision`; delivery never does. A run reads the revision before each batch and stops (rescheduling itself at once) when it moved, and its position write holds only while the revision is still the run's. A batch already on its way to an endpoint the admin just left therefore never moves the stream: its events go again to the new endpoint (at least once). A pause or removal during a run sends no further batch. The failure counters are written the same way: `failing_since` is kept in SQL (`coalesce(failing_since, now)`), conditioned on the revision, so a run that started before an admin's URL change can never write back the old endpoint's failing time and push the new one into `attention`.

### What is sent

The body is JSON Lines (`application/jsonl; charset=utf-8`, where a webhook sends `application/json`), at most 500 events and 512 KiB per request (the first event always goes). Each event line is exactly what the Audit page, the API and the export show (`AuditEventView`, written by `auditJsonLine`): kind, time, actor and target by display name and opaque ID, artifacts by name only while still the owner's (`artifactNames`), the kind's detail, which `AUDIT_DETAILS` already limits to counts, enums, booleans, versions, hosts and email domains. Never comment text, content, labels the reader does not show, tokens, secrets, URLs, full addresses or IPs. Two control lines carry a `record` field and are not events: `{"record":"gap","source","from","to","reason":"retention"}` and the test record `{"record":"test","id","at","stream"}`. Delivering never records an audit event, so a stream never feeds itself.

### Signing and idempotency

The same scheme and headers as webhooks (decision 0009, Standard Webhooks), so one verifier serves both: `webhook-id`, `webhook-timestamp` and `webhook-signature: v1,<base64 HMAC-SHA-256 of id.timestamp.body>` with the secret's bytes. `webhook-id` and `idempotency-key` hold a batch key, `asb_` and a SHA-256 of the stream, the source and the first and last positions it carries. The same events give the same key, but a retry is not promised to carry the same events: a batch that was not full can grow with events that settled meanwhile, and a gap line's range moves on. Receivers must deduplicate by event ID, which every line carries; the key is only a convenience. `portifact-audit-stream` names the stream, so a receiver tells a stream from a webhook by that header and the content type. A rotation keeps the previous secret signing next to the new one for 24 hours (space-separated signatures, which Standard Webhooks verifiers accept), so the endpoint switches without losing a request. An emergency rotation (`rotateSecret` with `revokeOldSecret`, "Replace now" on the dashboard after a confirmation that says what it does) stops the old secret at once: until the endpoint has the new one it refuses requests, which are retried, so nothing is lost.

### Failures

A 2xx delivers. Any 3xx is a failure (`redirect`, never followed); a 4xx or 5xx is `refused` with its status class; a connection error is `unreachable`, or `certificate` when the error names TLS; a timeout is `timeout`. Nothing of the response is kept but its status class (at most 4 KiB is read, then cancelled). The next request waits for the endpoint's `Retry-After` on a 429 or 503 (bounded to 1 minute to 6 hours), otherwise 1 minute, 5 minutes, 30 minutes, 2 hours, then every 6 hours. After 72 hours of failing without a success the platform pauses the stream with the state `attention` and the reason `failures`, records `audit_stream.paused` and ends the job; the admin fixes the endpoint, sends a test and resumes, and the stream goes on from its position. A URL that no longer passes the checks, or a value sealed with a key the Worker no longer holds, pauses it the same way (`invalid_url`, `key_unavailable`).

A daily request cap per owner (2,000 a UTC day, `rate_limits` key `audit-stream:attempts:<owner>:<day>`, counted before the send) bounds what one owner can spend; it is keyed by owner, so removing and creating streams never resets it. Creating (10 a day), testing (10 an hour) and changes that seal or resume (20 a day) are counted per owner the same way.

### Retention and gaps

The retention sweep is never held back for a stream, and it deletes by `at` before `auditPruneCutoff(retention, now)`, unrounded. The stream's gap rule uses that same domain function, so the two cannot drift (the first version rounded the cutoff down to the hour and missed events the sweep had already deleted). Because the stream reads by recorded time and the sweep deletes by `at`, the rule needs a bound on how much older `at` can be than `recorded_at`: `AUDIT_STREAM.gapMarginMs`, one day, far longer than any writer holds its `now`. Events recorded before `auditPruneCutoff + gapMarginMs` (`streamRiskBound`, taken again for every batch) may have been deleted, or may be before the stream reads them.

When a position (or the end of the last gap reported) is behind that bound, the batch of that source starts with a gap line `{"record":"gap","source","from","to","reason":"retention"}`: events recorded between `from` and `to` were or will be deleted by retention and may be missing. The stream still reads from its position, so whatever is still kept in that range is sent. The end of the gap is stored per database (`regional_gap_to`, `global_gap_to`), the next report starts there, and a range shorter than an hour waits to join the next, so a stream lagging at the edge reports contiguous ranges rather than one per run. A sweep that runs between two batches of one run deletes only events the gap already covered, because the margin is a day. When the operator lowers an owner's retention, the next run's bound uses the new value. A quiet, paused stream past retention reports a gap although nothing may have been deleted: the wording ("were or will be deleted", "may be missing") is true either way, and the customer documentation says so. A fresh backfill from the oldest event claims nothing before its first delivery.

### Starting point

A new stream starts from now by default: its positions are the database's clock when it is created (written by the insert itself), so events recorded before it are not sent and its own `audit_stream.created` event is the first. With a separate regional database the global position also takes the regional database's clock, the only one the insert can read; a few seconds of skew between the two databases' clocks can include or leave out the global events recorded in those seconds. It may instead start from the oldest event still kept: the positions are empty, and the backfill goes through the same bounded batches, cap and job, oldest first.

### Who and where

- Only admins (role action `audit`, the one that reads the log: whoever may read the whole log may send it out, and a narrower action would buy nothing because the log is admin-only already). Editors and members get `forbidden`, a non-member what a missing workspace gives, another owner's stream ID answers like a missing one. A service token never reaches `audit` (`TOKEN_ACTIONS`).
- Every write (create, change, test, removal) holds only while the caller is still an admin and, for a change, only from the revision it read. With one database the admin check is inside the write's batch (as `stillAdmin` for service tokens); with a separate regional database the caller is resolved again right before the batch, and a demotion landing between that read and the batch is not seen, as for issue integrations (decision 0018). A change that lost a race to another answers `version_conflict` instead of mixing the two (a rotation racing a URL change can no longer re-seal the old secret while recording a rotation).
- Only the dashboard session, at `/api/v1/audit/streams` with `?workspace=<slug>`, for every route including the list. The CLI's `credentials:manage` token does not manage streams, unlike webhooks: a stream sends the entire log of the space out of Portifact for as long as it exists, which is more than a webhook's activity summaries, there is no CLI command to use it, and the session check keeps the decision with a person in the dashboard. Rejected: reading a stream's state through bearer tokens, MCP or `portifact audit stream`. That a stream exists, where it points (its host) and who changed it are already in the log itself (`audit_stream.*` events, readable with `artifacts:read` like the rest of the log), so agents and scripts can see it without a new surface, and leaving the routes session-only means no parity table to keep in step. With no CLI or MCP surface the skill does not change.
- Creating, a new URL, resuming and testing need `auditExport` and then `audit` in the owner's plan (`plan_required` names the export first, as the file export does); reading the list and the log, pausing, renaming, rotating the secret and removing never do. A lapsed plan pauses delivery and keeps the rows; resuming after the plan returns continues from the position, subject to the gap rule.
- Switched off with webhooks: nothing is created or delivered unless both Workers have `WEBHOOKS_ENABLED="true"` and `WEBHOOK_KEY`. Without them creating, a new URL, resuming, rotating and testing answer `capacity_unavailable` ("Audit streams are not available yet."), the list says `serviceAvailable: false`, the dashboard shows nothing, jobs end without sending and the scan arms nothing. The deployed configuration sets neither ([releasing.md](../releasing.md), "Webhooks" and "Audit streams").
- For an `eu` owner the list says `euOwner: true` and the dashboard tells the admin that the endpoint may be outside the EU and that what it receives leaves the EU.

### Sealing

The URL and the secrets are sealed with the webhook key (`seal` and `open` in `webhook-keys.ts`, AES-256-GCM under `WEBHOOK_KEY`), bound to the stream's ID and column, as webhooks are. The jobs Worker re-seals streams of a retired key with the current one per region (`rewrapAuditStreamKeys`); the app Worker accepts `WEBHOOK_KEY_PREVIOUS` too, only so an admin can change a stream sealed before a rotation while the re-seal is still running.

### Audit events about streams

`audit_stream.created` (host, start), `audit_stream.changed` (host and which of label, URL, secret or state changed), `audit_stream.removed` (host) by the admin, and `audit_stream.paused` (host, reason) by the system, each in the batch of its change on its own condition. They are regional kinds. Details never hold the URL, its path, the label or the secret.

### What goes with an owner

Account deletion deletes the account's streams in both of its batches (the request and every run of its job) and clears who created a workspace's stream; workspace deletion deletes them in `deleteWorkspace` and `advanceWorkspaceDeletion`. Their log and jobs go with them (foreign key, and a job whose stream is gone is done). Removing a stream writes an `audit_stream` tombstone (with one database in the removal's batch, with a separate one globally first), which `exportTombstones` exports and `applyTombstones` re-applies in every region together with the streams of tombstoned owners, so a D1 Time Travel restore never brings a destination back. A restore that rewinds a position makes the stream send again what it had sent since (the consumer drops repeated IDs); it never skips, because positions are the database's recorded times and every row written afterwards is recorded later. A restore that rewinds the events but not the position loses nothing that was not already delivered. The account export lists streams by ID, label, host, state and creation time, never the URL, the secret or a position.

## Alternatives rejected

- **A webhook event type** (above).
- **Writing a mark or job on the audit write path** (a per-owner "has new events" row, or an outbox job with every event): it adds a statement to every batch that records an event, which the scope forbids, and the settle window plus the job's own cadence already bound the latency.
- **A scan that delivers**: one scheduled invocation would wait on customers' endpoints; deliveries belong in the queue consumer, beside webhooks, where a slow endpoint holds only its own job.
- **A stream row in the global database**: the job runs in the owner's region, and its deletion and backups are regional; with time positions the global source's position does not need to live next to the global events.
- **One position across both databases**: a merged order needs both databases' next events at once and still cannot order an event committed late in one against the other; two positions keep each source simple and exact.
- **Sending tests from the app Worker**: only the jobs Worker fetches user URLs; a test waits for the next run (within a minute through the relay).

## Open risks

- **Latency.** An event reaches the endpoint about 2 to 8 minutes after the database recorded it (the settle window, the idle interval and the relay).
- **A batch slower than the window.** The window assumes a D1 batch commits within 2 minutes of reading the clock. A slower batch could make a row visible behind a position. D1 bounds statement time well under that; release check 4 measures it on staging.
- **An `at` older than the margin.** The gap rule assumes an event's `at` is at most a day older than its recorded time. A writer that held its `now` longer and wrote an event within a day of the retention edge could have it swept unreported. Nothing does so today.
- **The platform behaviours of decision 0009** (DNS to private addresses, same-account reach, `CF-Worker`) apply to streams exactly as to webhooks; the same release checks cover both.
- **The receiver's view across sources.** A consumer that needs one total order must merge the two sources by `at`; this is documented for customers.
- **Read replicas.** Portifact does not use D1 read replication. If it ever does, the stream must read from the primary, or a replica's lag must stay under the window.
