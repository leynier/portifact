# Design system

All Portifact UI comes from one design system in `packages/ui`. This covers the dashboard, the viewer with the Portifact bar, the Markdown and TXT viewers served on artifact origins, and any visible part of the annotation bridge. The goal is a consistent product and a single place to change how it looks. Styles scattered across apps are not allowed.

## Layers

1. **Tokens.** Every visual value lives here: color, typography, spacing, sizing, radii, borders, shadows, z-index, motion and breakpoints. Tokens are CSS custom properties exposed through the Tailwind CSS v4 theme in `packages/ui/src/tokens`. Two levels:
   - Primitive tokens hold raw values, for example the color scale.
   - Semantic tokens describe intent, for example `--color-surface`, `--color-text-muted`, `--color-danger` and `--space-4`. Components and apps use semantic tokens only. Color tokens resolve to the neutral palette described below.
2. **Components.** Accessible React building blocks owned in `packages/ui/src/components` and exported from `@portifact/ui`: button (`primary`, `secondary`, `danger`, the destructive secondary action, such as "Disconnect" on an app card, with a dashed border at rest and the inverse fill on hover, `ghost`, `link`, `floating`, the inverse control that floats over content, such as the viewer's "Comment" next to a selection, and `field`, which looks like an empty field and opens a form in place, such as a thread's reply box; `secondary` shows `aria-pressed` for toggles, and `count` adds a count badge with words for screen readers), icon button and icon link (square, named by `label`, which their tooltip shows), tooltip (hover and keyboard focus but not the focus that follows a pointer press, below, above or `right` of the control with `align`, hoverable, Escape hides it, at most one shown at a time, `disabled` and `block` for the collapsed sidebar, hidden from assistive technology because it repeats the control's name), menu (the ARIA menu button pattern, with actions or links), avatar (a picture or initials in a circle, decorative: `outline` with one initial beside an author's name in `sm` and `md`, `solid` with `letters={2}` for the signed-in account in `md` and `lg`; a picture that fails to load falls back to the initials), badge (`normal`, `strong`, `quiet` and `subtle`), callout (`info`, `success` and `error`), confirm dialog (with a `danger` tone), copy field (with a `compact` one-row layout for bars and captions), detail list (`split` or `stacked`, framed or not), disclosure (a native `details`, `boxed` or `inline` for details inside a card that already has a frame, with `label` naming the summary when its text repeats, such as "Details of Claude"), drop zone, empty state, loading state (with skeleton rows, or `centered` and `cover` layouts that center a larger spinner over the label, as the viewer does while it loads and while it connects to the page), live region, meter, panel, steps, table (`framed` or `flush`), toast, text input, text area (with `compact` for short notes), search field (a compact toolbar box with its icon, visible label and a clear button that gives focus back to the input), select (one choice among many, `field` or the `compact` chip for toolbars, see below), checkbox, radio group (`stack` or `row`, each option a card that takes a press anywhere on it), sheet (a native modal `dialog` that rises from the bottom on phones and is centered on wider screens), drawer (an off-canvas native `dialog` from the start edge that closes on Escape, the backdrop or a followed link and locks the page's scroll through `data-scroll-lock`), resize handle (a focusable vertical `separator` with its value, dragged or moved with the arrow keys), file picker (with `canPickFolders`), progress bar and preview frame today, plus the `useMediaQuery` hook (`WIDE_QUERY` is the `sm` breakpoint); tabs as screens need them. Prefer a native element when it gives the behavior (the confirm dialog is a native `dialog` with `showModal()`), and use Radix UI primitives where none does, but not ones that inject inline `<style>` elements (such as Radix's scroll lock), which the strict page CSP refuses. The select is drawn by the design system, not the browser (`components/select.tsx`), following the WAI-ARIA select-only combobox pattern: a `button` with `role="combobox"` and a chevron keeps focus and points at the active option with `aria-activedescendant`; the listbox floats with `shadow-float`, rendered at the end of the landmark or modal dialog that holds the trigger and placed in the window with fixed coordinates through the CSSOM (`placeListbox`: under the trigger, above it when there is more room, never off screen); the chosen option sits on the selection color in bold with a check. Keys work like a native select: arrows, Home, End, Page Up and Down, typeahead (`typeaheadMatch`, a repeated letter cycles), Enter, Space, Alt+Up, Escape and Tab (which keeps the highlighted option); the highlight is outlined with the focus ring only while the keyboard moves it. The `compact` variant shows its label inside the chip before the value, and `active` (a filter that is on) gives it a solid strong border and a bold value. Variants such as size, tone and state are part of the component API, defined with `class-variance-authority`. Icons are Lucide, decorative and `aria-hidden`; the label carries the meaning.
3. **Patterns.** Compositions reused across screens, such as page layout, data table with filters, upload progress and annotation thread, in `packages/ui/src/patterns`. `AppShell` (skip link, a banner that from `md` is a fixed sidebar with the labelled navigation and the account at its foot, collapsible to an icon rail with tooltips and, expanded, resizable from its edge between 208 and 384 px, both remembered per browser under `storageKey` and working without storage, and below `md` a top bar whose menu button opens the navigation and the account in a `Drawer`; the width is set as `--pf-sidebar-width` through the CSSOM and read by the `w-sidebar` and `pl-sidebar` utilities, and the focusable `main` sits on the backdrop with its page column capped by `max-w-page` (88rem) and aligned to the sidebar, never centered between empty gutters), `SidebarAccount` (avatar, name or the email's local part and email, truncated, linking to the profile, and a sign-out icon button; avatar and button only in the rail) `PageHeader` (the screen's single `h1`, with an optional `back` link, `meta` badges, description and actions) and `ViewerShell` (the viewer's Portifact bar with the artifact's name and version as plain text after the mark, `actions` and `account` from `sm`, the `toggle` at every width and an `overflow` menu below `sm`; the artifact edge to edge below the bar; and the comments sidebar, which sits beside the artifact from `lg` and covers it below, with a close button) and `SectionedPage` with `PageSection` (a long screen grouped by task with an "On this page" guide: from `xl` (`GUIDE_QUERY`) a titled, sticky column at the end (`grid-cols-guide`), so the content starts next to the sidebar and takes the free space, and below it a compact menu (a `details` with the current section in its summary) that stays at the top and closes when a section is chosen; the guide comes first in the tab order. Its current link is a selection band with `aria-current`, chosen by an `IntersectionObserver` scroll spy, the last section once the page is scrolled to its end, and a followed link until the person scrolls again (wheel, touch or a scroll key). Following a link scrolls smoothly unless reduced motion is asked for, moves focus to the section (`tabIndex={-1}`, as `Panel`s with an `id` have) and updates the fragment with `replaceState`. Its sections are `PageSection`s (an `h2` holding `headingLevel={3}` panels; `tone="danger"` puts a dashed rule above the destructive section) or `Panel`s with an `id`; both keep their heading clear of the sticky bars when scrolled to) and `FrameOverlay` with `Floating` and `FloatingPanel` (a layer over a frame, clipped to its box, for controls the page draws next to something in the frame: placed by coordinates set through the CSSOM, the dynamic-geometry exception, or a bottom sheet kept above the on-screen keyboard through the visual viewport, `keyboardInset`) exist today.
4. **Apps.** Screens compose components and patterns. They only arrange layout using tokens.

## Visual direction

Portifact is a publishing and review tool for developers and their agents. The look is a quiet, precise workbench: dense enough to scan many artifacts, calm enough to read comments, and monochrome like the brand. One element carries the personality, taken from the logo: **the selection**, a light band held between two text-selection handles.

- **Selection band.** `selection-band` (in `theme.css`) draws the band (`--pf-color-selection`) with a handle at each end (a bar with a knob on top at the start and one with a knob below at the end, sized by `--pf-handle-width` and `--pf-handle-knob`). It means "selected or current" and nothing else: the current page in the navigation (`current:selection-band`), the chosen radio option (`has-checked:selection-band`), the chosen option of a select (the selection color with a check), the in-page section being read (`current-item:selection-band`), the current step of a flow (`aria-current="step"`) and a drop zone while files are dragged over it. Never use it as decoration, and always pair it with weight, a check or `aria-current`, so it never relies on its tone.
- **Depth.** Screens sit on `backdrop`; sections are panels on `canvas` with a hairline `border` and `shadow-sm`; subtle fills (table heads, cards inside panels, code values) use `surface`; hover uses `surface-hover`; menus, toasts and dialogs float with `shadow-raised` or `shadow-float`. Dark mode keeps the same order with lighter surfaces on a near-black backdrop, and borders carry the depth where shadows do not show.
- **Radii by role.** `xs` for badges and navigation items, `sm` for controls (buttons, inputs, radio options), `md` for callouts and nested cards, `lg` for panels, tables, empty states and dialogs.
- **Typography.** The system UI stack, so the dashboard loads no font files (a self-hosted typeface needs a license review first: the usual open fonts are OFL-1.1, which `AGPL_COMPATIBLE` does not list). Hierarchy comes from size and weight: page titles `text-2xl`/`sm:text-3xl` semibold with tight tracking, panel titles `text-base` semibold, body and controls `text-sm`, terms and captions `text-xs` muted. Numbers in tables, meters and dates use `tabular-nums`. Monospace is only for things people copy or type: URLs, IDs, paths and commands.
- **Density.** Controls are `h-10` (`h-8` small); table cells `py-3.5`; panels `p-5`; screens stack panels with `gap-6`. The page column is at most `max-w-page` (88rem), starts at the sidebar and uses the width for grids (panels side by side from `xl`, cards and meters in columns); prose keeps a readable measure (`max-w-3xl` on descriptions), never the whole page.
- **Motion.** Only motion that answers an action: `animate-pop` when a toast or dialog appears, `animate-shimmer` for loading placeholders and busy button icons, 150 ms color transitions on hover. All of it is `motion-safe:` and nothing moves under reduced motion.
- **States.** Never tone alone: `strong` badges are solid inverse (suspended, purging), `quiet` ones dashed (archived, draft), access modes are `subtle` badges with a lock, people or globe icon, meters turn hatched near the limit and say "Near the limit" or "Limit reached", and errors are callouts with a thick handle on the left edge.

## Palette

Portifact is monochromatic. The whole product, including the logo, dashboard, viewer, Markdown and TXT viewers, CLI output, documentation and emails, uses only black, white and a neutral gray scale with zero saturation. No hue appears anywhere, including accents, links, focus rings, charts and status states.

- The primitive scale is a single neutral ramp from white to black, defined once in `packages/ui/src/tokens`. Semantic tokens map onto it for light and dark themes.
- Hierarchy comes from contrast, weight, size and spacing, not from color.
- Links are distinguished by an underline, not by color.
- States (danger, warning, success, info) are semantic tokens like any other, but they map to neutral values. They are always conveyed by an icon, a text label and, where useful, weight or border style. A state is never shown through tone alone; see [accessibility.md](accessibility.md).
- Annotation highlights and selection in the viewer use neutral tints that keep the underlying text at the required contrast.
- Content published by users keeps its own colors. The rule applies to everything Portifact draws around it, such as the bridge highlights and viewer chrome.

Exception: third-party status badges in the readme (release, license, CI, coverage) keep their conventional colors, because their color carries meaning readers already know.

Adding any other hue requires changing this section first, in a separate change with a reason.

Semantic surfaces: `backdrop` (behind panels), `canvas` (panels, inputs and published documents), `surface` (subtle fills), `surface-raised`, `surface-hover` and `surface-inverse`. The token tests require body text at 7:1 and muted text at 4.5:1 on every surface and on the selection band, in both themes.

The `terminal`, `terminal-text`, `terminal-muted` and `terminal-border` tokens draw terminal and agent-session blocks, and dark bands such as the landing page's security section. They stay dark in both themes, so use them only where a dark surface is the point.

## Theming

Portifact's own pages offer three themes: System (the default, which follows the operating system), Light and Dark. The landing page, the legal and MCP pages, the auth pages, the dashboard and the viewer's chrome all follow the choice; artifacts never do (see below).

- **Tokens.** Under System the root has no `data-theme` and the dark tokens come from the `prefers-color-scheme: dark` media query, which skips a root marked `data-theme="light"`. A Light or Dark choice sets `data-theme` on the root; the forced `[data-theme="dark"]` block repeats the dark tokens after the light block, so it wins at the same specificity. The token tests keep the media and forced blocks identical.
- **Before the first paint.** `THEME_SCRIPT` (`packages/contracts/src/theme.ts`) is inlined at the end of every page's `<head>` by the `portifact-theme-script` plugin in `apps/web/vite.config.ts`. It reads the stored choice and sets `data-theme` before the body is parsed, so a reload never flashes the other theme. The pages' CSP allows exactly its text by `THEME_SCRIPT_HASH` (see "Theme script" in [security.md](security.md)); changing the script means updating the hash and `apps/web/public/_headers`, which the tests enforce. The localized pages are rendered from the built English ones (`src/i18n/site-build.ts`), so they carry the same script byte for byte under the same hash; `src/i18n/site.test.ts` and `apps/app/test/site.test.ts` check it.
- **Storage.** The choice lives in `localStorage` under `portifact.theme` (absent means System), read and written in try/catch: with blocked storage the switch still works for the page and the next load starts from System. Storage is per origin, so `portifact.com` and `app.portifact.com` keep their own choice on purpose: sharing it would need a cookie scoped to `portifact.com`, which the privacy page promises we do not set ("Cookies are restricted to the address that set them"). Tabs of one origin follow each other through the `storage` event.
- **Runtime.** `@portifact/ui/theme` (`packages/ui/src/theme/theme.ts`) applies and remembers a choice (`setThemePreference`) and wires static switchers (`setupThemeSwitchers`, used by the landing's `main.ts`). React code uses `useThemePreference`.
- **Controls.** `ThemeSwitcher` is a native radio group (`fieldset` and `legend`), so arrow keys move between choices and screen readers announce the group, the choice and its state; the chosen option carries the selection band and focus shows the focus ring around the option. `compact` shows icons only, with each name in a tooltip and kept for assistive technology, and `orientation="vertical"` stacks them for the collapsed rail. The dashboard shows it in Settings, "Appearance", and as a compact quick switch above the account in the sidebar and the drawer; the landing page has a static copy in its footer, written with `themeSwitcherClasses` (the landing test compares them). Strings come from the `theme.*` keys of the dashboard catalog.
- **Images.** A `<source media="(prefers-color-scheme: dark)">` alone follows only the operating system. On static pages the theme script (while the page loads) and `applyTheme` (after) point every such source at the choice: `media="all"` under Dark, `media="not all"` under Light, back to the system query under System, marking it `data-theme-media`. React screens use `ThemedImage`, which renders the source's `media` from `darkSourceMedia`. Keep writing dark sources with that exact media text so they are found. A browser's preload scanner may still fetch the other variant of an image when the choice differs from the system; nothing shows it. The favicons are SVG files the page cannot reach, so they follow the operating system only.
- **Artifacts are not themed.** What a creator published, inside the viewer's frame and on `portifact.dev`, keeps its own look. Rendered Markdown and TXT documents follow the operating system through `TOKENS_CSS`, and emails follow the mail client; neither sees the choice.

## Motion and patterns

Motion tokens and utilities live in `packages/ui/src/tokens/theme.css`: `animate-rise`, `animate-fade`, `animate-type`, `animate-sweep`, `animate-blink`, `animate-pop` and `animate-shimmer`, staggered with `animate-delay-<n>`. Always apply them through the `motion-safe:` variant, so nothing moves under `prefers-reduced-motion` and every element rests in its final state. Motion is decorative only; it never carries information.

The landing hero types its second line with `apps/web/src/typewriter.ts`: one pass through the phrases, then it settles on the first and the caret fades, so nothing keeps moving. The `h1` keeps a visually hidden, complete sentence for assistive technology and marks the animated part `aria-hidden`; invisible copies of every phrase share one grid cell so the line never changes height. Under reduced motion the script does nothing and the caret (`typing-caret`, a block sized in `em` and colored with a token utility such as `bg-text`) is hidden.

The `current:` variant styles the link to the page being shown (`aria-current="page"`), such as the active navigation item, and `current-item:` the item a list points at (`aria-current="true"`), such as the selected thread in the review viewer; use them instead of an arbitrary `aria-[...]` variant.

Whole cards and rows take a press anywhere on them without nesting controls (the stretched-link pattern): a radio card's label has an `::after` over the card (the input stays above it, so a press on the radio itself still reaches it), and a `TableRow` with `linked` is positioned so the link with `rowLinkClasses` covers the row, while controls in the row take `rowControlClasses` to stay above it. The link stays a real link for the keyboard, a middle click and "open in new tab", and the accessible names do not change. `Table` with `stacked` turns each row into a stack of its cells below `sm` (cells take `label`, shown only to the eye, and `stack`: `full`, `inline` or `end`) and keeps explicit table roles, because some browsers drop a table's semantics when its display changes. The `input-focus` variant draws the focus ring around a field box whose input has keyboard focus, and `search-plain` hides the browser's own clear button of a search input.

Pattern utilities (`selection-band`, `bg-dot-grid`, `bg-hatch`, `bg-highlight` for a selection-style text highlight on `mark`, `marker-none` for custom `summary` disclosures, `progress-bar` for the native `progress` element, `meter-bar` for the native `meter` and `typing-caret`) and the `shadow-sm`, `shadow-raised` and `shadow-float` elevations are defined there too. Visually hidden text inside a scrolling region needs a positioned ancestor, or its absolute box widens the page; `Table` is `relative` for that reason. Tailwind's default shadows are removed.

The base layer gives every enabled `button`, `[role="button"]`, `[role="tab"]`, `[role="option"]`, `summary` and `label[for]` the pointer cursor, which Tailwind v4 preflight no longer sets. Do not add `cursor-pointer` to those elements in apps.

Brand and client icons, such as the supported-agents strip on the landing page, are inline SVG with `fill="currentColor"`, so they take a token text color and never show brand colors.

## Landing page

The landing page (`apps/web/index.html`) shows the product as it is, never as a drawing. Product screens (the hero's viewer, the review section's viewer and the dashboard tab's artifact list) are screenshots of the real app, and terminal and agent-session blocks are text with the real output. `bun run landing:shots` makes both: it starts the e2e stack, publishes and shares made-up example artifacts with the real CLI (signed in through the device page), has example reviewers comment in the real viewer, captures each screen in light and dark at 2x and writes WebP files at 1x and 2x into `apps/web/src/assets/landing/` (Vite hashes them under `/assets/`), and writes the CLI transcripts into `index.html` between `<!-- shots:<name> -->` and `<!-- /shots:<name> -->` markers, with the stack's hosts shown as `portifact.com` and `portifact.dev`. The script is `e2e/shots/landing.shots.ts`, its example content `e2e/shots/demo.ts`. Re-run it in the same change as any visible change to the viewer, the dashboard's artifact list, the CLI output of `publish`, `access` or `annotations export`, or the MCP tool results, and review the images before committing them. The copy around them (captions, `alt` and `aria-label` text) describes what they show and never calls them "real"; that is a rule for building the page, not a claim to make on it. The hero's primary action is "Sign in" to `app.portifact.com`; installing stays in the top bar, the install section and the closing call to action. The page is prerendered in every language from `index.html` ("Languages" above): every visible text, `alt` and `aria-label` carries a marker, while the transcripts between the shots markers, commands and the agent prompt stay English, so `landing:shots` keeps writing only `index.html`.

Each screenshot is a `<picture>` with a `prefers-color-scheme: dark` source (which follows the chosen theme too; see "Theming"), `srcset` with the 1x and 2x widths and `sizes`, explicit `width` and `height` (the screenshot's size in CSS pixels, `SHOTS` in the script), `decoding="async"`, `loading="lazy"` except the hero's (`fetchpriority="high"`), and an `alt` that describes what the image shows; `apps/web/src/landing.test.ts` checks all of it against the files' real dimensions. Terminal blocks stay `role="img"` with an `aria-label` that summarizes the output. Diagrams that are not product UI (access circles, lifecycle timeline, the origin wall) stay drawn in HTML; keep their facts in line with `LIMITS` and the product.

## Writing style

- Titles and headings (page titles, headings, buttons, labels, taglines) never end with a period.
- Never use em dashes (the long dash). Use a comma, a colon, parentheses or two sentences instead. The design-system check rejects em dashes in UI code.

## Languages

Portifact's interface is in English, Spanish, Portuguese (Brazil), French, German, Russian, Japanese and Simplified Chinese. The languages are `LOCALES` in `packages/contracts/src/locales.ts` (`@portifact/contracts/locales`, free of imports so static pages can use it), each with its BCP 47 code, its own name and its direction. English is the source of every text and the fallback. The CLI, MCP tool text, agent skills, the legal texts, terminal transcripts and the operator's emails stay English, and so do, for now, the content Worker's short status pages on artifact origins (such as "Review ended. You can close this tab" in `apps/content/src/index.ts`); only its review tab banner is translated.

- Which language: on `app.portifact.com`, `?lang=` (the landing's links ask for the page's language, and the dashboard routes pass it on to the login page), then for a signed-in dashboard the account's `locale` (account settings, so other devices and future emails follow it), then the choice kept in this browser (`localStorage` key `portifact.locale`, read and written in `try`), then the browser's languages (`negotiateLocale` in `packages/domain/src/locale.ts`: exact tag, then the same language, so `es-MX` gets `es`), then English. Every page sets `lang` and `dir` on `html`. The static pages are decided by their URL: English at `/`, every other language under its prefix (`/es/`, `/es/terms`), with canonical and `hreflang` alternates; nothing redirects by language, and a visitor whose languages prefer another one sees a dismissible note linking to it (`src/locale-suggestion.ts`).
- Static pages are translated with markers on the English HTML: `data-i18n="key"` replaces the element's content and `data-i18n-alt`, `-aria-label`, `-title`, `-content` and `-placeholder` one attribute (`apps/web/src/i18n/markers.ts`). Mark the smallest element holding a whole sentence; wrap text that sits beside an icon in a `span`. Messages may hold inline markup copied from the English (same elements and links). `site-build.ts` renders the pages after Vite's build (and in the dev server, `/es/...`) and fails on any marker without a message; the auth pages apply the same markers at runtime. Legal pages translate only the chrome around `main` ([legal.md](legal.md)).
- Switchers: `LanguageSwitcher` (`@portifact/ui`, the design system's select with each language's own name marked with `lang`) in Settings ("Language", saved to the account) and above the account in the sidebar; the static pages and the auth pages draw `languageLinksHtml` (`@portifact/ui/language-links`), links to the same page in each language, a `details` menu in the top bar and a row in the footer.
- Dates, numbers, plurals and relative times go through `Intl` with the active language (`useFormatDate`, `useFormatNumber`, Lingui's ICU plurals; `pluralForm` and `formatExpiry` in the emails); never format them by hand. ICU plurals keep every case English has and add the language's own (`few` and `many` in Russian).
- Fonts: no web fonts. Chinese and Japanese pages get their system fonts after the Latin ones (`:root:lang(ja)` and `:root:lang(zh-CN)` in `packages/ui/src/tokens/tokens.css`, `fontSans` in `packages/emails/src/theme.ts`), each language's own first, since the same characters take different forms in each.
- Longer languages: German, French, Russian and Portuguese run up to half again as long as English. Buttons (`buttonClasses`) keep their label on one line while it fits and wrap it inside the button when it does not, and action rows wrap; wide tables scroll inside a focusable region. `i18n.spec.ts` checks that no page scrolls sideways at 320 px in German, Russian and Japanese.
- Tests keep the catalogs whole: `dashboard/i18n/catalog.test.ts` (same keys, arguments and plural or select cases, valid ICU, no dashes), `auth/i18n/catalog.test.ts`, `i18n/site.test.ts` (every marker of every page translated, same markup and links, legal text untouched) and the email tests.

To add a language:

1. Add its entry to `LOCALES` (code, own name, direction). The typecheck then lists every catalog and loader that is missing.
2. Add `apps/web/src/dashboard/i18n/<code>.ts` (`satisfies Catalog`) and its loader in `CATALOG_LOADERS`.
3. Add `apps/web/src/auth/i18n/<code>.ts` and its loader in `auth/i18n/i18n.ts`.
4. Add `apps/web/src/i18n/site/<code>.ts` with the chrome and every page marker, and register it in `site/catalogs.ts`. The build then emits `/<code>/` pages and `apps/app/src/site.ts` serves the documents under the prefix.
5. Add the language to `LANDING_MESSAGES`, to each email template's text (`TEXT`, `EXPIRY_TEXT`) and to `BANNER_TEXT`. Catalog files use the lowercase code as their name (`pt-br.ts`, `site/pt-br/`) and a camel-case identifier (`ptBR`), and the URL prefix is the lowercase code (`/pt-br/`, `/zh-cn/`).

## Brand assets

The logo is the "selection" wordmark: the name `portifact` held between two text-selection handles over a light band. Source files live in `assets/brand/`:

- `wordmark.svg` for light backgrounds and `wordmark-dark.svg` for dark ones, with PNG renders.
- `symbol.svg` and `symbol-dark.svg`: the lowercase p between the handles, for app icons and avatars.
- `favicon-16.svg` and `favicon-32.svg` are redrawn by hand for those sizes and switch to dark colors with `prefers-color-scheme`. Serve the SVG favicon first and `favicon.ico` (16, 32 and 48 px) as the fallback.

Use the files as they are: do not recolor, stretch, add effects or rebuild the logo from a font. Pick the light or dark variant by background, and keep clear space around the logo of at least the height of the band. The only colors are `#000000`, `#FFFFFF`, `#DEDEDE` (band on light) and `#3A3A3A` (band on dark).

## Rules

- Apps never declare their own colors, font sizes, spacing values, radii or shadows. Use tokens through components or token-based utilities.
- No raw hex, `rgb()` or `hsl()` values, and no arbitrary Tailwind values such as `p-[13px]` or `text-[#333]`, outside `packages/ui/src/tokens`.
- No inline `style` props for visual styling. Dynamic geometry, such as annotation highlight positions, is the only exception and must use token values for everything except coordinates.
- No per-screen CSS files. If a component needs custom CSS, it lives in `packages/ui` next to the component.
- Do not restyle a component from outside with overriding classes. Add or extend a variant in the design system.
- If something is missing, add the token, variant or component to `packages/ui` first, with its story and tests, then use it.
- Light and dark themes are both driven by semantic tokens, so a component never branches on the theme. Images with a light and a dark version are the one exception: use `ThemedImage` (see "Theming").

Emails are the one exception to the inline style rule: mail clients drop or rewrite stylesheets, so the templates in `packages/emails/src` write inline styles (`isEmailTemplate` in `packages/ui/src/design-check.ts` exempts them from that rule only). Their colors still come from the tokens (see "Emails" below), never raw values.

`bun run check` runs `scripts/check-design-system.ts` (rules in `packages/ui/src/design-check.ts`), which fails on arbitrary Tailwind values, inline `style` attributes, Tailwind's default palette and raw color values outside `packages/ui/src/tokens`. The Tailwind theme in `packages/ui/src/tokens/theme.css` removes the default palette, so only token colors exist as utilities. Do not disable it; if a rule blocks a legitimate case, change the rule in a separate, explained change.

## Auth pages

The login, device, consent and report pages (`apps/web/{login,device,consent,report}.html`, scripts in `apps/web/src/auth` and `src/report`) are static pages with small scripts, not React, so they load fast under the strict page CSP. They share one shell: a skip link, the wordmark, a faint `bg-dot-grid` band, one card (`bg-surface-raised`, `shadow-float`, `rounded-lg`, entering with `motion-safe:animate-rise`) on `bg-surface`, and the legal footer. Inside the card they use the design-system classes of the components they stand for: `buttonClasses` primary and secondary for buttons, the error `Callout` (2px border, icon, `role="alert"`, the message in its `[data-message]` child) for the error summary, the `TextInput` field classes, and bordered `divide-y` lists for details. Change the shared shell in all four pages together.

- The login card shows the sign-in notice above the methods (see [legal.md](legal.md)), then Google and GitHub with their monochrome marks, then the email form. The code step replaces the methods with "Check your email", a large one-time-code field, the expiry and a "Send a new code" link that counts down the Worker's one-minute limit. The human check sits below everything and shows its explanation only when Cloudflare asks for an interaction.
- A single invalid field moves focus to itself, with its error linked; the error summary is for failures of the request.
- Their text is translated with the markers of "Languages" above: every visible text and accessible name carries one, the scripts read their messages from `messages` (`src/auth/messages.ts`, replaced by the page's catalog before setup), and the footer holds the language links. A new text needs a marker or a message in every catalog.

## Emails

Every email is built by `packages/emails`: one layout (`layout.ts`) and a template per message (`sign-in-code.ts`, `budget-alert.ts`, `expiry-notice.ts`), each with an HTML version and a plain-text alternative. The HTML is table-based with inline styles so it renders the same in Gmail, Outlook and Apple Mail: a quiet page, the hosted wordmark (`https://portifact.com/brand/wordmark.png` and its dark variant, published from `assets/brand` by `apps/web/vite.config.ts`, with "Portifact" as the alternative text), one card and small print. Colors are the semantic tokens resolved to their values (`theme.ts`); a `prefers-color-scheme: dark` block repaints them for clients that honor it, and the light version is pure grays so the clients that invert it on their own keep it legible.

- Callers pass text; every value goes through `escapeHtml`. Never build email markup elsewhere.
- A code is one unbroken string, large and in a monospace font; the spacing between its digits is `letter-spacing`, so copying it copies only the digits. Codes never go in the subject or the preview text, which lock screens show.
- A template a user receives is written in their language: its texts are a `TEXT` record typed by the locale list and the layout takes the `lang`. The sign-in code follows the login page's language, which the page sends as `Accept-Language` (`emailLocale` in `apps/app/src/auth/email.ts`); emails not tied to a page should use the account's `locale` (`loadSettings`), falling back to English. The expiry notice follows the owner's `locale` (the jobs Worker passes it from `sendExpiryNotice`), English when they chose none; the budget alert goes to the operator and stays English.
- Names and other text people choose never go in a subject, and are collapsed to one line in the plain-text version so they cannot fake another entry (see `expiry-notice.ts`). Dates are shown in UTC and say so, with the weekday and a 24-hour clock, in the email's language (`formatExpiry`). Chinese and Japanese texts leave no space after their full-width punctuation (`gap`).
- `bun run --cwd packages/emails preview` writes every email (`src/previews.ts`) to `/tmp/portifact-email-previews` as `.html` and `.txt` for review; add a sample there with every new email.

## Forms

Forms use TanStack Form through a single form hook created with `createFormHook` in `packages/ui/src/forms`, imported as `@portifact/ui/forms`. `useAppForm` binds the design-system fields once (`TextField`, `TextAreaField`, `CheckboxField`, `RadioGroupField` and `SelectField` today; OTP as screens need it), plus `Form` and `SubmitButton`, so screens never wire inputs, labels, errors or ARIA attributes by hand. `Form` submits through TanStack Form and, when validation fails, focuses the first invalid control; `SubmitButton` is busy while the submit runs. Do not add another form library or build ad hoc field state with `useState`.

Validation applies the schemas from `packages/contracts` (for example `Email.safeParse`), so the client and the API apply the same rules, but the message comes from the screen's i18n catalog, because Zod's messages are not translated. Use `validationLogic: revalidateLogic()` with an `onDynamic` validator: nothing is flagged while the user types the first time, errors appear on submit and then clear as soon as the value is fixed.

## Catalog and tests

- Every component and pattern has a Storybook story covering its variants and states, including loading, empty, error and disabled. Storybook is not set up yet; until it is, each component's tests render every variant and state and check them with `axeViolations` from `@portifact/ui/testing`.

- Visual changes to tokens are reviewed in Storybook in both themes.

## Artifact-origin viewers

The Markdown and TXT viewers and the bridge run on `portifact.dev` and ship in their own small bundles. They import tokens and the few components they need from `packages/ui`, so they stay consistent with the dashboard without loading the full dashboard bundle. They must not depend on anything served from `portifact.com`.

The bridge's overlay (the thread highlights, the element-mode outline and its hint) lives in a closed shadow root and is styled by a constructed stylesheet built from `TOKENS_CSS` with `:root` rewritten to `:host`, so a page's CSP does not block it and the page's styles do not reach it. Positions are set through CSSOM properties, the dynamic-geometry exception above. Its visible text comes from the viewer's i18n catalog through the bridge messages.

Published Markdown and TXT documents end with the viewer chrome: a `footer.pf-chrome` outside `main` with the "Report this artifact" link to `/__portifact/report`, styled by `DOCUMENT_CSS` with tokens only. The editor's preview renders without it (`reportLink` off). The Markdown and TXT documents rendered by `packages/render` load no bundle at all, except the diagram script of a Markdown document with Mermaid blocks: they inline `TOKENS_CSS` (`@portifact/ui/tokens-css`) and `DOCUMENT_CSS` (`@portifact/ui/document-css`) in one `<style>`. `DOCUMENT_CSS` uses only `var(--pf-*)` tokens, including the type scale, spacing, measure and border widths in `tokens.css` that exist for surfaces styled without Tailwind. `tokens-css.ts` is generated from `tokens.css`: after editing the tokens, run `bun run --cwd packages/ui sync-tokens`, or the drift test fails.

Highlighted code in Markdown documents (`pf-tok-*` spans, written at commit) is monochrome like the rest of the product: keywords, literals and markup names bold, types and built-ins italic, strings and metadata in the muted grey, comments muted and italic, additions bold and deletions struck through; everything else is plain text. No hue, in either scheme, and only the `color-text` and `color-text-muted` tokens, so the code keeps the contrast the token tests require on `surface`. Mermaid diagrams are drawn by the diagram script with Mermaid's `base` theme painted from the tokens at runtime (canvas, surface, text, muted text and strong border, read from the root's custom properties), so they are greyscale and follow the light and dark schemes, redrawn when the scheme or the root's `data-theme` changes. Authors may still color their own diagrams: published content keeps its colors. A drawing sits in a hairline-bordered `figure.pf-diagram` on `canvas` with the "Diagram source" disclosure under it (a quiet underlined button with `aria-expanded`), which unfolds the source block below; without the script, readers see the source as code. The editor's preview shows the source too ("Untrusted content" in [security.md](security.md)).
