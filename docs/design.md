# Design system

All Portifact UI comes from one design system in `packages/ui`. This covers the dashboard, the viewer with the Portifact bar, the Markdown and TXT viewers served on artifact origins, and any visible part of the annotation bridge. The goal is a consistent product and a single place to change how it looks. Styles scattered across apps are not allowed.

## Layers

1. **Tokens.** Every visual value lives here: color, typography, spacing, sizing, radii, borders, shadows, z-index, motion and breakpoints. Tokens are CSS custom properties exposed through the Tailwind CSS v4 theme in `packages/ui/src/tokens`. Two levels:
   - Primitive tokens hold raw values, for example the color scale.
   - Semantic tokens describe intent, for example `--color-surface`, `--color-text-muted`, `--color-danger` and `--space-4`. Components and apps use semantic tokens only. Color tokens resolve to the neutral palette described below.
2. **Components.** Accessible React building blocks owned in `packages/ui/src/components` and exported from `@portifact/ui`: button (`primary`, `secondary`, `ghost`, `link`, `floating`, the inverse control that floats over content, such as the viewer's "Comment" next to a selection, and `field`, which looks like an empty field and opens a form in place, such as a thread's reply box; `secondary` shows `aria-pressed` for toggles, and `count` adds a count badge with words for screen readers), icon button and icon link (square, named by `label`, which their tooltip shows), tooltip (hover and keyboard focus, hoverable, Escape hides it, hidden from assistive technology because it repeats the control's name), menu (the ARIA menu button pattern, with actions or links), avatar (a person's initial, decorative), badge (`normal`, `strong`, `quiet` and `subtle`), callout (`info`, `success` and `error`), confirm dialog (with a `danger` tone), copy field (with a `compact` one-row layout for bars and captions), detail list (`split` or `stacked`, framed or not), disclosure (a native `details`), drop zone, empty state, loading state (with skeleton rows), live region, meter, panel, steps, table (`framed` or `flush`), toast, text input, text area (with `compact` for short notes), search field (a compact toolbar box with its icon, visible label and a clear button that gives focus back to the input), select (one choice among many, `field` or the `compact` chip for toolbars, see below), checkbox, radio group (`stack` or `row`, each option a card that takes a press anywhere on it), sheet (a native modal `dialog` that rises from the bottom on phones and is centered on wider screens), file picker (with `canPickFolders`), progress bar and preview frame today, plus the `useMediaQuery` hook (`WIDE_QUERY` is the `sm` breakpoint); tabs as screens need them. Prefer a native element when it gives the behavior (the confirm dialog is a native `dialog` with `showModal()`), and use Radix UI primitives where none does, but not ones that inject inline `<style>` elements (such as Radix's scroll lock), which the strict page CSP refuses. The select is drawn by the design system, not the browser (`components/select.tsx`), following the WAI-ARIA select-only combobox pattern: a `button` with `role="combobox"` and a chevron keeps focus and points at the active option with `aria-activedescendant`; the listbox floats with `shadow-float`, rendered at the end of the landmark or modal dialog that holds the trigger and placed in the window with fixed coordinates through the CSSOM (`placeListbox`: under the trigger, above it when there is more room, never off screen); the chosen option sits on the selection color in bold with a check. Keys work like a native select: arrows, Home, End, Page Up and Down, typeahead (`typeaheadMatch`, a repeated letter cycles), Enter, Space, Alt+Up, Escape and Tab (which keeps the highlighted option); the highlight is outlined with the focus ring only while the keyboard moves it. The `compact` variant shows its label inside the chip before the value, and `active` (a filter that is on) gives it a solid strong border and a bold value. Variants such as size, tone and state are part of the component API, defined with `class-variance-authority`. Icons are Lucide, decorative and `aria-hidden`; the label carries the meaning.
3. **Patterns.** Compositions reused across screens, such as page layout, data table with filters, upload progress and annotation thread, in `packages/ui/src/patterns`. `AppShell` (skip link, a banner that is a fixed sidebar on wide screens and a bar on narrow ones, labelled navigation, an optional `aside`, the account rendered once, and the focusable `main` on the backdrop) `PageHeader` (the screen's single `h1`, with an optional `back` link, `meta` badges, description and actions) and `ViewerShell` (the viewer's Portifact bar with the artifact's name and version as plain text after the mark, `actions` and `account` from `sm`, the `toggle` at every width and an `overflow` menu below `sm`; the artifact in a bordered panel; and the comments sidebar, which sits beside the artifact from `lg` and covers it below, with a close button) and `SectionedPage` with `PageSection` (a long screen grouped by task: an in-page navigation, a sticky column on wide screens and a wrapping row on narrow ones, whose current link is a selection band with `aria-current`, beside `h2` sections that hold `headingLevel={3}` panels; `tone="danger"` puts a dashed rule above the destructive section) and `FrameOverlay` with `Floating` and `FloatingPanel` (a layer over a frame, clipped to its box, for controls the page draws next to something in the frame: placed by coordinates set through the CSSOM, the dynamic-geometry exception, or a bottom sheet kept above the on-screen keyboard through the visual viewport, `keyboardInset`) exist today.
4. **Apps.** Screens compose components and patterns. They only arrange layout using tokens.

## Visual direction

Portifact is a publishing and review tool for developers and their agents. The look is a quiet, precise workbench: dense enough to scan many artifacts, calm enough to read comments, and monochrome like the brand. One element carries the personality, taken from the logo: **the selection**, a light band held between two text-selection handles.

- **Selection band.** `selection-band` (in `theme.css`) draws the band (`--pf-color-selection`) with a handle at each end (a bar with a knob on top at the start and one with a knob below at the end, sized by `--pf-handle-width` and `--pf-handle-knob`). It means "selected or current" and nothing else: the current page in the navigation (`current:selection-band`), the chosen radio option (`has-checked:selection-band`), the chosen option of a select (the selection color with a check), the in-page section being read (`current-item:selection-band`), the current step of a flow (`aria-current="step"`) and a drop zone while files are dragged over it. Never use it as decoration, and always pair it with weight, a check or `aria-current`, so it never relies on its tone.
- **Depth.** Screens sit on `backdrop`; sections are panels on `canvas` with a hairline `border` and `shadow-sm`; subtle fills (table heads, cards inside panels, code values) use `surface`; hover uses `surface-hover`; menus, toasts and dialogs float with `shadow-raised` or `shadow-float`. Dark mode keeps the same order with lighter surfaces on a near-black backdrop, and borders carry the depth where shadows do not show.
- **Radii by role.** `xs` for badges and navigation items, `sm` for controls (buttons, inputs, radio options), `md` for callouts and nested cards, `lg` for panels, tables, empty states and dialogs.
- **Typography.** The system UI stack, so the dashboard loads no font files (a self-hosted typeface needs a license review first: the usual open fonts are OFL-1.1, which `AGPL_COMPATIBLE` does not list). Hierarchy comes from size and weight: page titles `text-2xl`/`sm:text-3xl` semibold with tight tracking, panel titles `text-base` semibold, body and controls `text-sm`, terms and captions `text-xs` muted. Numbers in tables, meters and dates use `tabular-nums`. Monospace is only for things people copy or type: URLs, IDs, paths and commands.
- **Density.** Controls are `h-10` (`h-8` small); table cells `py-3.5`; panels `p-5`; screens stack panels with `gap-6`. The main column is at most `max-w-7xl`.
- **Motion.** Only motion that answers an action: `animate-pop` when a toast or dialog appears, `animate-shimmer` for loading placeholders and busy button icons, 150 ms color transitions on hover. All of it is `motion-safe:` and nothing moves under reduced motion.
- **States.** Never tone alone: `strong` badges are solid inverse (suspended, purging), `quiet` ones dashed (archived, draft), access modes are `subtle` badges with a lock, people or globe icon, meters turn hatched near the limit and say "Near the limit" or "Limit reached", and errors are callouts with a thick handle on the left edge.

## Palette

Portifact is monochromatic. The whole product, including the logo, dashboard, viewer, Markdown and TXT viewers, CLI output, documentation and emails, uses only black, white and a neutral gray scale with zero saturation. No hue appears anywhere, including accents, links, focus rings, charts and status states.

- The primitive scale is a single neutral ramp from white to black, defined once in `packages/ui/src/tokens`. Semantic tokens map onto it for light and dark themes.
- Hierarchy comes from contrast, weight, size and spacing, not from color.
- Links are distinguished by an underline, not by color.
- States (danger, warning, success, info) are semantic tokens like any other, but they map to neutral values. They are always conveyed by an icon, a text label and, where useful, weight or border style. A state is never shown through tone alone; see [accessibility.md](accessibility.md).
- Annotation highlights and selection in the viewer use neutral tints that keep the underlying text at the required contrast.
- Content published by users keeps its own colors. The rule applies to everything Portifact draws around it, such as the bridge highlights and viewer chrome.

Exception: third-party status badges in the readme (release, license, CI, coverage) keep their conventional colors, because their color carries meaning readers already know.

Adding any other hue requires changing this section first, in a separate change with a reason.

Semantic surfaces: `backdrop` (behind panels), `canvas` (panels, inputs and published documents), `surface` (subtle fills), `surface-raised`, `surface-hover` and `surface-inverse`. The token tests require body text at 7:1 and muted text at 4.5:1 on every surface and on the selection band, in both themes.

The `terminal`, `terminal-text`, `terminal-muted` and `terminal-border` tokens draw terminal and agent-session mocks, and dark bands such as the landing page's security section. They stay dark in both themes, so use them only where a dark surface is the point.

## Motion and patterns

Motion tokens and utilities live in `packages/ui/src/tokens/theme.css`: `animate-rise`, `animate-fade`, `animate-type`, `animate-sweep`, `animate-blink`, `animate-pop` and `animate-shimmer`, staggered with `animate-delay-<n>`. Always apply them through the `motion-safe:` variant, so nothing moves under `prefers-reduced-motion` and every element rests in its final state. Motion is decorative only; it never carries information.

The landing hero types its second line with `apps/web/src/typewriter.ts`: one pass through the phrases, then it settles on the first and the caret fades, so nothing keeps moving. The `h1` keeps a visually hidden, complete sentence for assistive technology and marks the animated part `aria-hidden`; invisible copies of every phrase share one grid cell so the line never changes height. Under reduced motion the script does nothing and the caret (`typing-caret`, a block sized in `em` and colored with a token utility such as `bg-text`) is hidden.

The `current:` variant styles the link to the page being shown (`aria-current="page"`), such as the active navigation item, and `current-item:` the item a list points at (`aria-current="true"`), such as the selected thread in the review viewer; use them instead of an arbitrary `aria-[...]` variant.

Whole cards and rows take a press anywhere on them without nesting controls (the stretched-link pattern): a radio card's label has an `::after` over the card (the input stays above it, so a press on the radio itself still reaches it), and a `TableRow` with `linked` is positioned so the link with `rowLinkClasses` covers the row, while controls in the row take `rowControlClasses` to stay above it. The link stays a real link for the keyboard, a middle click and "open in new tab", and the accessible names do not change. `Table` with `stacked` turns each row into a stack of its cells below `sm` (cells take `label`, shown only to the eye, and `stack`: `full`, `inline` or `end`) and keeps explicit table roles, because some browsers drop a table's semantics when its display changes. The `input-focus` variant draws the focus ring around a field box whose input has keyboard focus, and `search-plain` hides the browser's own clear button of a search input.

Pattern utilities (`selection-band`, `bg-dot-grid`, `bg-hatch`, `bg-highlight` for a selection-style text highlight on `mark`, `marker-none` for custom `summary` disclosures, `progress-bar` for the native `progress` element, `meter-bar` for the native `meter` and `typing-caret`) and the `shadow-sm`, `shadow-raised` and `shadow-float` elevations are defined there too. Visually hidden text inside a scrolling region needs a positioned ancestor, or its absolute box widens the page; `Table` is `relative` for that reason. Tailwind's default shadows are removed.

The base layer gives every enabled `button`, `[role="button"]`, `[role="tab"]`, `[role="option"]`, `summary` and `label[for]` the pointer cursor, which Tailwind v4 preflight no longer sets. Do not add `cursor-pointer` to those elements in apps.

Brand and client icons, such as the supported-agents strip on the landing page, are inline SVG with `fill="currentColor"`, so they take a token text color and never show brand colors.

## Writing style

- Titles and headings (page titles, headings, buttons, labels, taglines) never end with a period.
- Never use em dashes (the long dash). Use a comma, a colon, parentheses or two sentences instead. The design-system check rejects em dashes in UI code.

## Brand assets

The logo is the "selection" wordmark: the name `portifact` held between two text-selection handles over a light band. Source files live in `assets/brand/`:

- `wordmark.svg` for light backgrounds and `wordmark-dark.svg` for dark ones, with PNG renders.
- `symbol.svg` and `symbol-dark.svg`: the lowercase p between the handles, for app icons and avatars.
- `favicon-16.svg` and `favicon-32.svg` are redrawn by hand for those sizes and switch to dark colors with `prefers-color-scheme`. Serve the SVG favicon first and `favicon.ico` (16, 32 and 48 px) as the fallback.

Use the files as they are: do not recolor, stretch, add effects or rebuild the logo from a font. Pick the light or dark variant by background, and keep clear space around the logo of at least the height of the band. The only colors are `#000000`, `#FFFFFF`, `#DEDEDE` (band on light) and `#3A3A3A` (band on dark).

## Rules

- Apps never declare their own colors, font sizes, spacing values, radii or shadows. Use tokens through components or token-based utilities.
- No raw hex, `rgb()` or `hsl()` values, and no arbitrary Tailwind values such as `p-[13px]` or `text-[#333]`, outside `packages/ui/src/tokens`.
- No inline `style` props for visual styling. Dynamic geometry, such as annotation highlight positions, is the only exception and must use token values for everything except coordinates.
- No per-screen CSS files. If a component needs custom CSS, it lives in `packages/ui` next to the component.
- Do not restyle a component from outside with overriding classes. Add or extend a variant in the design system.
- If something is missing, add the token, variant or component to `packages/ui` first, with its story and tests, then use it.
- Light and dark themes are both driven by semantic tokens, so a component never branches on the theme.

Emails are the one exception to the inline style rule: mail clients drop or rewrite stylesheets, so the templates in `packages/emails/src` write inline styles (`isEmailTemplate` in `packages/ui/src/design-check.ts` exempts them from that rule only). Their colors still come from the tokens (see "Emails" below), never raw values.

`bun run check` runs `scripts/check-design-system.ts` (rules in `packages/ui/src/design-check.ts`), which fails on arbitrary Tailwind values, inline `style` attributes, Tailwind's default palette and raw color values outside `packages/ui/src/tokens`. The Tailwind theme in `packages/ui/src/tokens/theme.css` removes the default palette, so only token colors exist as utilities. Do not disable it; if a rule blocks a legitimate case, change the rule in a separate, explained change.

## Dashboard

The dashboard is a React 19 single-page app in `apps/web/src/dashboard`, built by Vite as `dashboard.html` and served by the `portifact-app` Worker at its client routes on `app.portifact.com`. TanStack Router defines the routes in `router.tsx` (keep them in sync with `DASHBOARD_ROUTES` in `apps/app/src/app-host.ts`; the Worker serves the dashboard with `dashboardCsp`, which adds the storage endpoint to `connect-src` and the rendered documents' stylesheet hash to `style-src`) and TanStack Query loads data through `api.ts`, which validates every response with `packages/contracts`. Screens read the API client and navigation out of the app through `DashboardContext`, so tests pass fakes.

- The shell is `AppShell` with Artifacts, Publish and Account in the navigation (Artifacts stays current on artifact pages and the review viewer). Every screen opens with `PageHeader` (back link, title, state and access badges, primary actions on the right) and stacks `Panel`s; a loading screen shows `LoadingState` with skeleton rows in the shape of what is coming.
- Results of actions appear in the shell's `Toast`, which is also its polite live region: the text stays in the region after the toast hides, and hovering or focusing it keeps it open. Errors stay inline as alert callouts, never only in a toast.
- Every user-facing string goes through Lingui: add it to `i18n/en.ts` (ICU MessageFormat) and read it with `useT()`. Message IDs are typed, so a missing key fails the typecheck. Dates go through `useFormatDate()`.
- Lists and details refresh at most every 30 seconds while the tab is visible, pause in the background and back off after errors (`refresh.ts`, plan section 2). A failed refresh keeps the last data and says so.
- After a client-side navigation, focus moves to `main`, and each screen sets the document title with `useDocumentTitle`. Results of actions are announced through the shell's live region with `useAnnounce()`; errors use an alert callout.
- Destructive actions, such as deleting an artifact, open a `ConfirmDialog` first. So do actions that end something elsewhere: signing out other sessions and disconnecting an app.
- The empty artifact list is the first-publish guide (`FirstPublish`): the browser upload, the CLI install and publish commands and the MCP server URL (`<app origin>/mcp`), each in a `CopyField`; copying is announced through the toast.
- Each row of the artifact list shows a type icon, the name with its type and ID, state and access badges, and quick actions (open the published page, review) while the artifact is active; their accessible names include the artifact's name. The whole row opens the artifact page (a `linked` row) and the quick actions stay above it. Below `sm` the table is `stacked`: each artifact is a card of its name, badges, expiry, size and activity, with the actions at the end, and nothing scrolls sideways.
- Phones get layouts of their own, not squeezed desktop ones: tables that would scroll are `stacked`, panel actions wrap under the panel title, and controls that do not fit move into a `Sheet`. Check every screen at 375 px wide.
- The artifact list (`/`, `screens/artifact-list.tsx`) has a search and filter toolbar, not a form panel: a `SearchField` (applied on Enter, its clear button ends the search) and four `compact` selects (state, type, access and comments, "Any" by default) that apply as soon as they change, with "Clear filters" only while something is on. Below `sm` (`useMediaQuery(WIDE_QUERY)`, so one set of controls exists at a time) the search stays in the toolbar and the selects move into a `Sheet` opened by "Filters", which shows how many are on. The API applies them (`ArtifactListQuery`), so they cover every page, and they live in the URL search (`parseListSearch`, the route's `validateSearch`), so they survive going to an artifact and back and can be shared. The router keeps search keys a route does not validate, so the screen parses the search again before using it. A search changes only the URL search, so focus stays in the form; the last results stay on screen while new ones load (`keepPreviousData`), and the count is a status message. The form is hidden while the account has no artifacts. Each row also shows the artifact's activity from the list response (`activity`): the current version's size and the retained versions, the last update, the open threads on the current version (while comments are on, or when some are still open) and when a thread last changed. Traffic is counted per account (`traffic_counters`), so the list says so under the table and links to the usage section instead of inventing a per-artifact figure.
- The artifact page leads with its name, state and access badges, "Publish a new version" and "Review and comment" (a full page load to the viewer) in the header, and its link in a `CopyField` (copy, open). Below, a `SectionedPage` ("Artifact sections") groups it by task: Overview (details, with "Renew for 30 days" or "Restore" beside the dates, and content: history, edit), Sharing (access, the people added, link settings), Comments (comment settings), Activity (who opened it) and Danger zone (archive, delete) at the end. Each settings group is its own form with its own save button and an "Unsaved changes" note, so nothing is saved far from what it saves. Destructive confirmations use the dialog's `danger` tone.
- The artifact page's settings live in `screens/access-settings.tsx`: "Access" (the three modes as a radio group, each with who it lets in, saved with "Save access"), "People you added" (add, remove and, beside each person, a `Select` with a visually hidden label ("Comments <email> sees") for their exception, sent as soon as it changes; its default option names the artifact's setting; rows stack on phones), "Link settings" (the Portifact bar, indexing and embedding, saved with "Save link settings") and "Comment settings" (whether comments are open, locked or off, through the annotations mode endpoint, and "Who sees comments", with what each choice shows readers, saved together with "Save comment settings"). Widening (the artifact to everyone, or a reader to all comments) first opens a `ConfirmDialog` saying comments already written become visible; narrowing applies at once. The reply box of a thread the owner started says every reader who sees the comments sees the reply. The viewer's composer says who can read a new comment: everyone for the owner, the owner (who chooses who else) for a reader. It states that republishing never widens access. It explains the API's refusals in the terms of the rule (account too new for public, with the date from the session's `createdAt`; the 500-reader cap; a `version_conflict`, after which it reloads the policy). Public is disabled while the account is in its first 15 minutes, unless the artifact is already public, so narrowing stays possible. The access query does not refresh on a timer, so a refresh never discards unsaved choices; it loads again when the artifact's access mode (which does refresh) stops matching it, because access changed elsewhere, such as from the CLI, and each group restarts from the server's values only when they change.
- The artifact page's "Who opened it" section (`screens/access-log.tsx`) lists the access log page by page with "Show more". "Export as CSV" and "Export as JSON" (`access-log-export.ts`) read the whole log again, following the API's cursor at the largest page size, and save it through `DashboardEnv.save`, so an export never depends on how many pages are on screen. The JSON is what `portifact logs --json` prints; the CSV has an `openedAt,email` header, CRLF line ends and RFC 4180 quoting, and any cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading apostrophe inside quotes so a spreadsheet never runs it as a formula (visitor emails are untrusted text). The buttons are hidden while the log is empty.
- Publishing shows its steps (Choose, Review, Publish) with `Steps`, and the sources sit in a `DropZone`: dropped folders are walked through the entries API (`readDrop`) and keep their paths, one dropped ZIP is read as an archive, and the pickers inside remain the keyboard path. The result shows the link in a `CopyField` with the artifact page, review and "Publish something else".
- Publishing (`/publish` for a new artifact, `/artifacts/<id>/publish` for a new version, `screens/publish.tsx`) runs in steps: choose the type and a source (files, a folder where the browser can pick one, a ZIP, which is the only option where it cannot, or a Markdown or text file or pasted text), review the manifest, what was left out and who will be able to open the result, then upload with a progress bar, cancel and resume. Nothing reaches the API before the review. The manifest is built by `publish/manifest.ts` inside a Web Worker (`publish/worker.ts`, wrapped by `publish/builder.ts`); hashing and ZIP expansion are incremental, and the API revalidates everything. Uploads (`publish/upload.ts`) go straight to storage through `publish/transport.ts`; errors are explained in the terms of the rule that refused them (`publish/failures.ts`), and resume is offered only when a retry can help. A new version is published on the artifact's current version, so a publish made elsewhere meanwhile is a conflict, never an overwrite.
- The document editor (`/artifacts/<id>/edit`, `screens/document-editor.tsx`) loads the current source through a download link, checks it against the manifest, and saves by publishing a new version on that one in which only the text changes; assets and sources keep their stored objects. Its preview is the server's rendering (`POST /api/v1/documents/preview`) shown in `PreviewFrame`; never render user markup in the dashboard's own document.
- The history (`/artifacts/<id>/history`, `screens/history.tsx`) lists the retained versions, downloads published files or sources (checked against the manifest and packaged as a ZIP in the page when there are several, `publish/download.ts`), and rolls back after a confirmation. While the artifact is archived it shows the purge date with restore and delete. "Conversations on earlier versions" (`screens/earlier-conversations.tsx`) loads every version's threads (`version=all`, the viewer's query for that filter) and shows those of versions that are no longer current, read-only, one `Disclosure` per version (newest first, numbered within the version); threads of versions that are no longer listed (pruned, or older than the loaded pages) share one group. Thread pieces shared with the viewer (target summary, message content) live in `review/thread-parts.tsx`.
- `DashboardEnv` also carries the manifest builder, the storage transport and `save` (hands a file to the user), so tests pass in-process and fake versions.
- The viewer (`/view/<id>`, `screens/viewer.tsx`) is where a top-level visit to an artifact's page lands ("The viewer" in [security.md](security.md)), and the artifact page links to it ("Review and comment", a full page load, like the viewer's links back, so each page keeps its own policy). It is a route of the dashboard SPA outside the shell (`Frame` in `router.tsx`), served with or without a session, and draws `ViewerShell` in the visual direction above: the page on `backdrop`, a slim bar on `canvas` with `shadow-sm` (symbol, a hairline divider, the artifact's name as the page's `h1` in plain `text-sm` normal weight, truncated with its full text in `title`, and the version badge; then icon buttons with tooltips: "Copy link", which copies the artifact's own link and says so in the toast, or shows the link there when the browser refuses the clipboard, and "Manage" for the owner or "Report this artifact" for everyone else; the "Comments" toggle (`aria-pressed`) with the count of open threads on the current version; and after a divider "Your artifacts" and "Your account" (the account's initial in an `Avatar`), or a primary "Sign in". Below `sm` the bar keeps the mark, the name, the toggle (its label visually hidden, the count shown) and one "More" menu with the rest), the artifact frame in a panel with a strong border, so its content never reads as part of the bar (no caption row: the maintainer removed it on 2026-11-09, "The viewer" in [security.md](security.md)), and the comments sidebar, open by default on wide screens and closed on narrow ones, where it covers the artifact instead of squeezing it. It reads `?path=` and the fragment once, through `viewerPath` and `viewerHash`, and opens the frame there. Anonymous visitors of a public artifact get the page itself in the frame and a sidebar with "Sign in to comment" (hidden while comments are off); signed-in visitors get the review session described next. The viewer provides its own announcement context and reports results with the `Toast`. In the sidebar, threads are cards (`review/thread-card.tsx`) on `canvas`: a header with the thread's number in a small chip (the `selection-band` on the current thread), the quote kept to two lines, the state badges, and icon buttons for "Show in the artifact" and resolve or reopen, plus a "More actions" menu with "Delete thread" for the owner (after a `ConfirmDialog`); then the messages, each with the author's `Avatar`, name, a relative time (the full date in `title`) and a "More actions" menu (Edit for your own, Hide or Show again and Delete for the owner on other people's) shown on hover and focus, always on touch screens; then a `field` button "Reply" that opens the reply form in place (Escape cancels back to it). Clicking a card (outside its controls) selects it and shows it in the artifact; the selected card has a strong border and `shadow-raised`, others selected with it a strong border. Resolved threads are dashed cards on `surface`, folded to their header and a "Show the comments" link until opened or selected. "Filter and export" is a `Disclosure`, closed by default, whose summary says when filters are on. The bridge draws no numbered markers: each thread's text gets a translucent highlight, layered so overlapping threads read darker ("Highlights and overlapping threads" in [anchors.md](anchors.md)). Clicking highlighted text selects every thread there: the sidebar opens, shows several in a group ("2 threads on the text you clicked", with "Show all threads") with the innermost or most recent first and emphasized, and says so in a polite live region without moving focus. Pointing at or focusing a thread outlines its text in the page. For signed-in visitors it shows the pinned version in a sandboxed iframe next to the comments sidebar: general comments ("Comment on the page" in the sidebar), inline comments on a selection, element mode for sites (a toggle button with `aria-pressed`), replies, editing your own messages, resolve and reopen, and the owner's moderation. Selecting text (or picking an element) shows a `floating` "Comment" button just below the selection's left edge (above it when there is no room), drawn in a `FrameOverlay` over the frame ("Inline comments" in [security.md](security.md)); activating it opens a `FloatingPanel` there with the quote kept to two lines, a compact "Comment" text area, Cancel and Save (Enter saves, Shift+Enter adds a line, Escape cancels), or a bottom sheet below 40rem or when it does not fit. The selection is announced in a polite live region, never in the toast. Your own visible messages on writable threads get "Edit" in their menu, an inline form with Save and Cancel that sends the revision it started from; a conflict says the message changed elsewhere, loads the latest text and lets the reader save again; edited messages show "Edited". Threads are numbered by creation and keep a visible state badge; a thread the page cannot locate shows "Without location", and one on another file shows its path. Thread numbers exist only in the sidebar. Readers get no sidebar while comments are off; the owner keeps it to turn them on. When review cannot run in the frame (cookie dropped, page silent, session ended, no code issued, a review session the viewer did not start, the frame no longer answering from the artifact, newer version), a callout says why and what still works, including "Open without the Portifact bar" (the artifact on its own origin, through `/__portifact/raw`). Refreshes are incremental with the API's cursor (`review/use-threads.ts`). A "Filter and export" section narrows the panel by status and author (over the loaded threads, keeping each thread's number) and, for the owner, by version: another version or all of them is its own query (`threadsQuery(artifactId, version)`), and threads of other versions show "Earlier version" and are never highlighted. Highlights follow the filters. Export downloads the file `portifact annotations export` writes, JSON or Markdown, for the chosen version and status (the author filter is the panel's alone), through `DashboardEnv.save`; the dashboard never renders the Markdown.
- The viewer's bar shows everyone but the owner a "Report this artifact" link to `/report?artifact=<id>`. A visitor's first comments on other people's artifacts need the human check, run like the login page's: when the thread list's `humanCheck` says so, every composer and reply form runs the Turnstile widget invisibly from the moment it opens (`review/human-check.tsx` over `auth/human-gate.ts`), shows it inside the form with calm copy only when Cloudflare asks for an interaction, and posts as soon as it is solved; an unexpected `human_verification_required` starts the check and retries once with a new idempotency key, and a second refusal is a calm status line, never an error callout. Owners are never asked. `DashboardEnv.humanCheck` provides the widget (`src/human-check/turnstile.ts`, shared with the login page), so tests pass a fake.
- The account screen has an in-page section navigation ("Account sections") beside its panels, and usage shows each quota as a `Meter`.
- The account screen (`/account`, `screens/account.tsx`) shows the email, the sign-in methods (`/api/auth/list-accounts`), the browser sessions with "Sign out other sessions" and the connected apps with "Disconnect" (`/api/v1/account/*`). App names come from OAuth clients, so they are untrusted text and only ever rendered as text.

## Auth pages

The login, device, consent and report pages (`apps/web/{login,device,consent,report}.html`, scripts in `apps/web/src/auth` and `src/report`) are static pages with small scripts, not React, so they load fast under the strict page CSP. They share one shell: a skip link, the wordmark, a faint `bg-dot-grid` band, one card (`bg-surface-raised`, `shadow-float`, `rounded-lg`, entering with `motion-safe:animate-rise`) on `bg-surface`, and the legal footer. Inside the card they use the design-system classes of the components they stand for: `buttonClasses` primary and secondary for buttons, the error `Callout` (2px border, icon, `role="alert"`, the message in its `[data-message]` child) for the error summary, the `TextInput` field classes, and bordered `divide-y` lists for details. Change the shared shell in all four pages together.

- The login card shows the sign-in notice above the methods (see [legal.md](legal.md)), then Google and GitHub with their monochrome marks, then the email form. The code step replaces the methods with "Check your email", a large one-time-code field, the expiry and a "Send a new code" link that counts down the Worker's one-minute limit. ## Emails

Every email is built by `packages/emails`: one layout (`layout.ts`) and a template per message (`sign-in-code.ts`, `budget-alert.ts`), each with an HTML version and a plain-text alternative. The HTML is table-based with inline styles so it renders the same in Gmail, Outlook and Apple Mail: a quiet page, the hosted wordmark (`https://portifact.com/brand/wordmark.png` and its dark variant, published from `assets/brand` by `apps/web/vite.config.ts`, with "Portifact" as the alternative text), one card and small print. Colors are the semantic tokens resolved to their values (`theme.ts`); a `prefers-color-scheme: dark` block repaints them for clients that honor it, and the light version is pure grays so the clients that invert it on their own keep it legible.

- Callers pass text; every value goes through `escapeHtml`. Never build email markup elsewhere.
- A code is one unbroken string, large and in a monospace font; the spacing between its digits is `letter-spacing`, so copying it copies only the digits. Codes never go in the subject or the preview text, which lock screens show.
- `bun run --cwd packages/emails preview` writes every email (`src/previews.ts`) to `/tmp/portifact-email-previews` as `.html` and `.txt` for review; add a sample there with every new email.

## Forms

Forms use TanStack Form through a single form hook created with `createFormHook` in `packages/ui/src/forms`, imported as `@portifact/ui/forms`. `useAppForm` binds the design-system fields once (`TextField`, `TextAreaField`, `CheckboxField`, `RadioGroupField` and `SelectField` today; OTP as screens need it), plus `Form` and `SubmitButton`, so screens never wire inputs, labels, errors or ARIA attributes by hand. `Form` submits through TanStack Form and, when validation fails, focuses the first invalid control; `SubmitButton` is busy while the submit runs. Do not add another form library or build ad hoc field state with `useState`.

Validation applies the schemas from `packages/contracts` (for example `Email.safeParse`), so the client and the API apply the same rules, but the message comes from the screen's i18n catalog, because Zod's messages are not translated. Use `validationLogic: revalidateLogic()` with an `onDynamic` validator: nothing is flagged while the user types the first time, errors appear on submit and then clear as soon as the value is fixed.

## Artifact-origin viewers

The Markdown and TXT viewers and the bridge run on `portifact.dev` and ship in their own small bundles. They import tokens and the few components they need from `packages/ui`, so they stay consistent with the dashboard without loading the full dashboard bundle. They must not depend on anything served from `portifact.com`.

The bridge's overlay (the thread highlights, the element-mode outline and its hint) lives in a closed shadow root and is styled by a constructed stylesheet built from `TOKENS_CSS` with `:root` rewritten to `:host`, so a page's CSP does not block it and the page's styles do not reach it. Positions are set through CSSOM properties, the dynamic-geometry exception above. Its visible text comes from the viewer's i18n catalog through the bridge messages.

Published Markdown and TXT documents end with the viewer chrome: a `footer.pf-chrome` outside `main` with the "Report this artifact" link to `/__portifact/report`, styled by `DOCUMENT_CSS` with tokens only. The editor's preview renders without it (`reportLink` off). The Markdown and TXT documents rendered by `packages/render` load no bundle at all: they inline `TOKENS_CSS` (`@portifact/ui/tokens-css`) and `DOCUMENT_CSS` (`@portifact/ui/document-css`) in one `<style>`. `DOCUMENT_CSS` uses only `var(--pf-*)` tokens, including the type scale, spacing, measure and border widths in `tokens.css` that exist for surfaces styled without Tailwind. `tokens-css.ts` is generated from `tokens.css`: after editing the tokens, run `bun run --cwd packages/ui sync-tokens`, or the drift test fails.
