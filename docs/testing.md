# Testing

Portifact handles access control, uploads and untrusted HTML, so the tests are the main proof that it is safe. The goal is the highest coverage we can reach with tests that verify real behavior. A test that cannot fail when the code is wrong is worse than no test, because it creates false confidence.

## What a real test is

A test earns its place when all of these hold:

1. It asserts an observable outcome: a return value, a stored row, an HTTP status and body, an emitted event, a rendered result or a rejected request.
2. It fails if the behavior it covers breaks. Check this when you write it: break the code on purpose and watch the test fail.
3. It exercises real collaborators where practical: real D1, R2 and Queues bindings in the Workers runtime, the real router and the real domain services.
4. Its name states the behavior, for example `rejects publish when the account has no active slots`.

Not acceptable:

- Tests without meaningful assertions, or that only assert that a function was called.
- Snapshot-only tests for logic. Snapshots are allowed only for small, reviewed outputs such as rendered Markdown fixtures, next to explicit assertions.
- Mocking the unit under test, or mocking so much that the test only checks the mocks.
- Asserting private implementation details that can change without changing behavior.
- Tests written only to raise coverage, such as calling getters or constructors with no assertion about their effect.
- Skipped or `.only` tests in committed code.

Mock only true external boundaries: identity providers, the email provider and the system clock. Prefer fakes with real behavior over call-recording mocks.

## Layers

| Layer                 | Tool                                                                     | Covers                                                                                                                                             |
| --------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit                  | Vitest                                                                   | Pure logic: quota math, path normalization, anchors, lifecycle dates, manifest validation, policy decisions.                                       |
| Property-based        | fast-check with Vitest                                                   | Inputs with large spaces: path and ZIP normalization, Unicode anchors and offsets, date arithmetic, quota reservations under random interleavings. |
| Integration (Workers) | Vitest with `@cloudflare/vitest-plugin` (formerly `vitest-pool-workers`) | API routes, MCP tools, content delivery, auth flows and jobs running in the Workers runtime against real local D1, R2 and Queues.                  |
| Contract and parity   | Vitest                                                                   | The same operation through API, MCP and CLI yields the same result, error and side effects.                                                        |
| End to end            | Playwright on Chromium, Firefox and WebKit                               | Login, publish, protected access, review mode with third-party cookies blocked, annotations, archive and restore.                                  |
| Security              | Vitest and Playwright with hostile fixtures                              | The invariants in [security.md](security.md), each with at least one test that tries to break it.                                                  |

Workers tests run inside workerd through `@cloudflare/vitest-plugin`, which supports Vitest 4, so the workspace catalog stays on Vitest 4. Keep `compatibility_date` in each `wrangler.jsonc` no newer than the date the installed workerd supports, or the test runtime refuses to start.

D1 tests use the real local D1 inside workerd: `packages/db/test/apply-migrations.ts` applies `packages/db/migrations` before the tests, the same SQL that production runs. The services, app, content and jobs tests also bind the access log database as `ACCESS_DB` and apply `packages/db/access-migrations` to it in their setup file (`TEST_ACCESS_MIGRATIONS`); the Workers get the binding from their `wrangler.jsonc`, whose placeholder ID is fine locally. Assert on database errors through the `cause` chain, because Drizzle wraps SQLite errors.

Multipart uploads are tested with the local R2 in workerd, which enforces R2's rules: every part but the last must be at least 5 MiB and the same size. Tests pass a small `MultipartConfig` (a 6 MiB threshold and 5 MiB parts, so a 12 MiB object has three parts) to `preparePublish` in `packages/services` and through `createHarness({ multipart })` in `apps/app`, upload parts with the binding's `resumeMultipartUpload(...).uploadPart` as a client would through its presigned URL, and run the `abort_multipart` job with `runJob`. The 64 MiB boundary is checked at prepare only, without sending its bytes. The clients check bounded memory structurally: the CLI test wraps `runtime.fileBody` and `runtime.fetch` to assert that a large file is only opened in part-sized ranges with at most `UPLOAD_CONCURRENCY` parts in flight, and the dashboard test checks that parts are `Blob` slices.

To control the clock in Workers tests, call the app's `fetch` from the test (it runs in the same isolate) and fake only `Date` with `vi.useFakeTimers({ toFake: ["Date"] })`, so I/O keeps working. Apply D1 migrations in a setup file with `readD1Migrations` and `applyD1Migrations`. `apps/app/test` shows both.

Auth tests in `apps/app/test` build the Worker with `createWorker(() => deps)` from `harness.ts`, where `deps` is a fake email sender (an outbox the test reads codes from) and a fake network for Client ID Metadata Documents behind the production transport (`createClientMetadataFetch`). The fake documents carry an `ETag` and `max-age=300` and answer a matching `If-None-Match` with 304, as `chatgpt.com` does for Codex, so a test that moves `Date` past five minutes exercises the plugin's revalidation. Google and GitHub are faked by replacing the global `fetch` with `vi.stubGlobal`, because Better Auth calls them through it; send provider callbacks with `accept: text/html` and `sec-fetch-mode: navigate`, as a browser does, or Better Auth answers a continued authorization with JSON instead of a redirect. The D1 database is shared by every test in a file, so use a distinct email per test; the `signIn` helper clears the rate-limit counters first, and rate-limit tests reset them in `beforeEach`. Routing and asset tests use `SELF.fetch`, which goes through the static assets layer like production; they need `apps/web` built first, which Turborepo does before `@portifact/app#test`.

Content Worker tests call `handle(request, env, now)` from `apps/content/src/index.ts` with an explicit clock and send the `Sec-Fetch-*` headers a browser would (`navigate` for page loads, `same-origin` for subresources, `same-site` for a sibling artifact); without them the Worker fails closed. The read-session tests play the app's part with `issueReadHandoff` from `@portifact/services`, the same call `/read/<id>` makes, and `apps/app/test/read-handoff.test.ts` tests the app route. `drizzle-orm` is not a dependency of `apps/content`, so its tests change rows with raw SQL through `env.DB` (and read the access log through `env.ACCESS_DB`). `handle` takes a `logOpening` callback after `countTraffic`, so tests see the openings a request records without waiting for a batch. Handoffs need a live dashboard session (`sessions` row, a foreign key), so these tests insert one per user and sign out by deleting it.

`packages/services/test/artifacts.test.ts` also checks the artifact list's query plan (`explain query plan` on the statement the service sends): every activity subquery must search an index, never scan. Drizzle leaves columns unqualified in select fields, so a correlated subquery there must name each column's table, or the outer column binds to the subquery's own table and the figure is silently wrong.

Races between a request's checks and its write batch are tested deterministically: `racing(before)` in `packages/services/test/annotations.test.ts` (and the shared copy in `packages/services/test/fixtures.ts`, with helpers that publish through the real flow for fresh users) wraps the database so the next `batch` first lets a competing change commit. Two calls in `Promise.all` do not interleave their D1 queries in the test runtime, so they do not exercise the in-batch guards.

MCP tests in `apps/app/test` use the official SDK client (`@modelcontextprotocol/client`) against the Worker in process, pinned to the 2026-07-28 revision (`test/mcp-helpers.ts`), and raw JSON-RPC when a test needs the HTTP status or `WWW-Authenticate` header. `test/mcp-parity.test.ts` runs each operation through `/api/v1` and MCP for one user at the same faked time and compares bodies, errors and scope challenges; extend it with every new tool. Advance the faked clock by minutes there, not hours, or the access tokens expire. Annotation writes are rate limited per author (5 a minute), so annotation parity tests move the clock a minute forward between groups of writes. Services under test take a `RegionalDb`: build it with `regionsFromEnv(env).get("default").db`, not `createDb(env.DB)`.

Rendered HTML in `packages/render` is asserted on the DOM a browser would build: `src/test-html.ts` parses it with parse5 (the WHATWG parser), and the security tests check every element and attribute against an allowlist, including for random hostile input with fast-check. `src/golden.test.ts` snapshots a reviewed rendering; when it changes, bump `RENDERER_VERSION`, and when the change fixes a security flaw, raise `SECURE_RENDERER_VERSION` to it too. `src/highlight.test.ts` checks with fast-check that highlighting never changes the text and writes only token spans. The diagram runner (`src/browser`, typechecked with the DOM library by `tsconfig.dom.json`) runs in happy-dom against a fake Mermaid and checks with the real `AnchorDocument` that drawn diagrams leave the anchored text unchanged. The content Worker's tests alias `@portifact/render/diagrams-bundle` and `@portifact/render/diagrams-version` to small stubs (`apps/content/test/diagrams-*.stub.ts`, a real brotli body of a short script), because the real 1.6 MB module is larger than the Workers test pool can send to workerd; `e2e/tests/diagrams.spec.ts` loads the real one in every engine. A related limit: for each test file, `@cloudflare/vitest-plugin` sends workerd every module Vite transformed for that file's import graph in one WebSocket message (Vitest's warm modules, each listed twice), and workerd refuses messages over 32 MiB, which crashes the worker ("Message is too large", "Worker exited unexpectedly"). The message holds each module of the file's import graph that earlier files already transformed (the whole app, through the harness), twice. The `apps/app` suite is close to it, so `apps/app/vitest.config.ts` loads highlight.js from disk through `miniflare.modulesRules` instead of through Vite, and a test-only Vite plugin (`portifact:no-dependency-sourcemaps`) drops the source maps of `node_modules` modules, which were about three quarters of the message (33.5 MB down to 14.7 MB); the package's own code keeps its maps, so coverage and stack traces are unchanged. A `modulesRules` entry only helps for a module that nothing Vite transforms imports: zod and markdown-it rules did not shrink the message. If the crash comes back, measure first, rather than splitting the suite. The renderer also runs inside workerd: `packages/services/test/documents.test.ts` renders at commit against local D1 and R2, and `apps/content/test/documents.test.ts` publishes through the real `preparePublish` and `commitPublish` before requesting the page and the original, so delivery tests see exactly what a commit stored.

CLI tests in `packages/cli` run on Node, so `Bun.secrets` is absent: commands take a `Runtime` (fetch, clock, sleep, browser launcher, OS credential store, config directory, git) and tests pass a fake credential store and a clock that `sleep` advances instead of waiting. HTTP goes to a real local server, `src/testing/fake-server.ts`, that answers the device code, token, revoke and `/api/v1/me` requests like `apps/app`, with scripted answers to device polls. Its `/api/v1` publishing, artifact, access and version routes (`src/testing/fake-api.ts`) validate requests with `packages/contracts`, replay idempotency keys, check scopes and deduplicate by SHA-256, and a fake presigned storage target refuses uploads whose size, checksum, bytes or URL expiry are wrong and serves downloads only through unexpired links without an `Authorization` header (`server.api.gets` records them). `server.api.seedVersion(artifact, files)` adds a committed version with stored bytes and takes paths as given, so pull tests can play a hostile server. Its annotation routes (`src/testing/fake-annotations.ts`, state in `server.annotations`) keep modes, threads, revisions, idempotency replay and incremental cursors for a caller who owns every artifact; set `server.annotations.role` to `participant` to see refusals. Multipart uploads use the same fake: `server.api.multipart` sets the threshold and part size (tiny in tests, `null` for a server without multipart), part PUTs answer with an `ETag` (`server.api.hideEtag` drops it, as storage does without the CORS rule), `server.api.partPuts` and `partReports` record them, and the commit assembles the reported parts. `server.faults` answers, drops or alters the next matching request, which is how tests lose a prepare answer, expire a URL or fail a commit. Publishing tests write real files with `h.files`, and `h.signIn()` stores tokens with every scope. Every test that prints checks that no issued token appears in the output. ZIP tests build archives with `src/testing/zip-writer.ts`, which can force any name, mode, flag, method, size, CRC or offset, so every refusal of the reader (zip slip, links, collisions, overlap and expansion bombs) is reproduced byte for byte; point `TMPDIR` at a scratch folder to check that nothing expanded is left behind. Source tests create real git repositories with the `git` binary, set `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1` so the developer's configuration cannot leak in, and pass `gitRunner("<missing path>")` to test a machine without git. Commands get git from `runtime.git`: `createHarness({ git })` swaps it, for example to fail one git subcommand and check that `pull --git` leaves the history as it was. Tests that check for leftovers in the temporary folder point `TMPDIR` at a folder of their own, because test files run in parallel and share the system one; name a test's own folders with a prefix the CLI never uses (`pf-`, not `portifact-zip-`). `server.api.usage` is what the fake `GET /api/v1/usage` answers. Check credential storage against the real OS store by building the binary (`bun run build:cli`) and running it against that server; to force the file fallback on Linux, set `DBUS_SESSION_BUS_ADDRESS` to a path that does not exist.

The auth pages and the report page in `apps/web` are tested with happy-dom against their real markup: `src/auth/test-page.ts` loads the page's HTML and fakes the `/api/auth` calls. `src/auth/pages-axe.test.ts` runs axe on every page in each state a visitor reaches (methods, errors, code step, visible human check, signed in, terms review, device review and approval, consent, report sent). The login tests pass a fake `HumanCheckWidget` that records each render and lets the test solve, expire, fail or show a challenge, and fake `setTimeout` or `setInterval` only (`vi.useFakeTimers({ toFake: [...] })`) for the human check's wait and the resend countdown, so `settle` keeps working. Emails are tested in `packages/emails` on the DOM parse5 builds (code in one piece, expiry, the ignore line, escaping of every block, token colors only). The operator tool's commands (`apps/jobs/src/operator.ts`) run in workerd against local D1 in `apps/jobs/test/operator.test.ts`; the script around them only opens the binding, and the backup commands get an in-memory file system instead of the disk.

Outbox and queue tests: `packages/services/test/outbox.test.ts` simulates a Worker dying mid-request with a database whose `batch` fails after the first n (`crashAfterBatches`) and a bucket whose deletes fail, then runs the left-over job with `runJob`, twice for duplicate delivery and after changing the artifact's generation for a stale job. The relay uses a fake queue that records messages or refuses them, the one external boundary there. `apps/jobs/test/queue.test.ts` calls the Worker's `queue` handler with `createMessageBatch` and reads acks and retries with `getQueueResult`; that result does not record retry delays, so the test also spies on each message's `retry`. The scheduled run there sends to the real local queue, whose consumer may run the job in the background, so assertions after `runScheduled` accept either outcome. `packages/services/test/backups.test.ts` simulates a D1 Time Travel restore by snapshotting rows before deletions and inserting them back after removing their tombstones; the storage reconciliation keeps when its pass started, so its tests move the clock forward on every pass.

Webhook deliveries never reach a network in tests: `deliverWebhook` takes its `fetch` in `WebhookDeps`, so `packages/services/test/webhooks.test.ts` scripts each answer (statuses, a thrown network error, a fetch that waits for the abort signal for timeouts with a small `timeoutMs`, a stream that never ends or never closes) and records each request, and the jobs Worker's tests pass a fake to `runQueue`. The signature test checks the recipe in the skill with WebCrypto, written independently of `signWebhook`. The e2e control host's `/webhooks` runs due delivery jobs with the jobs Worker's real deps and a network that only answers `hooks.receiver-e2e.example.com`, keeping each request in the local bucket, and `e2e/tests/webhooks.spec.ts` verifies the signature with Node's `crypto`. Tests that set a budget override clear it in a `finally`: the `platform_budget` row is shared by every test in a file.

Content search runs on the real FTS5 table in workerd: `packages/services/test/content-search.test.ts` publishes through the real commit, runs the `search_index` jobs with `runJob` and checks every removal path, the role table, token reach, the plan gate, paging and hostile queries against D1. The extractor and the MATCH builder are fuzzed with fast-check in `packages/domain` (`html-text.test.ts`, `content-search.test.ts`), including a linear-time check on 2 MiB of pathological HTML. Biome turns `\uE000`-style escapes in string literals into the raw characters, so the snippet markers are built with `String.fromCharCode`. In e2e, the control host's `/search-index` (`runSearchIndexing` in the fixtures) runs the waiting jobs, and `e2e/tests/content-search.spec.ts` publishes, indexes and finds the artifact from the dashboard.

The dashboard is tested the same way, through its real API client and router: `src/dashboard/test-support.tsx` renders the app with memory history over an in-memory `/api/v1` and session endpoint, including the access policy (it applies `AccessUpdate` and the reader cap like the Worker), `/api/auth/list-accounts` and the account endpoints; `server.bodies` holds the JSON each request sent. It also fakes publishing, versions, rollback and the document preview the way the Worker answers them, and presigned storage (`server.storage`): uploads must carry the signed size and checksum and matching bytes, downloads serve stored bytes, and `storage.fail` answers, drops or corrupts the next transfers while `storage.hold()` keeps an upload pending so a test can cancel it. `seedVersion(server, artifactId, files)` adds a committed version with stored bytes. The fake artifact list validates its query with `ArtifactListQuery` and applies the search and filters like the Worker, and answers each item's `activity` from `server.activity` (`DEFAULT_ACTIVITY` otherwise); the annotations routes honor the `version` filter (other versions only for the owner) and serve the export as JSON or Markdown; the access log route (`server.accessLogs`) pages by the smaller of the request's `limit` and `server.pageSize`, so a test can make the export follow several pages. Manifests are built in process (`inProcessBuilder`) through the same messages the Web Worker sends; the worker logic (`publish/manifest.ts`, `publish/zip.ts`) is tested directly with archives built by fflate and then damaged on purpose. `axeViolations` does not enter frames: the only frames hold rendered user documents. The design system's select is a combobox and a listbox, not a native `select`: choose with `choose(name, optionLabel)` and read the options and the chosen one with `selectOptions(name)` from `test-support.tsx`, never `fireEvent.change`. For narrow layouts, `setViewportWidth(px)` from `@portifact/ui/testing` makes `matchMedia` answer for that width (happy-dom's window is 1024 px); call `resetViewport()` after the test. Query by role and accessible name, and run `axeViolations` from `@portifact/ui/testing` on each screen and state; happy-dom has no layout, so the helper skips color contrast, which the token tests and the end-to-end tests cover. Failed queries retry once after about a second, so error-state assertions wait up to 3 seconds. For refresh timing, use `vi.useFakeTimers({ shouldAdvanceTime: true })` and TanStack Query's `focusManager` for a hidden tab. Component tests in `packages/ui` and `apps/web` set `// @vitest-environment happy-dom` per file and call `cleanup` after each test, because Vitest globals are off.

End-to-end tests of review mode must block third-party cookies explicitly and prove it with an unpartitioned control cookie. Chromium needs the full browser (`channel: "chromium"`) with a profile that sets `profile.cookie_controls_mode = 1`; the headless shell ignores profile preferences. Firefox uses `network.cookie.cookieBehavior`. WebKit blocks by default, but only macOS uses Safari's cookie layer: WebKit on Linux has no partitioned cookies. `spikes/review-cookies` shows all three and maps hosts through a local proxy, which works in every engine. `spikes/artifact-data-grant` (decision 0026's grant handoff experiment) uses the same projects and proxy; CI's e2e job of each engine runs it after the suite (`bun run --cwd spikes/artifact-data-grant spike -- --project=<project>`), and `scripts/e2e-matrix.test.ts` keeps its projects equal to the suite's.

`bun run test:e2e` builds `apps/web`, the bridge and the diagram script (`packages/render`), then runs Playwright in `e2e/` (not part of `bun run test`). `e2e/global-setup.ts` starts the stack once per run: `e2e/worker` is a test-only Worker that serves the real app and content Workers by host from one wrangler dev process, so they share one local D1 (migrated with `wrangler d1 migrations apply --local`) and R2; an HTTPS front end with a throwaway certificate gives browsers `app.portifact.test`, `portifact.test` (the e2e Worker serves it as `portifact.com`: the landing, legal and MCP pages with their real headers) and `<id>.portifact-content.test`; and the CONNECT proxy from the spike maps those hosts in every engine. The front end forwards raw HTTP with `MF-Original-URL`, because Node's `fetch` rewrites `Sec-Fetch-Mode`, and it sets an unpartitioned `SameSite=None` control cookie next to the review cookie, so each run proves third-party cookies are blocked. Artifacts are seeded with the Portifact bar on, as in production, so a test's top-level visit to an artifact lands in the viewer; tests of what the artifact itself serves at top level publish with `bar: false`, and `e2e/tests/viewer.spec.ts` covers the viewer. Tests seed users (a signed Better Auth session cookie), artifacts and threads through the control host of that Worker (`e2e/worker/control.ts`), which only the test runner reaches, and read the content requests the front end saw. The projects are Chromium with third-party cookies blocked, Firefox in CHIPS-only mode, Firefox with all third-party cookies blocked (the fallback) and WebKit, whose expectation follows the platform: review works on macOS and falls back on Linux. WebKit on Linux needs its system libraries (`npx playwright install-deps webkit`, which uses `sudo`); install the browsers once with `bun run --cwd e2e browsers`. CI's `e2e` job installs them with `--with-deps` and runs every project, so WebKit on Linux is covered there even when a workstation cannot launch it; run the others locally with `bun run test:e2e -- --project=chromium-3pc-blocked --project=firefox-chips --project=firefox-3pc-blocked`. `e2e/tests/design.spec.ts` evaluates axe-core's source through `page.evaluate` (the dashboard's CSP blocks injected script tags, and the test must not weaken it) and checks the main dashboard screens (the account pages, the collapsed sidebar and the phone drawer included) with color contrast in both themes. `e2e/tests/account.spec.ts` covers the shell and the account pages: the sidebar collapsed and resized from the keyboard, both kept through a reload; at 375 px the drawer instead of the sidebar (Escape returns focus, the page behind does not scroll, a followed link closes it) and no account page wider than the screen; saving the defaults for new artifacts; and the redirects of the old `/account` anchors. `e2e/tests/dashboard.spec.ts` covers the artifact list's search and filters from the keyboard (kept in the URL through reload and back), each artifact's activity in the list and the earlier versions' conversations in the history (opened from the keyboard), and the viewer's comment filters and Markdown export download. The control host's `/publish` takes `update: { artifactId, baseVersionId }` to publish a new version of an artifact. `e2e/tests/dashboard-layout.spec.ts` covers whole rows and option cards that take a press anywhere (pressed through `page.mouse` at the element's middle, because Playwright's own click refuses when the row's stretched link or the card's label takes the press, which is what the test proves), the artifact page's sections with each group saved on its own, and the phone layout at 375 px: stacked rows, the filters sheet, no sideways scrolling and axe. `e2e/tests/theme.spec.ts` chooses Dark on the landing page and in the dashboard's settings, under the real CSP, and checks the computed background, the logo's source and that the choice survives a reload; the switcher's radios are visually hidden, so it presses their labels. `e2e/tests/preferences.spec.ts` covers the theme and language shared by the two hosts: Dark and Español chosen on the landing show in the dashboard and English chosen there sends the Spanish landing to the English one, the reverse from the dashboard to the landing and a scriptless legal page (whose switcher must not bounce back), a landing choice reaching the login page, and a first visit with other browser languages that is served as asked with no cookie. The preference cookies use `Domain=portifact.com`, which the browser refuses on the stand-in host, so the e2e Worker rewrites it to `portifact.test` on the site's responses (`siteCookies` in `e2e/worker/index.ts`), and `PREFERENCE_DOMAINS` lists `portifact.test` for the pages' own writes. A spec that visits a static page after the app saw `?lang=` gets the kept language, so it asks for the page's language with `?lang=` too (as `i18n.spec.ts` does). In unit tests, happy-dom keeps `document.cookie` for a whole file: `apps/web/src/test-setup.ts` clears it before every test, and tests that block cookies redefine `document.cookie` and put the original descriptor back (`packages/ui/src/theme/theme.test.ts`) rather than `vi.spyOn`, whose restore broke the accessor. Choose an option of a design-system select by clicking the combobox and then `getByRole("option")`; `selectOption` only works on native selects. `e2e/tests/workspaces.spec.ts` covers workspaces from the dashboard: switching space from the menu and publishing into it, inviting someone who accepts from the email's link (`lastEmail`) in a second browser context signed in as them, the invitation page for another account and for a visitor, changing a role and removing a member, a member's read-only view, and moving an artifact into a workspace and back out. The dashboard's presigned uploads go to the bucket's S3 host, which the stack's proxy does not map: a spec that publishes from the browser calls `routeStorage(page)`, which forwards them to the control host's storage stand-in with the bucket's CORS answers. In component tests the fake server holds `workspaces` (built with `workspace(slug, role, overrides)`: the caller's view, members, seats, invitations, usage and brand), `incoming` invitations and invitation `links` by token, and answers the owner-scoped routes by `?workspace=` like the Worker (a slug the caller is not in is `not_found`, a member's list and usage `forbidden`). `e2e/tests/comment-visibility.spec.ts` seeds threads by the owner and two readers and checks the default (each reader sees their own and the owner's), the owner opening every thread from the dashboard and an exception narrowing one reader again. The front end answers `redirect.elsewhere.test/?to=<url>` (`bounced()` in `e2e/src/hosts.ts`) with a redirect to a stack host, which plays any third site an artifact could route a navigation through. `e2e/tests/injected-cookies.spec.ts` has an artifact (`cookieInjectingPage`) set 150 cookies on the shared content domain, some scoped to `/docs` and some imitating the read cookie, then checks that another artifact still loads, that its answers bring the visitor's shared cookies back under the limit, and that a protected artifact still asks for sign-in. Firefox can still list a cookie a response just expired (empty, past its expiry) in `context.cookies()`, so the test counts only live cookies, and the injecting page has an inline icon so a favicon request does not start clearing before the test counts.

Reading an e2e failure in CI: the suite has no retries, so download the job's `e2e-traces-<project>` artifact before running it again. Each failed test has `error-context.md` (the page as an accessibility tree at the moment of the failure) and `trace.zip`, whose `*.network` files list every request with its status. Two causes seen so far that are not product defects: a stylesheet that did not load (`net::ERR_TOO_MANY_RETRIES` on the `main-*.css` request, Chromium, 2026-11-12) leaves the page unstyled, and then accessible names lose the spaces layout gives them (`Acme Labs(opens in a new tab)`), so a role locator with a name reports "element(s) not found" although the element is in the tree; and a press whose release lands after the viewer shifted its layout focuses a control without activating it, which shows as a menu still open and no dialog, and is why a gesture in the viewer repeats until its effect is there (`openCreateIssue` in `e2e/tests/integrations.spec.ts`). A request that failed in the trace points at the stack, not the page.

`bun run landing:shots` (not a test, not part of `bun run test:e2e`) runs `e2e/shots/` on the same stack in Chromium to make the landing page's screenshots and transcripts ("Landing page" in [design.md](design.md)). The e2e Worker runs the content Worker on its own clock (`e2e/worker/clock.ts`): `setContentClock(artifactId, ms)` in the fixtures moves it ahead of real time for that one artifact through the control host, so a test passes a delivery time window, such as the 60-second read claims, without waiting; reset it to 0 in a `finally`. The app Worker keeps real time. The artifact data protocols (decision 0026, delivery 3) are tested without workerd: `packages/domain/src/testing/artifact-data-object.ts` is an in-memory documents object that composes the pure decisions the way delivery 4's Durable Object must, with every access to durable state going through one instrumented store (each storage map counts its own reads and writes, an index seek its rows and its probe) and restoring through an undo log when a transaction throws, with injectable faults after a mutation's work. An entry point that touched rows no metering step took throws, and the tests assert exact equality between what was accounted (`accounted()`) and what the store saw (`accesses`) plus `COUNTER_WRITE_ROWS` per counter write, after every property step and directly. The counter writes themselves are modelled at that fixed cost and not observed by the store, so this proves that every instrumented work access is metered, not the bookkeeping's own cost; delivery 4 measures real cursors. Every operation is checked against `OPERATION_ROW_BOUNDS` (a bound passed throws; `rowBounds` can be tightened for a negative control). `review-254.test.ts` and `review-254-r2.test.ts` hold the two code reviews' reproductions. `packages/domain/src/artifact-data/acceptance.test.ts` has one test per item of the record's "Acceptance tests for delivery 3" (A01 to A34), `properties.test.ts` checks the record's invariants after every step of random command sequences (and fails when a generator stops reaching a path), `model-check.test.ts` compares every delivery order of a few lifecycle and replay messages with a separately written reference model, and `review-findings.test.ts` carries the design reviews' reproductions. A32 loads an export file into SQLite with `node:sqlite`. Measured on 2026-11-12 with Stryker restricted to the new files, after the code review's rework: `packages/domain/src/artifact-data` 97.78% (2,489 killed, 22 timeouts, 50 survived, 7 without coverage; survivors are mostly messages, conditions an earlier check already decides and `sha256` bounds that only matter past 512 MiB) and `packages/contracts/src/artifact-data.ts` 98.83% (169 killed, 2 survived).

The same suites run against the real documents object (decision 0026, delivery 4): their bodies live in `packages/domain/src/testing/artifact-data-suites` and drive a `DataObject` (`packages/domain/src/testing/artifact-data-driver.ts`) that awaits every command, so the domain's `*.test.ts` files run them on `MemoryObject` and `apps/data/test` on the Durable Object on SQLite in workerd (`test/driver.ts`: each command is a `runInDurableObject` call into the object, with deterministic IDs, strict bounds, a recorded alarm instead of the platform's, recorded socket output and an `Instrument` kept across evictions). `test/pair.ts` sends every command to both objects and fails at the first step where their answers or states differ (measured costs, file sizes, the storage sequence and which day rows exist follow the measured rows and are not compared); the property sequences run on the real object alone and paired, with a fixed seed and bounded runs (20 and 5 sequences drawn once and split into at most four tests each, `slices`), and the model check runs every 11th delivery order in twelve tests per set; the path check covers every slice together. The driver keeps the last view until the next command and, when the suite read the state since the last command, takes the next snapshot in that command's own request, because a request into the object, not the work, is most of a step's cost. Keep each real-object test small: CI's runner is several times slower than a workstation under load, and the domain's own property and model-check runs are sliced for the same reason (`slices`, the same sequences and every order). `test/storage.test.ts` covers what a driver cannot: synchronous commands and racing requests, storage faults injected at the statement boundary (`Faults.statement`), every statement's query plan, measured costs at the largest legal shapes and for dense, sparse and empty queries at two collection sizes, the one-row cold start, the alarm scheduler (120 writes over an hour wake it twice; late, repeated and held alarms; a failed re-arm), hibernation and a close lost before it, the payload-only erase and the file-size headroom. `test/review-257.test.ts` holds the two code reviews' reproductions and the rules decided on them: a storage fault on a read, an export, a fence, a connect, an alarm and a mutation (whose second transaction charges it, or fails too) leaves the counters, the pending usage and the oracle agreeing, with the rows it left uncharged counted as lost and nothing held or refused afterwards; a fault in the scheduler does not fail a committed command; the file-size check on declarations, index steps and connects, never on work that does not grow its documents, and its position after the charge (tested with the measured file fixed until the charge's own write and one page larger after it, a stand-in for a page boundary the real file reaches only at particular row counts); and three checks that fail under the mutants the first review found alive (a dense query's lower bound on rows read, the physical tables after a whole erase, the storage sequence after a flush only a read triggered). The pair does not compare measured usage, `describe`'s included, the storage sequence or which day rows exist; storage failures and the largest shapes are proven on the real object alone, not by the pair. A test of the real object never depends on wall-clock time: commands take `now`, and the platform alarm is used only where a test needs the handler itself.

Every Vitest config sets `testTimeout: 30_000` and `hookTimeout: 30_000` (the spikes included; `content-search` uses 60 seconds for both, and `edit-suggestions` 120 seconds for both in its Node configuration, whose corpus tests are the heaviest, and 60 in its workerd one). Vitest's defaults are 5 seconds for a test and 10 for a hook, and a `beforeAll` that starts the Worker and its databases passed 10 seconds on a loaded runner and failed a release's test step. CI runs every package's tests at once on one runner, so heavy property and size tests can take several times longer than locally; a test that cares about speed asserts its own time budget, and the timeout only catches hangs. Benchmarks at size limits do not belong in `bun run test`: under coverage on a loaded runner a few seconds became more than two minutes (`spikes/edit-suggestions`, pull request #247). Prove the property on small inputs by asserting counted work (parses, renders, nodes) or ratios, and put wall-clock measurements at the limits in a separate script, as `spikes/edit-suggestions` does with `bun run --cwd spikes/edit-suggestions bench`. For the same reason `apps/web/src/test-setup.ts` raises Testing Library's `asyncUtilTimeout` from one second to ten: a file's first render under that load has taken almost two, which made `findBy` queries of correct tests fail now and then.

The Workers test pool (`@cloudflare/vitest-pool-workers`) sends every module of a test file's graph, already transformed, in one WebSocket message, and workerd refuses a message over 32 MiB: the files of the suite then crash with "Message is too large" before any test runs. `apps/app` imports the most code and reached the limit as features were added (33.5 MB measured, three quarters of it the inline source maps of dependencies). Its `vitest.config.ts` has a small plugin that drops the source maps of modules under `node_modules`, which more than halves the message; this package's own code keeps its maps, so coverage and stack traces into `src` are unchanged. If another Workers suite fails that way, give it the same plugin.

## Suggestion planners

The planners of decision 0027 (`packages/domain/src/suggestions`) are tested against an independent checker in `packages/domain/src/testing/suggestions/checker.ts`, test code that shares nothing with them: it reads pages with happy-dom (the planners use parse5), compares IDs and references with a regular expression and the markup with text removed, checks the bytes outside the approved range, derives on its own the source interval the selected text occupies (HTML and text: from the selected rendered occurrence and its own decoding of the file, references decoded with happy-dom) and refuses any byte changed outside it or written text that does not decode to the inserted text (Markdown, where it has no source map of its own: the bytes that really differ between the two files, widened to whole references and backslash escapes and decoded, must be the deleted and the inserted text or a stretch of them repeated, which a rewrite next to the selection is not; this bounds a change tightly and is not a proof of the selected interval), and compares every text node of the whole document, head included, at its DOM path with the old text changed at the reviewer's location. `checker.test.ts` holds its mutation tests (a wrong repeated occurrence, a hidden comment change, an offset mistake): keep them failing for wrong results. The seeded corpus (`corpus.ts`) and every counterexample of the two design reviews (`review-findings.test.ts`) and of the three code reviews of pull request #252 (`review-252.test.ts`, `review-252-r2.test.ts`, `review-252-r3.test.ts`) run in `bun run test`; the digest test changes every leaf of a plan's contents in turn, generated from its shape. Budgets are asserted by counting work (`Work`: parses, renders, anchor indexes, source maps, decoded references, identity hashes), never by time, and that nothing is hashed before sizes are checked by both `Work.hashes` (the synchronous identity hash) and a spy on `crypto.subtle.digest`; the wall-clock benchmark at the size limits stays in the spike (`bun run --cwd spikes/edit-suggestions bench`), outside `bun run test`. Test pages are positioned with happy-dom and `packages/anchors` over the page's `body`, as the bridge positions them. The preview builder's CSS bounds run in workerd (`packages/services/test/suggestion-preview-workerd.test.ts`), and its output is checked in real engines by the spike's browser suite (`bun run --cwd spikes/edit-suggestions browser`), which CI runs in the e2e jobs' Chromium and first Firefox (about 5 and 8 seconds).

## Required cases

Every feature covers:

- The success path.
- Each documented failure path and error code.
- Permission boundaries: owner, authorized reader, other authenticated user and anonymous. For token-based access, also insufficient scope, revoked token and wrong audience.
- Paid features: an owner-level setting served only to the dashboard session, with no MCP tool or CLI command (the brand), is not a `GATED` line: its gate is tested with the same `plan_required` body in its own app test (`apps/app/test/branding.test.ts`) and its owner-plan and role rules in the services. Every other operation a plan gates gets one line in `GATED` in `apps/app/test/plan-gates.test.ts` (the `route(...)` helper: the API route and the MCP tool), which checks that a free owner gets `plan_required` with the same body from both, that the lowest plan with the feature is not refused and that the plan counted is the artifact owner's (a workspace's), never the caller's; and one line in `GATED` in `packages/cli/src/plan-gates.test.ts` for each CLI command that reaches it (exit 7, the API's body as is). Share links (`create_share_link`, `portifact share create`) are the first real lines; add yours next to them.
- Workspace roles, for anything an owner does: admin, editor and member of a workspace owner, and a user with no role, who must get exactly what a missing artifact gives. Create workspaces and members by inserting `workspaces` and `workspace_members` rows; `packages/services/test/workspaces.test.ts` has the role matrix through the services and `apps/app/test/workspace-parity.test.ts` the same through the API and MCP.
- Quotas and limits at, just below and just above the boundary.
- Concurrency where state is shared: two publishes on the same base, two uploads racing for the last slot, duplicated callbacks and queue redelivery.
- Time-dependent rules with a controlled clock. Never wait real time.

Every bug fix starts with a failing test that reproduces the bug.

## Mutation testing

StrykerJS (`@stryker-mutator/core` with the Vitest runner) runs on the critical packages: `packages/domain`, `packages/anchors`, `packages/contracts`, `packages/render` and `packages/services`. It changes the code in small ways and expects a test to fail for each change. A surviving mutant means a missing or weak assertion: fix the test, or explain why the mutant is equivalent.

- `bun run test:mutation` runs every package one after another (Turborepo with `--concurrency=1`); `bun run --cwd packages/<name> test:mutation` runs one. Reports land in `reports/mutation/` of each package (HTML and JSON, ignored by git).
- Settings shared by all packages live in `stryker.base.mjs`; each package's `stryker.config.mjs` lists what it mutates and its break threshold.
- Each run uses 2 test runner processes (`concurrency: 2`), restarts them every 25 mutants and caps every Node heap at 1 GB through `NODE_OPTIONS` in the `test:mutation` scripts, so a run stays within a few GB on a shared machine. Raise the concurrency on a machine of your own with `-- --concurrency 6`. Tests run in forked processes (`vitest.pool: forks`), because worker threads ignore the heap cap. Never run mutation testing next to other heavy suites on a shared machine.
- Local runs are incremental: unchanged code and tests reuse the last results from `reports/mutation/stryker-incremental.json`. Pass `-- --force` for a full run.
- TypeScript 7 has no JavaScript API, so Stryker's tsconfig rewrite is skipped (`tsconfigFile` points at a file that does not exist) and every sandbox lives in `<root>/.stryker-tmp/sandbox-*`, at the same depth as the packages, so `"extends": "../../tsconfig.base.json"` still resolves. A Vitest config must not reach other packages by relative path from a sandbox; `packages/services` finds the D1 migrations through `@portifact/db`.
- `packages/services` runs in workerd through `@cloudflare/vitest-plugin`, like its normal tests, and it works with Stryker's per-test coverage. It is the slowest package (about 1.5 hours on the workflow's runner). Its break threshold, 83, comes from the first full run of the `mutation` workflow on 2026-11-08.
- A mutant that loops while allocating crashes its runner, which Stryker restarts. Where such a mutant costs gigabytes before it crashes, disable it with a `// Stryker disable next-line <mutators>: <reason>` comment that explains why, as in `packages/anchors/src/normalize.ts`.

The `mutation` workflow (`.github/workflows/mutation.yml`) runs each package in its own job only when started by hand (Actions, `mutation`, Run workflow), never on pushes or pull requests, because `packages/services` alone takes about 1.5 hours, and keeps the reports as workflow artifacts. A package fails when its score drops below its break threshold.

Break thresholds are the measured scores rounded down; raise them as tests improve, never lower them to make a change pass. Measured on 2026-11-08 (Node 24, concurrency 2):

## Load and concurrency

`bun run test:load` builds `apps/web` and the bridge, then runs `scripts/load-test.ts` on Node. By default it starts the e2e Worker (`e2e/load/local.ts`: the real app and content Workers over one local D1 and R2 in workerd, through wrangler) and runs four scenarios through the public API, as a client would:

| Scenario      | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `quota-race`  | Fills 49 active slots, then sends 8 new publishes at once (prepare, presigned uploads, commit). Exactly one may take the last slot; the others fail at prepare with `quota_exceeded` and leave no open upload.                                                                                                                                                                                                                                       |
| `max-upload`  | Publishes exactly 250,000,000 bytes (an entry page and one object of almost 250 MB, uploaded as 16 MiB presigned multipart parts and reported part by part) after checking that one byte more is refused at prepare. Bytes are generated and hashed in streaming passes, and memory is sampled separately while uploading and while committing (the commit rehashes the assembled object and copies it to its key).                                  |
| `delivery`    | Serves a published public site to 32 connections for 10 seconds with the fetch metadata a browser sends, and reports throughput, latency percentiles and statuses.                                                                                                                                                                                                                                                                                   |
| `annotations` | Four readers of an artifact with open annotations each send 8 thread writes at once. Each reader first gets three comments written two minutes earlier through the control host, because an account's first comments on other people's artifacts need a solved human check (Turnstile) that a script cannot do. Each gets exactly 5 (the per-author minute limit), the rest answer `rate_limited`, and the stored threads match the accepted writes. |

Locally, presigned uploads go to the e2e Worker's control host (`/storage` in `e2e/worker/control.ts`), a stand-in for R2's S3 endpoint that refuses a body whose length differs from the signed `content-length`, lets R2 refuse a wrong checksum and streams into the local bucket. The local Worker runs over HTTPS like the e2e stack, because the app refuses session mutations whose `Origin` does not match the scheme it sees.

Options: `--scenario a,b`, `--publishers`, `--concurrency`, `--duration`, `--authors`, `--writes` and `--json`; `--help` lists them. Pass them after `--`, for example `bun run test:load -- --scenario delivery --duration 30`. Run it alone on a shared machine, never next to mutation testing or another suite.

To target staging, pass `--app-url https://<staging app>` and `--content-domain <staging artifact domain>`, list the scenarios with `--scenario`, give `--artifact <id>` for `delivery` (a public artifact) and `annotations` (one with open annotations that the token's account may annotate and has already commented on past the human check), and put a bearer token with `artifacts:write`, `artifacts:read` and `annotations:write` in `PORTIFACT_LOAD_TOKEN` (never on the command line). Remote runs check limits against what the account had before (`quota-race` creates artifacts and leaves them; their IDs are printed). The script refuses `portifact.com`, `portifact.dev` and their subdomains unless `--i-know-this-is-production` is given; nothing in the repository passes it.

## Two regions

Every Workers test suite (services, app, content, jobs) and the e2e Worker bind a second region, `eu`, to its own control database, access log database and bucket (`DB_EU`, `ACCESS_DB_EU`, `ARTIFACTS_EU`, with the same migrations), and set `REGION_GUARD` to `strict` (decision 0005, "Two-region audit"). The guard (`packages/db/src/region-guard.ts`) throws when product code sends a statement that names the other side's tables through a handle, or a batch with statements from another handle; statements a test file prepares itself pass, so arranging rows through `db()` is fine, but read and write global rows through `db().global` anyway. A crossing still to fix is listed in `KNOWN_CROSS_DATABASE`, keyed by file and function, with its reason; never add one to make a test pass, fix the code (`scripts/region-guard-known.test.ts` fails for an entry that no longer matches). The paths that span both sides are tested in both shapes: one database (`regionsFromEnv({ DB: env.DB, … })`, or a test proxy marked with `aliasBinding` so `sameDatabase` sees through it, as `race.ts` does) and a separate one (`env.DB_EU`, or `env.SECOND_DB` as a default region of its own); `write-costs.test.ts` pins the D1 calls of the write paths to what develop made. `REGION_GUARD=collect bun run --cwd <package> test` records every crossing instead of failing and prints them at the end of each test file, for an inventory. Each package's `two-regions.test.ts` runs the flows with a workspace in the EU. A test that needs exactly one region builds its regions from `{ DB: env.DB }`. `e2e/tests/eu-workspace.spec.ts` is the end to end proof (E5.8): an EU workspace created through the operator tool (the control host's `/operator`, which runs `runOperator`), dashboard publishing to the EU bucket (`routeStorage` sends the presigned URL's bucket name to the storage stand-in), reading, commenting, a share link, a refused move, a deletion and the workspace's deletion, with the control host's `/jobs` running every region's outbox through the jobs Worker's consumer (`runQueue`, each message naming its region) and `/where` reporting, per region's control database, access log and bucket and in the global tables, where an owner's rows and objects are. The control host's `/publish`, `/thread`, `/access`, `/share-link` and `/sql` take `region`. The e2e Worker passes the content Worker's region to the traffic, opening and view meters, as the content Worker does; dropping it sent an EU owner's counts to the default access database, which the spec caught. `/where` also counts the idempotency records (`operations`) of the people the spec names (`actorIds`), and the storage stand-in refuses a bucket name the stack does not have. `apps/app/test/idempotency-regions.test.ts` runs every keyed API and MCP operation on an EU workspace (record home, replay, refused body) and pins the keyed adapters' D1 calls with one region bound. `scripts/log-fields.test.ts` refuses `console` outside `packages/domain/src/logs.ts` and checks every `logEvent` call's fields and values ("Secrets and logs" in [security.md](security.md)); a test that asserts a log line compares the exact JSON `logEvent` writes.

## Fixtures

- `@portifact/domain/testing/images` (`packages/domain/src/testing/images.ts`, excluded from coverage and mutation) builds PNG, JPEG and WebP files byte by byte for the brand logo's tests: `png()` is a real decodable image, and the options truncate it, append data, break a checksum, add an animation chunk or hide markup in a text chunk.

- `fixtures/artifacts/` holds sample sites, Markdown and TXT, including maximum-size and edge cases.
- `fixtures/hostile/` holds malicious inputs: ZIP path traversal, symlinks, zip bombs, HTML that tries cookie tossing, forged `postMessage`, CSRF forms, service worker registration, script-injecting Markdown and oversized selectors.
- Fixtures are small and deterministic. Large fixtures are generated in the test, not committed.
- Outside services are fakes behind the same interfaces production injects: Cloudflare custom hostnames and DNS over HTTPS are `FakeDomains` (`@portifact/services/testing`), used by the services, app, jobs and e2e tests; the real clients are tested only against a fake `fetch`, and no test calls a real Cloudflare endpoint. The e2e stack serves custom hosts under `*.customer-e2e.test` (in its certificate and proxy, `customHost` in `e2e/src/hosts.ts`), and its test-only Worker has `CUSTOM_DOMAINS_ENABLED` on; the control host attaches a domain directly (`fakeDomains({ attach })`).
- GitHub and Linear for issue integrations (decision 0018) are `FakeIssueTrackers` (`@portifact/services/testing`): one `fetch` that answers the REST and GraphQL calls Portifact makes, checks credentials, keeps the issues it created and can script the next answers (a status, a redirect, an oversized or slow answer, a network error, or `lose`, which creates the issue and then fails the call like a lost answer). The services, app, jobs and e2e tests use it (`e2e/worker/integrations.ts`, the control route `/issues` runs the jobs); no test calls GitHub or Linear.

## CI gates
